# 構成と設計

**「なぜそうしたか」を書く場所。** 迷ったところ、踏んだ落とし穴、選ばなかった案。
全体像 (入れ替え・イメージのタグ・クラスタの前提) はここに置き、機能ごとの話は
それぞれの文書にあります (一覧は [README](../README.md#もっと詳しく))。

コードの置き場や設定名の一覧はここには書きません (app.md・config.md と二重に持つと必ず片方が古くなる。話に要る名前だけ出す)。

## 全体

```text
チューナー ── エージェント ── denpa ── 録画(mkv) ─┬─→ ブラウザでそのまま観る
                                                    └─→ テレビのアプリ (denpa-tv)
```

メディアサーバは置きません。エンコードしたもの (AV1・H.265・H.264 + Opus の mkv) はブラウザが
そのまま読むので `/watch` で観られ、テレビのアプリへは denpa がファイルを配ります。
ブラウザが読めない元の TS (MPEG-2) や違うコーデックは、denpa がその場で詰め替え・変換して流すか、
ブラウザが WebAssembly でデコードします ([library.md](library.md#何で観るかはサーバが出せるものから画面が選ぶ))。
外部のプレイヤーには対応しません。

**境界は「電波を受けるところ」と「中身を読むところ」で切ってあります。** エージェントは
チャンネルを選局して素の TS を流すだけで、NIT も SDT も EIT も読みません。局の選り分けも、
番組表の組み立ても、ロゴの取得も denpa です ([agent.md](agent.md))。
エージェントの中で OS ごとに違う USB の扱い (並べる・開く・抜き差し) は、`IUsbHost` の 1 か所にまとめてあります
([agent.md](agent.md#usb-の機材を探す開く境目-iusbhost))。機材ごとのコードは OS を見ません。

エージェントは何台でもつなげます (DB の `agents`)。**どのエージェントに送るかは denpa が決め、エージェントの中のどのチューナーかはエージェントが決めます。**
通知・ログ・バージョン・チャンネルの控え・チューナーの一覧は全部のエージェントから受け取ります。スキャンとその結果と、設定のカードリーダーの表は並びの先頭の 1 台に送ります
([agent.md](agent.md#エージェントは別イメージ別プロセス))。

**選局は、局を受けられるエージェントの中から 1 台に振り分けます** (`tuner.openChannel`)。全部のエージェントの選ぶ順 (`rank`) を 1 つの順にまとめ
(`agent-order.ts`)、振り分けと予約の割り振り (`conflict.ts`) が同じ関数を使います。2 か所で並べると、振り分けた先と割り振りが食い違うためです。

- **まとめた順は、同じエージェントの中は `rank` の順、ほかのエージェントとは受けられる種別が狭いほうを前にします。** 決まらなければエージェントの並びの順です。
  並びだけで決めると、地上波も衛星も受けるチューナーのあるエージェントが前のとき、地上波の録画がそちらに入り、あとの衛星の録画が録れません (#668 と同じこと)
- 振り分けは、同じチャンネルを同じか高い優先度の利用者が読んでいるエージェントがあればそこで共有し、無ければまとめた順に、使ってよいチューナーのある最初のエージェントへ送ります。
  共有は同じエージェントの同じチャンネルでだけ起きます。予約の割り振りも、共有の単位を「エージェントとそのチャンネル」で数えます
- **送ってから一覧に出るまでの選局は手元で数えます。** 一覧は訊いた時点のものなので、同じ定期チェックで録画が 2 本始まるときに同じ空きを 2 本に数えないためです
- 局を受けられるエージェントは、控えにその TS があって一覧を返し、そこで受信できないと決めていないもの (全部で受信できないと決めていれば全部) です。
  番組表の取得も TS ごとに 1 回で、どのエージェントで受けるかは振り分けに任せます。スキャンと放送の一覧の読み直しは並びの先頭の 1 台で回し、振り分けません
- **録画とライブは、その局を復号できる見込みのいちばん高いカードのエージェントに絞ってから振り分けます** (`agent-cards.ts`)。契約中と確かめたカード、確かめていないカード、
  未契約のカード、カード無しの順です。カードは世帯で 1 枚を 1 台に挿し、ほかは `CARD_URL` で鍵を貰う勧め方のままで、そのときはカードを使えるエージェントがみな同じ順になります。
  契約を確かめるのはカードごとに 1 台 (そのカードを手元に持つエージェント)、後から復号させるのは元の TS の置き場が見えるエージェント (`POST /denpa/raw/probe` で確かめる) です
- 局を受けられるエージェントが 1 台だけなら、一覧もカードも訊かずにそこへ送ります。エージェントが 1 台のときの動きは、振り分けを入れる前と同じです
- **1 台が落ちても録画は止めません。** 取り直しは新しい 1 回の選局なので、同じ TS を受けられるほかのエージェントに空きがあればそちらに入ります。
  動いている録画を、落ちる前に別のエージェントへ移すことはしません (新旧の選局を重ねて継ぎ目を denpa が持つことになるため)。予約の割り振りは、落ちているエージェントを最後に返した一覧で数えます

**チャンネルの控えはエージェントごとで、denpa は「どの TS を、どのエージェントのどのチャンネルで受けられるか」を DB に写します** (`agent_channels`。`agent-channels.ts`)。
局 (`services`) は局の ID で 1 行で、物理チャンネルは持ちません。中継局やエージェントによって、同じ TS を別の物理チャンネルで受けることがあるためです。
局からチャンネルを引くときは局の TS で引きます。受信の記録 (`channel_reception`) もエージェントごとで、局を番組表・ライブ・ルールから外すのは、
その局を受けられる全部のエージェントで受信できないと決めたときだけです ([data.md](data.md#bs-と-cs-は放送の一覧から作る))。

## 入れ替えと録画

ArgoCD が同期すると Pod が差し替わります。録画中に来ても困らないように、
**denpa は SIGTERM を受けても録画が終わるまで待ってから止まります**
(`SHUTDOWN_WAIT`、既定 6 時間)。録画していなければすぐ止まるので、普段の入れ替えは変わりません。

TS は追記で開き、次の起動で `recoverOrphanedRecordings` が続きから録り直すので、
落ちても丸ごとは失いません。それでも待つのは、入れ替わるまでの十数秒は
どうやっても落ちるからです。ArgoCD の同期は待てますが、放送は待ちません。

すぐ入れ替えたいときは `SHUTDOWN_WAIT=0` にすると「落ちて、続きから録り直す」になります。
Kubernetes の `terminationGracePeriodSeconds`・docker compose の
`stop_grace_period`・Mac の plist の `ExitTimeOut` (install.sh) は `SHUTDOWN_WAIT` より長くしておくこと。短いと待っている
途中で SIGKILL されます。Windows には止まれの合図が無いので、install.ps1 が録画の終わりを待ってから止めます。

**待っている間も画面は開けます。** ここは 2 箇所で落ちていました
(実機では、録画中に同期が来て 34 分間ずっと画面だけ開けなかった)。

1. **adapter が SIGTERM を受けたその場で listen を閉じる** (adapter-bun は `server.stop()`)。
   止まれの合図は `takeOverSignals` でこちらが受け取り、先に入っていた後始末は外します。
   閉じるのは本当に止まる直前 (`process.exit`) だけです。

   **引き取りは 1 回では足りません。** adapter が合図を登録するのは `build/index.js` の
   いちばん最後で、こちらはその手前 (`hooks.server.ts` はアプリの読み込みで走る) なので、
   最初の引き取りでは外すものがまだ無い。そのままだとプロセスは生きたままポートだけ閉じます。
   入口の `server.js` が `build/index.js` を読み終えたところで、もう一度引き取らせます。
   2 度目の合図でも落ちないようにしてあります (`once` で受けていた頃は、2 回目のデプロイで録画の途中でも終わっていた)。

2. **Kubernetes は `deletionTimestamp` が付いた Pod を Service から外す。**
   Service に `publishNotReadyAddresses: true` を付けると、止まりかけの Pod にも回ります。
   readinessProbe は無く、`strategy: Recreate` で新旧の Pod が並ぶこともないので、副作用はありません。

### 待っている間も、始まる録画は始めます

始めないでいた頃は、デプロイの最中に始まった番組の冒頭が **9 分 42 秒ぶん欠けて**いました
(`scheduler.ts` に実測)。始めればそのぶん待ちが伸びますが、`SHUTDOWN_WAIT` が歯止めになります。

### エージェントも録画が終わるまで待ちます

TS を流しているのはエージェントなので、そちらが先に消えれば使っていたストリームごと切れます
(実機では、エージェントの Pod を入れ替えただけで 30 分番組が丸ごと失敗した)。
エージェントも `SHUTDOWN_WAIT` を見て、録画が終わるまで待ちます。番組表・ロゴ・スキャンは
取り直せばいいので待ちません (`use` が `rec` で始まるものが録画)。

**止まれの合図はエージェント自身が受け取ります** (`Program.cs` の `Drain`)。既定の受け取り役に
任せると、その場で Kestrel が開いている応答への書き込みを止めます。`takeOverSignals` と同じ理由です。

**待っている間も、新しい選局は断りません。** denpa と同じく、来た録画は録り終えるまで待ちます。
ライブや番組表の選局も受けますが、それを理由には待たず、録画が終われば一緒に切れます。

**録画が無ければすぐ止まります。** 通知 (`/denpa/events`) やライブの選局が開いたままだと、Kestrel は
受け口だけ閉じて 30 秒待ってから止まっていました。そのぶん入れ替えの隙間が伸び、実機ではその間に始まった
録画の冒頭が約 35 秒欠けました。いまは止まるときにエージェントのほうから閉じます。

### それでも切れたときは取り直します

電源やネットワークで切れることはあります。読んでいる最中に例外が飛んだときも、EOF と同じように取り直して
終了時刻まで録り続けます (`recorder.ts`)。TS は追記なので、落ちるのは切れていた数秒だけです。

### 隙間はイメージの取得時間だった

新旧の Pod を並べられないので、入れ替えの隙間はどうやっても空きます。実機で測ると、
ほとんどがイメージの取得 (13.6 秒) でした。そこで、マニフェストを当てる前にイメージだけ引いておく Job を
ArgoCD の PreSync フックに置いています (`denpa-prepull`。土台は distroless で `/bin/true` も無いので、
`bun --version` で終わる)。エージェントも同じで、`tuner-agent-prepull` が `denpa-agent --version` で終わります。
隙間は起動そのものだけになります。

### 録画そのものは引き継がない

引き継ぐには新旧の Pod が同時にいる必要がありますが、denpa は 1 つの SQLite に書き、スケジューラも EPG 取得も
エンコード待ち行列も抱えているので、2 つ動くと全部が二重になります。
録画をエージェント側に持たせれば denpa の入れ替えと録画が切り離れますが、
番組追従・スクランブルの復号・保存名の付け方まであちらへ移すことになり、
「エージェントは中身を読まない」という切り分けが崩れます。**この方式は選びません。**

### イメージのタグ

| タグ         | いつ動くか                                             | 誰が指しているか                                                                           |
| ------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `develop`    | main へ入るたび                                        | `deploy/application.yaml` の `helm.valuesObject` (この構成。入れ替えの合図は `imageMarks`) |
| `latest`     | GitHub でリリースを作ったときだけ                      | `compose.prod.yml` (入れて使う人)                                                          |
| `1.20`       | その系列でリリースを作るたび (1.20.1 を出せばそちらへ) | バージョンを決めて使う人                                                                   |
| `1.20.0`     | 動かない                                               | 固定して使う人・戻したいとき                                                               |
| `sha-<12桁>` | 動かない。中身ごとに 1 つ                              | 中身のコミットから辿るとき                                                                 |

**どのタグも amd64 と arm64 を束ねた索引 (multi-arch manifest) を指します。** CI は
arch ごとにその arch のランナー (amd64 は `ubuntu-latest`、arm64 は `ubuntu-24.04-arm`) で
組んで digest だけで push し、最後に両方を束ねた索引へ名前を付けます
(`.github/workflows/build-and-deploy.yml`)。QEMU で arm64 を組むと ffmpeg と Native AOT が
何倍も掛かるので使いません。片方の arch が落ちたら名前は付けません (片方だけの
`develop` が出ていくより、前のものが残るほうがいい)。中身の違いは GPU の部品だけで、Intel・AMD の VA-API のドライバ・
NVIDIA の NVENC は amd64 に、Rockchip の MPP は arm64 にだけ入れています
([encode.md](encode.md#gpu-でエンコードする-va-api))。

`denpa-aio` (本体とエージェントを 1 つにしたもの) も同じ名前で出ます。組み直さず、束ねた 2 つを
写すだけです (`.github/aio.Dockerfile`)。main では `develop` と `<denpa の sha>-<agent の sha>`、
リリースではバージョンの名前と `latest` を貼ります。

**バージョンの名前は、入れた人がバージョンを固定して戻せるように貼ります** (git のタグ `v1.20.0` から `v` を落としたもの)。

**`develop` は動くタグなので、マニフェストは変わりません。** そのままだと ArgoCD には
何も変わっていないように見えるので、CI は `deploy/application.yaml` の `imageMarks` に
ビルドした中身のコミットを書き戻し、chart がそれを Pod の注釈 (`denpa.doany.io/denpa-image`) にします。
注釈が変われば Pod が入れ替わり、`imagePullPolicy: Always` が新しい `develop` を引きます
(`IfNotPresent` だと、古い `develop` がノードに残っているかぎり黙ってそれで上がる。
引き替えに、GHCR に繋がらないと Pod が起動しません)。

リリースを作ると、組み直さずにそのコミットの `sha-` のイメージへバージョンの 1 層 (`DENPA_VERSION`。`update.ts` が新しいバージョンの
通知に使う) を足し、バージョンと `latest` を貼ります (`.github/workflows/release.yml`・`.github/release.Dockerfile`)。試したものとリリースしたものを別にしないためです。
貼り足すときも両方の arch のままです。

**プレリリース (prerelease) には `latest` を貼りません** (`compose.prod.yml` が指しているので、
入れて使っている人のところへ降ってしまう)。`x.y.z` の形式になっていないタグ (`nightly` など) には
バージョンの名前も貼りません。

## ライブ視聴

**denpa 自身が配ります** (`/live`)。外のメディアサーバにも IPTV 向けのプレイリストにも
任せていません。視聴・追っかけ録画・チューナーの取り合いを 1 箇所で決めたいからです。
チューナーを取り合う相手 (録画・番組表・ロゴ・スキャン) が全部 denpa 側にあるので、
視聴だけ外に出すと、足りないときにどの用途を先にするかの決め方が 2 箇所に割れます。

任せる先もありません。エージェントは局も番組表も持っていないので、IPTV 向けの
プレイリストと番組表 (m3u + XMLTV) を出せる相手がいません。

映像・音声・字幕・データ放送・双方向 (通信系コンテンツ) まで入っています。
どこまで入っているか、エンコード方式・遅延の詰め方・WebSocket の作りは [stream.md](stream.md) にあります。

録画済みのものをテレビで観るには、テレビのアプリ ([denpa-tv](https://github.com/danything/denpa-tv)) を使います
([library.md](library.md#テレビのアプリ))。

## クラスタ側の前提条件

**入れ方は Helm chart** ([charts/denpa](../charts/denpa)。エージェントだけ置くなら
[charts/denpa-agent](../charts/denpa-agent))。このリポジトリ自身の本番は ArgoCD が
[deploy/application.yaml](../deploy/application.yaml) の Application から同じ chart を当てていて、
値はそこの `helm.valuesObject` にあります (chart の使い方の実例として読めます。なぜそう置くかは
ファイルの冒頭のコメント)。クラスタの初期構築や共通アドオンは別のリポジトリです。chart を当てる前に以下が要ります。

- StorageClass は `persistence.storageClassName` (空ならクラスタの既定)。PVC を消させない設定は
  `persistence.protectFromPruning` (values.yaml に理由つき)
- Gateway API の Gateway か Ingress。chart の `httpRoute.parentRefs` / `ingress` が指す先です。証明書は
  Gateway 側のリスナーが持ちます。前段を置かずにノードの IP で開くなら `service.type=NodePort` ([install-talos.md](install-talos.md))
- DNS で、denpa の名前が Gateway のアドレスを指すこと
- チューナードライバ。エージェントは `privileged: true` かつ `/dev/bus`・`/dev/dvb` を
  hostPath でマウントするので、DVB の機材はノード側にドライバが読み込まれていること。
  PX-MLT5 系・PX-Q3U4 などの IT930x の機材と、smsusb を blacklist した PX-S1UD はノードに
  何も要らない (エージェントが `/dev/bus/usb` で USB を直に持つ。
  [tuner-it930x.md](tuner-it930x.md)・[tuner-px-s1ud.md](tuner-px-s1ud.md))
- GHCR から `ghcr.io/danything/denpa-agent` と `.../denpa` を pull できること

## 画面で動いてよいもの (CSP)

**画面の HTML には Content-Security-Policy を付けています** (設定は `vite.config.ts` の
`csp`、SvelteKit が毎回付ける)。[auth.md](auth.md) は「誰を通すか」ですが、ここは「通した人の画面で、
**誰が書いたスクリプトを動かすか**」です。

**狙いは放送が書いたスクリプト。** データ放送のエンジン (`src/lib/bml/`) は BML の
`onclick` などを DOM に写さず、自前の VM で動かします (描く要素に付くのは `style` と画像の
`src`・`alt` だけ)。それでも写し漏れがあったとき、放送の文字列が **denpa の origin で本物の
JS として動き**、ログインの控えで API を呼べることになるので、「放送のものを本物の JS として
動かさない」最後の砦として CSP でも止めます。

| 指令                       | 値                                                                      | 理由                                                                                                                                                                                                                                                                                                                                |
| -------------------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `script-src`               | `'self'` + nonce                                                        | 自分の束 (`_app/`。データ放送のエンジンの遅延読み込みも) と、SvelteKit の起動・後から流すデータの `<script>` (nonce)。**`'unsafe-inline'` と `'unsafe-eval'` は入れない**                                                                                                                                                           |
| `script-src-attr`          | `'none'`                                                                | `onclick="…"` などの属性のハンドラを止める (上の穴そのもの)                                                                                                                                                                                                                                                                         |
| `style-src`                | `'self' 'unsafe-inline'`                                                | 下の「スタイルは止めない」                                                                                                                                                                                                                                                                                                          |
| `img-src`                  | `'self' data: blob:`                                                    | 局ロゴ・ポスターは自分。データ放送の画像と DRCS (外字) は作り直して blob:。data: は CSS に埋めたアイコン                                                                                                                                                                                                                            |
| `font-src`                 | `'self' data: blob:`                                                    | Denpa Font は自分 (`/api/font/`。woff2 の 2 つ)                                                                                                                                                                                                                                                                                     |
| `media-src`                | `'self' blob:`                                                          | 録画は自分。ライブの MSE と端末に保存した録画は blob:                                                                                                                                                                                                                                                                               |
| `connect-src`              | `'self' wss://nx-jikkyo.tsukumijima.net https://jikkyo.tsukumijima.net` | fetch・SSE・データ放送の双方向の中継 (`/api/bml/…`)・ライブの WebSocket。`'self'` は同じ host の `ws:` / `wss:` も含む。外の 2 つは実況のコメント (下の「端末が外へ繋ぐもの」)。ホストまで書き、世帯の設定がオフでも許したまま (CSP は組むときに決まる。繋ぐかどうかは画面が設定を見て決める)                                       |
| `worker-src`               | `'self'`                                                                | 変換せずに観る経路の worker (`src/lib/raw/worker.ts`) と PWA の ServiceWorker                                                                                                                                                                                                                                                       |
| `object-src`               | `'none'`                                                                | 使わない。BML の `<object>` はエンジンが画像 (`<img>`) か映像の場所の目印にするので読み込まない                                                                                                                                                                                                                                     |
| `frame-src`                | `'self'`                                                                | Hybridcast のアプリを入れる iframe (`/api/bml/hybridcast`) だけ。中身は sandbox で使い捨てのオリジンになり、denpa には触れない ([stream.md](stream.md#hybridcast))                                                                                                                                                                  |
| `base-uri` / `form-action` | `'self'`                                                                | `<base>` とフォームの送り先は自分だけ                                                                                                                                                                                                                                                                                               |
| `frame-ancestors`          | `'self'`                                                                | denpa の画面を枠に入れてよいのは自分だけ。外のサイトの隠した iframe で、信頼するネットワークの人の権限のままボタンを押させるのを止める ([auth.md](auth.md#アプリのペアリング))。古いブラウザ向けに `X-Frame-Options: SAMEORIGIN` も付ける (`hooks.server.ts` の `finish`)。Home Assistant の Ingress のような同じオリジンの枠は通る |
| `default-src`              | `'self'`                                                                | 上に無いもの (マニフェストなど)                                                                                                                                                                                                                                                                                                     |

**画面の移動は関わりません。** OIDC のログイン (`/login` が Entra へ 302)・
Hybridcast (別のタブで開く)・更新のお知らせのリンクは移動なので、上のどれにも掛かりません。
フォームの送り先 (`form-action 'self'`) は自分だけで、送ったあとに外へ回すフォームはありません
(ログアウトは `/login/out` へ戻すだけ。期限切れの POST はリダイレクトせず 401)。

**WebSocket を `'self'` で通すのは CSP3 の決まり**で、今のブラウザ (Chrome・Edge・Firefox・Safari)
は同じ host の `ws:` / `wss:` を `'self'` に含めます。CSP3 より前の作りの古いブラウザ (数年前の Safari など) では
ライブが繋がりません。`ws:` / `wss:` を足せば通りますが、どこへでも繋げるようになるので足していません。

### nonce にする (hash ではなく)

**設定の画面 (録画・受信) は、load から Promise を返して後から流しています**
(SvelteKit のストリーミング)。流れてくる `<script>` はヘッダを送ったあとに組まれるので、
hash を先頭に載せられず、hash の方式だと止まります。`app.html` の先頭のスクリプト (色当てと、スマホの形の印 `data-phone`) も
`nonce="%sveltekit.nonce%"` で通しています。

nonce は毎回変わるので、**画面の HTML は 304 になりません** (中身の指紋が毎回変わる)。
HTML は小さく、重いもの (`_app/immutable/`) は永く持たせたままなので困りません
(`hooks.server.ts` の `finish`)。

### スタイルは止めない

`style-src` には `'unsafe-inline'` を残しています。その場で書くスタイルが多いためです。
サーバで組んだ HTML の `style` 属性 (Svelte の `style:` と、観る画面の映像の箱などに直に書いたもの) と、
`+layout.svelte` の @font-face の `<style>`。属性のスタイルは nonce では通せず、hash で通すには
`'unsafe-hashes'` と 1 つずつの hash が要るので見合いません。データ放送のエンジンは
`element.style` (CSSOM) で書くので、これには頼っていません (CSSOM からの書き込みは CSP に掛からない)。

**CSS からできることは、スクリプトよりずっと少ない。** 見た目を変えることと、
上の `img-src` / `font-src` の範囲での読み込みまでです (外へは出られない)。denpa の DOM に
CSS で抜き出して困る秘密 (属性に入った鍵など) はありません。

**この「外へは出られない」は `img-src` / `font-src` を自分・data:・blob: に絞っているから**
成り立っています。外のサーバの画像や字を許すと、差し込まれた CSS (属性セレクタ + `url()`) で
画面の中身を外へ送れるようになるので、そのときはスタイルも絞り直します。データ放送の CSS はブラウザの CSS に
渡さず、エンジンが読んで確かめた値だけを `element.style` に書く (`src/lib/bml/css.ts`) ので、この経路にはなりません。
`connect-src` に外を足しても、CSS からは `connect-src` を使えないので、ここは崩れません。

### 増やすとき

新しく読み込み元を足したら (外のサーバの画像・iframe など) ここの表と `vite.config.ts` を一緒に
直します。止められたものは開発者ツールのコンソールに `Refused to …` と出ます。
E2E (`tests/e2e/35-csp.spec.ts`) は主な画面を回って違反が 1 つも出ないこと、
BML の `onclick` を押しても動かないことを見ています。

## 端末が外へ繋ぐもの (実況のコメント)

**ふだんの画面は denpa のサーバにしか繋ぎません。外へ繋ぐのは、実況のコメントを流す・書き込むときだけです。**
世帯の設定 (連携の「実況」) と端末の ⚙ の「実況」の両方がオンの端末が、denpa のサーバを通さずに次の 2 か所へ繋ぎます
(宛先は `src/lib/jikkyo/endpoints.ts`。CSP の `connect-src` に同じものを書いています)。

| 宛先                                                         | 使うとき                             | 方式                                                           |
| ------------------------------------------------------------ | ------------------------------------ | -------------------------------------------------------------- |
| NX-Jikkyo (`wss://nx-jikkyo.tsukumijima.net`)                | ライブと、録画中の追っかけの新しい所 | WebSocket (視聴の WS → コメントの WS)                          |
| ニコニコ実況 過去ログ API (`https://jikkyo.tsukumijima.net`) | 録画と、録画中の追っかけの古い所     | fetch (`credentials: "omit"`・`referrerPolicy: "no-referrer"`) |

どちらも tsukumijima さんが個人で運営している非公式のサービスで、過去ログ API の前には Cloudflare が立っています。
相手に見えるのは次のものです。

| 見えるもの                        | NX-Jikkyo                                       | 過去ログ API                        |
| --------------------------------- | ----------------------------------------------- | ----------------------------------- |
| 端末の IP                         | 見える                                          | 見える                              |
| ブラウザの User-Agent             | 見える (NX-Jikkyo は記録に残す)                 | 見える                              |
| denpa のアドレスのホスト (Origin) | 見える (WebSocket の手順でブラウザが必ず付ける) | 見える (CORS のリクエストに付く)    |
| denpa のページの URL (Referer)    | 付かない                                        | 付けない                            |
| どの局をいつ観ているか            | 見える (繋いだチャンネルと時刻)                 | 見える (どの局のどの時間を取ったか) |
| Cookie・ニコニコのアカウント      | 送らない (ログインしない)                       | 送らない                            |

- **denpa のサーバ・世帯のほかの端末・録画の一覧・ログインの情報は出ません。** 出るのは、その端末で何を観ているか (と、書き込んだもの) だけです
- 受けたコメントは本文と時刻と流し方 (色・位置・大きさ) だけにして、利用者の ID などはその場で捨てます。コメントは端末のメモリにだけ置き、画面を閉じれば消えます
- **局の勢い (ライブの「実況」タブ) だけはサーバが中継します。** NX-Jikkyo の REST は CORS を許していないためです
  (`GET /api/jikkyo/ranking`。呼ばれたときだけ読み、30 秒だけメモリに持つ)。NX-Jikkyo に見えるのは denpa のサーバの IP です
- **ライブでは、端末から NX-Jikkyo に書き込めます** (同じ視聴の WS に `postComment` を送る。denpa のサーバは通しません。CSP も同じ宛先のまま)。
  ニコニコと連携している世帯では、書き込みは denpa のサーバが公式のニコニコ実況へ送り、端末は外へ繋ぎません ([下記](#ニコニコとの連携-denpa-hub))。
  書いた中身は公開され、消せません。ニコニコのアカウントは使わず匿名 (184) ですが、書き込みには NX-Jikkyo が端末の IP とブラウザの種類などから作る ID が付き、
  誰でも読めます。**同じ端末から書いたものは、その ID で結び付けられます** (IP やブラウザが変わると ID も変わります)。決まりは [watch.md](watch.md#実況に書き込む)

## ニコニコとの連携 (denpa-hub)

**ニコニコのアカウントのトークンは denpa のサーバだけが持ち、端末には渡しません。** 世帯で 1 つの連携で、設定の「連携」の「実況」から始めます。
ニコニコの OAuth は、Doa が動かす denpa-hub (`DENPA_HUB`。既定 `https://dh.doany.io`) が中継します。家ごとに違う denpa のアドレスをニコニコに登録できず、
クライアントのシークレットを各家庭の denpa に配れないためです。ニコニコ固有の値 (エンドポイント・スコープ) は hub の設定にだけあり、denpa のコードには書きません。
hub の作りは [denpa-hub の docs/niconico.md](https://github.com/danything/denpa-hub/blob/main/docs/niconico.md) にあります。

1. 「ニコニコと連携」(`/settings/integrations/niconico/link`) で、サーバが P-256 の鍵の組を作り、画面を hub の `/niconico/authorize` へ送る。
   秘密鍵はサーバのメモリにだけ 10 分持ち、Cookie (`denpa_niconico`) で始めたブラウザと結び付ける
2. ニコニコで同意すると、hub が戻り先 `/settings/integrations/niconico/return` に `#result=` (サーバの公開鍵に宛てて暗号化したトークンの応答) を付けて返す。
   画面はフラグメントをすぐ URL から消し、`result` をサーバへ送る (`…/niconico/finish`)。開けるのは鍵を持つサーバだけ
3. サーバは開いたトークンを暗号化して DB に置く (`niconico_link`。鍵は DB の隣の `niconico.key`)。更新に使うトークンには期限が無く、ニコニコに失効のエンドポイントも無いので、
   DB だけが出回っても使えないようにする。denpa を別の機械へ移すときの写しからも消す
4. アクセストークンは使う直前に期限を見て、切れかけていたらサーバが hub の `/niconico/token` で更新する。更新のたびに更新に使うトークンも替わるので、
   更新はサーバの中で 1 本だけ走らせ、受けたものはすぐ DB に書く。ニコニコが断ったら (`invalid_grant`) 連携が切れた状態にし、設定の画面で連携し直してもらう
5. 「連携を解除」は手元のトークンを消し、開いている公式の実況への接続を切る。ニコニコの側の許可は、ニコニコのアカウント設定から取り消す
6. 連携している世帯では、ライブの書き込みを**公式のニコニコ実況へ denpa のサーバが送る** (`src/lib/server/niconico-live.ts`)。
   書き込みの欄が開いている間、端末が `POST /api/jikkyo/niconico/session` を 30 秒おきに呼び、サーバは hub の `/niconico/live/watch` から
   視聴の WebSocket の接続先 (それ自体が資格情報) を受け取って自分で繋ぐ。やり取りは NX-Jikkyo と同じ形。
   端末の書き込みは `POST /api/jikkyo/niconico/comments` で受けて、いつも匿名 (184) で送る。2 分呼ばれなければ切り、同時に繋ぐのは 2 つの局まで

- **hub が戻り先として受け付けるのは、家の中のアドレス** (プライベートの IP・`localhost`・`.local`・`.home.arpa`) **だけです。** 名前で開いている
  (`tv.example.com`・`*.ts.net`) ときは、LAN のアドレスで開いてから連携します (連携は 1 回だけの操作なので)。前段のパスの下 (Home Assistant の Ingress など) では連携できません
- アクセストークン (テレビのアプリ) では、連携を始める・外すことはできません (端末に渡した資格で、世帯のアカウントを差し替えさせない)
- hub はトークンを保存しません。hub に見えるのは、連携・更新・接続先を受け取るときのトークン、書く局、denpa のサーバの IP です。書いた本文は hub を通りません
- ニコニコに見えるのは、世帯のアカウントと家の IP (denpa のサーバの IP) です。匿名 (184) で書いても、誰のアカウントかはニコニコには分かります
