# 放送波ストリーミングシステム 構成設計

> **映像・音声・字幕・データ放送 (第1〜3段階) が入っています。** 低遅延の追い込みは
> [やめました](#webrtc--whep-による低遅延化--不採用)。
> どこまで入っているかは [§4](#4-実装の順序) を見てください。

## 1. 前提

| 項目 | 内容 |
| --- | --- |
| デプロイ形態 | **セルフホスト（1ユーザー = 1サーバ）** |
| アプリ | SvelteKit 単一アプリ（配信・視聴の両方を担当） |
| 入力ソース | 放送波 MPEG-TS（ISDB-T / ISDB-S） |
| 目標コーデック | AV1 + Opus |
| 必須機能 | ARIB字幕、データ放送（双方向含む）、複数音声・映像ストリーム |
| 非機能要件 | 低遅延 |

セルフホストなので、以下は**設計で考えない**:

- NVRAM のマルチユーザー分離（受信機 = サーバ = ユーザーが 1:1:1）
- ユーザーごとの地域設定・リモコン設定の分離
- 通信系コンテンツのプロキシにおけるユーザー識別

## 2. 全体構成

```
┌─────────────────────────────────────────────────────────────────┐
│ チューナー (エージェント)                                     │
└────────────────────────────┬────────────────────────────────────┘
                             │ MPEG-TS (チャンネル丸ごと)
                             ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ            │
              │  ・1局に絞る (ServiceFilter)  │
              │  ・プロセス管理／再起動        │
              │  ・WebSocket ハブ             │
              │  ・BML通信系プロキシ           │
              └───┬──────────────────────┬───┘
                  │ 1局ぶんの TS          │ (押した人が居るときだけ)
                  ▼                      ▼
     ┌───────────────────────────┐  ┌──────────────────┐
     │ ffmpeg + libaribcaption   │  │ BmlDecoder       │
     │  ├→ pipe:1 fMP4 (映像音声) │  │ カルーセルを     │
     │  └→ pipe:3 mkv (字幕の絵) │  │ 組み立てる       │
     └─────────────┬─────────────┘  └────────┬─────────┘
                   └───────────┬─────────────┘
                               ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ (配る)     │
              └──────────────┬───────────────┘
                             │ WebSocket (メディア + サイドチャネル)
                             ▼
              ┌──────────────────────────────┐
              │   ブラウザ (SvelteKit client) │
              │  ・MSE 直接        → 映像音声 │
              │  ・canvas 重ね     → 字幕     │
              │  ・web-bml         → データ放送│
              └──────────────────────────────┘
```

**映像と字幕は同じ ffmpeg の2つの出口。** 別々に起こすと時刻が揃わない
（[§5.2](#52-字幕sub2video)）。データ放送へは、絞った TS を denpa の中で分ける
（`tee` は要らない）。

### 設計上の中核

**メディアとメタデータは同じコンテナに載らない。** ARIB字幕（B24 PES）もデータ放送（DSM-CC カルーセル + PSI/SI）も、fMP4 / WebM には規格上入れられず、ffmpeg も GStreamer も扱えない。そこで:

> **サイドチャネル用の WebSocket を 1 本用意し、字幕とデータ放送を同じ経路に相乗りさせる。**

迂回路ではなく、この設計の柱。

### 字幕はサーバで絵にする

**ブラウザに B24 を渡さない。** サーバ側で libaribcaption に描かせ、絵と時刻だけを送る。

放送に絵は流れてこない。テレビは文字と配置の指定から毎回描いている。その描画を libaribcaption に
やらせたのが「放送どおりの字幕の絵」で（[encode.md「字幕は PGS 1本だけ」](encode.md#字幕は-pgs-1本だけ)）、
録画側で実装・実測済み（`src/lib/server/subtitle.ts`）。live は出口だけ違い、`.sup` の代わりに WebSocket へ流す。

| | サーバで描く（採用） | ブラウザで描く（aribb24.js） |
| --- | --- | --- |
| 外字 (DRCS) | そのまま絵になる | 実装依存 |
| 位置・背景の箱・点滅 | 放送どおり | 実装依存 |
| 録画との見た目 | **完全に同じ**（同じ描画系） | 別実装なので揃わない |
| 帯域 | 変わった枚だけ送るので映像の隣では誤差（[§5.2](#52-字幕sub2video)） | 数百バイト／字幕 |
| サーバ負荷 | 映像と同じ ffmpeg の出口が1つ増えるだけ（実測では埋もれた） | なし |
| クライアント側の自由度 | 拡大は画像の拡大になる | 文字サイズを変えられる |
| 持つコード | 出口だけ（録画と共通） | 字幕ライブラリ1本 |

時刻は絵に添えられたものをそのまま使う。映像と同じ ffmpeg が付けたので、受け側の
再生位置と直に比べられる（[§5.4](#54-時刻同期)）。

### 送るのは PGS ではなく PNG

録画側は同じ絵を PGS にしているが、**ブラウザに PGS のデコーダが無い**。自分で書くうえ、
PGS は色を YCrCb 限定レンジでしか持てず、サーバで変換してクライアントで戻す往復が入る。
この変換は mkv に入れるための制約で、live には無い。PNG なら `createImageBitmap()` に
渡すだけ。組むのは ffmpeg（[§5.2](#52-字幕sub2video)）。

## 4. 実装の順序

作るものは1つ。難所は「AV1 のリアルタイムエンコード」だけに絞れているので、そこだけ逃げ道を用意する。

1. **メディア経路** — `ffmpeg → fMP4 → WebSocket → MSE`。まず映像音声だけ出す — **入っています**
2. **字幕** — 同じ ffmpeg の2つ目の出口からサイドチャネルへ流し、canvas に重ねる — **入っています**
3. **データ放送** — 1局に絞った TS の写しを自前の `BmlDecoder` で解き、組み立て済みのモジュールをサイドチャネルへ — **入っています** ([§5.6](#56-データ放送の統合))
4. ~~**低遅延の追い込み（任意）**~~ — **やめました。** 縮むのは受け側の貯め (0.2秒〜) だけで、
   開いてから映るまではむしろ伸び、「止めた所から見られる」「5分戻れる」を捨てる
   （[§6](#webrtc--whep-による低遅延化--不採用)）

**コーデックは段階ではなく設定にする。** AV1 が回らない環境・Safari では H.264 + AAC に
切り替える。エンコーダとコンテナ以外は共通なので、字幕もデータ放送もそのまま動く。

### 入っているもの

| | |
| --- | --- |
| 画面 | `/live`。左に映像、右にチャンネル。前回見ていた局から開く |
| 焼き方 | H.264 + AAC / AV1 + Opus を見ながら選べる（[§5.1](#51-エンコード)）。`src/lib/server/live.ts` |
| 運び方 | WebSocket 1本。多重化の頭は [§5.3](#53-websocket-プロトコル) のまま |
| チューナー | 優先度 **9**。録画 (10) にだけ譲り、番組表・ロゴ・スキャンからは取り上げる |
| 相乗り | 同じ局を2人で見ても、チューナーも ffmpeg も1つ |
| 生で送る | **家の中のブラウザでは焼かずに送れる**（端末の設定。既定は切）。[§5.5](#55-放送そのままmpeg-2を-lan-で送る) |
| 畳み方 | **見ている人が0になったら離す**。接続そのものが在席の印 |

**相乗りの単位は局・音声・焼き方・字幕。** 1本の物理チャンネルに複数の局が乗り、
ffmpeg には局を名指しさせている（下記）ので、絵は局ごとに違う。二カ国語を主音声で
見る人と副音声で見る人も別のものを焼く。字幕も映像と同じ ffmpeg が焼くので
（[§5.2](#52-字幕sub2video)）、何本目を選ぶかで別になる。チューナーはエージェント側で
相乗りになり、増えるのは ffmpeg だけ。

### 多重音声はサーバで1本に決める

**「多重音声」には中身の違う2通りがある。** 見る人にはどちらも「音声を選ぶ」操作なので、
1つの一覧に平らに並べる（`arib.audioTracks`）。

| | 中身 | 分け方 |
| --- | --- | --- |
| デュアルモノ | 音声は1本。左に主音声・右に副音声（二カ国語・解説放送） | `-af pan=stereo\|c0=c0\|c1=c0`（副音声は `c1`） |
| 複数の音声 | 音声そのものが2本以上 | `-map 0:p:<局>:a:<何本目>` |

デュアルモノは1本から3つ（主・副・主+副）出てくる。テレビの「音声切換」と同じ3択。

**選ぶのはサーバ側。** 音声を全部送ってブラウザで切り替える手もあるが、複数の音声を
入れた fMP4 を MSE で切り替えられないブラウザがある（`audioTracks` の実装がまちまち）。
焼くときに1本に決めれば、どのブラウザでも同じに鳴る。代償は選び直しが焼き直しに
なることだが、チューナーは掴んだままで、かかるのは焼き始めのぶんだけ。

**選べるものは繋いだあとでないと分からない。** 二カ国語の映画が終わればステレオに
戻るので、局の一覧からは決められず、選局のたびに現物を `tuned` に載せて送る。
覚えていた合言葉が選べなくなったら先頭に落とす（`arib.pickTrack`）。落とさないと
番組が変わった瞬間に音が消える。

### 追っかけ再生とライブは別物

止めたり帯を戻したりして**わざと遅れて見ている**状態を、ライブと分けて持つ。

| | ライブ | 追っかけ |
| --- | --- | --- |
| 大きく離れたら | 跳んで詰める（別のタブから戻ったとき） | 跳ばない（見ようとしていた場面が飛ぶ） |
| 速さ | 自動（1.05倍まで） | 選べる（1 / 1.25 / 1.5 / 2倍） |
| 追いついたら | — | 自分でライブに戻る |

分けていなかった頃は `pacing` が「別のタブから戻った」と「わざと遅れて見ている」を
区別できず、8秒より長く止めて再開すると放送の今へ跳んでいた。

**追いついたらライブに戻す。** 選ばれた速さのまま進むと放送を追い越し、溜まりを
使い切って止まる。実機で 15.8 秒遅れから2倍で追わせると、14.9 秒で追いついて
速さが 1 に戻った。

録画中の録画を頭から観る `/chase/<id>` も同じ器で流す（`server/chase.ts` が伸びる生TSを
追い読みする。チューナーは掴まない。[app.md](app.md#画面)）。ここでいう「追っかけ」とは別の話。

### 開いてから絵が出るまでの内訳

実機（PT3 + `earth_pt3`）で割った。**チューナーが温まっていれば ≈0.89 秒**、
冷えていれば頭に選局の 0.66 秒が付く。

| | |
| --- | --- |
| 画面が動き出して札を取り、WebSocket が繋がるまで | 160ms |
| ffmpeg の立ち上がり（固定） | 530ms |
| 放送の I フレーム待ち | 0〜501ms（GOP はちょうど 501ms） |
| **貯めてから始める**（`pacing.ts` の `FLOOR`） | 200ms（0.4秒だったのを半分に。ただし下の「覚えておく」） |
| MSE に入れて1枚映るまで | 40ms |

**貯める量はこちらの都合で動かせる唯一のところ。** 再生は「貯まった尺 ≧ 貯める量」
かつ「絵を出せるようになっている」（下の「貯まっただけでは始めない」）で始まる。
電波は実時間で届くので、0.4 秒貯めるには 0.4 秒かかる。0.2 秒 = 塊4つぶん
（サーバは 0.05 秒ずつ出す）まで下げた。足りずに止まれば 0.6 ずつ増え、荒れる経路では
自分で伸びるので、小さいほうから始めてよい。

#### 選局の 0.66 秒と、削れなかったもの

冷えているときの選局 0.66 秒の中身:

| | |
| --- | --- |
| 頼んでから選局の ioctl を出すまで | 42ms |
| **復調器がロックするまで** | 320ms（実測 319〜323ms。ISDB-T の OFDM フレームは約 205ms） |
| ドライバが TS を出しはじめるまで | 0〜7ms |
| ロックしてから denpa の1バイト目まで | 240ms（PAT 60ms → PMT 110ms → ECM 50〜250ms → カードの往復） |

**削れたのは 160ms だけだった。** 開く局はページを組む時点で決まっているので、画面が
繋いでくる前にサーバ側で焼きはじめる（`server/live.ts` の `warm`）。その 160ms が
ffmpeg の 530ms と重なる。

> **PSI を先に流す手は外した。** 前に開いたときの PAT/PMT を先に流し、選局待ちの 0.66 秒に
> ffmpeg の入口の仕事を重ねる手で、単体では効いた（888ms → 707ms、ばらつき 342ms → 77ms）。
> 実機では、電波より先に入口を読み終えた ffmpeg が `-map 0:p:<局>:v:0` を解決できずに
> 終了し、切り替えが壊れた（`Failed to set value '0:p:24632:v:0' for option 'map'`）。測ったときは
> 選局済みだったので見えなかった。同じ落ち方は相乗りの多い TS（tvk / T15）でも起き、
> [渡す前に1局へ絞る](#渡す前に1局へ絞る)で直した。

削れなかった残りは、放送か機材か ARIB の都合:

- **ロックの 320ms はチップの物理時間。** ドライバを替えても同じ。
  `dvb_override_tune_delay` を 1ms にすると、DVB core が同期の途中で周波数を
  振り直して 451ms に悪化した。あの値は「諦めるまでの猶予」で、ロックの検出間隔
  ではない（検出はこちらが 10ms 間隔で直に読んでいる）
- **ロック後の 240ms はスクランブル解除。** ECM が来るまで鍵が作れない
- **I フレーム待ちは放送の GOP。** MPEG-2 は I フレームからしか復号を始められない
- **符号器は道の上に居ない。** `-tune zerolatency` は B フレームも先読みも作らない。
  インタレ解除・音声・塊の細かさを外しても縮まなかった（実測）

### 一瞬止まって遅延が増えていく

宅内なのに一瞬止まり、そのたびに遅れが増えて戻らなかった。エージェントの環
（6分視聴 + 番組表3本で溢れ 0回）・送り出し（H.264 25分で 0.5秒以上の間 0回）・流量
（`-maxrate 8M` で 8.4 Mbit/s まで削っても8分に10回）と順に外して、残ったのは**ちょうど60秒ごと**という周期だった。

周期が揃うなら電波の混み具合ではない。遅延（ここでは手元の貯まり。[「遅延」は2つある](#遅延は2つある)）
は毎回「3.1秒 → 1.05倍で詰めて 0.3秒 → 止まる」で、縮める先をいつも `FLOOR` にしていたのが原因だった。

**止まった高さのすぐ上を次の下限にする**（`pacing.ts` の `PROBE`）と、焼き方を触らずにこうなった:

| | 途切れ | 貯まり 中央 | 貯まり 最大 |
| --- | --- | --- | --- |
| 直す前 | 8分に10回 | 1.4秒 | 3.2秒 |
| 下限を覚える | 8分に5回 | 0.7秒 | 3.2秒 |
| 下限を下げ直すまでを2分→10分 | 10分に3回（最後の6分は0回） | 0.9秒 | 1.1秒 |
| `-maxrate` を外す | **10分に1回** | **0.6秒で平ら** | **0.7秒** |

`-maxrate` は見立て違いで入れたもので、外した。宅内なら帯域は余っていて、削られるのは
動きの多い場面の絵になる。細い経路には AV1 を選ぶ道がある。

### 絵だけが遅れる（音と字幕は合っている）

開き直すと直る、絵だけの遅れが出た。字幕は再生位置（音が刻む時計）に合わせて貼って
いるので、**絵だけが遅れるなら遅れているのは復号**で、運び方でも貯め方でもない。
ブラウザは遅れたまま出し続けるので開き直すまで溜まり、放送との差の数字にも出ない。

`requestVideoFrameCallback` の `mediaTime` と再生位置の差が「絵だけの遅れ」になる。0.1秒（口の動きの
ずれが分かりはじめるところ）を超えたらその場へ跳び直す（`live-player.svelte.ts` の `unslip`。3秒に1回まで）。
跳べば必ず `waiting` が上がるが、跳んで起きた詰まりは数えない。数えると絵を直すたびに貯める量が増える。

#### 測れないこともある

`mediaTime` は合成器へ渡した時点のコマの時刻。Windows の Chrome / Edge は映像を別の面（DirectComposition の
overlay）に出すので、**面のほうが遅れても数字に出ない**。実機では「絵と音がずれるのに跳び直しが一度も出ない」
形で出た（ソフトウェア合成の Chromium で 18,000 コマ測っても遅れは最大 0.058 秒で、再現しない）。
そこで途切れのたびにも跳び直す。元手は1コマぶんで、絵が止まった直後なので目立たない。

**コマ落ちは合図にしない。** Windows Edge (152) では落ち着いたあとも絶えず 5.6% 落ち、合図にすると
跳び続ける（90秒に 31回。途切れだけなら 1回。跳ぶたびに音が 0.02 秒飛ぶ）。跳ぶせいで落ちが増えるのではない。

画面の「コマ落ち」「絵の遅れ 最大」「絵の遅れ直し N回」は、運び側（途切れ）と復号側を分けて読むためのもの。
「絵の遅れ 最大」が 0 のままなのに絵と音が合わないなら、遅れているのは面のほう。

### 「遅延」は2つある

画面に出す2つは**意味が違います**。

| 出す名前 | 何の差 | 入っているもの |
| --- | --- | --- |
| **放送から N秒** | 隣に置いたテレビが映すはずの時刻と、いま映しているコマの差 | 端から端まで（ffmpeg の焼き上がり・回線・手元の貯まり） |
| **貯まり N秒** | `buffered.end - currentTime` | 手元にあと何秒ぶん持っているかだけ |

長いこと後者しか出しておらず、詰める作業をするのに上流でどれだけかかっているかが見えなかった。

#### 結びつけ方

放送の PCR と映像の PTS は同じ時計で打たれている。**PCR をサーバが受け取った時刻と組にして覚えれば**
（[ts/clock.ts](../src/lib/ts/clock.ts) の `BroadcastClock`）、「このコマは隣のテレビなら何時何分に映るか」が
サーバの時計の上で言える。焼いたものの物差しへは、ffmpeg が入口で 0 に寄せたぶん
（入口の `Duration: N/A, start: 72575.147089`）を引くだけ。

- **遅れて読んだ組は採らない。** `受け取った時刻 − PCR` がいちばん小さい組を採る。PCR とサーバは別の水晶
  なので 30秒ごとに選び直す（直前の区切りのぶんも残して比べる）
- **端末の時計は当てにしない。** 知らせにサーバの時計を添えて差を覚え、以降はサーバの時計の上で数える
  （LAN の片道は 1ms 未満）。時計の絶対値は要らず、サーバの NTP がずれていても数字は変わらない
- チューナーの中とエージェント→サーバの時間は入らない（測っていない。同じ機械の中なら小さいはず）

**放送の時刻 (TDT/TOT) とは組にしない。** 以前は TDT と組にしていたが、TDT は局ごとに固定でずれている。
NTP で合わせたサーバの時計と突き合わせると、11局（地上波9・BS 2）で -0.72秒（フジ）〜
+0.90秒（tvk）の 1.6秒幅。負の値もあるので秒未満の切り捨てでは説明が付かず、何本待っても寄らない（2026-09-26 実測）。
T26 と T15 で「放送から」が 1.3秒違って見えていたのは、ほぼこのずれだった
（[data.md](data.md#時刻合わせ-tdt--tot-は持たない) と同じ結論）。

出口の寄せ幅が入口の `start:` と同じことも確かめた（録画を切り出してライブと同じ引数で
焼き、`-debug_ts` と fMP4 を突き合わせて差 2ms）。映像は音声より 0.5秒ほど遅れて始まるが、頭は同じ絵で埋まり、
映像だけ 0 に詰められることは無い（[encode.md](encode.md#頭の音声だけの区間はずらさずに捨てる) の件は
Matroska を読むプレイヤーの話で、MSE ではない）。

#### 貯まりより小さく出ることはある

**テレビも PTS まで待って映す。** 放送の映像は着いてから映すまで 0.41〜0.50秒（音声は 0.12〜0.15秒）
待たせる作りで、着いた端から焼く denpa はそのぶん先回りできる:

```text
放送から = 焼き上がり + 回線 + 貯まり − (テレビが待つぶん 0.4秒ほど)
```

貯まりより小さい値はおかしな値ではない。待つぶんはどの局もほぼ同じなので、局どうしの比較には使える。

### 貯まっただけでは始めない（音だけ先に出る）

**チャンネルを変えると、音が先に出て絵が遅れて始まっていた。** 器を作り直した直後は復号器が立ち上がって
おらず、重ねてあるのは前の局の静止画（`freeze`）なので、絵が止まったまま新しい局の音が鳴る
（Windows Edge で選局を繰り返すと、音から1枚目まで中央 41ms・最大 1043ms）。貯まりの長さだけで `play()` を
呼んでいたためで、`readyState` が `HAVE_CURRENT_DATA` に上がるまで待てば一緒に始まる（`live-player.svelte.ts` の `canStart`）。

ただし待ちきりにはしない。絵の無い放送や復号の失敗で音まで出なくなるほうが困るので、1.5秒で諦めて音だけ先に出す。

#### 新しい局の1枚目が少し止まるのは、直さない

代わりに、新しい局の1枚目が 150ms ほど止まって見える（実機で 135〜174ms）。**意図した姿で、不具合ではない。**
止まっている間は貯まりが `target`（最短 0.2秒）に届くのを待っていて、止まって見える長さ ≒ 貯める量。

変えられるのは、その間に何を見せるかだけ。前の局の絵（音は新しい局）ではなく、新しい局の1枚目（音はまだ
出ない）を採る。見えるものと聞こえるものが食い違わないからで、前の形は「絵と音がずれている」と報告された。

### 落ち着いた高さは覚えておく

上の下限は**端末に覚えさせている**（`live-player.svelte.ts` の `FLOOR_KEY`)。
毎回 0.2 秒から始めていた頃は、どの経路でも足りずに開いて30秒以内に必ず1回止まり、
そこから当たりを探し直していた。

置き場が端末なのは、これが経路の性質だから。同じ人でも宅内の PC と出先の
タブレットでは値が違う（続きの位置 `resume_ms` をサーバに置くのとは逆の理由）。
長く無事なら少しずつ下げて試し直すので、宅外から帰ってくれば戻る。

戻るのは 10分ごとに 0.3 秒ずつ（`ts/pacing.ts` の `FORGET` / `PROBE`）なので、線を繋ぎ替えた
直後は前の経路の値のまま余計に遅れる。そのために**覚えたものを捨てる口も出してある**
（`live-player.svelte.ts` の `relearn`）。押すと覚えたものを消し、貯めているぶんも下限まで
詰めて放送の今へ戻す。覚えているものがあるときだけ出す。

低すぎる側に外れたぶんは放っておいてよい。止まればその場で上がる。

### 渡す前に1局へ絞る

**1本の物理チャンネルに複数の局が乗っている。** `-map 0:v:0` は「最初に見つけた映像」でしかないので、
MX2 を選んでも MX1 の絵が出うる（実機の T26 は Eテレ1/2/3 とワンセグの 320x180 H.264 が並ぶ）。
`-map 0:p:<局>:v:0` で局を名指しする。

名指しだけでは足りない。ffmpeg は名指しした局を `-probesize` のぶん読む間に見つけられなければ
そのまま終了する。3局相乗りの T15 で probesize を下げて測ったもの（3回ずつ）:

| probesize | 丸ごと渡す | 1局に絞る |
| --- | --- | --- |
| 20KB | 0/3 通る | 3/3 |
| 50KB | 0/3 通る | 3/3 |
| 120KB | 1/3 通る | 3/3 |
| 400KB | 3/3 | 3/3 |

録画と同じ `ServiceFilter` を通して局が1つだけの TS を渡せば、局を探す仕事が消える。映像だけを焼いていた
頃は 20KB まで下げていた（100KB との差は最短どうしで 33ms。これが固定費で、中央値の差は GOP 待ちのばらつき）。
**いまは字幕も見つけさせるので 100KB。**

- **量はほとんど減らない**（tvk 17.6 → 16.8、日テレ 17.3 → 14.5 Mbit/s）。相乗りの局は同じ ES を指していることが
  多く、落ちるのは他局の表と詰め物だけ。狙いは ffmpeg に局を探させないこと
- **名指しは絞ったあとも残す。** 万一違う局が入っていたら、黙って別の局を映すより落ちるほうがいい
- **コマ数は `-fpsmax` で上限を言う。** probesize が小さいと ffmpeg がでたらめなコマ数を起こすことがあり、
  SVT-AV1 は突っぱねる（20KB のまま AV1 で 0/3、上限を付けて 3/3）。固定（`-r`）では本当に 59.94p の局
  （720p）でコマを落とす
- ffmpeg が降りたら、その場で「映像を出せませんでした」を出す（[下](#焼けなくなったらその場で言う)）

### 焼けなくなったら、その場で言う

切り替えの間は前の絵を貼る。器を作り直すと `<video>` は何も映さないので、捨てる前に1枚だけ canvas へ
写して重ね、次の絵が実際に出た時点で剥がす（`requestVideoFrameCallback`。`play()` が返っただけではまだ
映っていない）。貼りっぱなしを避ける上限は6秒（`live-player.svelte.ts` の `HOLD_MOST`）。**壊れているのに
動いて見えるのがいちばん悪い。**

ffmpeg が降りても何も伝えていなかった頃は、前の絵のまま6秒たって黒くなるだけで、失敗が「切り替えに6秒
かかった」に見えた。直したのは2つ:

- **終わりを ffmpeg の終了で見る。** 流し込みは書き込み先が閉じても終わらないことがあり、3つ揃うのを
  待つと死んだことに永久に気づかない
- **畳んだセッションを掴んだままにしない。** 同じ局を選び直しても「もう見ている」と見なされ、「やり直す」が効かなかった

**放送が止まっているだけのときは、そう言う。** エージェントの「電波が来ていないか、その周波数に放送が
ありません」は、アンテナや配線を疑わせる。実機の「T27 がときどき同期しない」は、48時間の失敗10回が
すべて 01:04〜02:54 で、番組表の「放送休止」（00:11〜05:00）の中だった。NHK総合は保守の晩に送信機ごと
止める（Eテレは搬送波を出したままで一度も失敗していない）。番組表を持つのは denpa だけなので、
同期しなかったときだけ「放送休止です」に言い換える。塞がっていたときや ffmpeg が降りたときに
出すと、今度はこちらが嘘をつく（`server/live.ts` の `whyNotTuned`）。

### `tsreadex` は挟まない

一度は入れかけたが、**挟む理由はどれも ffmpeg 単体で足りた**。

| 欲しかったもの | 結論 |
| --- | --- |
| デュアルモノ分離 | ffmpeg で足りる。録画と同じ見分け方（番組表の音声情報）で、選ばれた側を両耳へ配る（上記）。録画は左右を2トラックに分けるが、ライブは器が1つなので片方を採る |
| 局の選び分け | ffmpeg で足りる。`-map 0:p:<局>:v:0`。実機で確認済み |
| 音声・字幕が消えたときに無音を挿す | tsreadex にしかできない。ただし**実害を確認していない** |
| `aac: Input buffer exhausted` | 直らない。壊れた AAC フレームの修復は tsreadex の仕事ではない |

イメージに1つ足す代償に対して、得られるのは最後の2行だけ。3行目の実害を踏んだら入れる。

### 入口が1つ増えている

**bun の `node:http` は WebSocket の握手ができない**（`upgrade` は上がるが、socket に書いても1バイトも届かない）。
adapter-node はその上に居り、`svelte-adapter-bun` も今の SvelteKit では `websocket` フックを挿し込めない。
そこで `Bun.serve` を前に置き、`/api/live/socket` の WebSocket だけそこで受けて、残りは 127.0.0.1 の
adapter-node へ中継する（`server.js`。試したことと、`Host` をそのまま渡す理由は冒頭の説明に）。

**開発サーバ（`bun run dev`）ではライブが繋がらない**（vite も `node:http`）。確かめるときは `bun run build && bun ./server.js`。

### 繋ぐときの認証

**ブラウザは WebSocket の握手に `Authorization` を付けてくれない。** ログインで
守っている denpa では、そのままだとチューナーを掴む口が素通しになる。

画面が先に `POST /api/live/ticket` で使い捨ての札を取り、それを URL に付けて繋ぐ。
札の発行は普通の HTTP なので、OIDC も信頼したネットワークもそのまま効く。
URL は履歴にもログにも残るので、1回使ったら消す。寿命は30秒。

## 5. 実装詳細

### 5.1 エンコード

**いまの形は `src/lib/server/live.ts` の `encodeArgs` にあります。** 1本の
ffmpeg が映像と音声を1つの pipe へ多重化し、`Fmp4Splitter` が `moof`+`mdat` ごとに
割って WebSocket へ流します。

```bash
ffmpeg -nostats -fflags nobuffer -probesize <小さく> <字幕の入口> -i pipe:0 \
    -vf <インタレ解除> \
    -map 0:p:<局>:v:0 -fpsmax <上限> <映像の焼き方> \
    -map 0:p:<局>:a:<何本目> [-af pan=...] <音声の焼き方> \
    -f mp4 -movflags +empty_moov+default_base_moof \
    -frag_duration 50000 -flush_packets 1 pipe:1 \
    <字幕の出口 → pipe:3>
```

**値は書かない。形だけ。** 実測した値と理由は `encodeArgs` / `videoArgs` の説明にあり、写すと片方が古くなる
（実際ここに写した `-frag_duration`・`-probesize`・`-preset`・音声の量が古いまま残っていた）。

- **`-copyts` は付けない**（[§5.2](#1本にしたのは時刻を揃えるため)）
- **`-loglevel` は下げない。** 選べる字幕は入口の見出し（info で出る）から拾う
  （[§5.2](#52-字幕sub2video)）。進み具合の数字だけ `-nostats` で止める
- クライアント側の SourceBuffer は `segments`（既定）で使う。`sequence` は届いた順に
  詰めるので、1つ取りこぼすと以降ずっとずれる。
  再生位置の面倒（貯めてから出す・離れたら速める）は `src/lib/ts/pacing.ts`

トラックごとに pipe を分けるなら `-movflags +frag_every_frame` に戻せる。1本に多重化している間は、映像だけ・
音声だけの塊が交互に並んで MSE が引っかかる（`encodeArgs` の「コマごとに切らない」）。複数映像も
そのときの話で、いまは映像1本・音声1本。

#### 焼き方は見ながら選べる

画面の操作列から H.264 / AV1 を選び直せる（`LiveCodec`）。音声と同じく、選び直すと
焼き直しになる。**局を変えても引き継ぐ。** 絵の中身ではなく「その端末で出るか」の話なので。

**AV1 でも落ちこぼれない。** 設計では「ソフトウェアの AV1 は厳しい」としていたが、実機
（Xeon E5-2696 v4 / 44スレッド / HW エンコーダ無し）で 1080i を解いて 60 コマ/秒という
いちばん重い形でも、焼けた尺が実時間に付いていった。コア数で間に合っている。
代償は立ち上がりが 0.45 秒遅いことで、既定はどの端末でも出る H.264 のまま。
実測は `videoArgs` の説明に（[§5.1 冒頭](#51-エンコード) と同じ理由で、ここに写さない）。

量はまだ何とも言えない。どちらも品質を指定して焼く（ビットレートを決めていない）ので、
量は場面で動き、実測も揃わなかった。

**音声は AV1 のとき Opus、H.264 は AAC。どちらも 256k。** 元の放送（AAC 256kbps）
に合わせた値で、録画側も前から `libopus -b:a 256k`。

#### 役割を分ける — H.264 は「速く」、AV1 は「小さく」

H.264 は**量を捨てて速さを採る**（`-preset ultrafast`、画質は既定のまま）。
画質を上げると最初の1枚が太り、書き出しに時間がかかるので必ず遅くなる。
`-crf` を付けないのが最速で、絵は今までと同じ（同じ crf 23）。増えるのは
量だけで、同じ画質を `ultrafast` で出すと 3 倍になる（実測は `videoArgs`）。
宅内向けの値なので、宅外から見るときは AV1 を選ぶ。

> **戻れる幅はバイト数でも切る。** 5分（`KEEP`）は「毎秒 3Mbit なら 110MB」の
> つもりの値だった。太った流れで5分持つと `appendBuffer` が `QuotaExceededError` で
> 落ち、そこから絵が出なくなる。受け取っている速さから 120MB に収まる長さを出し、
> 時間と小さいほうで切る（`live-player.svelte.ts`）。

AV1 は `lookahead=0` が要る。SVT-AV1 は既定で先読みのぶん貯め、それがそのまま遅れになる。
preset 12 を採る（13 は目に見えて粗く、10 は間に合わない）。

> **付けてもまだ溜め込む。** 電波が届いてから mp4 の塊が出るまでが H.264 の数倍かかり、
> 低遅延指定（`pred-struct=1`）は実時間に間に合わない（出口が 6秒 → 22秒 と
> 離れていった）。**AV1 を選ぶと放送の今から1秒ぶん離れる**（切り替えの画面にはまだ出していない）。

**受け取れない端末では H.264 に戻す。** `MediaSource.isTypeSupported` が false なら
その場で戻し、理由を画面に出す。黙って別の形にすると、切り替えが効かない理由が分からない。

HW エンコーダのある機材なら `av1_nvenc`（RTX40以降）/ `av1_qsv`（Arc・Meteor Lake 以降）/
`av1_amf`（RDNA3以降）に載せ替えられる。

### 5.2 字幕（sub2video）

**映像と同じ ffmpeg が焼く。出口を2つ持つ**（`src/lib/server/captions.ts`）。

```bash
ffmpeg <上の映像の形と同じ> \
    -sub_type bitmap -canvas_size 1920x1080 -font '<丸ゴシック>' -i pipe:0 \
    ... pipe:1 \
    -filter_complex '[0:p:<局>:s:<n>]null[s]' -map '[s]' -fps_mode passthrough \
    -c:v png -pix_fmt rgba -cluster_time_limit 1 -cluster_size_limit 1 \
    -flush_packets 1 -f matroska pipe:3
```

**ここも形だけ**（[§5.1](#51-エンコード) と同じ理由）。値と実測は
`captionInput` / `captionOutput` の説明にある。

- 字幕をフィルタの入力にすると、字幕1枚ごとに映像フレームになる（sub2video）。
  通すこと自体が目的なので、通す先は `null` でよい
- `-canvas_size` は必須。無いと libaribcaption は 1440x1080 (PROFILE_A) とみなし、
  1920x1080 の放送では字幕だけ横に伸びる
- **局を名指しする。** 映像と同じ理由（1本の物理チャンネルに複数の局が乗っている）
- **Matroska で受ける。** 時刻をコマと一緒に運ばせるため（下の「時刻はコマに付けて運ぶ」）

#### 1本にしたのは、時刻を揃えるため

以前は映像を作らない ffmpeg をもう1本、同じチャンネルに当てていた。**それでは時刻が
揃わない。** ffmpeg は入口で時刻を 0 に寄せ直すが、寄せ幅はプロセスごとに違う。
別々に起こした2本は焼き始めの鍵フレームがずれ、出てきた時刻どうしを突き合わせても
意味が無い。`-copyts` で放送の絶対時刻を保っても、mp4 の多重化器がその時刻を
0 に詰め直す（`-avoid_negative_ts disabled` も `-muxdelay 0` も `-output_ts_offset` も
効かない。実機で確認）。

1本にすれば入口の寄せが1回で済み、両方の出口に効く。実機で突き合わせると 1ms 以内で
一致し、費用も埋もれた（実測は `captions.ts`）。

引き換えに、音声や焼き方を選び直すと字幕も焼き直しになる（前は局ごとに1本だったので
途切れなかった）。字幕は次が来るまで出しっぱなしなので、焼き直しの間はサーバが
最後の1枚を配り直して繋ぐ。

> **字幕を持たない放送はある**（ショッピングやサブチャンネル）。そこに `[0:p:X:s:0]` を
> 頼むと ffmpeg は組み立ての時点で降り、映像も出ない。そうと分かったら
> 字幕なしで焼き直し、その局は15分覚えておく（`server/live.ts` の `captionless`）。

#### 時刻はコマに付けて運ぶ

生の PNG を並べただけ（`image2pipe`）では時刻が乗らないので、**器に入れて運ばせる。**
Matroska は使うところだけなら小さい。`src/lib/ts/mkv.ts` が読むのは
`TimestampScale` / `Cluster > Timestamp` / `SimpleBlock` と `BlockGroup > Block` だけ。
NUT はコマの見出しを組み立てるのに表の復元が要り、mp4 は PNG を入れられない。

塊の上限を最小（`-cluster_time_limit 1` / `-cluster_size_limit 1`）にして、1枚ごとに
書き出させる。溜められるとそのぶん遅れる。

**別の口と組にしない。** 以前は `showinfo` が標準エラーへ喋る時刻と標準出力の PNG を来た順に組にしていたが、
同じ時刻の枚は多重化で落ちるので数が合わない。一度ずれると戻らず、字幕の出た枚に1つ前の「空」が当たって
「消す」に化け、「字幕が遅れて固まって出る」になっていた（実測は `captions.ts`）。

#### PNG は ffmpeg に組ませる

設計では生の RGBA を受け取り、denpa が切り抜き・256色化・パレット PNG の組み立てまで
やるつもりだった。**実機では ffmpeg に PNG まで畳ませるほうが速かった**。生は書く量が
桁違いで、256色に落とすと半分になるが CPU を4倍払う（実測は `captions.ts`）。
denpa 側の切り抜き・色数落とし・PNG 組み立ては丸ごと要らなくなった。

送るのは画面まるごとの PNG で、受け側は映像と同じ枠に敷いて引き伸ばすだけ。
録画側は PGS の「1秒あたりに送れる量」の決まりのために切り抜くが、こちらにその縛りは無い。

#### 変わったときだけ送る

**sub2video は同じ絵を何度も出す。** 一本化してからは映像のコマが心拍になって枚数は
さらに増えるが、中身が変わるのはごく一部なので、同じ絵は配り直さない。

空の枚（全部透明）もそのまま送る。重ねれば消えるので、「消す」
（[§5.3](#53-websocket-プロトコル) の `0x21`）に置き換えなくてよい。

#### 焼き方ごとに分かれる

字幕は焼き方（音声・コーデック・何本目の字幕か）ごとに分かれる（[相乗りの単位](#入っているもの)）。
**その代わり TS をもう1本もらわずに済む。** 別建てだった頃は
字幕のためにチューナーの相乗りをもう1本頼み、地上波2本のうち1本を番組表集めが使っていると断られていた
（`[captions] GR:T15: チューナーに空きがありません`）。

> **字幕が1枚も来ない番組はある**（本編に字幕が無ければ0枚。異常ではない）。ボタンを出すかは届いた枚数では
> なく、ffmpeg の入口の見出しで決める（`TrackList`）。届いてから出していた頃は、間隔の空く番組（実機の
> 「みんなの手話」。番組表には [字] と出ている）でボタンが出なかった。持っていない放送では出さない。

### 5.3 WebSocket プロトコル

単一接続で全チャネルを多重化する。

```
[1 byte: channel][8 bytes: 時刻 (90kHz, BE)][payload...]

channel:
  0x00  video init segment (ftyp + moov)
  0x01  video media  (moof + mdat)。音声も同じ器に入る
  0x02  生の TS      1局に絞った TS そのまま (§5.5)。時刻は 0。init は無い
  0x10  audio init segment   ※いまは使わない (映像と同じ器)
  0x11  audio media          ※同上
  0x20  字幕の絵     [2:x][2:y][2:w][2:h][PNG...]
  0x21  字幕を消す   (中身なし) ※いまサーバは送らない
  0x30  データ放送   web-bml の ResponseMessage (JSON)。時刻は 0
  0x40  制御         ここだけ双方向の JSON (選局・追っかけ・データ放送の指示 / tuned・字幕一覧・時計 等の知らせ)。時刻は 0
```

- init セグメントは接続直後に必ず送る（再送用にサーバ側で保持）
- MSE はバイト列をそのまま `appendBuffer()` に投げられるので、映像音声のパースは不要
- 字幕の座標は `-canvas_size` の座標系。表示側の拡大率に合わせて canvas を伸ばす
- **頭の時刻は「焼いた mp4 の物差し」。** 映像も音声も字幕も同じ ffmpeg が焼くので、
  受け側の `video.currentTime` と直に比べられる（[§5.4](#54-時刻同期)）
- **生の道（0x02）では、字幕の時刻は放送の PTS そのまま**（受け側の時計が放送の PTS なので。[§5.5](#字幕)）
- 途中から入ってきた視聴者のために、いま出ている字幕はサーバが1枚だけ保持して再送する

### 5.4 時刻同期

| 対象 | 方法 |
| --- | --- |
| 映像・音声 | fMP4 の timescale で自動的に整合 |
| 字幕 | 添えられた時刻（映像と同じ ffmpeg が付けた mp4 の物差し）に置く |
| データ放送 | カルーセルは時刻同期不要（PMT/TOT と denpa の番組表の更新に追従） |

**いまは測っていません。** 字幕のコマに付いてくる時刻を再生位置と比べ、
「追い越していない中の最後の1つ」を出すだけです（`ts/captions.ts`）。
映像と字幕を同じ ffmpeg で焼いているので揃います（[§5.2](#52-字幕sub2video)）。

> 「放送から N秒」は遅れを見せるためだけのもので（[「遅延」は2つある](#遅延は2つある)）、
> 映像・音声・字幕を揃えるのには使っていない。

#### そこへ来るまでに3回外した

どれも別々の ffmpeg の出口どうしを突き合わせて測っていた:

| 使った基準 | 実測のずれ |
| --- | --- |
| mp4 の 0（＝焼かれた1コマ目のつもり） | **2.4秒**。多重化器が 0 に合わせるのは probe の間に溜まった音声 |
| 焼いている絵の時刻（映像側の `showinfo`） | **5秒**。フィルタは符号器より先を走る |
| 字幕側の `showinfo` が言う放送時刻 | **1秒ほど遅れる**。行と絵の数が合わず、組がずれる |

「待たせる量を渡す」に替えても3回外した。別々に起こした ffmpeg は鍵フレームが 0〜0.5 秒ずれるので、
測れないものを測っていた。**直したのは測り方ではなく作り**で、1本の ffmpeg に両方を焼かせ、測るもの
自体を無くした（[§5.2](#1本にしたのは時刻を揃えるため)）。`-copyts` は効かないうえ、実機で
`Assertion next_dts <= 0x7fffffff failed at libavformat/movenc.c` で映像ごと落ちた（放送時刻は 32bit に収まらない）。

- **貼り直すのは映した1枚ごと**（`live-player` の `follow`）。届いた塊に相乗りしていた頃は、遅れる方向にだけ 0〜50ms ずれていた
- **焼き直しのたびに、待たせている字幕は捨てる**（`forget`）。mp4 の時刻が 0 から数え直しになるため

### 5.5 放送そのまま（MPEG-2）を LAN で送る

**家の中のデスクトップのブラウザでは、焼かずに送れます。** 1局に絞った TS をそのまま
WebSocket に流し、ブラウザが WebAssembly の MPEG-2 復号器で解いて WebGL2 で描き、音は
AudioDecoder で解いて Web Audio で鳴らします。**端末ごとの設定で、既定は切**（設定画面の
「ライブを生で見る」）。

```
エージェント → 1局に絞る ┬→ WebSocket (0x02 生の TS) → worker ┬→ PES → WASM (mpeg2video) → WebGL2 (bob)
                         │                                    └→ ADTS → AudioDecoder ─→ 画面 → Web Audio (時計)
                         ├→ ffmpeg (字幕だけ。-copyts) → 0x20 字幕の絵 (放送の PTS のまま)
                         └→ BmlDecoder → 0x30 データ放送 (焼く道と同じ)
```

**ブラウザに MPEG-2 の復号器は無い**ので持ち込んでいます。Chromium 151 で実際に聞いた結果:

| 聞き方 | `mp2v` / `mpeg2video` | `avc1` | `av01` | `vp09` | AAC |
| --- | --- | --- | --- | --- | --- |
| `MediaSource.isTypeSupported` | **×** | ○ | ○ | ○ | ○ |
| `VideoDecoder.isConfigSupported` | **×** | ○ | ○ | ○ | ○ |

（`video/mp2t` そのものは ○ だが、これは**中身が H.264 の TS** の話）

得るもの: **ffmpeg の立ち上がり 0.5〜0.7 秒と、焼くのに掛かっているぶん**（電波が届いてから
塊が出るまで。実測は `server/live.ts` の `videoArgs`）**が丸ごと消え**、サーバの CPU も
350〜470% からほぼ 0 になります（字幕を描く ffmpeg だけ残る。映像を解かないので軽い）。
残る遅れは受け側の貯め（`ts/pacing.ts` の `FLOOR` から始まる貯め）だけです。

#### いつ生になるか

3つが揃ったときだけ。**決めるのは最後の1つを持つサーバ**です。

| | 誰が見る | 外れたら |
| --- | --- | --- |
| 端末の設定が入っている | 画面 (`raw/setting.svelte.ts`、localStorage) | いつもどおり焼く |
| その端末で解ける (WebAssembly・worker の WebGL2・AudioDecoder の AAC・AudioContext) | 画面 (`raw/support.ts`) | 焼いたものを頼み、理由を断り書きに出す |
| **家の中から来ている** | サーバ (`auth.mayStreamRaw`)。札を取ったときの住所で決めて札に持たせる (`tickets.Grant`) | 焼いたものを送る。札の答え (`raw`) を見て、画面が理由を断り書きに出す |

**家の中 = `TRUSTED_NETWORKS` に当たり、しかも私設・ループバック・リンクローカルの住所。**
`TRUSTED_NETWORKS` だけで決めないのは、全部開ける書き方（`0.0.0.0/0`）があるためで、
それは「家の中に居る」ではありません。CGNAT（100.64.0.0/10）は外 — Tailscale などで外から
入ってくる住所です。住所を見るのが札のとき（HTTP）なのは、前段（Traefik）が居る構成では
本当の接続元がヘッダにしか無く、それを読み分けているのが SvelteKit の側だから。

**AudioDecoder は安全な繋ぎ（https か localhost）でしか出てこない**ので、LAN でも http で
開いていると生にはなりません（[player.md](player.md#lan-でも-https-で開く)）。

**生で見ている途中でも、焼いたものへ自分で戻ります**（戻したら、その画面を開いている間は
頼み直さない — 戻しては諦めるを繰り返すと、そのたびに絵が止まる）:

- 解くのが間に合わない（下の「間に合わないとき」）
- 復号器が入っていない（`/api/live/mpeg2` が 404）・worker が落ちた
- 絵は出ているのに音が 5 秒来ない・AudioDecoder が続けて転ぶ

#### 復号器

FFmpeg の **mpeg2video の復号器と絵の区切りを探す parser だけ**を emscripten で組んだもの
（`wasm/mpeg2/`）。**Dockerfile の `mpeg2wasm` 段で毎回組み**、git には入れません（生成物を
抱えると FFmpeg を上げるたびに差し替えが要り、組んだ手順と中身が食い違っても気づけない）。
FFmpeg はサーバの ffmpeg と同じ版に揃え、emsdk は版で固定しています。置き場はアプリの外
（`/opt/denpa/mpeg2`、`MPEG2_DIR`）で、`/api/live/mpeg2/<名前>` から配ります — 開発と E2E の
compose はソースを `/app` に被せるので、中に置くと隠れます。

| | |
| --- | --- |
| 大きさ | `decoder.wasm` 473KB（brotli 160KB / gzip 196KB）+ 読み込み口 `decoder.mjs` 14KB |
| 速さ（手元の Chromium、ヘッドレス） | BS の 1920x1080i で **90〜97 コマ/秒**、1440x1080i で 110〜130 コマ/秒 — **実時間の3倍** |
| 組む時間 | 2分ほど（amd64 / arm64 どちらのランナーでも。中身は同じ） |
| **GPU が無いとき** | 描くほうが間に合わない。ソフトウェアの WebGL（SwiftShader）では 1080 の1コマを上げて描くのに 40〜60ms かかり、10〜14 コマ/秒しか出ない — 5秒で焼いたものに戻る（下の「間に合わないとき」）。E2E が通るのは絵が小さい（256x144）から |

**スレッドも SIMD も使いません。** スレッド版は SharedArrayBuffer のために COOP/COEP
（`crossOriginIsolated`）を全ページに要求することになり、データ放送の中継やロゴ、別オリジンへ
開く Hybridcast と噛み合いません。SIMD は1割ほどしか変わりませんでした。1本で実時間の3倍
出ているので、払う理由がありません。

#### 時計と口合わせ — 時計は鳴っている音

**鳴っている音を時計にします**（`raw/playout.ts`）。音は途切れると誰でも気づきますが、絵は
1コマ遅れても気づかれにくい。だから音は届いた順に隙間なく Web Audio の時間の上へ予約し、
絵は「いま耳に届いている PTS」を追いかけて、番が来たコマを出します。放送の PTS は音と絵で
同じ時計（PCR）に乗っているので、それで口が合います。

- 「いま耳に届いている PTS」は `AudioContext.getOutputTimestamp()` から出す — 予約している
  位置ではなく**出口までの遅れを引いた位置**。それを performance の時刻と組にして worker へ
  流し（20ms ごと）、worker は組から外挿してコマを選ぶ
- **PCR は受け側では使いません。** 貯めは「届いた音の端 − 鳴っている位置」で見るので、
  放送の時計と手元の時計の対応は要らない（`clock` の知らせは「放送から N 秒」を出すのにだけ使う。
  生の道では ffmpeg の `start:` を引かず PCR をそのまま渡す）
- **PTS は 26.5 時間で一周する**ので、受け側は増え続ける数に伸ばして持つ（`ts/pes.ts` の
  `unwrap`）。字幕と時計の知らせも、同じ物差しの近くへ伸ばしてから比べる
- 自動再生で音を断られたら、**壁時計を時計にして絵だけ進め**、「音を出す」を押された時点で
  鳴っている位置のまま音の時計へ移る（`RawEngine.follow`）。逆に音が止められたら（出口が
  外れた・OS に止められた）壁時計へ戻り、絵は止めない

#### 貯め方

**焼く道と同じ考えで、決め方も同じものを使います**（`pacing.nextTarget`。止まったら伸ばし、
無事が続いたら縮め、止まった高さを覚える）。覚える置き場も同じ（`FLOOR_KEY`）。

- 貯まった音の尺が `target` に届いてから、**放送の今から `target` 手前で**鳴らし始める
- **使い切ったら止まって貯め直す**（止まった回数は焼く道の「途切れ」と同じ数に出る）
- 溜まりすぎ（`target` + 1秒が3秒続く。裏に回ったタブが戻ったとき・時計のずれ）は
  **放送の今へ跳ぶ**。焼く道のように 1.05 倍で詰めることはしません — 音を速めると音程が
  変わる（MSE は保ったまま速めてくれていた）

**貯めるのは解く前**です。1080 の絵は1枚 3MB あるので、貯めのぶんを解いた絵で持つと
1秒で 90MB になる。圧縮のまま（PES）持っておき、**番の 0.3 秒前に解きます**（1コマ 10ms
前後なので間に合う）。解けた絵は復号器の中で順番待ちさせ（8枚まで）、番を過ぎたものは
テクスチャに上げずに捨てます（コマ落ちとして数える）。

#### インタレ解除 — bob

1080i の1コマには時刻の違う2枚（フィールド）が1行おきに入っています。**フィールドごとに
出して、抜けた行を上下の行の平均で埋めます**（`raw/render.ts` のシェーダ。色差も同じ）。

- **動きが 60 枚/秒のまま出る**（焼く道の `bwdif` と同じ）。スポーツや流れるテロップが滑らか
- 前後のコマを持たなくていい。テクスチャ1組で描けて、GPU の手間は誤差
- 引き換えに、**止まっている細かい模様（テロップの縁）が1行ぶん上下に揺らいで見える**
  （bob の宿命）。前のコマと比べて止まっているところだけ織り直す（motion adaptive）手は
  あるが、テクスチャを2組持って毎コマ比べることになる。**実機で気になれば足す**

インタレの印の無いコマ（720p など）はそのまま出します。色は HD が BT.709、SD が BT.601
（限定レンジ）。1440x1080 は画素の縦横比を掛けて 1920 幅で描きます。

#### 選局と途切れ

- **局を変えても worker と復号器は作り直しません**（`reset` で中身だけ捨てる）。復号器を
  開き直し、**I フレームが来るまで渡さない** — MPEG-2 は I からしか解けず、先に P/B を渡すと
  灰色の絵が出る（放送の GOP は 0.5 秒）
- 貯めている間は**新しい局の1枚目を出して待つ**（焼く道の[「新しい局の1枚目が少し止まる」](#新しい局の1枚目が少し止まるのは直さない)と同じ判断）。
  それまでは前の局の最後の絵が canvas に残る
- 大きく遅れたら（0.5秒）解きながら追わずに I フレームまで飛ぶ。止めている間に溜まる圧縮の
  待ちも8秒で切る
- サーバの相乗りは局と字幕の単位（音声と焼き方では分けない — 音声は全部送って画面が選ぶ）。
  チューナーの掴み方・畳み方・`warm` は焼く道と同じ

#### 字幕

**字幕だけは ffmpeg に描かせます**（放送に絵は乗っていない。§2）。映像を解かない ffmpeg を
1本起こし（`captions.rawCaptionArgs`）、**`-copyts` で放送の時刻のまま**出させます。

焼く道で「同じ ffmpeg に両方焼かせる」のは、入口で時刻を 0 に寄せる幅がプロセスごとに違う
からでした（[§5.2](#1本にしたのは時刻を揃えるため)）。生の道の受け側は放送の PTS そのものを
時計にしているので、字幕も放送の PTS のまま出せば突き合わせられます。mp4 の多重化器が 0 に
詰め直す問題は、字幕の出口（Matroska）には無い。実機の録画で、出てきた字幕の時刻が元の TS の
字幕 PES の PTS と 1ms 単位で一致しました（71759.734333 → 71759.734）。**`-copyts` を外すと
合いません** — 映像を出さない ffmpeg は寄せ幅を入口の `start:` と違う値にし（同じ録画で
0.3〜0.7秒）、それを外から知る方法が無い。

字幕の ffmpeg が転んでも映像は止めません（映像はそもそも ffmpeg を通っていない）。流し込みも
待たせない — 書き込みが捌けていない間に来た塊は字幕の側に渡さない（字幕が1枚欠けることは
ありうるが、映像が止まるよりいい）。

#### データ放送

**変わりません。** 1局に絞った TS の写しを `BmlDecoder` が解くのは同じで、描く側は映像の入れ物を
動かすだけ — 生の canvas もその入れ物の中に居るので、一緒に動きます。

#### 間に合わないとき

**1コマを解く時間の 95 パーセンタイルが1コマの長さの 8 割を超えるか、絵が時計から
0.25 秒以上遅れる**のが、**1秒ごとに数えて5秒続いたら**焼いたものに戻します（`raw/budget.ts`）。
1回の重さ（タブを戻したとき・GC・選局の直後）では戻さない — 戻すと焼き直しで 1 秒近く
絵が止まるので、一瞬の詰まりより高くつく。解く時間は操作列に「解く N ms」と出ます。

#### 払うもの

- **帯域。** 1局に絞った生の TS は実測 14.5〜16.8 Mbit/s で、中身によらずほぼ一定
  （焼いたものは形と場面で動き、AV1 なら数分の1まで）。**宅外へは出さない**のはこのため
- **端末の CPU と電池。** デスクトップなら1コマ 10ms（1本で実時間の3倍）だが、携帯や
  非力なノートでは電池を目に見えて使う。**既定を切にしてあるのはこのため**
- **MSE に乗っていたものが無くなる:**
  - **止めて再開は放送の今から**（止めた所からは見られない）。5分戻る帯・追っかけの速さも無い。
    1局 15Mbit/s を遡れるだけ持つと 5 分で 600MB になる
  - 焼き方（H.264 / AV1）の選び直し（焼いていない）
  - 切り抜き（絵は worker の canvas に居て、まだ写し取る口が無い）
  - 5.1ch の番組は頭の2本だけ鳴らす（下げ方を持っていない）
- インタレ解除は bob（上）で、`bwdif` よりは落ちる

#### 実機で確かめること

ヘッドレスの Chromium（GPU 無し・SwiftShader）と偽の放送（`src/lib/ts/synth-av.ts` の小さい
MPEG-2 と無音の AAC）でしか通していません。本物の GPU・本物の放送で見るべきところ:

- **口合わせ**（`getOutputTimestamp` の遅れの見積もりが Bluetooth などの出口で合っているか）
- bob の揺らぎがテロップで気になるか（気になれば motion adaptive を足す）
- 1080i を実時間で解けるか（ノート・古い PC・Firefox / Safari）。「解く N ms」を見る
- **デュアルモノ**（二カ国語）と**複数音声**の切り替え、**5.1ch** の番組（AudioDecoder の面の順）
- 長時間（数時間）見て、音の時計と放送の時計のずれで跳び（溜まりすぎ）が何回起きるか
- 携帯・タブレットの電池（既定は切だが、入れたときにどれだけ減るか）

### 5.6 データ放送の統合

web-bml は Node.js サーバ + ブラウザクライアント構成。**映像は denpa が持つ。**

サイドカーとして起動して iframe で抱えると、**映像を出すプレイヤーが2つ**になる。
web-bml は Mirakurun / EPGStation / TSファイルを受け取り、自前の ffmpeg で HLS を作って
自分の `<video>` に映すので、denpa の貯め方も字幕も焼き方の切り替えもその画面では
使われない。HLS の遅延は数秒で、denpa の 0.6秒 の絵に重ねることもできない。

**借りるのは描画側と、渡す形の取り決めだけ。解く側は自前です。**

一度は解く側 (`server/decode_ts.ts`) も借りたが、998行のうち denpa が通るのは3割 (DSM-CC と PMT の記述子) で、
残りの EIT/SDT/NIT・字幕は自前のものがある (`ts/eit.ts` / `ts/psi.ts` / ffmpeg)。その3割のために
`@chinachu/aribts` (2.3MB) を抱えるより書き直すほうを選んだ。

運び方は衛星のロゴと同じ DSM-CC で、denpa は既に持っていた
(`ts/logo-dsmcc.ts`、DII を読んで DDB を揃える)。共通のところを `ts/dsmcc.ts` に
括り出し、データ放送の読み方だけを `ts/bml.ts` に足した。

渡す形は借りたまま (`web-bml/protocol` の `ResponseMessage`)。描画側との契約なので、
自前で詰めても**食い違えば型検査が止めてくれます**:

| 型 | 中身 |
| --- | --- |
| `pmt` | データ放送の component (PID・componentId・BXML の情報) |
| `moduleListUpdated` | どのモジュールが何バイトか (DII) |
| `moduleDownloaded` | 揃ったモジュール。ファイルごとに base64 と MIME |
| `esEventUpdated` / `currentTime` | イベントメッセージ・NPT・放送の時刻 |

TS を直に読むので、psisiarc も要らない。

```
エージェント → denpa ┬→ ffmpeg     → fMP4 → MSE          (映像・音声)
                     ├→ ffmpeg     → mkv  → canvas       (字幕の絵)
                     └→ BmlDecoder → 組み立て済みモジュール → web-bml の描画側
```

ffmpeg は1本のまま、チューナーも1つのまま、遅延も 0.6秒 のまま。

### いま入っているところ

**解く側 (`server/databroadcast.ts`) も描画側 (`components/player/DataBroadcast.svelte`)
も入っています。**

1局に絞った TS の写しを `BmlDecoder` へ分け (`Session.pump`)、出てきたものを
`CHANNEL.data` (0x30) に JSON で載せます。覚えておくぶんは `ts/carousel.ts`。

実機の録画 (1局に絞った 79MB = 約40秒ぶん) で測ったもの:

| | |
| --- | --- |
| 出てきた知らせ | `moduleDownloaded` 16 / `currentTime` 13 / `moduleListUpdated` 3 / `pmt` 1 |
| 揃ったモジュール | 16個・約 1.4MB (application / image / text / audio) |
| 速さ | 128 MB/s。放送の 17 Mbit/s に対して**1コアの 1.7%** |
| 繋いできた人に配り直すぶん | 18個・2MB |

**借りていた `decodeTS` と突き合わせて、揃うモジュール16個・ファイル数・バイト数・
種別まで完全に一致しました。** 違うのは、出さないものが2つあることだけです
(下の「決めたこと」)。

**頼まれてから解きます。** 解くのは 1.7% と安いのですが、見ている人のほとんどは
押さないので、全員のぶんを解き続ける理由がありません。画面から
`{ type: 'data', on: true }` が来たときだけ回し、誰も出していなければ畳みます。

引き換えに、押してから出るまでカルーセルが一周するのを待ちます。放送は同じ
ものを何度も回すので待てば揃いますが、大きいモジュールほど間隔が空きます。

決めたことが4つ:

- **`pcr` は出さない。** 毎秒50個ほど来るうえ、denpa では映像そのものが時計です
- **`programInfo` は解く側から出さない。** 借りていた側は EIT/SDT/NIT から
  組み立てていましたが、denpa は自前の番組表から作るほうが正確で安い
  (`Session.programInfo`)。**これが無いと画面が出ません。** 描く側は入口の BML を
  開く前に `getProgramInfoAsync()` で待つので、モジュールが全部揃っていても
  待ち続けます (実機で踏みました)。
  中継の番号 (`transportStreamId`) だけは、絞るときに読む PAT の頭から拾います
  (`ServiceFilter`)。テレ朝の TVerリンクは `browser.getProgramID(4)` でこれを取り、
  TVer のサーバへ機器の識別子と並べて送ります。`null` のままだと文字の "null" が
  飛んで断られ、画面には「情報を取得することができませんでした。[エラーコード:DT-RE]」
  とだけ出ます (実機で再現。`DT` は dtoken_common、`RE` は返ってきた `e`)
- **`pmt` は変わったときだけ。** 放送は同じ表を何度も送ります。モジュールも
  同じ版は配り直しません (カルーセルは回り続け、版が上がらなくても同じものが何度も揃う)
- **解く側が転んでも映像は止めない。** データ放送は映像の付け足しなので、転んだら
  諦めて映像は流し続けます。投げ返すと TS を送り込んでいるところごと落ち、
  映像まで出なくなります (作りものの放送で実際に落ちました)

### 描画側をどう抱えるか

**繋ぎ口はぴったり合っている。** `client/bml_browser.ts` の `BMLBrowser` は、
denpa が作る `ResponseMessage` をそのまま食べる:

```ts
const browser = new BMLBrowser({
    containerElement,        // BML を描く場所
    mediaElement,            // 映像が居る入れ物。**denpa の <video> をそのまま渡す**
    videoPlaneModeEnabled,   // BML が指す位置に映像を置き直すか
});
browser.emitMessage(msg);    // ← ts/bml.ts が吐くものをそのまま
browser.destroy();
```

**映像は渡すだけ。** 向こうの `VideoPlayer` (`client/player/*.ts`) は単体ページが hls.js / mpegts.js で自前再生
するためのもので、`BMLBrowser` は受け取らない。描く側を書き直す道は無い (ES2 の処理系まで抱えることになる)。

#### 持ち込み方 — npm の `web-bml`

**普通の依存として npm から引く** (2026-08 に上流がライブラリ化)。`exports` に denpa の使う入口
(`.` / `./entity-parser` / `./protocol`) が揃い、`dist` の `.d.ts` で型が最後まで通る。
`emitMessage(msg: ResponseMessage)` の食い違いを型検査で止められることが、解く側を自前にした意味そのもの。
引く依存は5つで追従は Renovate 任せ、koa・react・hls.js・mpegts.js は `BMLBrowser` の木に入らない。
それまでは 46ファイル・1.2MB を `src/lib/vendor/` に写していた (当時は `exports` が無かった)。移しても束は増えていない。

#### 入れたあと

| | |
| --- | --- |
| 束 | 700KB (gzip 前)。押すまで落ちてこない (`import()` で分けてある。どのみちカルーセルの一周を待つので、そこに紛れる) |
| フォント | 字幕を焼くのと同じ `rounded-mplus-1m-arib`。BML が要る等幅・丸ゴシック・ARIB外字を1本で満たす (借りている側の Kosugi 4.4MB は外字を持たない)。イメージには ttf と woff2 を置き、`/api/font` で配る |
| 覚えるもの | NVRAM は端末の localStorage。`denpa_bml_denpa_nvram_` で他と混ざらないようにしてある |
| 郵便番号 | 設定画面から入れて、器を作る前に NVRAM へ写す (`nvram://receiverinfo/zipcode`)。放送はこれで天気・地域のニュース・防災情報の場所を決め、入れないと「郵便番号が正しく設定されていません」と出る。家の場所は端末で変わらないので、置き場はサーバ |
| リモコン | 十字・決定・戻る・数字・色・d をそのまま渡す (`keyCodeToAribKey`)。指で押すぶんは自前 (`components/player/Remote.svelte`: 色・十字・決定・戻る・d・数字) で、右の列に置く。放送の画面は枠を下まで塗り潰すので、映像に重ねると埋もれる |
| d ボタン | **テレビと同じ振る舞い。** 出す操作を文書への d の1押しとしても届け (`knock`。日テレ・テレ朝・フジの待機ページはこれでメニューを開く)、返事が無ければ 2.5秒おきに押し直す (TOKYO MX の入口は最初の2秒に受けた d を捨てる)。開いたメニューを閉じてしまう局があるので、押すのは3回まで。出ている間の d は、文書が聞いていれば渡し、聞いていなければ器を閉じる (`pressD`)。右の縦列の d ボタンは放送に渡さず、その場で畳む逃げ道 |

**映像の入れ物は、描く場所の親にしてはいけない。** 借りている側は BML の文書を
組むときに `mediaElement` を動かすので、その中に `containerElement` が居ると
`appendChild ... contains the parent` で転ぶ。denpa では映像だけを
`<div>` に入れ、データ放送はその兄弟に置いている。

**描く場所は毎回作り直す。** 借りている側は渡された要素に閉じた影
(`attachShadow({ mode: "closed" })`) を張る。影は外せないので、同じ要素を
渡し直すと2度目で転び、消して出し直すと出なくなる。

閉じた影は外から中身が見えないので、切り分けのためだけに
`data-showing` / `data-receiving` / `data-handed` を外へ出してある
(ここに1日使った)。

##### 借りものが持っていないぶん

**`BMLBrowser` は画面の器を持っていない。** 向こうの単体ページがやっていたこと（d を渡す・映像を戻す・枠に
合わせる・映像の入れ物を style で書く・データ取得中を出す・郵便番号を渡す）はこちらでやる。どれも抜けると
「押しても何も出ない」形で壊れる（実機で全部踏んだ）。中身は
[DataBroadcast.svelte](../src/lib/components/player/DataBroadcast.svelte) の頭の1箇所だけに置く（両方に書いていた頃、片方だけ古くなった）。

**局を変えたら作り直す。** 借りている側は一度に一つの放送しか持てず
(カルーセルも覚えるものも局ごと)、前の局の文書が映像を掴んだままになる。

### 5.7 双方向（通信系コンテンツ）プロキシ

放送局の通信系サーバは受信機の専用ネットワークスタックが前提で、CORS ヘッダを返さない。
そこで **SvelteKit サーバが中継する** (中身は
[server/bml-network.ts](../src/lib/server/bml-network.ts))。

| 口 | BML の API | 何をする |
| --- | --- | --- |
| `/api/bml/proxy` | `browser.Ureg` 系の取得 (`get`) | GET して中身をそのまま返す |
| `/api/bml/post` | `transmitTextDataOverIP` | POST して返りをそのまま返す |
| `/api/bml/confirm` | `confirmIPNetwork` | 相手の 443 番へ繋がるか (ICMP は器の中から撃てない) |

#### 「送る」は応募・投票のためだけの口ではない

最初は「正規受信機以外からの送信は想定外」として `transmitTextDataOverIP` を
渡さなかった。それでは足りなかった。

**放送のアプリは `isIPConnected` の申告を信じない。** NHK は送る口へ一度投げてみて、
返らなければ「インターネットに接続されていません」と案内する (実機で確認。
`confirmIPNetwork` は呼びに来もしない)。渡さないと借りものは「その機能は無い」と
答えるので、双方向を入れていても入っていないのと同じ画面になっていた。

**既定オフ。** 設定画面の「データ放送の双方向」を入れるまで、この口は 403 を返し、
画面側も `isIPConnected` に 0 を返す。そのとき放送のアプリが出す「インターネットに
接続されていません」は事実の通りで、消したければ入れる。web-bml 系の実装も同じ方針
（TVTDataBroadcastingWV2:「通信機能は既定では無効であり、その場合すべての外部への
リクエストはブロックされます」）。

#### 局ごとのドメイン表は持たない

「いま映している局のドメインだけ許す」には、局とドメインの対応表が要る。
**その表は必ず古くなり**、新しい局や引っ越した先で黙って繋がらなくなる。しかも
「繋がらない」は放送側の不調と見分けが付かない。

代わりに繋ぎ先ではなく繋ぐ範囲を縛る。危ないのは放送局以外に繋ぐことではなく、
**denpa のサーバが内側に繋ぐこと** (SSRF) だから。

| | |
| --- | --- |
| 手 | GET と POST。中身は組み立てない。借りものが `Denbun=…` まで作って渡してくるので、`application/x-www-form-urlencoded` として素通しし、返りも解かずに返す |
| 相手 | **公開アドレスのみ**。私設・ループバック・リンクローカル (雲のメタデータ)・CGNAT・多重放送は断る |
| 仕組み | http と https。`file:` などへ逃がす道は塞ぐ |
| 見方 | 名前ではなく引いた先で見る。`localhost` の別名や、内側を指す公開の名前は綴りでは見分けられない。名前は `BML_DNS` で引く。家庭の DNS フィルタが局のドメインを 0.0.0.0 に落とすと、上の防御が正しく断ってしまう（[app.md](app.md#環境変数)） |
| 追いかけ | 3回まで。行き先ごとに確かめ直す (1回目が公開でも、飛ばされた先が内側のことがある) |
| 大きさ | 4MB / 待ち 10秒 |
| 持ち物 | 何も渡さない (cookie も認証も)。denpa の資格情報が外へ出ない |
| 記録 | 断ったものは何に繋ごうとしたかを残す |

#### 動作範囲の現実的な想定

| 種別 | 可否 |
| --- | --- |
| dボタン、ページ遷移、地域選択、クイズ選択肢 | ○ 受信機内で完結するため動作 |
| NVRAM への保存・読み出し | ○ web-bml に実装あり |
| 通信系コンテンツの取得（HTTP GET） | ○ 中継口経由 (既定は切) |
| 応募・投票などのデータ送信（HTTP POST） | ○ 中継口経由 (既定は切)。繋がっているかの判定もここを通る |

### 5.8 Hybridcast

**在ることは言う。動かさない。**

データ放送 (BML) と違い、**アプリが電波に乗っていません**。
乗っているのは AIT という表だけで、中身は放送局のサーバから HTTPS で取ります。

```
PMT ─ ES に application_signalling_descriptor (0x6F) ─→ その PID に AIT
AIT ─ transport_protocol_descriptor        (URL の頭)
    └ simple_application_location_descriptor (その先の道)  →  アプリのURL
```

「電波を解く」仕事はほとんど要りません
([ts/ait.ts](../src/lib/ts/ait.ts) は表を読むだけ)。**押されなくても読みます。**
解く量が無いうえ、押すまで在ることが分からないのでは出したいものが出せないためです。
載っていない局では PMT に印が無いので、AIT を待つこともしません。

見つけたら、操作列の下の帯に**別のタブで開くボタン**を出します。d ボタン (右の縦列) と
同じ形にはしません。あちらは denpa の中で開くもの、こちらは外へ出ていくもので、
押した結果がまるで違います。

#### 動かさないのは、越えられない壁が3つあるから

1. **受信機の API は、アプリのページの中に無いと意味がない。** Hybridcast の
   アプリは `hcApp` などの API を呼びます (放送の映像面の制御・いまの局と番組・
   受信機の記憶・スマホとの連携)。放送局のサーバから来るページは別オリジン
   なので、iframe に入れても中に手を入れられません。同一オリジンに見せるには
   URL を全書き換えして中継し、IPTVFJ STD-0010/0011 の API を実装する
   必要があります。仕様1本ぶんの仕事です
2. **放送局のサーバが、認証された受信機を期待している。** 受信機の証明書や
   識別子を見るものが多く、素性を偽って通す気はありません
3. **映像は DRM 付き。** MPEG-DASH + Widevine/PlayReady で、ライセンスサーバが
   また端末を見ます

**2番は denpa 側の努力では越えられません。** なので1番に仕様1本ぶんを注ぎ込む理由もありません。

#### できないものを、できる顔で出さない

借りている BML ブラウザは `AITControlledApp.Start` に 0 (できない) と
答えます。実機の NHK はこれを聞きに来て、その答えでデータ放送側の
「Hybridcast」ボタンを死なせています。**ここを 1 にしてはいけません。**
BML が起動を頼んできて、そのまま返らなくなります。

## 6. 技術選定の記録（採用しなかったもの）

### ブラウザ側での字幕デコード（aribb24.js）— 不採用

B24 をそのままブラウザへ送り、クライアントで描く構成。**録画と live で描画系が
二重になる**（比較は [§2 の表](#字幕はサーバで絵にする)）。サーバ負荷を理由に戻す道も
ほぼ消えた。映像と同じ ffmpeg の出口が1つ増えるだけで、実測では焼く手間に埋もれる。
サイドチャネルの形は変わらない（B24 を 0x20 で流すだけ）。

### H.264 + MPEG-TS + mpegts.js で先に全機能を通す — 不採用

前例が豊富（KonomiTV / web-bml と同一構成）で、段階を踏む案として有力だった。
**字幕の経路が録画側で先に完成した**ので、あとで捨てるコードを書く理由が無くなった。
Safari や AV1 非対応環境のための H.264 は、段階ではなくコーデックの設定として残す。

### GStreamer — 不採用

当初は「tsdemux の private pad で B24 を映像と同一クロック上で取れる」ことを理由に有力視した。だが字幕は ffmpeg の
2つ目の出口で同じ時計に乗り（[§5.2](#52-字幕sub2video)）、データ放送は denpa の中で TS を分けて自前で解くので、
**この論拠は無くなった**。残る比較でも ffmpeg が優位で、libaribcaption を組み込める（`--enable-libaribcaption`）。
tsreadex / psisiarc / KonomiTV など周辺も同じ CLI パイプラインの形で、QSVEncC / NVEncC / VCEEncC も使える。
GStreamer には ARIB/ISDB の知識も前例も無い。

### WebRTC / WHEP による低遅延化 — 不採用

設計では「低遅延の追い込み（任意）」として MediaMTX 経由の WHEP を候補に置いていたが、入れない。

**縮むのは待っている間だけで、開いてから絵が出るまではむしろ伸びる。** WHEP で消せるのは受け側の貯め
（`ts/pacing.ts`。宅内で 0.2〜0.9 秒）だけで、焼くのに掛かるぶんは符号器の中の話なので運び方では消えない
（[§5.1](#51-エンコード)）。代わりに開くたびに ICE と DTLS の往復が増え、テレビと同じに使うときにいちばん効く
「押してから映るまで」が遅くなる。

| | いま（WebSocket + MSE） | WHEP にすると |
| --- | --- | --- |
| 積むもの | Bun.serve の WebSocket 1本 | MediaMTX がもう1プロセス（+ SFU の設定・鍵・NAT） |
| 字幕・データ放送 | 同じ1本に相乗り（[§5.3](#53-websocket-プロトコル)） | 別建て（DataChannel を自分で組む） |
| 止めて見る・追っかけ・5分戻れる | MSE の `buffered` がそのまま | 全部書き直し（溜めが無いので追い越されて終わる） |
| 音声・焼き方の選び直し | 焼き直して繋ぎ直すだけ | 交渉からやり直し |

「止めた所から見られる」「戻れる」は貯めているから成り立ち、低遅延はその貯めを削ることなので、両者は同じものの
両端にある。削れる幅も経路が決め、実測では 0.2 秒では止まり続け、落ち着いたのは 0.6 秒だった
（[一瞬止まって遅延が増えていく](#一瞬止まって遅延が増えていく)）。1秒足らずのためにその2つを捨てるのは割に合わない。
**本当に縮めたいなら、焼くのをやめるほうが桁違いに効く**（[§5.5](#55-放送そのままmpeg-2を-lan-で送る)）。WHEP はその後でいい。
ffmpeg の WHIP muxer も H.264/Opus 固定の experimental で AV1 が使えず、通すなら MediaMTX 経由になる。

### MPEG-TS への AV1 多重 — 保留

AOM 公式仕様（AOMediaCodec/av1-mpeg2-ts、stream_type 0x06 + format_identifier `AV01`）はあるが、
FFmpeg は PR、GStreamer は WIP 段階で、ブラウザ側のデマクサも無い。継続監視する。

### Media over QUIC — 低遅延化の候補

字幕・データ放送を第一級のトラックとして扱える唯一の選択肢だが、IETF ドラフト段階。

## 7. 既知のリスク・未解決事項

| 項目 | 内容 | 対応 |
| --- | --- | --- |
| Safari 非対応 | Opus in mp4 / AV1 が MSE で通らない | H.264 + AAC の設定に切り替え |
| 字幕の拡大 | 絵なので、拡大すると文字も引き伸ばされる | `-canvas_size` は 1920x1080 で固定し、受け側が映像の枠に合わせて伸ばす（放送が 1440x1080 でも表示は 16:9 なので辻褄が合う） |
| web-bml の実装範囲 | STD-B24 / TR-B14 / TR-B15 の部分実装。一部イベント・API 未実装 | 実際のチャンネルで動作確認。完全互換は期待しない |
| 規約面 | 通信系サーバへの非受信機アクセス | 個人の視聴環境の範囲に留める |

リスクとして挙げていて解決済みになったものは、それぞれの節に実測ごと畳んである。
AV1 の負荷は [§5.1](#51-エンコード)、字幕を焼く費用は [§5.2](#52-字幕sub2video)、
字幕と映像のズレは [§5.4](#54-時刻同期)。
