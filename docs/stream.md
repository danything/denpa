# 放送波ストリーミングの仕組み

映像・音声・字幕・データ放送が入っています。入れた順序・採用しなかったもの・残っているリスク・
決めたときの測定は [stream-history.md](stream-history.md) にあります。

## 前提

| 項目         | 内容                                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| デプロイ形態 | **セルフホスト（1 ユーザー = 1 サーバ）**                                                                  |
| アプリ       | SvelteKit 単一アプリ（配信・視聴の両方を担当）                                                             |
| 入力ソース   | 放送波 MPEG-TS（ISDB-T / ISDB-S / ISDB-C）。ケーブルの 4K は MMT/TLV ([4K の局のライブ](#4k-の局のライブ)) |
| コーデック   | 自動 (既定) / AV1 + Opus / H.265 + AAC / H.264 + AAC / MPEG-2 (放送のまま)                                 |
| 必須機能     | ARIB 字幕、データ放送（双方向含む）、複数音声・映像ストリーム                                              |

セルフホストなので、NVRAM・地域設定・リモコン設定のユーザーごとの分離と、通信系コンテンツの中継での
ユーザー識別は**設計で考えない**（受信機 = サーバ = ユーザーが 1:1:1）。

## 全体構成

```
┌─────────────────────────────────────────────────────────────────┐
│ チューナー (エージェント)                                     │
└────────────────────────────┬────────────────────────────────────┘
                             │ MPEG-TS (チャンネル丸ごと)
                             ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ            │
              │  ・1局に絞る (ServiceFilter)  │
              │  ・プロセス管理／再起動        │
              │  ・WebSocket ハブ             │
              │  ・BML通信系プロキシ           │
              └───┬──────────────────────┬───┘
                  │ 1局ぶんの TS          │ (押した人がいるときだけ)
                  ▼                      ▼
     ┌───────────────────────────┐  ┌──────────────────┐
     │ ffmpeg                    │  │ BmlDecoder       │
     │  ├→ pipe:1 fMP4 (映像音声) │  │ カルーセルを     │
     │  └→ pipe:3 mkv (字幕)     │  │ 組み立てる       │
     └─────────────┬─────────────┘  └────────┬─────────┘
                   └───────────┬─────────────┘
                               ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ (配る)     │
              └──────────────┬───────────────┘
                             │ WebSocket (メディア + サイドチャネル)
                             ▼
              ┌──────────────────────────────┐
              │   ブラウザ (SvelteKit client) │
              │  ・MSE 直接        → 映像音声 │
              │  ・canvas に描く   → 字幕     │
              │  ・自前のエンジン  → データ放送│
              └──────────────────────────────┘
```

**映像と字幕は同じ ffmpeg の 2 つの出口。** 別々に起こすと時刻が揃わない（[字幕](#字幕)）。
データ放送へは、絞った TS を denpa の中で分ける。

### 設計上の中核

**メディアとメタデータは同じコンテナに載らない。** ARIB 字幕（B24 PES）もデータ放送（DSM-CC カルーセル + PSI/SI）も、
fMP4 / WebM には規格上入れられず、ffmpeg も GStreamer も扱えない。そこで:

> [!IMPORTANT]
> **サイドチャネル用の WebSocket を 1 本用意し、字幕とデータ放送を同じ経路で一緒に送る。**

### 字幕はサーバでデコードして、描くのは受け側

**置き場所を決めるところまではサーバで、描くのはブラウザ (とテレビのアプリ) で。** 送るのは
「どの字を・どこに・どの大きさで・何色で」まで決めた**文字の配置** (JSON。[api.md](api.md#字幕の文字の配置))。

libaribcaption は「デコードする (decoder)」と「描く (renderer)」が分かれていて、置き場所・大きさ・色・外字の
置き換えはデコードする側で決まる。**デコードする側を TypeScript に写して** (`packages/arib/src/b24caption.ts`) サーバで回し、
描く側だけを受け側に持つ。全画面でも画面の画素で描け、1 枚は数百バイト〜1KB で済む。テレビのアプリは描く側を
Kotlin で持つ (denpa-tv 0.16.0 から)。画像 (PNG) を配っていた頃との比較は
[stream-history.md](stream-history.md#字幕を画像で配っていた頃)。

外字 (DRCS) は置き換え表で字にできるものは字に、できないものは画像で送り (1 字 3.5KB ほど)、受け側が字の枠いっぱいに引き伸ばす。
放送の外字は 16〜36 画素の白黒か 4 階調の画像で、そのまま伸ばすと 1 点が 4x4 の階段になる。
**サーバで斜めを丸めた濃淡の画像にしてから送る** (`packages/arib/src/drcs-smooth.ts`。水増しされた行・列を畳み、Scale2x で斜めを
細かくし、4x4 ずつ平均して縁に中間の濃さを付ける。16 階調・一辺 64〜256)。
録画には放送の字幕がそのまま入る (`S_ARIBSUB`) ので同じ描き方で観られる。PGS の画像が入った古いエンコード済みの録画の字幕は読まない。

時刻は字幕に添えられたものをそのまま使う。映像と同じ ffmpeg が付けたので、受け側の
再生位置と直に比べられる（[時刻同期](#時刻同期)）。

## コンポーネント選定

| 役割       | 採用                                                                                                                                                                                | 備考                                                                                                                                                           |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| エンコード | FFmpeg (設定でコーデックのエンコーダに GPU を選んであれば、ライブも録画も GPU でエンコードする。エンコーダは録画とライブで別々。[encode.md](encode.md#gpu-でエンコードする-va-api)) | CLI パイプラインで差し替え可能                                                                                                                                 |
| 字幕       | 自前 (`packages/arib/src/b24caption.ts`。libaribcaption のデコーダを写したもの)                                                                                                     | ffmpeg は `-c:s copy` で写すだけ                                                                                                                               |
| データ放送 | 自前 (`src/lib/bml/`。デコードする側は `packages/arib/src/bml.ts`)                                                                                                                  | [データ放送の統合](#データ放送の統合)                                                                                                                          |
| 再生       | MSE 直接                                                                                                                                                                            | エンコードしたものは fMP4 (H.264 / H.265 / AV1)。放送のままの MPEG-2 と互換モードは WebCodecs・WASM で、ボックスは自前で読む (`ts/fmp4.ts`・`ts/mkv-media.ts`) |

tsreadex・mpegts.js・aribb24.js・GStreamer を使わない理由は [採用しなかったもの](stream-history.md#採用しなかったもの)。

## ライブ

**コーデックは選べる。** 既定は「自動」で、端末と開いた場所 (家の中か) で MPEG-2 (放送のまま)・AV1 + Opus・
H.265 + AAC (ライブのエンコーダが GPU のときだけ)・H.264 + AAC から画面が選ぶ ([どの形式で流すか](#どの形式で流すか))。メニューで AV1 か MPEG-2 を選べばそれを使う。
エンコーダとコンテナ以外は共通なので、字幕もデータ放送もそのまま動く。

### 入っているもの

|                |                                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 画面           | `/live`。左に映像、右に局の一覧。前回見ていた局から開く                                                                         |
| エンコード方式 | AV1 / H.265 (GPU のみ) / H.264（[エンコード](#エンコード)）。`src/lib/server/live.ts`                                           |
| 運び方         | WebSocket 1 本（[WebSocket プロトコル](#websocket-プロトコル)）                                                                 |
| チューナー     | 録画にだけ譲り、番組表・ロゴ・スキャンからは取り上げる（[録画に譲る](#録画に譲る)）                                             |
| 共有           | 同じ局を 2 人で見ても、チューナーも ffmpeg も 1 つ                                                                              |
| 変換せずに送る | コーデックで MPEG-2 を選ぶとエンコードせずに送る（端末ごとに覚える）。[放送そのまま（MPEG-2）を送る](#放送そのままmpeg-2を送る) |
| 畳み方         | **見ている人が 0 になったら離す**。接続そのものが在席の印                                                                       |
| 画面の外へ     | `GET /api/services/<id>/live` で同じものを HTTP で流す（同じ取り合い・共有。字幕・データ放送は載せない。[api.md](api.md)）      |

**共有の単位は局・音声・エンコード方式・字幕・名指しのチューナー・段。** 1 つの物理チャンネルに複数の局が入っていて、
ffmpeg には局を名指しさせている（[渡す前に 1 局へ絞る](#渡す前に1局へ絞る)）ので、映像は局ごとに違う。
二カ国語を主音声で見る人と副音声で見る人も別のものをエンコードし、字幕も何本目を選ぶかで別になる。
チューナーはエージェント側で共有され、増えるのは ffmpeg だけ。

### 多重音声はサーバで1本に決める

**「多重音声」には中身の違う 2 通りがある。** 見る人にはどちらも「音声を選ぶ」操作なので、
1 つの一覧に平らに並べる（`arib.audioTracks`）。

|              | 中身                                                      | 分け方                                          |
| ------------ | --------------------------------------------------------- | ----------------------------------------------- |
| デュアルモノ | 音声は 1 本。左に主音声・右に副音声（二カ国語・解説放送） | `-af pan=stereo\|c0=c0\|c1=c0`（副音声は `c1`） |
| 複数の音声   | 音声そのものが 2 本以上                                   | `-map 0:p:<局>:a:<何本目>`                      |

デュアルモノは 1 本から 3 つ（主・副・主+副）出てくる。テレビの「音声切換」と同じ 3 択。

**選ぶのはサーバ側。** 複数の音声を入れた fMP4 を MSE で切り替えられないブラウザがある（`audioTracks` の実装がまちまち）。
エンコードするときに 1 本に決めれば、どのブラウザでも同じに鳴る。選び直すと再エンコードになるが、チューナーは確保したまま。

**選べるものは繋いだあとでないと分からない。** 二カ国語の映画が終わればステレオに戻るので、選局のたびに現物を
`tuned` に載せて送る。覚えていた音声が選べなくなったら主音声に落とす（`arib.pickTrack`）。落とさないと番組が変わった瞬間に音が消える。

### 追っかけ再生とライブは別物

止めたりシークバーを戻したりして**わざと遅れて見ている**状態を、ライブと分けて持つ。

|                | ライブ                                                  | 追っかけ                                                                               |
| -------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 大きく離れたら | 飛んで詰める（別のタブから戻ったとき）                  | 飛ばない（見ようとしていた場面が飛ぶ）                                                 |
| 速さ           | 自動（0.97〜1.05 倍。Safari と隠れたタブは 1〜1.05 倍） | 選べる（1 / 1.25 / 1.5 / 2 倍）                                                        |
| 追いついたら   | —                                                       | 自分でライブに戻る（選んだ速さのまま進むと放送を追い越し、バッファを使い切って止まる） |

録画中の録画を最初から観る `/chase/<id>` も同じ仕組みで流す（`server/chase.ts` が伸びる元の TS を
追い読みする。チューナーは使わない。4K の局の録画は `.mmts` を読む。[4K の局のライブ](#4k-の局のライブ)）。ここでいう「追っかけ」とは別の話。

### 開いてから映像が出るまでの内訳

実機（PT3）と合成の TS で割った。**チューナーが温まっていれば、I フレーム待ちを除いて 0.44〜0.67 秒**、冷えていれば先頭に選局の 0.66 秒が付く。

|                                                |                                                                             |
| ---------------------------------------------- | --------------------------------------------------------------------------- |
| 画面が動き出して WebSocket が繋がるまで        | 160ms（チケットを `/api/live/ticket` で取っていた頃。いまは下の注記）       |
| ffmpeg の立ち上がり（固定の部分）              | 40〜270ms（バッファをまとめて受けると 40ms 前後、実時間で受けると約 240ms） |
| 放送の I フレーム待ち                          | 0〜501ms（GOP はちょうど 501ms）                                            |
| **貯めてから始める**（`pacing.ts` の `FLOOR`） | 200ms                                                                       |
| MSE に入れて 1 枚映るまで                      | 40ms                                                                        |

ffmpeg の立ち上がりは、合成の TS（1080i の MPEG-2・GOP 0.5 秒）をエージェントと同じように流し込んで、最初の moof までを
測った値。エージェントは溜めるのをやめたときに溜めたぶんを一度に渡すので、その先頭に I フレームがあれば 40ms 前後で出る
（以前の 530ms は [stream-history.md](stream-history.md#選局の待ちで試したこと)）。

**チケットはページと一緒に受け取る。** 本番の記録 (2026-11-11、ブラウザ、変換しない MPEG-2。[下](#本番の記録で割る)) では、
ページを開くたびにチケットの往復が 104〜138ms あり、繋がるまで (220〜251ms) の半分を占めていた。ライブのページを組むとき (`load`) に
1 枚配り、最初の 1 回はそれで繋ぐ ([繋ぐときの認証](#繋ぐときの認証))。縮んだあとの値はまだ本番で測っていない。

**貯める量はこちらの都合で動かせる唯一のところ。** 再生は「貯まった尺 ≧ 貯める量」かつ「映像を出せるようになっている」
（[貯まっただけでは始めない](#貯まっただけでは始めない音だけ先に出る)）で始まる。0.2 秒 = 塊 4 つぶん（サーバは 0.05 秒ずつ出す）。
足りずに止まれば増え、荒れる経路では自分で伸びるので、小さいほうから始めてよい。

冷えているときの選局 0.66 秒は、選局の ioctl まで 42ms・**復調のロック 320ms**・ロックから denpa の 1 バイト目まで 240ms
（PAT・PMT・ECM がそろってカードが答えるまで。測ったのはエージェントがこの 3 つを順に待っていた頃）。サーバ側で削れたのは 160ms だけで、開く局はページを組む時点で決まっているので、
画面が繋いでくる前にエンコードし始める（`server/live.ts` の `warm`）。その 160ms が ffmpeg の立ち上がりと重なる。

削れなかった残りは放送か機材か ARIB の都合（試して外したものは [stream-history.md](stream-history.md#選局の待ちで試したこと)）:

- **ロックの 320ms はチップの物理時間。** ドライバを替えても同じ
- **ロック後の 240ms はスクランブルの復号。** ECM が来てカードが答えるまで鍵が作れない。縮められる PAT・PMT を順に待つぶんは、いまは ECM を先に読んで重ねている。
  ライブは観る局の service_id を渡し、エージェントはほかの局 (ワンセグ・データ放送の局) の PMT を待たない。前の選局で読んだ観る局の PAT・PMT をエージェントが覚えていれば、それで流し始め、届く PAT・PMT を待たない
  （[agent.md](agent.md#b25-の復号もカードリーダーも自前)）
- **I フレーム待ちは放送の GOP。** MPEG-2 は I フレームからしかデコードを始められない
- **エンコーダは遅れの原因ではない。** `-tune zerolatency` は B フレームも先読みも作らない

#### PX-MLT の地上波の同期は PT3 とそろえた

CXD2856ER の機種 (PX-MLT 系) の地上波は、もとの手順では PT3 の倍ほどかかっていた。TMCC のプリセットと、チューナーの 50 ms の待ちの後回しで
PT3 と同じ速さにした (手順は [agent.md](agent.md#it930x-の機材を直に持つ作り)。下の値は PX-MLT8PE の受信機 0 で、地上波 7 チャンネルを 2 周した 2 周目、2026-11-11)。

| 手順                        | 同期        | TS のロックまで |
| --------------------------- | ----------- | --------------- |
| もとの手順                  | 759 ms      | 684 ms          |
| 50 ms の後回しだけ          | 693 ms      |                 |
| プリセットだけ              | 423 ms      | 約 306 ms       |
| 両方 (いま)                 | 371 ms      |                 |
| PT3 (`earth_pt3`。比べる先) | 365〜381 ms |                 |

受信機 2 でも、両方で 372 ms だった。両方を入れると、最初の 1 秒に transport_error_indicator が 1 のパケットは 1 チャンネルあたり約 18 個から約 67 個に増えた。
ロックのあとの 350 ms の待ち足しは、省くと誤りが増えたので残している。

#### 本番の記録で割る

選局 1 回につき、エージェントとサーバがそれぞれ 1 行ずつ残す。時刻はどちらも**その行の持ち主の物差し**（エージェントは
チューナーを取った時点、サーバはセッションを作った = 選局を求めた時点）からのミリ秒で、まだ来ていないものは `-`。

エージェント（`TunerPool.cs` の `Lease`、最初に送り出したとき）:

```text
[PLEX PX-MLT5PE 4-12.1 #0] T27: 前の読み出し - / 同期 318ms / 最初の TS 352ms / PAT 361ms / PMT 395ms / ECM 着 380ms (0x0901) / カード応答 512ms (0x0901) / 送り出し 514ms / カード 2 回 計 132ms (待ち 0ms・キャッシュ 0 回・未契約 0 回・準備 0ms)
```

| 項目              | 意味                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前の読み出し      | 同じチューナーを前に使っていた読み出しが止まった（取り上げていなければ `-`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| 同期              | 復調がロックした（選局し直さずに済んだら `-`）。IT930x の機材は括弧に、選局を始めた時点と、復調器がロックを確かめ始めてからロックするまでを添える (`始め 2ms・ロックまで 180ms`)。地上波はロックが早くても確かめ始めてから 350 ms 待ってから流す                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| 最初の TS         | デバイスから最初に読めた                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| PAT / PMT         | 先頭で溜めている間に PAT が来た・PAT の PMT がそろった（`B25.cs` の `Descrambler.HeldAt`）。観る局を渡した選局 (ライブ) は、その局の PMT が来た時点で、`PMT 501ms (局 1024)` のように局を添える。PMT の時刻は、PMT より先に来た ECM をカードに問い合わせる前に測るので、カードの往復を含まない。覚えた PAT・PMT で流し始めた選局は `PAT 覚えたもの / PMT 覚えたもの (局 1024)` と出す (本物の PAT が先に来ていれば PAT は時刻)。覚えたものを読み込んだが、本物の PAT・PMT が ECM より先にそろって本物で流し始めた選局は、時刻を本物で出し、カード応答のあとに `覚えた PAT・PMT は読み込み済み (本物で開始)` を足す。本物の PMT が本物の PAT より先に来たときも、PMT の時刻は本物の PAT が来てからになる |
| ECM 着（PID）     | 溜めている間に、待っていた ECM の最初のセクションが届いた。待つのは、観る局を渡した選局ならその局の PMT が挙げた ECM、ほかは PAT の全部の局の PMT が挙げた ECM。PMT より先に届いたものも数える。ECM が複数あれば、届いたのがいちばん遅いもの。届いていないものがあれば `-` で、括弧にその PID を出す                                                                                                                                                                                                                                                                                                                                                                                                    |
| カード応答（PID） | 溜めている間に、最後にカードの応答が来た。括弧はその ECM の PID。`ECM 着` との差は、PMT が挙げるまで問い合わせずに待った時間とカードの往復を足したもの                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 送り出し          | 溜めるのをやめて最初に流した                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| カード N 回 計    | 溜めている間に鍵の出どころ（カードか配る側）へ問い合わせた回数と往復の合計（ロックの待ちを含む）。番組表・ロゴ・スキャンだけの選局は「カード 使わない」                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| 待ち              | そのうち、別のストリームがカードと話し終えるのを待った合計（`BCas` のロック）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| キャッシュ        | カードに問い合わせず、別のストリームが先に問い合わせた応答を使った回数                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| 未契約            | カードが「契約が無い」と答えた回数                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| 準備              | カードの素（INT）を貰うのにかかった時間。起動したときに開いておけば 0ms 近く（`LocalCard.Warm`）                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

復号しない TS (SKY とケーブルの 4K) の行は、PAT からカード応答までとカードの項目の代わりに「復号しない (理由)」が入る。

覚えた PAT・PMT で流し始めた選局は、本物で確かめ終わったときにもう 1 行残す ([agent.md](agent.md#b25-の復号もカードリーダーも自前)):

```text
[PLEX PX-MLT5PE 4-12.1 #0] T27: 覚えた PAT・PMT は本物と同じでした (本物の PAT 361ms・PMT 395ms・捨てたのは 0 パケット)
```

本物と違ったときは「覚えた PAT・PMT が本物と違ったので、本物で作り直しました」、本物が来ないまま 8MB 読んだときは「覚えた PAT・PMT を本物で確かめられないまま 8MB 読んだので、捨てずに流します」で始まる。
時刻は上の行と同じ物差しで、PMT は観る局の本物の PMT が最後に来た時刻。捨てたのは、確かめ待ちの間に捨てたパケットの数。

端末（`live-player.svelte.ts` の `startup`、最初のコマを映したとき。ブラウザのコンソールに出す）:

```text
[live] 開くまで チケット ページから / 繋がる 73ms / tuned 520ms / 最初のバイト 640ms / 最初のコマ 1210ms
```

| 項目         | 意味                                                                                                                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| チケット     | WebSocket のチケットを受け取った。ページと一緒に受け取ったものを使ったときは「ページから」（繋がっている接続で局を替えたときは `-`）                                                                              |
| 繋がる       | WebSocket が繋がった（繋がっている接続で局を替えたときは `-`）                                                                                                                                                    |
| tuned        | サーバから `tuned` が届いた                                                                                                                                                                                       |
| 最初のバイト | `tuned` のあとで、元の TS の最初の塊が届いた（エージェントの「送り出し」にあたる）。エンコードした映像を受ける経路では `-`                                                                                        |
| 最初のコマ   | 新しい局の最初の 1 枚を映した。canvas で描く経路は 1 枚目を描いたとき (動き出すのは貯まってから)、video の経路は `requestVideoFrameCallback` を持つブラウザだけ。`tuned` より前に映ったものは前の局なので数えない |

時刻はどれも、局を選んで `begin` を呼んだ時点からの ms。エージェントの行と並べれば、「エージェントの送り出し → 最初のバイト」が
サーバと回線、「最初のバイト → 最初のコマ」が端末の分になる。canvas の経路は I フレーム待ちとデコード、video の経路はそれに貯める量が加わる。

同じページで局を替えたとき、前の局のコマで出していた頃は、canvas の経路の最初のコマが 10〜38ms と出ていた。最初のバイトも、前の局の残りで 6〜10ms と出ていた。

### 一瞬止まって遅延が増えていく

宅内で**ちょうど 60 秒ごと**に一瞬止まり、そのたびに遅れが増えて戻らなかった。バッファは
止まるたびに 3 秒ほどへ跳ね、1.05 倍で詰めて同じ高さでまた止まっていた。縮める先をいつも `FLOOR` にしていたのが原因だった (`pacing.ts` の「戻る先を覚える」)。

**止まった高さのすぐ上を次の下限にする**（`pacing.ts` の `PROBE`）。下限を下げ直すのは 10 分無事が続いてから（`FORGET`）。
これと `-maxrate` を外したことで、途切れは 8 分に 10 回から 10 分に 1 回へ、バッファは 0.6 秒で平らになった
（測った経過は [stream-history.md](stream-history.md#一瞬止まって遅延が増えていったときの測定)）。
宅内なら帯域は余っていて、`-maxrate` で削られるのは動きの多い場面の画質になる。細い経路では自動が段を下げる（[回線に合わせて画質を下げる](#回線に合わせて画質を下げる)）。

### たまに長く空く経路で止まり続ける

ふだんは滑らかに届き、15〜30 秒おきに 0.5〜0.9 秒だけ空く経路で、2 分半に 8 回止まった（#1210）。止まるたびに
下限が 0.3 秒ずつしか上がらず、届いた直後（バッファがいちばん多いとき）に 1.05 倍で詰めていたので、次の空きで使い切っていた。

- **届く間隔を覚える**（`pacing.ts` の `cover`・`GAP_WINDOW`）。ここ 3 分でいちばん長く空いた間隔の 1.2 倍 + 0.1 秒までは
  貯める（覚える下限とは別の下支え）。止まる前から上がり、止まったときもその高さまで一度に上がる。2 秒を超える空きは途絶えと見て覆わない
- **上げるのは証拠のぶんだけ。** 宅内（0.05 秒ごと）なら `FLOOR` のまま。空きが来なくなれば 3 分で忘れて縮む。
  空きで説明がつく途切れは端末に覚える下限（`FLOOR_KEY`）を動かさない
- **速さはバッファの低いところで決める**（`pacing` の `low` / `dip`）。届いた瞬間のバッファは束のたびに跳ねるので、
  次の塊が届く直前のバッファに、ここ数秒の届く間隔を足して見る（滑らかに届けば今までと同じ高さ）。それが狙いを割ったら
  0.97 倍に落とし（dash.js・hls.js などのライブと同じ。音程は保たれる）、狙いに戻ったらすぐ等速に戻す。
  1.5 倍を超えたら 1.05 倍で詰める。塊が届かない間も、映した 1 枚ごとに見て手を打つ
- **Safari では速さをなるべく触らない**（`pacing.ts` の `STEADY`）。Safari は再生中に速さを変えるたびに音と映像が
  90ms ほどつまずき（[WebKit bug 163433](https://bugs.webkit.org/show_bug.cgi?id=163433)）、Wi-Fi の iPad では
  0.97 倍に落とした瞬間にコマが落ちて「映像の遅れを補正」が続いていた。dash.js も Safari では 0.25 未満の変化をしない。
  遅くはせず、狙いより 1 秒多く貯まったときだけ 1.05 倍で詰め、狙いの 1.3 倍で戻す（hls.js と同じく、余裕があるときだけ触る）。
  iPad と iPhone はどのブラウザも中身が WebKit なのでこちらになる。速さを変えた回数は読みものに出す。
  **タブが隠れている間は、どのブラウザでもこちらにする** (`steeringWhen`。小窓で観ている間は除く)。隠れたタブで 1.05 倍のまま戻らず、音の高さが上がって聞こえていた (#2230)
- **報告に要る数を出す。** 操作バーの読みものに、いま効いている下限と受信の間隔の最大を出す（途切れたとき・下限が上がっているとき）。
  届き方の揺れなのか、受信機で落ちているのかを分けられる

### 映像だけが遅れる（音と字幕は合っている）

字幕は再生位置（音が刻む時計）に合わせて貼っているので、**映像だけが遅れるなら遅れているのはデコード**で、
運び方でも貯め方でもない。ブラウザは遅れたまま出し続けるので開き直すまで溜まり、放送との差の数字にも出ない。

`requestVideoFrameCallback` の `mediaTime` と再生位置の差が「映像だけの遅れ」になる。0.1 秒（口の動きの
ずれが分かりはじめるところ）を超えたらその場へ飛び直す（`components/player/unslip.ts`。3 秒に 1 回まで）。
録画を観る画面も同じ決まりで飛び直す。段を替えてデコーダが作り直されたあと、Android の Chrome で映像だけ遅れたまま戻らなかった。
飛んで起きた詰まりは数えない。数えると映像の遅れを直すたびに貯める量が増える。

- **測れないこともある。** `mediaTime` はコンポジタへ渡した時点のコマの時刻で、Windows の Chrome / Edge は映像を
  別の面（DirectComposition の overlay）に出すので、**面のほうが遅れても数字に出ない**。そこで Windows だけは途切れのたびにも飛び直す
  （`slipHidden`。元手は 1 コマぶんで、映像が止まった直後なので目立たない）。ほかの端末で途切れのたびに飛ぶと、遅れていなくても
  音が 0.02 秒ずつ飛ぶ（回線を 200 kbit/s に絞った手元の再現で、遅れは最大 0.022 秒なのに 20 秒で 5 回飛んだ）。測れる端末の遅れは 1 コマごとに直す
- **飛んだ直後の 1 コマは測らない。** 飛ぶ前のコマの時刻を持っていることがあり、飛んだ幅ぶん（8〜10 秒）遅れて見えた
  （「映像の遅れ 最大」が 8016ms。`unslipper`）。自分で飛んだときと、`seeking` のあと
- **コマ落ちは合図にしない。** Windows Edge では落ち着いたあとも絶えず 5.6% 落ち、合図にすると飛び続ける
- **ライブと追っかけは、飛び直しても遅れが戻るなら「自動」の画質を 1 段下げる**（`unslip.ts` の `DecodeLag`、`adapt.ts` の `decode`。録画を観る画面は飛び直すだけ）。
  測った遅れで 15 秒に 3 回飛んだか、10 秒の間にコマを 2 割より多く捨てたら、その端末にはその段が重いと見る
  （Windows Edge の 5.6% の 3 倍より上。エミュレータの AV1 1080p は 3 秒ごとに 82 回飛び、コマを約半分捨てていた）。
  下げた段から上へは、その再生の間はもう上げない。形式を手で選んでいるときは段を動かさない
- **映像が遅れているあいだ（遅れたか飛んだあと 5 秒）は再生を速めない。** 遅れを詰めようと 1.05 倍で回すと、デコードがさらに重くなる

画面の「コマ落ち」「映像の遅れ 最大」「映像の遅れを補正 N 回」は、運び側（途切れ）とデコード側を分けて読むためのもの。
「映像の遅れ 最大」が 0 のままなのに映像と音が合わないなら、遅れているのは面のほう。

### 「遅延」は2つある

画面に出す 2 つは**意味が違います**。

| 出す名前          | 何の差                                                     | 入っているもの                                            |
| ----------------- | ---------------------------------------------------------- | --------------------------------------------------------- |
| **放送から N 秒** | 隣に置いたテレビが映すはずの時刻と、いま映しているコマの差 | 端から端まで（ffmpeg のエンコード・回線・手元のバッファ） |
| **バッファ N 秒** | `buffered.end - currentTime`                               | 手元にあと何秒ぶん持っているかだけ                        |

#### 結びつけ方

放送の PCR と映像の PTS は同じ時計で打たれている。**PCR をサーバが受け取った時刻と組にして覚えれば**
（[ts/clock.ts](../src/lib/ts/clock.ts) の `BroadcastClock`）、「このコマは隣のテレビなら何時何分に映るか」が
サーバの時計の上で言える。エンコードしたものの物差しへは、ffmpeg が入口で 0 に寄せたぶん
（入口の `Duration: N/A, start: 72575.147089`）を引くだけ（出口の寄せ幅が入口の `start:` と同じことは実機で確かめた。差 2ms）。

- **遅れて読んだ組は採らない。** `受け取った時刻 − PCR` がいちばん小さい組を採る。PCR とサーバは別の水晶
  なので 30 秒ごとに選び直す（直前の区切りのぶんも残して比べる）
- **端末の時計は当てにしない。** 通知にサーバの時計を添えて差を覚え、以降はサーバの時計の上で数える
  （LAN の片道は 1ms 未満）。サーバの NTP がずれていても数字は変わらない
- チューナーの中とエージェント→サーバの時間は入らない（測っていない）
- **放送の時刻 (TDT/TOT) とは組にしない。** TDT は局ごとに固定でずれている（11 局で -0.72〜+0.90 秒、2026-09-26 実測。
  [data.md](data.md#時刻合わせ-tdt--tot-は持たない) と同じ結論）

#### バッファより小さく出ることはある

**テレビも PTS まで待って映す。** 放送の映像は着いてから映すまで 0.41〜0.50 秒（音声は 0.12〜0.15 秒）
待たせる作りで、着いた端からエンコードする denpa はそのぶん先回りできる:

```text
放送から = エンコードの完了 + 回線 + バッファ − (テレビが待つぶん 0.4秒ほど)
```

待つぶんはどの局もほぼ同じなので、局どうしの比較には使える。

### 貯まっただけでは始めない（音だけ先に出る）

MSE を作り直した直後はデコーダが立ち上がっておらず、重ねてあるのは前の局の静止画なので、バッファの長さだけで `play()` を
呼ぶと映像が止まったまま新しい局の音が鳴る。`readyState` が `HAVE_CURRENT_DATA` に上がるまで待てば一緒に始まる
（`live-player.svelte.ts` の `canStart`）。映像の無い放送やデコードの失敗で音まで出なくなるほうが困るので、1.5 秒で打ち切って音だけ先に出す。

#### 新しい局の1枚目が少し止まるのは、直さない

新しい局の 1 枚目が 150ms ほど止まって見える。**意図した姿で、不具合ではない。** 止まっている間はバッファが
`target`（最短 0.2 秒）に届くのを待っていて、止まって見える長さ ≒ 貯める量。その間に見せるのは前の局の映像（音は新しい局）
ではなく、新しい局の 1 枚目（音はまだ出ない）。見えるものと聞こえるものが食い違わないから。

#### キーフレームより前の映像は渡さない（音声だけの塊は渡す）

誰かが見ている局に後から入ると、塊はキーフレームの途中から届く。キーフレームを含む塊まで MSE に渡さない
（`ts/key-gate.ts` の `KeyGate`）。渡すと Safari はそのコマをデコードしては捨て（コマ落ち）、Chromium は手前から音だけ鳴らす。

**映像の入らない塊は待っている間も渡す。** 選局したての ffmpeg は、放送の音声が映像のキーフレームより先に来ると、最初の
塊が音声だけになる。これを捨てていた頃は音声の先頭が欠けて映像より後から始まり、Chromium は始めた直後に速さを変える
（`pacing`。選局の直後は必ず狙いより貯まっている）と**再生の時計が止まった**。1 枚目のまま 0.3〜0.6 秒、ときに 7.9 秒動かなかった。
映像より前の音声は MSE の範囲（`buffered`）に入らないので、渡しても始める位置は変わらない。

### 落ち着いた高さは覚えておく

下限は**端末に覚えさせている**（`live-player.svelte.ts` の `FLOOR_KEY`）。毎回 0.2 秒から始めると、開いて 30 秒以内に必ず 1 回止まる。
置き場が端末なのは、これが経路の性質だから（同じ人でも宅内の PC と出先のタブレットでは値が違う）。

長く無事なら 10 分ごとに 0.3 秒ずつ下げる（`ts/pacing.ts` の `FORGET` / `PROBE`）ので、線を繋ぎ替えた直後は前の経路の値のまま
余計に遅れる。そのために**覚えたものを捨てるボタンも出してある**（`relearn`。覚えているものがあるときだけ）。押すと覚えたものを消し、
貯めているぶんも下限まで詰めて放送の今へ戻す。低すぎる側に外れたぶんは放っておいてよい。止まればその場で上がる。

### 渡す前に1局へ絞る

**1 つの物理チャンネルに複数の局が入っている。** `-map 0:v:0` は「最初に見つけた映像」でしかないので、
`-map 0:p:<局>:v:0` で局を名指しする。

名指しだけでは足りない。ffmpeg は名指しした局を `-probesize` のぶん読む間に見つけられなければそのまま終了する
（3 局が入っている T15 で、丸ごと渡すと 120KB で 1/3 しか通らず、1 局に絞ると 20KB でも 3/3）。
録画と同じ `ServiceFilter` を通して局が 1 つだけの TS を渡せば、局を探す仕事が消える。字幕も見つけさせるので probesize は 100KB。

- **量はほとんど減らない**（tvk 17.6 → 16.8 Mbit/s）。落ちるのは他局の表と詰め物だけ。狙いは ffmpeg に局を探させないこと
- **名指しは絞ったあとも残す。** 万一違う局が入っていたら、黙って別の局を映すより落ちるほうがいい
- **コマ数は `-fpsmax` で上限を言う。** probesize が小さいと ffmpeg がでたらめなコマ数を起こすことがあり、
  SVT-AV1 は突っぱねる。固定（`-r`）では本当に 59.94p の局（720p）でコマを落とす

### エンコードできなくなったら、その場で言う

切り替えの間は前の映像を貼る。MSE を作り直すと `<video>` は何も映さないので、捨てる前に 1 枚だけ canvas へ
写して重ね、次の映像が実際に出た時点で剥がす（`requestVideoFrameCallback`。`play()` が返っただけではまだ
映っていない）。貼りっぱなしを避ける上限は 6 秒（`live-player.svelte.ts` の `HOLD_MOST`）。**壊れているのに
動いて見えるのがいちばん悪い**ので、ffmpeg が降りたらその場で「映像を出せませんでした」を出す:

- **終わりを ffmpeg の終了で見る。** 流し込みは書き込み先が閉じても終わらないことがある
- **畳んだセッションを持ったままにしない。** 持っていると、同じ局を選び直しても「もう見ている」と見なされる

**放送が止まっているだけのときは、そう言う。** エージェントの「電波が来ていないか、その周波数に放送が
ありません」は、アンテナや配線を疑わせる。NHK総合は保守の晩に送信機ごと止める（番組表では「放送休止」）。
番組表を持つのは denpa だけなので、同期しなかったときだけ「放送休止です」に言い換える。塞がっていたときや
ffmpeg が降りたときに出すと、今度はこちらが嘘をつく（`server/live.ts` の `whyNotTuned`）。

**局がスクランブルされたまま届いたら、理由を出して止める。** エージェントは、カードが鍵を返さなかった (未契約の) 局の ES を
スクランブルされたまま流す ([agent.md](agent.md#b25-の復号もカードリーダーも自前))。別の合図は送らない。それを ffmpeg に渡すと局の ES を
読み取れず、`Failed to set value '0:p:201:s:0' for option 'map'` で降りる (BS10プレミアムをケーブルで受けたときに実機で出た)。
denpa は 1 局に絞った TS の映像・音声・字幕のパケットを 500 個ずつ数え、半分を超えて transport_scrambling_control が
立っている 500 個が 2 つ以上、3 秒続いたら、ffmpeg を待たずに止める (`server/live.ts` の `SCRAMBLE_PACKETS` と `SCRAMBLE_LASTING_MS`。放送のままの経路も同じ)。
スクランブルされているのが半分以下の 500 個が 1 度来たら、復号できているとして数えるのをやめる。**先頭だけでは決めない。**
復号できる局でも、選局したての数百パケットがスクランブルされたまま届くことがある (2026-11-11 の本番の地上波では、エージェントが PMT の来ていない番組の ES を
そのまま流し、denpa は先頭の 500 個で無料の局を「契約されていない」として止めた)。3 秒は、エージェントが鍵を受け取れなかった ECM で問い合わせ直すまでの 2 秒より長い。
ffmpeg が決まる前に降りたら、いちばん新しく数えた 500 個 (いま数えている途中のものが 50 個に届いていればそれ) で決める。
出す文は「復号できませんでした」にそろえ、理由をカードと契約の状態から決める (`contracts.ts` の `scrambledLiveMessage`)。

| どんなとき                                          | 文                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| カードを読めない                                    | 「B-CAS カードを読めないため、スクランブルを復号できませんでした」         |
| 契約の期限が切れている                              | 「この局は契約の期限が切れているため、スクランブルを復号できませんでした」 |
| 契約中と確かめた局                                  | 「カードが鍵を返さないため、スクランブルを復号できませんでした」           |
| それ以外 (未契約・確かめていない・契約の情報が無い) | 「この局は契約されていないため、スクランブルを復号できませんでした」       |

**ffmpeg が局の映像か音声を指定できずに降りたら、そう言う。** `Failed to set value '0:p:<局>:v:0' for option 'map'` は、
字幕を外してもエンコード方式を替えても同じところで降りるので、起こし直さずに「この局の放送から映像を見つけられなかったため、
映像を出せませんでした」を出す (`missingMedia`)。字幕の指定 (`:s:`) で降りたときは、字幕なしで起こし直す ([字幕](#字幕))。

### 録画に譲る

**ライブは録画にだけ譲る**（`config.priority`）。エージェントは録画より優先度の低い相手（ライブを含む）しか
いないチューナーも使ってよいものとみなし、要れば取り上げる（[agent.md](agent.md#選ぶ順の約束)）。予約表で通した組を
録れるようにするためで、代わりに**ほかのチューナーが空いていてもライブがチューナーを取り上げられることがある。**

取り上げられたときの動き（画面もテレビのアプリも同じ）:

1. **まず同じ局をリクエストし直す。** 使ってよいチューナーが空いていればそこに入り、見ているものは変わらない
2. **入れなかったときだけ、チューナーを取り上げた録画の追っかけに切り替える**（録れているところの少し手前から）。
   通知は「録画が始まったため、局を切り替えました: <番組名> (録画中を再生しています)」で、隣に「ライブに戻る」
3. 「ライブに戻る」はリクエストし直しを試す。まだ録画がチューナーを塞いでいれば追っかけに戻り、
   「録画が終わるまでライブは観られません (<終了時刻>)」と言う

同じチャンネルの録画は選局を共有するので、取り上げられず何も起きない。入れなかった理由は見分けない
（録画が終わったあとに別の理由で入れなかったときは文言が外れる）。

**どの録画に取り上げられたかはサーバが読む**（`server/live-yield.ts`）。エージェントは予約を持たないし、取り上げた相手を
教える API も無い。そこでライブはチューナーを確保できた時点で自分の利用者（`live <種別>/<チャンネル>`）がいるチューナーを
選局を送ったエージェントの `GET /denpa/tuners` から覚えておき、ストリームが途切れたらそのチューナーの利用者にいる `rec <録画ID>` を読む。
1 回の選局の利用者は終わるまで同じチューナーにいる約束なので、覚えたチューナーは取り上げられるまで変わらない。

**取り直すのは見ている側。** サーバはチューナーのストリームが途切れたらセッションを畳み、`lost` の通知（チューナーを取り上げた録画を添えて）を送る。
再エンコードしたものを途中から渡すと受け側（MSE・テレビの fMP4）が続きとして読めないので、セッションの中では取り直さない。
画面はいつもの繋ぎ直し（待ちが倍々）に乗せる。HTTP で観ているもの（テレビのアプリ）には同じものを通知
（`GET /api/events` の `yielded`。[api.md](api.md#変化の通知-get-apievents)）でも流す。

### 番組が替わって並びが変わったら作り直す

ffmpeg は起きたときの映像・音声・字幕の並び (PMT) のまま `-map` で選ぶので、番組が替わって音声の本数や
字幕の PID が変わると追従しない。並びは局に絞るところ (`ServiceFilter.streams`) で読み、変わったかは
`StreamsWatch` で見る (データ放送などの増減では変わったことにしない)。

| 経路                                   | 変わったら                                                                                                                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ライブ (エンコード)                    | セッションを畳んで `restart` を送る。画面はすぐ同じ局をリクエストし直す                                                                                                       |
| 追っかけ (エンコード)                  | セッションを畳んで `restart` を送る。画面は届いたぶんを観終えてから、観ていた位置をリクエストし直す                                                                           |
| 放送のまま (MPEG-2) のライブ・追っかけ | 畳まない。受け側が PMT を読んで PID を選び直し (`packages/arib/src/pes.ts` の `PesDemuxer`)、字幕の ffmpeg だけ起こし直す ([放送のままのときの字幕](#放送のままのときの字幕)) |
| 元の TS の字幕 (録画・追っかけ)        | 閉じない。字幕の ffmpeg だけ起こし直す                                                                                                                                        |

**エンコードする経路はその場で起こし直さない** (`lost` と同じ理由)。
30 秒以内に続いたらいつもの繋ぎ直し (待ちが倍々) に乗せ、切り替わりの前後で並びが行き来する局で作り直しを繰り返さない。
HTTP で観ているもの (テレビのアプリ) にはストリームを閉じて伝える ([api.md](api.md#ライブ-get-apiservicesidlive))。

**追っかけは観ていない先を飛ばさない。** 送り込みは倍速なので (`server/chase.ts`)、作り直すときには観ている位置より
先まで届いている。画面は手元が尽きるまで観てから、観ていた位置をリクエストし直す (`resumeChase`)。位置は秒で、バイトへは
比例で当たりを付けるので、少し手前に当たると前の番組の PMT を読んでからまた変わる。そこでサーバは**変わったところ (読んだ塊の末尾のバイト) を
録画ごとに覚え**、その 15 秒以内をリクエストされたらそこから読む (`chase.ts` の `resumePlan`)。テレビのアプリにも同じように効く。

### 入口が1つ増えている

公式の adapter-bun は `Bun.serve` を自分で呼ぶが、`websocket` を渡す方法が無い。そこで入口の `server.js` が
`Bun.serve` を包んでから `build/index.js` を読み、adapter の設定に `websocket` を足して、`/api/live/socket` の
ハンドシェイクだけ SvelteKit の手前で受ける（理由と、`Host` をそのまま扱う理由は `server.js` の先頭のコメントに）。

**開発サーバ（`bun run dev`）ではライブが繋がらない**（vite も `node:http`）。確かめるときは `bun run build && bun ./server.js`。

### 繋ぐときの認証

**ブラウザは WebSocket のハンドシェイクに `Authorization` を付けない。** 画面が先に `POST /api/live/ticket` で
使い捨てのチケットを取り、それを URL に付けて繋ぐ。チケットの発行は普通の HTTP なので、OIDC も信頼したネットワークも
そのまま効く。URL は履歴にもログにも残るので、1 回使ったら消す。寿命は 30 秒。

**最初の 1 回は、ページと一緒に受け取ったチケットで繋ぐ。** ライブのページを組むとき (`routes/live/+page.server.ts` の `load`) に
サーバが 1 枚配る。ページも認証を通った人にしか返らないので、守り方は `POST /api/live/ticket` と同じ。
`/api/live/ticket` の往復 (本番で 104〜138ms) が無くなる。

- 画面は受け取ってから寿命の半分 (15 秒) までしか使わない。サーバと端末の時計は合わせていないので、端末の時計で数え、HTML が届くまでのぶんを残りの半分で覆う
- 断られたら `/api/live/ticket` から取り直して繋ぐ。戻るで開き直したページは、ブラウザが手元に持っていた HTML (使い終えたチケットが入っている) を出すことがある
- 繋ぎ直しと 2 回目からは、いままでどおり `/api/live/ticket` から取る。追っかけはページで配らない

## エンコード

**いまの引数は `src/lib/server/live.ts` の `encodeArgs` にあります。** 1 本の
ffmpeg が映像と音声を 1 つの pipe へ多重化し、`Fmp4Splitter` が `moof`+`mdat` ごとに
割って WebSocket へ流します。

```bash
ffmpeg -nostats -probesize <小さく> [<GPU の入口>] -i pipe:0 \
    -vf <インタレ解除> \
    -map 0:p:<局>:v:0 -fpsmax <上限> <映像のエンコード方式> \
    -map 0:p:<局>:a:<何本目> [-af pan=...] <音声のエンコード方式> \
    -f mp4 -movflags +empty_moov+default_base_moof \
    -frag_duration <塊の長さ> -flush_packets 1 pipe:1 \
    <字幕の出口 → pipe:3>
```

**値は書かない。引数の並びだけ。** 実測した値と理由は `encodeArgs` / `videoArgs` の説明にあり、写すと片方が古くなる。下の表も役割だけ (preset などの値は `videoArgs`。録画の値は [encode.md](encode.md))。

- **`-fflags nobuffer` は付けない。** 入口の解析の間に読んだ I フレームを捨てて次の GOP を待つことがある。外しても遅れは増えない（`encodeArgs` の「入口の解析で読んだぶんを捨てさせない」）
- **`-copyts` は付けない**（[1 本にしたのは、時刻を揃えるため](#1本にしたのは時刻を揃えるため)）
- **`-loglevel` は下げない。** 選べる字幕は入口の見出し（info で出る）から読む（[字幕](#字幕)）。進み具合の数字だけ `-nostats` で止める
- クライアント側の SourceBuffer は `segments`（既定）で使う。`sequence` は届いた順に詰めるので、1 つ取りこぼすと以降ずっとずれる。
  再生位置の面倒（貯めてから出す・離れたら速める）は `src/lib/ts/pacing.ts`
- 1 本に多重化している間は `+frag_every_frame` を使わない。映像だけ・音声だけの塊が交互に並んで MSE が引っかかる
  （`encodeArgs` の「コマごとに切らない」）。いまは映像 1 本・音声 1 本

### エンコード方式は見ながら選べる

画面のコーデックのメニューから AV1 を選び直せる（`LiveCodec`。H.264 と H.265 はメニューに並べず、自動が選ぶ。既定の「自動」は[下](#どの形式で流すか)）。音声と同じく、選び直すと
再エンコードになる。**局を変えても引き継ぐ。** 映像の中身ではなく「その端末で出るか」の話なので。

|      | H.264                                                                       | AV1                                                                                               |
| ---- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 役割 | **速く。** いちばん速い preset と低遅延の指定。画質は既定のまま。量は増える | **小さく。** SVT-AV1 の速い preset で、先読みはしない (先読みのぶん貯めるのがそのまま遅れになる)  |
| 遅れ | 電波が届いてから塊が出るまで 0.24〜0.49 秒                                  | 1.1〜1.5 秒。**放送の今から 1 秒ぶん離れる**。低遅延指定 (`pred-struct=1`) は実時間に間に合わない |
| 音声 | AAC                                                                         | Opus (どちらも元の放送のビットレートに合わせる)                                                   |
| 向き | AV1 を受け取れない端末                                                      | 宅外・細い経路。自動の外での既定                                                                  |

**H.265 はライブのエンコーダが GPU のときだけ出す**（ソフトウェアのエンコーダを組んでいない。[encode.md](encode.md#h265-は-gpu-でだけ)）。
AV1 を受け取れず H.265 なら受け取れる端末（Safari など）向けで、同じ画質なら H.264 より小さい。音声は AAC、入れ物の中の名前は
`hvc1`（Safari は `hev1` を受け取らない）。出せるかはサーバが決めて画面に渡し（`server/viewing.ts`）、出せなければ自動でも選ばない。
GPU でエンコードできずに降りたらソフトウェアには降りず、画面が H.265 をやめて次の形式でリクエストし直す。そのあとしばらくは、
H.265 の指示を受けてもサーバが H.264 にする（`live.liveHevc`）。追っかけでは出さない。

HW エンコーダの無い実機（44 スレッド）で、1080i をデコードして 60 コマ/秒の AV1 も実時間に付いていった（立ち上がりは 0.45 秒遅い）。
量はどちらも品質指定なので場面で動く。実測は `videoArgs` の説明にある。

> [!NOTE]
> **戻れる幅はバイト数でも切る。** 5 分（`KEEP`）を太ったストリームで持つと `appendBuffer` が `QuotaExceededError` で
> 落ち、そこから映像が出なくなる。受け取っている速さから 120MB（`BUDGET`）に収まる長さを出し、
> 時間と小さいほうで切る（`live-player.svelte.ts`）。

**受け取れない端末では H.264 にする。** 自動では先に `MediaSource.isTypeSupported` に問い合わせて (`#lib/live.ts` の `codecsFor`)、
受け取れなければ AV1 (と H.265) を飛ばす。選んだ AV1 を受け取れなければ次の形式に移り、理由を画面に出す。

- **受け取れると答えても、流すと断る端末がある。** Android の Chrome 133 は MP4 の `Opus` を受け取ると答え、流すと
  `CHUNK_DEMUXER_ERROR_APPEND_FAILED` で断った (小文字の `opus` なら再生できた)。小文字を受け取れる端末には小文字で渡す
  (`live.ts` の `mseType`。Safari は小文字を断るので大文字のまま)
- **`<video>` がエラーになったら、送り込みを止めて次の形式に移る** (`onMediaError`。理由も同じく画面に出す)。
  Chrome は断ったあと SourceBuffer を外すので、それまでは外れたものを読み続けて「読み込み中」のまま止まっていた

> [!NOTE]
> **iPhone の Safari は `MediaSource` を持たず、`ManagedMediaSource`（iOS 17.1+）だけがある。**
> 無ければそちらを使う（`ts/media-source.ts`）。`disableRemotePlayback` を立てないと開かない。
> 送り込む頃合いの合図（`startstreaming` / `endstreaming`）は聞かず、ブラウザの刈り取り
> （`bufferedchange`）は `buffered` を毎回読み直すので手当てしていない。**実機では未確認。**

### どの形式で流すか

**既定は「自動」で、決めるのは画面です**（`#lib/live-choice.ts` の `autoCodec`）。コーデックのメニューは
自動 → AV1 → MPEG-2 の順に並びます（H.264 と H.265 は並べない。下の `HIDDEN_CODECS`）。メニューで選んだものは家の中でも外でもそのまま使い、
ライブでは端末ごとに覚えます（`LAST_COOKIE` の `choice`。自動で決まった形式は覚えない）。行の値には「自動 (MPEG-2)」のように、
いま決まっている形式を添えます。

**自動の順は、ライブ・追っかけ・録画の観る画面で 1 つの関数から出します**（`autoOrder`）。画面ごとの例外は作らず、その画面で出せない形式は並びから外すだけです。

| 場面                                  | 家の中                       | 外                  | 互換モード                                                        |
| ------------------------------------- | ---------------------------- | ------------------- | ----------------------------------------------------------------- |
| その場でエンコード (ライブ・追っかけ) | MPEG-2 → H.264 → AV1 → H.265 | AV1 → H.265 → H.264 | AV1 → H.264 → MPEG-2                                              |
| エンコード済み (録画の観る画面)       | AV1 → H.265 → H.264          | AV1 → H.265 → H.264 | [録画の観る画面も canvas に描く](#録画の観る画面も-canvas-に描く) |
| 録画しか無い (録画の観る画面)         | MPEG-2 → H.264 → AV1         | AV1 → H.264         | [録画の観る画面も canvas に描く](#録画の観る画面も-canvas-に描く) |
| 4K の局のライブ                       | HEVC → H.264 → AV1           | AV1 → H.264         | AV1 → H.264 (canvas は HEVC を描かない)                           |

- 家の中は開くまでの速さを採ります。MPEG-2 はエンコードせずに済み、画質も放送のままです。次はエンコードの立ち上がりが速い H.264 です
- 外は回線を採ります。放送のままは 1 局で 15Mbit/s ほどあるので選ばず、同じ画質で小さい順にします
- 互換モードで MPEG-2 を後ろにするのは、エンコードしたものより canvas に描くのが重いからです
- エンコード済みは小さい順です。もうエンコードしてあるので、開く速さはコーデックで変わりません。観る画面はファイルそのまま → 詰め替え → その場の変換の順に探し、
  ファイルそのままと詰め替えの中でこの順を使います (`ts/playback.ts` の `pickOffer`)。その場の変換は、その場でエンコードする行の順です
  (家の中なら H.264 → AV1、外なら AV1 → H.264。H.265 には変換しない)
- 録画しか無い録画 (エンコード済みが無い) の観る画面は、その場でエンコードする行と同じ順です。MPEG-2 は元の TS をそのまま流して
  この端末でデコードし、互換モードと同じく canvas に描きます ([録画の観る画面も canvas に描く](#録画の観る画面も-canvas-に描く))
- 4K の局は、放送のまま (MPEG-2) の場所に HEVC の詰め替えが入ります ([4K の局のライブ](#4k-の局のライブ))。H.265 にはエンコードしないので、
  エンコードする H.265 は並べません

TS の局の追っかけと、録画しか無い観る画面は H.265 を出さないので (その場の変換では H.265 を作らない)、家の中は MPEG-2 → H.264 → AV1、外は AV1 → H.264 になります。4K の局の録画の追っかけと観る画面は、MPEG-2 の場所に放送の HEVC の詰め替えが入り、家の中は HEVC → H.264 → AV1 です。

先頭から、この端末で使えるものを採ります。MPEG-2 はデコードできるか（`raw/support.ts`）、AV1・H.265・H.264 は MSE で受け取れるか
（互換モードなら描けるか。H.265 は互換モードでは使わない）。H.265 はそのうえで、ライブのエンコーダが GPU のときだけ使います。
途中で打ち切ったら（MPEG-2 のデコードが間に合わない・AV1 や H.265 を受け取れなかった・サーバが H.265 をエンコードできなかった）、その画面を開いている間は
次のものに移り、理由を断り書きに出します。選んだ MPEG-2 をデコードできない端末では、選択を自動に戻して覚え直します
（開くたびに断り書きを出さない）。

**形式を切り替えた断り書きは 10 秒で引っ込めます**（`adapt.ts` の `SWITCH_NOTE`。ライブ・追っかけ・観る画面で同じ）。サーバの `notice`
（エンコードを軽くした・混んでいて段を下げられなかった）と、音を別に鳴らせなくなったときの文も同じです。局を替えても消さないのは、
切り替えた先が映り始めても理由を読めるようにするためです。引っ込めたあとも、切り替えた先はメニューの行（「自動 (H.264)」）に残ります。
出しっぱなしにしていた頃は、メニューで選び直すまで映像の上に残っていました。

- 押して消せるようにはしない。映像の上の通知 (`StageNote`) はみな押せず、押した指は下の映像に届く (操作バーの出し入れ・2 回押しの再生/一時停止)。
  小さなラベルに押せる所を作ると、車の中のタブレットで映像を押した指が通知に取られる

**テレビのアプリの「自動」は、サーバが選びます。** アプリは再生できる形式 (`playable`) を送り、サーバが同じ `autoOrder` で選んで、
応答ヘッダの `X-Denpa-Codec` (録画は `playback` の `auto`) で返します (`server/viewing.ts` の `autoFormat`、`ts/playback.ts` の `autoPick`。
[api.md](api.md#形式をサーバに選ばせる-codecauto))。アプリは順番を持たず、再生できなかった形式を `playable` から外してリクエストし直します。
ブラウザの画面は同じ関数を自分で呼びます。ライブと追っかけは WebSocket で、再生できるかが開いている間に変わる (MSE、MPEG-2 のデコードが間に合うか、互換モード) ためです。

**家の中かは、開いたホスト名で決めます**（`#lib/host.ts` の `indoorHost`。サーバが決めて画面に渡す。`server/viewing.ts`）。
設定の「視聴」の「家の中の名前」に書いた名前と、プライベートの IP アドレス（127/8・10/8・172.16/12・192.168/16・`::1`・fc00::/7）・
`localhost`・`.local`・`.lan`・`.home.arpa`・`.internal` で終わる名前が家の中です。**相手の IP では決めません。** VPN（NetBird など）は相手のアドレスを書き換える
ことがあり、家の中だけの名前が外から引けることもあるためです。CGNAT（100.64.0.0/10）は VPN 越しのことが多いので家の中に入れません。
サーバは同じ決め方で、開いたときに先回りします（`live.warm`。自動なら家の中は放送のまま、外は AV1）。
ページを組む時点では端末が何を再生できるかが分からないので、何でも再生できるとみて決めます（`viewing.warmFormat`）。
MPEG-2 をデコードできない端末のように画面が別の形式をリクエストしたら、サーバはそのリクエストがチューナーを使えた時点で
先回りしたものを畳みます（`live.ts` の `dropWarm`。同じチャンネルなので選局は共有できる）。誰も来なければ 8 秒で畳みます。
畳まずに 8 秒待っていた頃は、その間に別の局を選ぶと、空いているチューナーがほかに無ければ「選局できませんでした」になっていました。

> [!NOTE]
> 家の中の既定 (MPEG-2) には、エンコードしたものにある **5 分戻れるシークバーと追っかけの速さがありません**（[払うもの](#払うもの)）。
> 録画中の録画の追っかけ (`/chase/<id>`) も同じで、速さのメニューを出しません。要るなら AV1 を選びます。

**メニューには H.264 と H.265 を並べません**（`#lib/live-choice.ts` の `HIDDEN_CODECS`）。
外すのはメニュー（ライブ・追っかけ・観る画面）だけで、AV1 を再生できない端末には自動で H.265 か H.264 を流します
（サーバは今までどおり出す）。前に H.264・H.265 を選んでいた端末は自動として扱います。テレビのアプリは外すものを
`GET /api/playback/options` の `hidden` で読みます（[api.md](api.md#観るときの決まり-get-apiplaybackoptions)）。

### GPU でエンコードする

設定の「録画」の「エンコード」（`/settings/recording#encoding`）のライブの列でそのコーデックのエンコーダに GPU を選んであれば、
**GPU でエンコードする**（録画とは別に選ぶ。Intel・AMD の VA-API、NVIDIA の NVENC、Windows の Intel の QSV・AMD の AMF、Mac の VideoToolbox、Rockchip MPP。引数と決め方は
[encode.md「ライブは別に選んだエンコーダで GPU に載る」](encode.md#ライブは別に選んだエンコーダで-gpu-に載る)）。
MPEG-2 を GPU でデコードできる環境ではデコードとインタレ解除も GPU に寄せる。`-fpsmax`・字幕の出口（`pipe:3`）・音声はそのまま通る。

**映像を出す前に GPU の ffmpeg が降りたら、ソフトウェアで再エンコードする**（その経路は 15 分覚えてソフトウェアでエンコードする）。NVENC が同時に開ける数を超えて降りたときは、その 1 本だけソフトウェアで、経路は覚えない（[encode.md「NVIDIA でエンコードする」](encode.md#nvidia-でエンコードする)）。
画面には断り書きを一行出す（`notice`）。HTTP のエンドポイント（`sessionStream`）は通知を捨てるので、
アプリには再エンコードが少し遅れて見えるだけ。

### 回線に合わせて画質を下げる

**回線が足りなくなったら、その位置から段を下げた変換に切り替えます。** 段は固定の表で（`src/lib/rungs.ts`）、サーバ（変換の引数・ライブの共有の目印）と
画面（段の上げ下げ）が同じ表を使います。低いビットレートのものを前もってエンコードしておくことはせず、足りなくなってから変換を始めます。

| 段  | 高さ                                                            | コマの上限 | 映像の上限 | 音声 |
| --- | --------------------------------------------------------------- | ---------- | ---------- | ---- |
| 0   | 下げない (エンコード済みのファイル・MPEG-2・ふだんのエンコード) | -          | -          | 256k |
| 1   | 720                                                             | 30         | 3 Mbit/s   | 96k  |
| 2   | 540                                                             | 30         | 1.5 Mbit/s | 96k  |
| 3   | 360                                                             | 30         | 0.6 Mbit/s | 96k  |

段の値は RK3588 と J4125 で測って直す前提の目安です（測り方は [encode.md](encode.md#段を下げた変換の重さを測る)）。

- **段は `rung` で伝えます。** WebSocket の `tune` と `chase`、HTTP の `?rung=`（`/api/recordings/<id>/stream`・`/chase`・`/api/services/<id>/live`）。
  段 0（省いたとき）は今までと同じ動作です。MPEG-2（放送のまま）と音声だけでは効きません
- **段を下げたときのコーデックはサーバが選びます**（`live.rungCodec`）。AV1 → H.265 → H.264（`autoOrder` のエンコード済みの順）のうち、端末が再生できて
  （`playable`）GPU でエンコードできる最初のものを使い、無ければソフトウェアの H.264 にします。SVT-AV1 と x265 は段に使いません。RK3588 なら
  AV1 は飛ばし、端末が H.265 を再生できれば hevc_rkmpp、できなければ h264_rkmpp です。選んだものは WebSocket なら `tuned` の `codec`、HTTP なら
  応答ヘッダの `X-Denpa-Codec` で返します。追っかけと録画の変換も、段を下げるときは H.265 になることがあります
- **引数は 1 か所で組みます**（`live.videoArgs` の `rung`。ライブ・追っかけ・録画の変換で共通）。放送は bwdif を 1 コマずつの出し方にして 30 コマ、
  エンコード済みは元が 30 コマを超えるときだけ `fps` で 30 コマに間引き（24 コマの録画はコマを足さずに 24 コマのまま）、`scale=-2:<高さ>` で縮めます。キーフレームは 1 秒ごとです。エンコーダごとのレート制御は
  [encode.md](encode.md#回線に合わせて下げた段も同じ関数で組む) の表のとおりです。
  VA-API でデコードから GPU に載せる経路は、GPU の上で 30 コマにして `scale_vaapi` で縮めます（フレームを CPU に降ろさない）
- **GPU が映像を出さずに降りたとき、H.264 はソフトウェアで再エンコードします。** AV1 と H.265 はソフトウェアに降りず、そこで止めて方式を 15 分覚えます。
  画面が同じ段をリクエストし直すと、覚えている間は次のコーデックになります
- **H.265 のエンコード済みからも変換します。** 段を下げないなら今までどおり写すだけです
- **段 1〜3 を新しくエンコードするときは、その場で変換する本数の枠を 1 つ使います**（ライブも。`live.rungSlot`）。同じ段をもう誰かが観ていれば
  共有するので使いません（共有の目印に段が入る）。追っかけと録画の変換はもともと枠を使うので、段を下げても 1 つのままです
- **枠が埋まっていたら段を下げません。** WebSocket のライブは、いま観ている局ならその段のまま、新しく開く局なら段 0 で開き、`tuned` の `rung` と
  断り書き「サーバが混んでいるため、画質を下げられませんでした」で知らせます。HTTP は 503（`サーバが混んでいます`）で、アプリは今のストリームを続けます
- **段 3 でも足りないときの最後の手は音声だけです。** ライブは WebSocket の `tune` の `codec: "audio"`（`rung` を 1〜3 にすると AAC 96k）と
  HTTP の `?audio=only`、録画は `stream?codec=audio`（AAC 96k の fMP4。時刻は映像と同じ物差し）。追っかけには音声だけがありません。
  音声だけは枠を使いません。枠は映像のデコードとエンコードの重さを抑えるもので、音声だけなら映像を扱わないためです（ファイルとライブの `audio=only` と同じ）

#### 送り出しの具合 (`pace`)

**サーバは測った値だけを返し、段を決めるのは画面です。** 回線が細いのか、サーバのエンコードが遅いのかを画面が読み分けるためです (`server/pace.ts`)。

| 経路                                        | `backlog`                             | `dropped`                    | `speed`                                      |
| ------------------------------------------- | ------------------------------------- | ---------------------------- | -------------------------------------------- |
| WebSocket (ライブ・追っかけ)                | 接続の送れずに溜まっている量 (バイト) | 前の `pace` から捨てた塊の数 | 出した映像の時刻の進み ÷ 実時間 (5 秒の窓)   |
| HTTP の変換 (`/api/recordings/<id>/stream`) | 0 (送る速さは TCP が決める)           | 0 (捨てない)                 | 出した映像の時刻の進み ÷ ffmpeg を待った時間 |

- WebSocket は 2 秒ごとか、塊を捨てた・バッファが 512KB 以上動いたときに `pace` を送ります（下の[プロトコル](#websocket-プロトコル)）
- `speed` はライブなら追いついていれば 1 前後で、0.95 (`#lib/rungs.ts` の `ENCODE_SLOW`。サーバと画面で同じ値) を下回り続けたらエンコードが遅れています。追っかけは倍速で読むので 2 前後まで出ます。
  エンコードしない経路・音声だけ・測れるまで（1 秒）は null です。画面は 0 を測れていない値と読み、エンコードの遅れに数えません
  （映像として読めないトラックでは、エンコードが進んでいても 0 になる。#2152）
- **HTTP は応答のヘッダで id を返し、画面が `GET /api/playback/pace?id=` で読みます**（`X-Denpa-Pace`）。サーバが自分で「出せる段」を決めて返す案は
  採りませんでした。判断が画面とサーバに分かれ、ライブ（WebSocket）と決め方がずれるためです。HTTP の変換は実時間より速く進むので、
  回線の速さは画面が受け取ったバイト数から測れます。サーバにしか分からないのは「ffmpeg を待っている時間」だけで、それを `speed` で返します。
  ffmpeg を待たずに済んでいる（回線のほうが遅い）と、`speed` は上限の 10 になります
- HTTP の追っかけ・ライブ（テレビのアプリ）は具合を返しません。アプリは自分で受け取りを測ります

**確かめていないこと:** 段ごとの画質（XPSNR）と、1.5 Mbit/s での veryfast と ultrafast の差、`scale_vaapi` が `-2` の幅を受けるか（手元に VA-API の GPU が無い）、
AV1・H.265 の VBR がどのドライバでも通るか、段を下げた変換の立ち上がり、RK3588 での速さと MPP を同時に動かせる本数。

#### ライブと追っかけの画面

**コーデックのメニューが「自動」のときだけ、画面が段を上げ下げします**（`live-player.svelte.ts` の `adapt`。決め方は `src/lib/adapt.ts` の `RungAdapter`、
指示の組み立てと、断り書きを上書きするかの決まりは `src/lib/live-adapt.ts`）。0.5 秒ごとに次のものを渡し、段を動かすと返ってきたら、その段で `tune`・`chase` を出し直します。

| 渡すもの         | どこから                                                                                                                                                                                                                                                             |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 詰まり           | `<video>` は `waiting` から `playing` まで、または先を持たない状態 (`readyState` が `HAVE_FUTURE_DATA` 未満) か、音は進むのにコマが映らない状態が 0.5 秒続いたとき (`STUCK_LEAST`)。canvas は詰まった次の刻みと、描いたコマ数が 1.5 秒増えないとき (`CANVAS_FROZEN`) |
| 先のバッファ     | `<video>` は届く直前の低いところ（`lows`）といまの値の低いほう。canvas は届いた音の端までの長さ                                                                                                                                                                      |
| 速さ             | 直近 5 秒に受け取ったバイト数（中身を問わない）。下げ先を決めるのと、段 0 へ上げてよいかを比べるのに使います                                                                                                                                                         |
| `pace`           | 届いた最後のもの。届くたびに新しいオブジェクトにします（`dropped` を 1 回だけ数えるため）                                                                                                                                                                            |
| 放送に対する遅れ | 実時間と届いた映像の端 (`<video>` は `buffered` の末尾、canvas は届いた音の端) の差が、4 秒でどれだけ伸びたか (`live-adapt.ts` の `LagMeter`)。追っかけは測らない                                                                                                    |
| 回線の速さ       | 上げる前にだけ測るもの (下の「上げる前に測る」)                                                                                                                                                                                                                      |

- **出し直しは選び直しと同じ経路です**（`requestAgain`）。前のコマを貼って隠し（`HOLD_MOST`）、映像はエンコードの立ち上がりのぶん止まります
- **段 0 は自動で決まった形式です。** 家の中で MPEG-2 を観ているときに下げると、`raw` を外して段 1 の変換に移り、段 0 へ上げ直すと MPEG-2 に戻ります
- 段 1〜3 の `playable` は MSE で受け取れるコーデックです (互換モードは下のとおり canvas に描けるもの)。段を下げた変換で GPU が降りた AV1・H.265 は、段を下げている間だけ外してリクエストし直します
- 音声だけは `codec: "audio"` と `rung: 3` です。追っかけでは音声だけにせず、段 3 のまま流します
- リクエストしてから `tuned` が来るまでと、止めている間は段を決めません (上げた段が映り始めるまでの待ちだけは数える。下の `PROBE_START`)。選局・シーク・段の切り替えのたびに測った値を捨てます（`RungAdapter.reset`）。段は局を変えても持ち越します
- `tuned` の段がリクエストより高ければ、サーバが混んでいて下げられなかったので、20 秒は下げ直しません（`RungAdapter.refused`）（断り書きはサーバの `notice`）
- メニューで形式を選ぶと段 0 に戻し、段は動かしません。足りないときは断り書きだけを出します
- **バッファがサーバの外に隠れても下げます。** 中継・カーネル・リバースプロキシが溜めると、サーバの `backlog` は 0 のままです。手元で 2 Mbit/s に絞って
  3 Mbit/s の段を流したときも 0 のままで、足りない兆しが見えないまま段 0 まで上がり、7〜22 秒止まりました。放送に対する遅れが 4 秒で 0.6 秒以上
  伸びたら足りないと見ます（`adapt.ts` の `LAG_SPAN`・`LAG_GROW`。届く速さが流している段の 85% ほどを切ると伸びる）
- **映像だけが止まって音が続くのも詰まりです。** 細い回線ではキーフレームの大きな塊が遅れて届き、音の時計は進むのにコマが映りません
  (`waiting` は来ず、`readyState` も落ちない)。v2.29.0 では、外から観ると映像が 5 秒おきに止まるのに「720p に下げました」のまま下がらなかった。
  映ったコマ (`requestVideoFrameCallback`) が 0.5 秒来なければ詰まっていると見ます（`stuckNow`）。canvas (MPEG-2・互換モード) は、
  RawEngine が 1 秒ごとに知らせる描いたコマ数が 1.5 秒増えなければ同じに見ます
- **足りなくて下げるときは、WebSocket を繋ぎ直します**（`freshSocket`）。前の段の映像が回線の途中に溜まっていて、同じ接続では
  `tuned` も下げた段の映像もその後ろに並ぶためです（手元で 0.25 Mbit/s に絞ったときは 32 秒）。閉じれば溜まったぶんは捨てられます。
  サーバが溜まりすぎて映像の塊を捨てたとき（`dropped`）の `pace` も同じ列に並ぶので、それを待つより画面が測れる遅れの伸びのほうが先に効きます
- **段 3 から音声だけにするのは、段 3 に移って 10 秒たち、直近 15 秒の 3 割以上が足りないときです**（`AUDIO_AFTER`・`AUDIO_WINDOW`・`AUDIO_SHARE`）。
  細い回線では 1〜2 秒止まって 1 秒ほど動くのを繰り返します。「途切れずに 10 秒」を待っていた頃は、動いている刻みで数え直しになり、
  0.25 Mbit/s で 360p が止まり続けても音声だけになりませんでした。シークしても、それまでの数は持ち越します
- **ライブは、上げる前に回線の速さを測ります。** 実時間でしか届かないので、受け取りの速さを見ても余裕は分かりません。足りない兆しが 30 秒無ければ、
  試しのデータ（`GET /api/playback/probe?bytes=`。乱数で埋めたもの）を取ります。量は、次の段の 1.2 倍から再生中の段の受け取りの速さを引いた残りで
  1 秒かかるぶん（64KB〜4MB）で、2 秒でやめます（細い回線で取り続けると映像が細る）。試しのデータの速さと再生中の段の受け取りの速さを足したものが
  次の段の 1.2 倍に届けば上げ、届かなければ上げずに同じ長さを待ち直します。測って届かなかったことでは待ちを倍にしません (細い間に測るたびに伸びると、回線が戻っても上がるのが遅れる。上げてみて足りなかったときに倍にした待ちはそのまま)（`RungAdapter.wantProbe`・`live-player.svelte.ts` の `probeLink`）。
  段 0 へ戻すときは、段 0 で足りていたときに受け取っていた速さと比べます
- **上げた段が 6 秒たっても映り始めなければ、上げる前の段に戻します**（`PROBE_START`・`RungAdapter.abandon`）。足りない段では最初のキーフレームが届かず、
  `tuned` も溜まった前の段の映像の後ろに並びます。上げてみて足りなかったときと同じく、待ちを倍にします
- **互換モード（エンコードしたものを canvas に描く）でも同じに段を動かします。** `playable` は canvas に描けるコーデック（`raw/support.ts` の `canvasSupport`）で、
  H.265 は入れません（互換モードでは描かない）。H.264 を描けない端末と、描ける形式をやめて MPEG-2 に移ったあとは段を動かしません。
  GPU でエンコードできるものが無ければ、下げた先はソフトウェアの H.264 になるためです。音声だけにはせず、段 3 のまま流します
  （映像の無い fMP4 を canvas に流す経路を確かめていない）。
  先のバッファは届いた音の端までの長さ、詰まりは RawEngine がバッファを使い切った次の刻みと、描いたコマ数が 1.5 秒増えないときです（`<video>` が無いので MPEG-2 と同じ）。
  デコードが間に合うかは今までどおり `raw/budget.ts` が見て、回線とは混ぜません（間に合わなければ段ではなく形式を替える）

**メニューの「自動」の行には段の高さを添えます**（「自動 (H.264 540p)」「自動 (音声だけ)」。`settings.ts` の `liveCodecs`）。選択肢の名前は「自動」のままです。
断り書き（`warning`）には次の文を出します。観る画面も同じ文です（`adapt.ts` の `stepLabel`・`adaptNote`）。

| とき                               | 文                                                                                                                            |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 下げた                             | 「回線が細いため、540p に下げました」「回線が細いため、音声だけにしました」                                                   |
| 端末のデコードが追いつかず下げた   | 「再生が追いつかないため、540p に下げました」                                                                                 |
| 上げた                             | 「回線が戻ったため、720p に上げました」「回線が戻ったため、元の画質に戻しました」                                             |
| 音声だけから戻した                 | 「回線が戻ったため、360p の映像に戻しました」                                                                                 |
| サーバのエンコードが遅れている     | 「サーバのエンコードが追いつかないため、再生が止まります」                                                                    |
| サーバが軽いエンコードに替えた     | 「サーバのエンコードが追いつかないため、30 コマに切り替えました」「…、GPU のエンコードに切り替えました」（サーバの `notice`） |
| 形式を手で選んでいて足りない       | 「回線が細いため、再生が止まります。コーデックを「自動」にすると、画質を下げて再生を続けます」                                |
| サーバが混んでいて下げられなかった | 「サーバが混んでいるため、画質を下げられませんでした」（サーバの `notice`）                                                   |

段を動かしたときの文 (下げた・上げた・戻した) は 6 秒で消します (`adapt.ts` の `ADAPT_NOTE`。ライブ・追っかけ・観る画面で同じ)。
サーバの `notice` の文は、形式を切り替えた文と同じく 10 秒で消します ([どの形式で流すか](#どの形式で流すか))。エンコードの遅れと手で選んでいるときの文は、ほかの断り書きを上書きせず、その状態が 20 秒来なければ消します。
サーバが軽いエンコードに替えたときの文だけは、エンコードの遅れの文で替えます。軽くしたあとも遅れているなら、替えたという文はもう当たっていないためです (`live-adapt.ts` の `replacesWarning`)。

#### エンコードが遅れたとき

**ライブのエンコードが実時間に追いつかなければ、サーバが段を下げずに軽い組み合わせで作り直します**（`server/live.ts` の `Session.lighten`）。
画面は指示を送らず、断り書きを出すだけです。

- **決めるのはサーバです。** エンコードの速さ（`pace` の `speed`）が 0.95 を切ったまま 5 秒続いたら、1 つ軽くします（`ENCODE_SLOW`・`LIGHT_LAG`）。0 は測れていない値とみなします。
  1 ちょうどにしないのは、塊の届き方で 1 の前後に揺れるためです。速さはセッションのエンコードの値で、観ている人の端末の都合ではありません
- **軽くする順は 60 コマ → 30 コマ、ソフトウェア → GPU です**（`nextLight`）。
  - 30 コマは段 0 の放送だけです（インタレ解除を `bwdif=mode=send_frame`・`deinterlace_vaapi=rate=frame` にし、`-g 30`）。段 1〜3 はもう 30 コマです
  - GPU は、同じコーデックを GPU でエンコードできるのにソフトウェアで動いているときだけです（同時に開ける数を超えてソフトウェアに降りた、など）。
    GPU を試すのは 1 回で、また降りても試し直しません
  - どちらも済んでいれば何もせず、画面は「サーバのエンコードが追いつかないため、再生が止まります」を出します
  - コーデックが替わる軽くし方（ソフトウェアの AV1 → GPU の H.264 など）はしません。共有の目印が変わるので、観る人がコーデックを選び直します
- **共有しているセッションは全員に効きます。** 同じセッションを観ている人は同じ遅れを受けているためです。断り書き（`notice`）のあとに
  `restart` を送り、全員にリクエストし直させます（番組が替わったときと同じ。途切れるのはエンコードし始めのぶん）。軽くしたものは
  作り直した次のセッションが受け継ぎ（30 秒以内。`keepLight`・`takeLight`）、そのセッションが閉じるまで戻しません
- **ライブだけです。** 追っかけは録画の書き込みを待つ間も速さが 1 を割るので、エンコードの遅れと読み分けられません。観る画面の変換
  （HTTP）も軽くしません。実時間より速く読むので、遅れは先のバッファで吸収できるためです

## 4K の局のライブ

**4K の局 (ケーブルで受けた MMT/TLV の局) は TS を経由しません。放送の HEVC と AAC は denpa が fMP4 に詰め替え、再生できる端末にはそのまま送り、
再生できない端末と回線が足りないときは、縮めてエンコードします。** エージェントは形式を変換せず、変換はサーバがします。

```text
エージェント (TLV。チャンネル丸ごと)
  → MmtServiceFilter (1 局に絞る。TLV のまま)
      ├→ HTTP の codec=raw (1 局に絞った TLV)
      └→ MmtMediaReader → MmtFmp4 (HEVC + AAC の fMP4)
           ├→ WebSocket → MSE                                              (hevc。エンコードしない)
           ├→ ffmpeg (縮める・HLG を SDR に・エンコード) → WebSocket → MSE  (h264・av1。段 1〜3 も)
           └→ TTML → 文字の配置 ─────────────────────→ WebSocket (0x22)
```

入口は `server/live-mmt.ts` の `MmtLive` で、ffmpeg を起こし直すたびに作り直します (fMP4 は init から出し直し、時刻 0 も数え直す)。
時刻 0 は最初に使う映像の頭出しできるコマの DTS です (`mp4/mmt.ts` の `MmtFmp4.origin`)。

**「放送のまま」は放送のコーデックを指します** (`#lib/live-choice.ts` の `BroadcastCodec`)。MPEG-2 の局は MPEG-2、4K の局は HEVC の詰め替えです。

- 自動の順は、放送のまま (MPEG-2) の場所に HEVC を入れたものです。家の中は HEVC → H.264 → AV1、外は AV1 → H.264 ([どの形式で流すか](#どの形式で流すか))。
  外で放送のままを選ばないのは MPEG-2 の局と同じで、4K の HEVC は 1 局で約 33Mbit/s あります (推定)
- **H.265 にはエンコードしません。** 4K の局の `hevc` は詰め替えだけを指し、GPU は要りません。メニューの「MPEG-2」の行は、4K の局では「H.265」と出します
- HEVC を再生できるかは、MSE で受け取れるか (`isTypeSupported`) に加えて、`mediaCapabilities.decodingInfo` に放送の値 (3840x2160・59.94 コマ・10 ビット・HLG・BT.2020) を
  渡して決めます (`#lib/hevc-4k.ts`)。受け取れると答えても 4K の 10 ビットをデコードできない端末があるためです (推定)。画面は 4K の局を初めて開くときに 1 回だけ調べます
- 渡す codecs は `hvc1.2.4.L153.B0` (Main 10・Level 5.1) と AAC です (`#lib/live.ts` の `BROADCAST_HEVC`)。入れ物の中の名前は `hvc1` で (Safari は `hev1` を受け取らない)、VPS・SPS・PPS は `hvcC` にだけ置きます。
  放送はコマの中にも送ってくるので、`hvcC` に入れたものと同じならサンプルから外します。違うものが来たら (番組が替わって符号化の設定が変わった、など) init から作り直します (`mp4/mmt.ts` の `parametersChanged`)。録画 (`.mmts`) は 1 本の fMP4 にするので作り直さず、違うものはサンプルに残します
- 局の行の伝送の形式 (`services.transport`) から決めます。画面は局の一覧の `broadcast` で知り (`live/+page.server.ts`)、サーバは選局の指示の
  `raw` を 4K の局では `hevc` に読み替えます (`live.liveForm`)。TS で送る 4K の局は局の行では分からず、PMT を読んでから決めます ([下](#ts-で送る-4k-の局))

**回線が足りないときは、今の段の仕組みのまま AV1 か H.264 に移ります** ([回線に合わせて画質を下げる](#回線に合わせて画質を下げる))。

- 詰め替えた HEVC には段がありません。段を下げるときのコーデックは、`playable` から H.265 を外して選びます (`live.liveRungCodec`)
- ffmpeg の入力は詰め替えた fMP4 (標準入力) で、局は 1 つなので番号で名指ししません (`-map 0:v:0`)。字幕の出口も付けません
- 段 0 は 1080p・60 コマ、段 1〜3 は段の高さと 29.97 コマに縮めます (`live.uhdVideoArgs`)。インタレ解除はしません (プログレッシブ)
- **縮めたあとで HLG (BT.2020・10 ビット) を SDR (BT.709・8 ビット) に直します** (`HLG_TO_SDR`)。入力の色の扱いは `setparams` でコマに書き込み、
  `zscale` で光の量に戻して BT.709 の色域に移し、`tonemap=hable` で明るいところを丸めます。映像の VUI に頼ると、色の印の無い映像で zscale が
  止まります (`no path between colorspaces`)。4K の放送は HLG で送っていると見ています (推定)。トーンマップの画質は実際の放送で見ていません
- デコードは CPU です。4K の HEVC 10 ビットを実時間でデコードできるかはサーバの CPU で決まり、遅れたら今の決まり ([エンコードが遅れたとき](#エンコードが遅れたとき)) で軽くします。
  VA-API などでデコードから GPU に載せることはまだしていません
- zscale (libzimg)・tonemap は、イメージと Mac・Windows の配布物の ffmpeg のどれにも組んであります

**字幕は ffmpeg を通しません。** MPU の TTML の文書を denpa が文字の配置にして (`@danything/arib/ttml`)、TS の字幕と同じ `0x22` で送ります。

- 時刻は詰め替えた fMP4 の物差しです。ffmpeg に渡したときは、ffmpeg が入力で 0 に寄せたぶん (`start:`) を引きます。
  入力の始まりは 0 の近く (B ピクチャのずれぶん。合成の素材で 0.033 秒) なので、TS の経路のように同じ ffmpeg から字幕を受けなくても、
  映像と字幕は同じ物差しに乗ります (推定。実際の放送の字幕では測っていない)
- 選べる字幕は、MPT に字幕のアセットがあれば「字幕」1 つです

そのほかの決まり。

- **時計は放送の提示時刻から作ります。** MMT には PCR が無いので、映像のコマの時刻と、MPU タイムスタンプ記述子が言うそのコマの提示時刻 (NTP) を組にします
  (`MmtOut.anchor`)。`clock` の通知の形は TS の局と同じです
- 音声は MPT の最初の音声のアセットだけです。詰め替えでは選べず (放送のまま)、エンコードするときはデュアルモノの左右を選べます
- 番組が替わってアセットの並び (MPT) が変わったら、TS の PMT と同じく作り直します ([番組が替わって並びが変わったら作り直す](#番組が替わって並びが変わったら作り直す))
- 映像・音声がスクランブルされたまま届いたら (ACAS)、「4K の放送のスクランブル (ACAS) には、まだ対応していないため観られません」を伝えて畳みます。
  決め方は TS の局と同じです ([上](#エンコードできなくなったらその場で言う)。500 個ずつ数え、3 秒続いたら止める)。数えるのは局の映像・音声・字幕の MMTP のパケットです (`MmtMediaReader.media`)。
  ふつうは選局の前に断っています (ACAS の局は `services.decodable` が false)
- 番組の切り替わりと延長には、TS の局と同じく追従します。観ている局の MH-EIT[p/f] を読み (`@danything/arib/mh-eit` の `MmtPresentFollowing`)、
  番組表と違えば番組表に写して `programs` を通知します (`live.followTlv` → `epg.followOnAir`。[data.md](data.md#放送の延長に追従する))。
  詰め替え・エンコード・HTTP の `codec=raw` のどれでも読み、追っかけでは読みません
- データ放送・Hybridcast は、4K の局ではまだありません
- **録画は 1 局に絞った TLV のまま `.mmts` で置きます** ([library.md](library.md#4k-の局の録画))。実際の 4K の放送は ACAS でスクランブルされていて、
  どの局もライブにも予約にも出ません

**録画中の 4K の局の録画も、追っかけで観られます** (`/chase/<id>`。HTTP は `GET /api/recordings/<id>/chase`)。伸びている `.mmts` を追い読みして
(`chase.followFile`)、ライブの 4K の局と同じ `Session` に流し込みます (`live.openChase` の `transport`)。

- 放送のまま (画面の「H.265」、HTTP の `codec=hevc`) は放送の HEVC と AAC の詰め替え (`runMmt`)。ffmpeg も変換の枠も使わない。HTTP の `codec=raw` は 1 局に絞った TLV
  (`application/x-arib-tlv`)
- H.264・AV1 は詰め替えた fMP4 を ffmpeg に渡して、縮めて SDR にする (ライブと同じ `uhdVideoArgs`)。段を下げるときも H.265 にはエンコードしない (`liveRungCodec`)
- 画面は録画の放送のコーデックを追っかけのページから知る (`chase/+page.server.ts` の `broadcast`)。HEVC を再生できるかの決め方はライブと同じ
- 番組が替わってアセットの並びが変わったら、読んだところから作り直す (`chase.resumeFrom`。TS の追っかけと同じ)。読み切ったら `ended` を伝えて閉じる

確かめたのは合成の素材 (ffmpeg で作った HEVC Main10 と AAC を `@danything/arib/synth-mmt-av` で MMT/TLV に包んだもの) だけです。
偽エージェントはスクランブルしていない 4K の局 (QC28) でこれを流します。

### TS で送る 4K の局

**ケーブルの 4K の局には、HEVC を TS に入れて送る局があります。サーバは選局して PMT を読み、映像が HEVC (stream_type 0x24) なら 4K の局と同じに扱います。**
報告のあった局 (J:COM の QC14 など) は HEVC Main 10・3840x2160・59.94 コマ・BT.2020/HLG と、AAC の LATM (stream_type 0x11) でした (issue #2729)。

- 局の一覧では MPEG-2 の局と見分けられません。局の行にも覚えず、セッションを開くたびに PMT を読みます (`captions.ts` の `peekPmt`・`pmtVideo`)
- 放送のまま (`raw`) をリクエストされたら、元の TS ではなく HEVC の詰め替えを送ります (`live.servedFormat`)。画面の MPEG-2 のデコーダ (WASM) は HEVC をデコードできないためです。
  詰め替えは ffmpeg で、映像は写し (`-c:v copy -tag:v hvc1`)、音声だけ AAC にエンコードします (MSE は LATM を受け取らない)。GPU も、その場で変換する本数の枠も使いません
- `hevc` をリクエストされたときも同じく写します (`live.copiesVideo`)。H.265 にエンコードはしません。
  段を下げた `hevc` は写せないので、PMT を読んでから 4K の局として段を下げるコーデックを選び直し (`live.liveRungCodec`)、選局の答えで知らせます。
  端末が再生できる形式を言っていなければ (画面の WebSocket・`?playable=` の無い HTTP) `h264` です。追っかけは開く前に形式を決めます ([下](#ts-で送る-4k-の局の録画))。HTTP の `?codec=hevc` は、GPU で H.265 を出せなければ選局の前に `h264` になります (`viewing.askedFormat`)
- `h264`・`av1` は 4K の局と同じく、インタレ解除をせずに 1080p (段を下げれば段の高さ) に縮め、HLG を SDR の 8 ビットに直してエンコードします (`live.uhdVideoArgs`)。
  デコードは CPU で、GPU でエンコードするときも直したものを上げて渡します。MPEG-2 の局と同じ経路 (`deinterlace_vaapi`・GPU のデコード) を通していた頃は、
  VA-API が `Error reinitializing filters` で止まり、ソフトウェアに降りていました
- 写すときは `-probesize` を 5MB にし、mp4 の `delay_moov` を付けます。mp4 のマルチプレクサは映像の大きさと VPS・SPS・PPS を知ってから書き始めるので、
  MPEG-2 の局の 100KB では足りないと見ています (推定)
- 字幕は MPEG-2 の局と同じく、同じ ffmpeg から受けます

**画面には、セッションが PMT を読んだあとの選局の答え (`tuned`) で知らせます。** 答えに `broadcast: "hevc"` を付け、放送のままをリクエストされていれば
`codec: "hevc"`・`raw: false` で答え直します (`Session.switchFormat`)。まだ何も送っていないので、画面は MPEG-2 のデコーダを畳んで MSE で受け直します。

- 画面はその局を開いている間、`Tuned.broadcast` を `hevc` にします。メニューの「MPEG-2」の行は「H.265」になり、自動の順も 4K の局のものになります。
  次からの指示にも `broadcast` を付け、サーバは選局の前から放送のままを HEVC の詰め替えとして受けます (`attend`)。局を替えると局の一覧の値に戻ります
- HEVC を再生できるかは、答えを受けてから 4K の局と同じ決め方で調べます (`#lib/hevc-4k.ts`)。再生できなければ H.265 をやめて次の形式に移ります
- 放送のままと段を下げた `hevc` で、送る前に PMT を読むのは、ケーブル (`CATV`) の局だけです (`Session.readsVideo`)。TS で送る 4K の局はケーブルにしか無く、
  ほかの局の HTTP の応答ヘッダを PMT まで待たせないためです
- HTTP のライブの `codec=raw` は、`?playable=` を付けたときだけ替えます。付けないものは今までどおり元の TS で、替えるものとは別のセッションにします
  (`Session.keepsTs`。目印の `key` も分ける)。画面の外のものにとって `raw` は元の TS だからです
- HTTP のライブは、PMT を読んでから応答ヘッダを返します (`live.liveServed`)。放送のままでも `X-Denpa-Codec: hevc` と `video/mp4` です。
  `?playable=` に `hevc` が無ければ `h264` (無ければ `av1`) をエンコードし、どれも無ければ「再生できる形式がありません」で畳みます
  ([api.md](api.md#ライブ-get-apiservicesidlive))。待つ間に切られたら、ストリームを閉じて抜けます
- 同じ局の放送のままを、HEVC を再生できる端末とできない端末が同時に観ると、先に開いた端末の答えで共有します。できない端末は、MSE が受け取れずに次の形式に移ります

確かめたのは引数とリクエストの扱いのテストだけです。実際の放送の TS で、写した HEVC を画面と ffmpeg で再生できるかは確かめていません。
VPS・SPS・PPS はコマの中にも残ったまま送るので、`hvc1` として受け取らない端末があるかもしれません (推定)。

#### TS で送る 4K の局の録画

**TS で送る 4K の局の録画も TS (`.m2ts`) で、拡張子では 4K の局と分かりません。追っかけと録画の観る画面は、開く前に録画の先頭の PMT を読んで決めます**
(`recorded-broadcast.ts` の `recordedBroadcast`)。映像が HEVC なら、4K の局の録画 (`.mmts`) と同じ決め方で形式を選びます。開いたあとで形式を替える仕組みは持ちません。

- 読むのは録画の先頭 4MB までです。その局 (`services.service_id`) の PMT が無ければ、今までどおり MPEG-2 の局の録画として扱います。
  録り始めたばかりで PMT がまだ書かれていない録画は、5 秒置いてから開くときに読み直します (`UNDECIDED_WAIT`。同期で読むので、続けて開き直すたびには読まない)。PMT を読めた録画は、録画のパスごとにメモリに覚えます (局の行にも録画の行にも持たない)
- 追っかけ (`live.chaseForm`) は、段 0 の `hevc` と画面の放送のまま (`raw`) を、放送の HEVC を写したものにします (ライブと同じ `copiesVideo`。変換の枠を使わない)。
  段を下げた `hevc` は、端末が再生できる形式 (`playable`) から H.265 を外して選び直します。`h264`・`av1` は縮めて SDR にします (`uhdVideoArgs`)。
  セッションには録画の放送のコーデックを渡すので、PMT を読み直す前から 4K の局の引数で起こします (`Session` の `broadcast`)
- 開く前に PMT を読めず MPEG-2 の局として段を下げた `hevc` を選んだ追っかけは、セッションが PMT を読んで HEVC と分かった時点で止めます
  (写すと段を見ずに 4K の HEVC を送るため)。画面は段を下げた H.265 が降りたときと同じく、H.265 を外して同じ段をリクエストし直し、そのときサーバは PMT を読み直します
- HTTP の追っかけ (`GET /api/recordings/<id>/chase`) は、`auto` と段の選び方を 4K の局のものにします (`live.chaseMedia`)。`codec=raw` は元の TS のままです
- 録画の観る画面 (`playback.ts`) は、エンコード済みが無ければ `hevc` (映像を写して音声を AAC にしたもの。`tsTranscodeArgs`) と、縮めて SDR にした `h264`・`av1` を出します。
  `mpeg2` (元の TS) は出しません。自動の順は 4K の局の録画と同じです (`broadcast: "hevc"`)
- ライブがチューナーを譲った録画の追っかけ (`live-yield.ts`) も、同じく録画の PMT で放送のコーデックを決めます。録り始めたばかりで読めなければ MPEG-2 で、
  追っかけを開くときにサーバが読み直します

確かめたのは合成した TS (PAT と、映像が HEVC の PMT) でのテストだけです。実際の放送の録画で、写した HEVC を再生できるかは確かめていません。
エンコード (`encoder.ts`) はまだ拡張子だけで 4K の局の録画を見分けていて、TS で送る 4K の局の録画は MPEG-2 の局の録画として変換します。

## 字幕

**映像と同じ ffmpeg から、字幕をデコードせずに写して受け取る。出口を 2 つ持つ** (`src/lib/server/captions.ts`)。
デコードして置き場所を決めるのは denpa (`packages/arib/src/b24caption.ts`)、描くのはブラウザ (`components/player/caption-draw.ts`)。

```bash
ffmpeg <上の映像の引数と同じ> -i pipe:0 \
    ... pipe:1 \
    -map 0:p:<局>:s:<n> -c:s copy -cluster_time_limit 1 -cluster_size_limit 1 \
    -flush_packets 1 -f matroska pipe:3
```

**ここも引数の並びだけ**。値は `captionOutput` の説明にある。

- **写すだけ** (`-c:s copy`)。Matroska には ARIB の字幕がそのまま (`S_ARIBSUB`) 入る
- **局を名指しする。** 映像と同じ理由
- 受けたコマをデコードして文字の配置にし (`CaptionText`)、0x22 で配る。**デコードして出てくるのは字幕が変わったときだけ**
  (字幕管理データや送り直しは何も出さない) なので、間引く必要も無い。同じ録画の 103 秒で、デコードの手間は 218 コマで 6ms

### 1本にしたのは、時刻を揃えるため

ffmpeg は入口で時刻を 0 に寄せ直すが、**寄せ幅はプロセスごとに違う。** 別々に起こした 2 本はエンコードし始めのキーフレームがずれ、
出てきた時刻どうしを突き合わせても意味が無い。`-copyts` で放送の絶対時刻を保っても、mp4 のマルチプレクサがその時刻を
0 に詰め直す (`-avoid_negative_ts disabled` も `-muxdelay 0` も `-output_ts_offset` も効かない)。
1 本にすれば入口の寄せが 1 回で済み、両方の出口に効く (実機で 1ms 以内。実測は `captions.ts`)。
別々の ffmpeg で測って合わせようとして外した記録は [stream-history.md](stream-history.md#字幕の時刻を測って合わせようとした頃)。

引き換えに、音声やエンコード方式を選び直すと別のセッションになり、字幕の出口も別になる。新しいセッションの字幕は次の 1 枚が
来るまで出ない。同じ組をほかの人がもう見ていれば、いま出ている 1 枚をすぐ渡す。

> [!NOTE]
> **字幕を持たない放送はある** (ショッピングやサブチャンネル)。そこに `0:p:X:s:0` を
> 指定すると ffmpeg は入口を探り終えてから終了し、映像も出ない (`-map …?` でも、字幕の出口が空になって終了する)。
> だから **ffmpeg を起こす前に PMT を読み**、字幕の ES が無ければ字幕の出口を指定しない (`server/captions.ts` の `peekPmt`。追っかけも同じ)。
> PMT を 3 秒で読めなかったときは指定し、終了したら字幕なしで起こし直して、その局を 15 分覚えておく (`server/live.ts` の `captionless`)。
> 起こし直すと映像が 1.5 秒ほど遅れる。放送のままの経路は映像が ffmpeg を通らないので、字幕の ffmpeg が終了しても映像は遅れない。

### 時刻はコマに付けて運ぶ

字幕を並べただけでは時刻が乗らないので、**コンテナに入れて運ばせる。** Matroska は使うところだけなら小さい。
`src/lib/ts/mkv-media.ts` の `MkvDemuxer` (`ts/mkv.ts` が使う) が読むのは `TimestampScale` / `Cluster > Timestamp` / `SimpleBlock` と `BlockGroup > Block`、
それに中身の種類 (`CodecID`) だけ。NUT はコマの見出しを組み立てるのに表の復元が要り、mp4 は ARIB の字幕を入れられない。

塊の上限を最小 (`-cluster_time_limit 1` / `-cluster_size_limit 1`) にして、1 枚ごとに書き出させる。溜められるとそのぶん遅れる。

### エンコード方式ごとに分かれる

字幕はエンコード方式 (音声・コーデック・何本目の字幕か) ごとに分かれる ([共有の単位](#入っているもの))。
**その代わり TS をもう 1 本もらわずに済む** (チューナーの共有をもう 1 つリクエストしなくてよい)。

> [!NOTE]
> **字幕が 1 枚も来ない番組はある** (本編に字幕が無ければ 0 枚。異常ではない)。ボタンを出すかは届いた枚数では
> なく、ffmpeg の入口の見出しで決める (`TrackList`)。届いてから出すと、間隔の空く番組でボタンが出ない。持っていない放送では出さない。

### 言語は全部デコードして、出す言語を人ごとに選ぶ

**ARIB の字幕は 1 本の中に最大 8 言語を持てる** (データグループの番号 1〜8。何番がどの言語かは字幕管理データに ISO 639 の
3 文字で書いてある)。ffmpeg は字幕をデコードせずに写すので、**全部の言語が denpa まで届いている。**

- **デコードは言語ごと** (`CaptionText`)。書式・位置・色は言語ごとに別に続くので、デコーダを言語の数だけ持ち、
  同じコマを全部に渡す。第 2 言語から後ろは字幕管理データに出てきてから作り、最後の字幕管理データを先に渡す
- **ライブと追っかけは視聴者ごとに選ぶ** (`Viewer.language`。既定は第 1 言語)。共有しているセッションでも
  再エンコードしない。選び直しは `{"type":"language","language":2}` で、いまのその言語の 1 枚 (無ければ空の 1 枚) が届く。
  `tune` / `chase` にも `language` を添えられる (繋ぎ直しても続くように)
- **載っている言語は `captions` の通知の `languages`** (字幕管理データが届いてから。対応していない受け側は読み飛ばせばよく、
  そのときは第 1 言語だけが届く)
- **録画 (`captions.json`) は全部の言語を 1 度に返す。** 第 1 言語は `pages`、第 2 言語から後ろは `others`。
  端末に保存したコピーにも全部の言語が入る (前に保存したものは第 1 言語だけ)
- **画面は言語の名前 (ISO 639) で端末に覚える** (`components/player/caption-pref.ts`)。第何言語かは番組ごとに違う。
  覚えた言語が載っていなければ第 1 言語。字幕の出し入れも同じく端末に覚える

> [!NOTE]
> **字幕のストリームが 2 本以上ある放送** (`TrackList`) の 2 本目から後ろは、ライブと追っかけでは選べる (再エンコードになる) が、
> エンコードした録画には 1 本目 (`s:0`) しか入れていない。録画で選べるのは 1 本目の中の言語だけ。

## WebSocket プロトコル

単一接続で全チャネルを多重化する。

```
[1 byte: channel][8 bytes: 時刻 (90kHz, BE)][payload...]

channel:
  0x00  video init segment (ftyp + moov)
  0x01  video media  (moof + mdat)。音声も同じ fMP4 に入る
  0x02  元の TS      1 局に絞った TS そのまま ([放送そのまま（MPEG-2）を送る](#放送そのままmpeg-2を送る))。時刻は 0。init は無い
  0x22  字幕の文字の配置  JSON (api.md「字幕の文字の配置」)。前の 1 枚を丸ごと置き換える
  0x30  データ放送   ResponseMessage (JSON。`packages/arib/src/bml-protocol.ts`)。時刻は 0
  0x40  制御         ここだけ双方向の JSON (選局・追っかけ・データ放送・字幕の言語・追っかけの送信の停止と再開 (hold) の指示 / tuned・字幕一覧・時計 等の通知)。時刻は 0
  (0x10・0x11 は以前の音声だけの fMP4、0x20・0x21 は以前の字幕の画像と「字幕を消す」。番号は空けておく)
```

- init セグメントは接続直後に必ず送る（再送用にサーバ側で保持）
- MSE はバイト列をそのまま `appendBuffer()` に渡せるので、映像音声のパースは不要
- 字幕の座標は字幕の面 (`plane`。ふつう 960x540) の単位。受け側は映像の枠に合わせて伸ばし、画面の画素で描く
- **ヘッダの時刻は「エンコードした mp4 の物差し」。** 映像も音声も字幕も同じ ffmpeg が書き出すので、
  受け側の `video.currentTime` と直に比べられる（[時刻同期](#時刻同期)）
- **放送のままの経路（0x02）では、字幕の時刻は放送の PTS そのまま**（[放送のままのときの字幕](#放送のままのときの字幕)）
- 途中から入ってきた視聴者のために、いま出ている字幕はサーバが言語ごとに 1 枚保持して再送する

**段の指示と `pace` の通知** ([回線に合わせて画質を下げる](#回線に合わせて画質を下げる))。型は `#lib/live.ts` の `TuneCommand`・`ChaseCommand`・`Notice`。

```jsonc
// 画面 → サーバ。rung は 0〜3 (省けば 0)。playable は端末が再生できるコーデック (省けば codec と h264)
{ "type": "tune", "channelType": "GR", "channel": "T27", "serviceId": 1, "codec": "av1", "rung": 2, "playable": ["av1", "hevc", "h264"] }
{ "type": "chase", "recordingId": 12, "at": 600, "rung": 1, "playable": ["hevc", "h264"] }
// 音声だけ (選局だけ。rung を 1〜3 にすると音声は 96k)
{ "type": "tune", "channelType": "GR", "channel": "T27", "serviceId": 1, "codec": "audio", "rung": 3 }

// サーバ → 画面。tuned に、いまの段 (rung) とサーバが選んだコーデック (codec) が入る
{ "type": "tuned", "channelType": "GR", "channel": "T27", "codec": "hevc", "codecs": "video/mp4; codecs=\"hvc1.1.6.L123.B0,mp4a.40.2\"", "raw": false, "rung": 2, "audio": "0:both", "audios": [] }
// 枠が埋まっていて下げられなかったとき (tuned の rung はリクエストより高い)
{ "type": "notice", "message": "サーバが混んでいるため、画質を下げられませんでした" }
// 2 秒ごとか、塊を捨てた・バッファが動いたとき。dropped は前の pace からの数、speed はエンコードしない経路と測れるまでは null
{ "type": "pace", "backlog": 1048576, "dropped": 3, "speed": 0.92 }
```

## 時刻同期

| 対象           | 方法                                                                                                                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 映像・音声     | fMP4 の timescale で自動的に整合                                                                                                                                                         |
| 字幕           | 添えられた時刻（映像と同じ ffmpeg が付けた mp4 の物差し）に置く。出しておく長さ (`duration`) があれば過ぎたら消す                                                                        |
| データ放送     | カルーセルは時刻同期不要（PMT/TOT と denpa の番組表の更新に追従）                                                                                                                        |
| 実況のコメント | `clock` の通知から、映しているコマの放送時刻を出し、そこまでに書かれたものを流す ([watch.md](watch.md#実況のコメント))。録画は録画の先頭の放送時刻 (`recordings.ts_head`) と再生位置から |

**測っていません。** 字幕のコマに付いてくる時刻を再生位置と比べ、「追い越していない中の最後の 1 つ」を出すだけです
（`ts/captions.ts`）。映像と字幕を同じ ffmpeg が書き出しているので揃います（[字幕](#字幕)）。

- **貼り直すのは映した 1 枚ごと**（`live-player` の `follow`）。届いた塊に合わせると、遅れる方向にだけ 0〜50ms ずれる
- **再エンコードのたびに、待たせている字幕は捨てる**（`forget`）。mp4 の時刻が 0 から数え直しになるため
- **`clock` の対応も ffmpeg ごとに作り直す**（`live.ts` の `startPts`）。0 に寄せる量は起こし直した時点の PTS になるので、前の値のままだと起こし直すまでに流れた秒数だけ放送時刻がずれる。新しい `start:` が読めるまでは配らず、読めたら次の塊で配る

## 放送そのまま（MPEG-2）を送る

**ブラウザでエンコードせずに見られます。** 1 局に絞った TS をそのまま
WebSocket に流し、ブラウザが WebAssembly の MPEG-2 デコーダでデコードして WebGL2 で描き、音も
同じ WebAssembly の AAC デコーダでデコードして Web Audio で鳴らします (バックグラウンド再生をオンにしている間は
`<audio>` を通す。下の「時計は鳴っている音」)。**家の中から「自動」で開いたときと、コーデックのメニューで MPEG-2 を選んだとき**に
放送のまま送ります ([どの形式で流すか](#どの形式で流すか)。選んだものはエンコード方式と同じく端末ごとに覚える。`LAST_COOKIE`)。

```
エージェント → 1局に絞る ┬→ WebSocket (0x02 元の TS) → worker ┬→ PES → WASM (mpeg2video) → WebGL2 (インタレ解除)
                         │                                    └→ ADTS → WASM (aac) ─→ 画面 → Web Audio (時計) [→ <audio>]
                         ├→ ffmpeg (字幕を写すだけ。-copyts) → デコードする → 0x22 文字の配置 (放送の PTS のまま)
                         └→ BmlDecoder → 0x30 データ放送 (エンコードする経路と同じ)
```

**ブラウザに MPEG-2 のデコーダは無い**ので持ち込んでいます (Chromium 151 で `MediaSource.isTypeSupported`・
`VideoDecoder.isConfigSupported` とも `mp2v` / `mpeg2video` は ×。`video/mp2t` が ○ なのは中身が H.264 の TS の話)。

得るもの: **ffmpeg の立ち上がり ([内訳](#開いてから映像が出るまでの内訳)で 40〜270ms) と、エンコードするのに掛かっているぶんが丸ごと消え**、サーバの CPU も
350〜470% からほぼ 0 になります (字幕を写す ffmpeg だけ残る)。残る遅れは受け側のバッファ (`ts/pacing.ts` の `FLOOR` から始まるバッファ) だけです。

### いつ放送のまま送るか

2 つが揃ったときだけ。決めるのは画面です。

|                                                                                           | 誰が見る                                                    | 外れたら                                                                         |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------- |
| コーデックのメニューで MPEG-2 を選んでいる、か「自動」で家の中から開いた                  | 画面 (`LAST_COOKIE` の `choice` と、サーバが決めた家の中か) | いつもどおりエンコードする                                                       |
| その端末でデコードできる (WebAssembly・worker の OffscreenCanvas と WebGL2・AudioContext) | 画面 (`raw/support.ts`)                                     | エンコードしたものをリクエストする (MPEG-2 を選んでいたなら理由を断り書きに出す) |

**家の外からでも (MPEG-2 を選べば)、http で開いた LAN でも放送のままで見られます。** 回線が 1 局ぶん (下の「払うもの」) 出るかは見る人が決める。
足りない回線では貯め直しを繰り返し、音が 5 秒来なければエンコードしたものへ戻ります。音を WebCodecs の AudioDecoder ではなく
映像と同じ FFmpeg でデコードするのは、AudioDecoder が https か localhost でしか出てこず、ブラウザごとの癖もあるため
([stream-history.md](stream-history.md#mpeg-2-の音を-audiodecoder-でデコードしていた頃))。WebAssembly の無い端末
(iOS の Gecko など) は「WebAssembly が使えません」と出してエンコードしたものに戻ります。

**放送のままで見ている途中でも、エンコードしたものへ自分で戻ります** (戻したら、その画面を開いている間は
リクエストし直さない。戻しては打ち切るを繰り返すと、そのたびに映像が止まる):

- デコードするのが間に合わない (下の「間に合わないとき」)
- デコーダが入っていない (`/api/live/mpeg2` が 404)・worker が落ちた
- 映像は出ているのに音が 5 秒来ない・AAC のデコードが壊れたコマで 20 回を超えて続けて失敗する (1 回なら飛ばす)

### デコーダ

FFmpeg の **mpeg2video のデコーダとフレームの区切りを探す parser、AAC のデコーダだけ**を emscripten で組んだもの
(`wasm/decoder.c`。互換モードの音のために Opus のデコーダと、それが当てにする swresample も入っている)。AAC の parser は組まない。
ADTS の区切りと時刻は JS (`packages/arib/src/pes.ts` の `AdtsSplitter`) が付け、デコーダは ADTS ヘッダを自分で読む。音も映像と同じ worker でデコードする
(1 秒ぶんで数 ms)。**Dockerfile の `mpeg2wasm` 段で毎回組み**、git には入れません (生成物を抱えると FFmpeg を上げるたびに差し替えが要り、
組んだ手順と中身が食い違っても気づけない)。FFmpeg はサーバの ffmpeg と同じバージョンに揃え、emsdk はバージョンで固定しています。置き場はアプリの外
(`/opt/denpa/mpeg2`、`MPEG2_DIR`) で、`/api/live/mpeg2/<名前>` から配ります。開発と E2E の compose はソースを `/app` に被せるので、
中に置くと隠れます。

|                                    |                                                                                                                                                                                                                                  |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 大きさ                             | `decoder.wasm` 1,090KB (brotli 354KB。FFmpeg 9.0.2・emsdk 6.0.13 で測った) + 読み込み用の `decoder.mjs` 12KB。**配るときは denpa が縮める** (`Accept-Encoding` を見て brotli か gzip。中身が変わったときに 1 度だけ縮めて覚える) |
| 速さ (手元の Chromium、ヘッドレス) | デコードだけで 1920x1080i が **210〜240 コマ/秒**、1440x1080i が 320〜380 コマ/秒で、**実時間の 7 倍ほど** (下の「どこに時間が掛かっているか」)                                                                                  |
| 音の速さ (同じ)                    | AAC-LC 48kHz の音 1 秒で **ステレオ 256kbps 1.0〜1.6ms、5.1ch 384kbps 2.3〜2.9ms**                                                                                                                                               |
| 組む時間                           | 2 分ほど (amd64 / arm64 どちらのランナーでも)                                                                                                                                                                                    |
| **GPU が無いとき**                 | 描くほうが間に合わない。ソフトウェアの WebGL (SwiftShader) では 10〜14 コマ/秒しか出ず、3 秒ほどでエンコードしたものに戻る。E2E が通るのは映像が小さい (256x144) から                                                            |

**スレッドは使いません。** 測ると、はっきり速くなるのはスレッドだけですが、要る COOP/COEP が効く端末が限られるので見送りました
([スライスのスレッドを見送った理由](#スライスのスレッドを見送った理由))。
**SIMD (`-msimd128`) と LTO (`-flto`) は掛けます** (効き目は [組み方の測定](stream-history.md#wasm-のデコーダの組み方を決めたときの測定))。

### どこに時間が掛かっているか

**端末の CPU を使うのは、ほぼ WASM の MPEG-2 のデコードだけです。** 描くのは GPU の仕事で、GPU のある端末では CPU にほとんど乗りません。
GPU の無い端末では、描くほうが桁違いに重くなります (上の「GPU が無いとき」)。

測り方: ヘッドレスの Chromium 156 (12 スレッドの PC の上のコンテナ。GPU 無しで、WebGL は SwiftShader) に、ffmpeg で作った
20 秒の 1080i の MPEG-2 TS (17Mbit/s・GOP 15・B 2 枚。testsrc2 の 1440x1080i、mandelbrot の 1920x1080i、雑音を足した 1920x1080i) を流し、
denpa の `PesDemuxer`・`AdtsSplitter`・`YuvRenderer` と Dockerfile と同じ手順で組んだデコーダに通して、段ごとに `performance.now()` で測った。
測るたびに 2〜3 割揺れるので、数字は数回の中央値か幅です。**描く段の数字は SwiftShader のもので、本物の GPU での重さの参考にはなりません**
(1 画素読み出して GPU の仕事が終わるのを待ってから測っている。待たないと SwiftShader は描かずに済ませる)。

| 段                                                                       | 1 コマあたり (1440x1080i / 1920x1080i)                                    | 1 コアに占める割合 (29.97 コマ/秒) |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------- | ---------------------------------- |
| TS → PES (JS の `PesDemuxer`。音のパケットも込み)                        | 0.25〜0.30ms                                                              | 1%                                 |
| PES を WASM のメモリへ写す                                               | 0.01ms                                                                    | —                                  |
| **MPEG-2 のデコード (WASM)**                                             | **平均 2.6〜3.1ms / 4.1〜4.6ms**。95 パーセンタイル 5〜6ms / 7〜9.5ms     | **8〜14%**                         |
| 3 面をテクスチャに上げる (`texSubImage2D` を 3 回。1 コマ 2.3MB / 3.1MB) | 1.0〜1.3ms (SwiftShader。GPU の仕事が終わるまで込み)                      | GPU の経路                         |
| 描く (インタレ解除の入ったシェーダ。1 コマで 2 回)                       | 1 回 31ms (SwiftShader)。インタレ解除しない素通しのシェーダでも 1 回 20ms | GPU の仕事                         |
| 音 (ADTS → AAC → 面ごとに写して画面へ)                                   | 音 1 秒で 1.2〜2.2ms                                                      | 0.2%                               |

重い順に、**デコード → テクスチャに上げる → TS → PES** です。写す回数はもう削ってあります:

- 圧縮のままのものは 2 回写す (PES の入れ物に足す・WASM のメモリへ)。1 コマ 70KB ほどで、合わせても 0.3ms に届かない
- デコードしたフレームは JS では写さない。WASM のメモリの上の 3 面をそのまま `texSubImage2D` に渡す (R8 のテクスチャ 3 枚。行の右の詰め物は
  `UNPACK_ROW_LENGTH` で飛ばす)。写すのはブラウザが GPU へ送るときの 1 回だけ
- 1 コマを上げるのは 1 回で、描くのはフィールドごとに 2 回。番を過ぎたコマは上げずに捨てる ([貯め方](#貯め方))
- GPU の無い端末では、素通しのシェーダでも 2 フィールドで 1 コマ 40ms かかり、実時間 (33ms) に届かない。インタレ解除を軽くしても足りないので、
  いまどおりエンコードしたものに戻す

**実機ではこうだった** (2026-10-25、Edge・CPU 12 コア・AMD の GPU の PC。GPU の使用率は Windows の性能カウンタで見た):

- 本番のライブ (地上波の 1440x1080i) を放送のままで見ると、そのタブの renderer のプロセスが 1 コアの 4〜19%、GPU のプロセスが約 5%。
  同じ局を H.264 (本番の変換) にすると、renderer が 2〜6%、GPU のプロセスが 6〜7%。ほかのタブの動きで Edge 全体の数字はぶれたので、タブのプロセスで比べた
- **机の上の PC では、今の経路の描画は重くなかった。** GPU のプロセスは H.264 で `<video>` に出すときと同じくらい
- WASM の中の速さ (worker 1 本) は、デコードだけで 365 コマ/秒 (1440x1080i)・214 コマ/秒 (1920x1080i)。ヘッドレスの Chromium で測った上の数字と同じくらい

#### スライスのスレッドを見送った理由

**スライスのスレッド (2〜4 本) は見送りました** (2026-10-25 に調べた)。1 コマのデコードは 1/1.5〜1/3 になりますが、効く端末が限られ、
効いてほしい端末には効きません。

- **要るもの:** SharedArrayBuffer のための `crossOriginIsolated`。付けるならアプリ全体に COOP `same-origin` と COEP `credentialless`
  (画面はもともと別オリジンから何も読まないので、ほぼ何も変わらない)。直すのは Hybridcast の iframe (その文書にも COEP が要る) と、
  worker のスクリプトを返すところ (adapter が直に配るので `server.js` で付ける) だけ。データ放送・ロゴ・フォント・PWA・OIDC のログイン
  (リダイレクトだけ)・PiP・denpa-tv は影響を受けない
- **ページごとに分けない:** SvelteKit の画面の移動は文書を替えないので、`/live` だけ isolated にするには、そこへのリンクを全部
  読み込み直しにすることになる
- **効くのは https (か localhost) の Chrome・Edge・Firefox だけ:** 安全でない繋ぎ (`http://192.168.…` の LAN) では COOP/COEP は
  仕様で読まれない。Safari・iOS と Firefox Android は `credentialless` に対応していない (Safari にも効かせるなら `require-corp` にして、
  Hybridcast の読み込みを全部中継に通すことになる)
- **どのみちスレッド無しのビルドも配る:** 効かない端末のため。Docker の組む時間が 2 分ほど延び、イメージは 1.1MB ほど大きくなる
- **見送った理由:** 机の上の PC では今でもデコードは 1 コアの 1 割ほどで、速くなっても体感は変わらない。重くて困るはずの iPhone・iPad には
  効かない。Hybridcast とビルドの手間に見合わない

変えないもの (理由は [組み方の測定](stream-history.md#wasm-のデコーダの組み方を決めたときの測定)): SIMD (`decoder.wasm` は 7% ほど大きくなるが、今のブラウザはどれも対応しているので外す理由も無い)・`-O3`・
フレームのスレッド・GPU の無い端末で描く量を減らすこと。

### 時計は鳴っている音 (リップシンク)

**鳴っている音を時計にします** (`raw/playout.ts`)。音は途切れると誰でも気づきますが、映像は
1 コマ遅れても気づかれにくい。だから音は届いた順に隙間なく Web Audio の時間の上へ予約し、
映像は「いま耳に届いている PTS」を追いかけて、番が来たコマを出します。放送の PTS は音と映像で
同じ時計 (PCR) に乗っているので、それで音と映像が合います。

- 「いま耳に届いている PTS」は `AudioContext.getOutputTimestamp()` から出す。予約している
  位置ではなく**出口までの遅れを引いた位置**。それを performance の時刻と組にして worker へ
  流し (20ms ごと)、worker は組から外挿してコマを選ぶ
- **PCR は受け側では使いません。** 貯めは「届いた音の端 − 鳴っている位置」で見る (`clock` の通知は「放送から N 秒」を出すのにだけ使う。
  放送のままの経路では ffmpeg の `start:` を引かず PCR をそのまま渡す)
- **PTS は 26.5 時間で一周する**ので、受け側は増え続ける数に伸ばして持つ (`packages/arib/src/pes.ts` の
  `unwrap`)。字幕と時計の通知も、同じ物差しの近くへ伸ばしてから比べる
- 自動再生で音を断られたら、**壁時計を時計にして映像だけ進め**、「音を出す」を押された時点で
  鳴っている位置のまま音の時計へ移る (`RawEngine.follow`)。逆に音が止められたら (出口が
  外れた・OS に止められた) 壁時計へ戻り、映像は止めない
- 音量 ([watch.md](watch.md#音量)) のリミッタ (DynamicsCompressorNode) は、先読みのぶん音を 6ms ほど遅らせる。
  時計には入れていない (1 コマより短く、気づかれない)

#### `<audio>` を通すとき

**バックグラウンド再生をオンにしている間と、押して小窓を開いている間は、音を `<audio>` から鳴らします**
(`#lib/sound.ts` の `Outlet.route`。Safari は除く。そちらは Audio Session を `playback` にする。理由は
[watch.md](watch.md#裏に回したら止めます))。リミッタの後ろを `createMediaStreamDestination()` に繋ぎ替え、
そのストリームを `<audio>` の `srcObject` に渡すだけで、予約の仕方も時計の物差し (`context.currentTime`) も変わりません。
変わるのは**耳に届くまでの遅れ**です:

- ストリームへ出した音はページの出口の遅れ (`baseLatency + outputLatency`) を通らず、代わりに `<audio>` の
  出口の遅れが掛かる (ヘッドレスの Chromium で、直に鳴らしたときより 84ms 早くストリームに入った)
- `<audio>` の出口の遅れはページから読めないので **見込み (`STREAM_OUT` = 30ms) で置く**。
  時計は `getOutputTimestamp()` の組のまま、PTS を `baseLatency + outputLatency − STREAM_OUT` だけ先へずらす。
  見込みは**少なめ**に置く。外れると音が映像より遅れる側に倒れる (人は音が先に来るほうに気づきやすい)
- オン/オフを切り替えたときは、その差のぶん時計が一度だけ飛ぶ (映像が 1〜数コマ止まるか飛ぶ)
- **止める・再開は `<audio>` にも写す。** ロック画面・車の操作・ブラウザの再生中の通知は
  `<audio>` を直に止めるので、それも操作バーに反映する (`RawEvents.remote`)
- CSP には掛からない (`srcObject` は URL を読まない)

#### 継ぎ目はサンプル単位でつなぐ

**AudioContext は放送と同じ 48kHz で作り、コマは前のコマの終わりのサンプルにつなぎます** (`raw/seam.ts`)。
音は AAC の 1 コマ (1024 サンプル、約 21 ms) ごとに `AudioBufferSourceNode` を作って予約するので、継ぎ目に
1 サンプルでも隙間や重なりがあると、そこで波形が飛んで「チリチリ」と聞こえる (#2684)。

- AudioContext のサンプルレートは、指定しなければ端末の出力に合う (Mac は 44.1kHz のことがある)。すると 1 コマが
  940.8 サンプルになり、ノードごとにサンプルレートを変換した端がずれる。48kHz で作れば、ブラウザが出力の手前で
  1 回だけ変換する。指定できないブラウザは端末のサンプルレートのまま作る (`audioContext`)
- 予約の時刻は PTS から出すので、PTS の揺れと秒に直したときの丸めで、1 サンプルの倍数からずれる。前のコマの終わりと
  1 ms (`SNAP`) 以内なら前のコマの終わりへ寄せ、それより離れていれば途切れとして時刻どおりに置く
- 止まった・飛んだとき、音の時計から壁時計に替えたときは、保持していた前のコマの終わりを破棄する (`stopAll`)
- [WebKit のライブの音](#ライブの音を-video-と別に鳴らす-webkit) (`raw/native-audio.ts`) も同じものを使う
- 1 kHz のサイン波を 1024 サンプルのコマに切って `OfflineAudioContext` で鳴らし、つないだだけの理想の波形と比べると、
  44.1kHz で作った AudioContext では 1 秒に 5.6 回、振幅の 9 割近い段差が出た (Chromium・WebKit とも。Firefox は出ない)。
  48kHz で作ってサンプル単位でつなぐと段差は出ない。PTS を ±2 tick 揺らしたときも同じ

### 貯め方

**エンコードする経路と同じ考えで、決め方も同じものを使います** (`pacing.nextTarget`。止まったら伸ばし、
無事が続いたら縮め、止まった高さを覚える)。覚える置き場も同じ (`FLOOR_KEY`)。

- 貯まった音の尺が `target` に届いてから、**放送の今から `target` 手前で**鳴らし始める
- **使い切ったら止まって貯め直す** (止まった回数はエンコードする経路の「途切れ」と同じ数に出る)
- バッファが多すぎる状態 (`target` + 1 秒が 3 秒続く。裏に回ったタブが戻ったとき・時計のずれ) は
  **放送の今へ飛ぶ**。1.05 倍で詰めることはしません。音を速めると音程が変わる

**貯めるのはデコードする前**です。1080 のフレームは 1 枚 3MB あるので、デコードしたフレームで貯めると
1 秒で 90MB になる。圧縮のまま (PES) 持っておき、**番の 0.3 秒前にデコードします**。デコードできたフレームはデコーダの中で
順番待ちさせ (8 枚まで。[デコードしたフレームを持つ数](#デコードしたフレームを持つ数))、番を過ぎたものはテクスチャに上げずに捨てます (コマ落ちとして数える)。

### インタレ解除は bob で、止まっているところと櫛になっていないところは織る

1080i の 1 コマには時刻の違う 2 枚 (フィールド) が 1 行おきに入っています。**フィールドごとに
出して、抜けた行はそのコマとひとつ前のコマで埋めます** (`raw/render.ts` のシェーダ。色差も同じ)。

- **動きが 60 枚/秒のまま出る** (エンコードする経路の `bwdif` と同じ)
- 抜けた行とその上下の行が**前のコマから変わっていなければ、もう片方のフィールドのその行をそのまま使う** (織る)。
  比べるのは輝度だけで、4/255 までは止まっている、12/255 からは動いている (間はなだらかに混ぜる)
- 変わっていれば、**もう片方のフィールドのその行が上下の行の間に収まっていればそのまま使う**
  (織る)。はみ出していれば櫛 (2 枚の間に動いた) なので、上下の平均で埋める (bob)。
  はみ出しが 8/255 までは雑音として織り、16/255 からは埋める (間はなだらかに混ぜる)
- 前のコマは輝度のテクスチャを 1 枚残すだけ (2 枚を交互に使うので、上げ直しは増えない)。GPU の手間は誤差

素の bob (いつも上下の平均で埋める) だと、上下のフィールドで縁になる行が 1 行ずれるので、**止まっているテロップの縁が毎秒 30 回上下に揺れる。**
織れば止まっているところは揺れない。ただ**コマの中だけでは止まっているかを決めきれない**。縁取りのある字や
細い横線は上下の行の間に収まらず、櫛と見分けがつかないので、埋める側に回ってちらついていた。前のコマと比べて
変わっていなければ織るようにして止めた (合成の 1080i で、止まった字の上下のフィールドの差は最大 153 → 0。
動くところの扱いは変わらない)。大きさが変わった直後は前のコマが無いので、コマの中だけで決める。局を変えても大きさが同じなら前の局のコマと比べるが、ほとんどの所が動いているとみなすので、結果はコマの中だけで決めたのと同じになる。

インタレの印の無いコマ (720p など) はそのまま出します。色は HD が BT.709、SD が BT.601
(限定レンジ)。1440x1080 は画素の縦横比を掛けて 1920 幅で描きます。

### コマを出す間合いは画面の切り替わりに合わせる

**フィールド (59.94 回/秒) と画面の切り替わり (たいてい 60 回/秒) はほぼ同じ間隔で並ぶので、
出す時刻が少し揺れるだけでカクつきます** (同じフィールドが 2 回出て、次のフィールドが飛ぶ)。worker の刻みの時刻で番を見ていた頃は、
切れ目と画面の切り替わりが近い間 (約 17 秒ごとに 2 秒ほど) ずっとこれが起きていました。いまは (`raw/cadence.ts`):

- **次の画面の切り替わりの時点で出すフィールドを選ぶ。** 画面の requestAnimationFrame の時刻を
  worker へ流し (`vsync`)、間隔と位置を覚えて次の切り替わりを見越す。worker の rAF は描いたものが画面に出る速さに引っ張られるので使わない
- **切り替わりごとの PTS は、切り替わりの間隔ぶんずつ進める** (`VsyncClock`)。時計 (鳴っている音) の
  組は 20ms ごとに数 ms 揺れて届くので、まず少しずつ寄せ (`SmoothClock`)、その上で時計へはごく少しずつ寄せる。
  8ms 以上食い違えば (飛んだ・貯め直した) 合わせ直す
- **描いた回はデコードしない。** **デコードは、描くものが次に変わる画面の切り替わりまでに終えて描けるときだけ始める** (`mayDecode`)。
  デコードしている間は描けないので、間に合わないと描くのが 1 回ぶん遅れ、同じフィールドが余分に出て次が飛ぶ。
  同じフィールドを続けて出す切り替わり (120Hz なら 1 回おき) はまたいでよい。掛かる時間は直近 8 枚の平均から見積もり、
  デコードできて待っているコマが多いうちは余裕を多く取る (平均の 1.15〜2 倍 + 2ms)。先にデコードしたものが無くなっていればいつでも始める

前は「画面の切り替わりの間隔の前半にだけ始める」でした。60Hz では切り替わりのたびにフィールドが変わるので、これで足りていました。
120Hz では間隔が 8.3ms しかありません。フィールドを描いた次の刻み (4ms 後) はたいてい間隔の後半なので、次の切り替わりのあとまで待ちます。
その切り替わりでは同じフィールドを続けて出すだけで、描かなくてよい回でした。待ったぶん、次にフィールドが変わるまでの残りが
12〜16ms に減り、1 枚 13ms のデコードでは描くのがたびたび遅れていました。worker の刻みを写した模擬 (`cadence-sim.ts`。29.97 コマの 1080i、GOP 15、
1 枚の時間は目安の ±25%) で、出すはずのフィールドと違うものが出た切り替わりは 1 分あたり次のとおりです。

| 画面  | 1 枚の時間 | 前の作り | いまの作り |
| ----- | ---------- | -------- | ---------- |
| 60Hz  | 5〜13ms    | 0        | 0          |
| 60Hz  | 16ms       | 13       | 8          |
| 90Hz  | 13ms       | 42       | 1          |
| 120Hz | 10ms       | 84       | 1          |
| 120Hz | 13ms       | 671      | 55         |
| 120Hz | 16ms       | 1406     | 501        |
| 144Hz | 10ms       | 330      | 18         |

区切らない (いつでも始める) と、120Hz では前の作りより少ないものの、90Hz の 13ms で 222 に増えました。
1 枚がフィールドの間隔 (16.7ms) に近いと、どの決め方でも残ります。どれも模擬までで、実機では確かめていません。

59.94 と 60 の差のぶん、約 17 秒に 1 回は同じフィールドが 2 回出ます (周波数を合わせない限り避けられない)。
裏に回って画面の rAF が止まっている間は、刻んだ時刻で選びます。エンコードしたもの (fMP4) も同じ時計で番を見ます。

単体テスト (`cadence.test.ts`) は刻みとデコードと時計の揺れを模してフィールドが飛ばないことを、`cadence-sim.test.ts` は
60・90・120・144Hz で前の作りより増えないことを確かめる。E2E (`43-raw-cadence`) は
偽の放送 (上下のフィールドで別の時刻の映像。`packages/arib/src/synth-av.ts`) を互換モードの観る画面で流し、worker の WebGL の呼び出しを数えて
画面の切り替わりごとにどのフィールドが出ていたかを確かめる (直す前は 150 回のうち重なり 9・飛び 8、直した後は 0・0)。
CI は混んで画面の rAF が来ないことがあるので、E2E は rAF が続けて来ていた切り替わりだけを数え、来ない回が多ければ測り直す
(4 回とも混んでいれば飛ばす)。rAF が半分ほど来ない間が続くと、worker の覚える切り替わりの間隔が 25〜30ms にずれて戻らなかった
(`Vsync` が 33ms を 1 回ぶん、50ms を 2 回ぶんと割る)。いまは 30 回続けて 2 回ぶん以上と割ったら、来た間の真ん中から測り直す
(120Hz から 60Hz に変わったときも同じ)。
**実機の画面 (120Hz・可変リフレッシュ) でどう見えるかは実機で見ないと分からない。**

### 選局と途切れ

- **局を変えても worker とデコーダは作り直しません** (`reset` で中身だけ捨てる)。デコーダを
  開き直し、**I フレームが来るまで渡さない**。MPEG-2 は I からしかデコードできず、先に P/B を渡すと
  灰色の映像が出る (放送の GOP は 0.5 秒)
- **前の局の音は、worker が `reset` を済ませたと返すまで捨てる。** `reset` を送った時点で、worker がデコードし終えた
  前の局の音がまだ画面へ向かっていることがある。それを貯めに入れると、新しい局の音の時刻が前の局より小さいとき
  (PTS は局ごとにばらばら)、追い越すまで新しい局の音が全部捨てられて鳴り出さなかった (E2E の 28-live-raw で、半分ほどの回が 0.5〜1.4 秒遅れていた)
- **選局したての先頭は捨てない。** 局に絞るところ (`ServiceFilter`) は PAT と PMT を読むまでどの PID が局のものか
  分からないが、その間に届いたものは取っておき、PMT を読んだら局のぶんを PMT の後ろに出す。捨てていた頃は PMT より前に
  始まった I フレームを失って次の GOP まで映らず、音も PMT のあとから貯め始めていた (合成の TS で PMT を遅らせると、
  PMT が届いてから鳴り出すまで 197ms → 16〜20ms)。録画とエンコードする経路も同じところを通るので、先頭が少し長く残る
- 貯めている間は**新しい局の 1 枚目を出して待つ** ([新しい局の 1 枚目が少し止まる](#新しい局の1枚目が少し止まるのは直さない)と同じ判断)。
  エンコードする経路で使う「前の映像を貼る」canvas は空にしておく (古い映像が放送のまま描く canvas の上にかぶさる)
- **1 枚目の I はデコーダが出すのを待たない** (`wasm/decoder.c` の `dec_still`)。FFmpeg のデコーダは B フレームを並べ替えるため、
  I を読んでも次の P を読むまで出さない。放送は I・B・B・P の順に届くので、3 コマぶんと parser が次のコマの先頭を待つ 1 コマぶん (29.97 コマ/秒で計算すると合わせて 0.13 秒ほど) 遅れていた。
  1 枚目の I だけは別に開いたデコーダにも渡し、持っているものを出しきらせてすぐ描く。I のデコードが 1 回増える。
  本体のデコーダが後から同じコマを出したら捨てる。録画で飛んだあと (飛び先より前を捨てている間) は使わない。
  動き出すのは今までどおり貯まってから (音の時計) で、その間は 1 枚目のまま止まって見える
- 大きく遅れたら (0.5 秒) デコードしながら追わずに I フレームまで飛ぶ。止めている間に溜まる圧縮の待ちも 8 秒で切る
- サーバでの共有は局と字幕の単位 (音声とエンコード方式では分けない。音声は全部送って画面が選ぶ)。
  チューナーの使い方・畳み方・`warm` はエンコードする経路と同じ

### 追っかけも放送のままで送る

**追っかけでも `chase` に `raw: true` を付けると、録画中の元の TS をそのまま送ります** (`live.ts` の `openChase`・`Session.runRaw`)。
読むのはエンコードする追っかけと同じ `followFile` で、読み始める位置は録れた秒数とファイルの大きさから割り出したバイト位置で、送り込みは倍速までです。

- **その場の変換の枠を使いません。** ffmpeg は字幕を写すものだけで、ライブの放送のままと同じです
- **捨てずに、読むほうを止めます。** ライブは詰まった客の TS を捨てますが、追っかけで捨てると観ていない先が欠けます。
  サーバは次のどちらかの間、録画のファイルを読まずに待ちます
  - 画面が `{ type: "hold", on: true }` を送ってきた (画面の受信バッファが溜まった・一時停止している)。`on: false` で読み直す
  - 送り先のバッファが捨て始める量 (4MB。`ws.ts` の `BACKLOG_LIMIT`) を超えている (回線が倍速に追いつかない)
- **番組が替わっても作り直しません。** 字幕の ffmpeg だけ起こし直すのはライブの放送のままと同じで、`restart` は送りません
- **読み切ったら `ended` を送って閉じます** (エンコードする追っかけと同じ)
- **`timeline` に録画の先頭の PTS を載せます** (`origin`。`ts/seek.ts` の `readHead`。観る画面の `X-Denpa-Origin` と同じ物差し)。
  画面は届いた PTS からこれを引いて再生位置を出すので、バイト数から割り出した位置より正しい位置が出ます。サーバは先頭を読み終えてから `timeline` を送って流し始めます
  (読むのは非同期で、読めたものは覚える)。録り始めたばかりで先頭が読めなければ省き、5 秒は読み直しません

画面はライブの放送のままと同じ配線で受けます (`live-player.svelte.ts`。`RawEngine` を追っかけ用の `chase` で開くだけ)。

- **画面の受信バッファが 20 秒を超えたら止めさせ、10 秒を切ったら送り直させます** (`live-chase.ts` の `nextHold`)。止めている間も止めさせます。
  worker が圧縮のまま持てるのは 30 秒までで (`raw/worker.ts` の `FOLLOW_PENDING_MOST`)、その手前で止めるので、ふだんは `full` からのリクエストし直しは起きません
- **速さは等速だけです。** 速さのメニューは互換モードと同じく出しません。音を自前で鳴らしていて、速めると音程が変わるためです
- **シークは、いつもリクエストし直します** (受信バッファにあるのは先だけ。互換モードの追っかけと同じ)
- **音声の選び直しはリクエストし直しません。** TS には全部の音声が入っています (`RawEngine.selectAudio`。ライブと同じ)
- 録れているところまで鳴らしきったら止めます (`ended` を受けて `RawEngine.finish`)。デコードが間に合わなくなったら、
  エンコードしたものに替えて再生していた位置からリクエストし直し、理由を断り書きに出します

### 放送のままのときの字幕

**字幕は ffmpeg に写させて、denpa がデコードします** (エンコードする経路と同じ)。映像をデコードしない ffmpeg を
1 本起こし (`captions.rawCaptionArgs`)、**`-copyts` で放送の時刻のまま**字幕だけを写させます。CPU は 0.2% ほど。

放送のままの経路の受け側は放送の PTS そのものを時計にしているので、字幕も放送の PTS のまま出せば突き合わせられます
(mp4 のマルチプレクサが 0 に詰め直す問題は、字幕の出口の Matroska には無い。実機の録画で元の TS の字幕 PES の PTS と 1ms 単位で一致)。
**`-copyts` を外すと合いません。** 映像を出さない ffmpeg は寄せ幅を入口の `start:` と違う値にし、それを外から知る方法が無い。

**テレビのアプリも同じ字幕を受け取ります** ([api.md](api.md#元の-ts-の字幕-get-apiservicesidcaptionsget-apirecordingsidcaptions))。
ライブは映像と同じセッション (放送のまま、または同じ形式と音声で変換したもの) を共有し、字幕 (0x22) と、字幕一覧と時計の通知 (0x40) だけを、1 つずつ先頭に長さを付けて HTTP で流します
(チューナーは増えない。字幕だけを受け取る接続は、畳むかどうかの判断に数えない)。元の TS の録画と追っかけは、
リクエストされた位置の少し手前から同じ ffmpeg を 1 本起こします。アプリは Media3 の TS のパーサが 0 に寄せた幅を
足し戻して放送の PTS にし、そこで突き合わせます。

字幕の ffmpeg が失敗しても映像は止めません。流し込みも待たせない。書き込みが捌けていない間に来た塊は字幕の側に渡さない
(字幕が 1 枚欠けることはありうるが、映像が止まるよりいい)。

**番組が替わって並び (PMT) が変わったら、字幕の ffmpeg だけ起こし直します** ([番組が替わって並びが変わったら作り直す](#番組が替わって並びが変わったら作り直す))。
`-copyts` で放送の時刻のまま写しているので、起こし直しても時刻は続きます。選べる字幕は新しい ffmpeg の見出しから数え直し、
字幕が無いと覚えていた局でも起こし直します (新しい番組には字幕があるかもしれない)。

データ放送は変わりません。放送のまま描く canvas も映像の入れ物の中にあるので、データ放送の小窓へ一緒に動きます。

### 間に合わないとき

**映像が時計から 0.25 秒以上遅れるか、出すはずのコマの 15% 以上を捨てる**のが、**1 秒ごとに数えて 3 秒続いたら**エンコードしたものに戻します (`raw/budget.ts`)。
捨てるコマを数えるのは、同じ端末で 2 本見ていたときに、遅れにぎりぎり掛からないまま紙芝居になっていたため
(飛び越し走査のフィールドの順番が崩れて、テロップの細い線が上下に震えて見えた)。
**1 コマをデコードする時間の 95 パーセンタイルが 1 コマの長さの 8 割を超えても、それだけでは数えません。**
時間は経過時間 (`wasm/decoder.c` の `last_ms`) なので、worker が割り込まれた間も入ります。1 秒 30 枚の 95 パーセンタイルは
2 番目に重いコマで、I フレームにほぼ当たります。この条件も数えていたころは、Galaxy S25 で映像がほとんど崩れていないまま
この条件だけに掛かり続け、数十秒〜数分で戻っていました (#2604)。`worker.ts` の刻みを写した使い捨ての模擬 (#2616。リポジトリには残していない) では、デコード中にスレッドが止まる場面を入れると
打ち切ったのはすべてこの条件だけで、捨てたコマは 0〜3% でした (実機では確かめていない)。本当に間に合わない端末は、遅れか捨てたコマに掛かります。
1 回の重さ (タブを戻したとき・GC・選局の直後) では戻さない。戻すと再エンコードで 1 秒近く
映像が止まるので、一瞬の詰まりより高くつく。**タブが戻ったとき・止めていたのを再開したときは、追いつくまでの 2 秒は数えません**
(`raw/worker.ts` の `catchUp`)。時計は放送の今へ進んでいて、映像は次のキーフレームまで飛ぶあいだ 1 秒ほど遅れるので、
数えると止める・再開するのを 2〜3 回続けただけでエンコードしたものに戻っていました。
**回線が詰まってデコードするデータが届いていないあいだと、届いて追いつくまでの 2 秒も数えません** (`raw/worker.ts` の `starve`)。
遅れていてもデコードが間に合わないのではなく、届いたあとに番を過ぎたコマをまとめて捨てるのも同じです。家の中の Wi-Fi で
放送のまま (約 17 Mbit/s) 受けると一瞬の詰まりは起きやすく、数えると変換した映像へ早めに戻っていました。それまでに数えた回数は残すので、
デコードが本当に遅い端末は届いているあいだに続けて数えて戻ります。その手前で、1 秒にコマを 3 枚以上捨てるか映像が 0.1 秒遅れたら、
まず B フレームのデコードを省きます (`raw/worker.ts` の `dec_skip`。動きは 1 秒 10〜15 コマに落ちるが、デコードの時間は半分ほどになる)。
デコードする時間は操作バーに「デコード N ms」と出ます。
戻したときは、数えた 1 秒ずつの窓ごとにどの条件に掛かったかをコンソールに出力します (`DecodeBudget.why`。
「[live] MPEG-2 を打ち切りました: デコード 28.4 ms (目安 26.7 ms)、映像の遅れ 0.31 秒 (目安 0.25 秒) / …」)。
デコードする時間が目安を超えた窓では、数えた条件の前にその時間も出力します。出力する前は、どの条件で戻したかが外から読めませんでした。

**見えていないタブでは映像をデコードしない** (`visible`。小窓に出しているときは別)。音は流し続け、見えるようになったら
いちばん新しいキーフレームからデコードし直します。裏に回したタブも 1 コマ 10ms 前後デコードし続けて、見ているタブが
間に合わなくなっていました。

### デコードしたフレームを持つ数

デコードできたフレームを何枚まで先に持つか (`DECODED_MOST`) は、放送のまま (`raw/worker.ts`。WASM の中のフレーム) と
互換モード (`raw/fmp4.ts`。VideoFrame と、渡したまま出てきていないもの) で別に決めています。**どちらも 8** ですが、
数えるものも決め手も違います (測った表と測り方は [stream-history.md](stream-history.md#decoded_most-を決めたときの測定))。

- **互換モードは GPU で上下に崖がある。** GPU のデコーダは受け取ってから出すまでに何枚か抱える (B フレームの並べ替え) ので、
  4 以下だと次を渡せずに毎秒 30〜40 コマまで落ちる。12 にすると GPU の置き場が尽きてデコーダが何も出さなくなる。
  6 は下の崖に近いので 8。CPU のデコーダはすぐ出すので 2〜12 のどれでも変わらない。崖を測ったのは Radeon 1 台だけなので、
  ほかの端末で「再生が追いつきません」が出るなら、まずここを下げて測る
- **放送のままは 1 回に 1 枚ずつデコードする**ので、待たせるのは多くて 3〜5 枚。2 だと追いつかず、6 以上でほぼ落とさない。
  WASM のメモリはどの値でも最初の 64MB から増えない

### 払うもの

- **帯域。** 1 局に絞った元の TS は実測 14.5〜16.8 Mbit/s で、中身によらずほぼ一定
  (エンコードしたものは形式と場面で動き、AV1 なら数分の 1 まで)。自動で放送のままにするのは家の中から開いたときだけで、細い回線では選ばないこと
- **端末の CPU と電池。** デスクトップなら 1 コマ 3〜5ms ([内訳](#どこに時間が掛かっているか)) だが、携帯や非力なノートでは電池を目に見えて使う。**家の中の自動でも MPEG-2 になるので、気になる端末は AV1 を選ぶ**
- **MSE に乗っていたもののうち、次のものが無くなる。**
  - **止めて再開は放送の今から**。5 分戻れるシークバー・追っかけの速さも無い (1 局 15Mbit/s を 5 分持つと 600MB になる)
  - エンコード方式の選び直し (選ぶとエンコードしたものに移る)
  - 5.1ch の番組は先頭の 2 つ (前の左右) だけ鳴らす (下げ方を持っていない)
- インタレ解除はそのコマとひとつ前のコマだけで決める (上) ので、前後のコマまで見る `bwdif` よりは落ちる

### ライブの音を `<video>` と別に鳴らす (WebKit)

WebKit の MSE / ManagedMediaSource は、`<video>` の音を Web Audio に通すと無音しか渡さず、音量のつまみが効かない
([WebKit #266922](https://bugs.webkit.org/show_bug.cgi?id=266922))。**WebKit (Safari、iPhone のどのブラウザも) のライブでは自動で、
映像は `<video>` のまま (PiP もそのまま)、音だけ同じ fMP4 から WASM でデコードして `Outlet` で鳴らす** (`raw/native-audio.ts`)。
設定には出さない (起きるかはブラウザで決まる)。見分けは UA (`native-audio-choice.ts`)。

- 映像の時計と AudioContext の対応を 1 つに保って予約し、大きくずれた・飛んだ・止めた・速さを変えたときだけ組み直す
- AudioContext は 48kHz で作り、コマは前のコマの終わりのサンプルにつなぐ (放送のままの経路と同じ。[継ぎ目はサンプル単位でつなぐ](#継ぎ目はサンプル単位でつなぐ))
- AudioContext はプレーヤーが 1 つ持ち、画質を切り替えて MediaSource を作り直しても使い回す。閉じるのは画面を離れるとき。
  iOS の Safari は押したとき以外に作った AudioContext を止めたまま始めるので、作り直すたびに作っていた頃は自動再生を断られたとみて消音にしていた (#2728)
- 組み直すときは、鳴っている音を 8 ms で絞りきってから止める。組み直した直後と、コマを捨てて間が空いたあとは、8 ms で音量を上げながら鳴らす。
  波形が途中で 0 に飛ぶと「プツッ」と聞こえる (#2474)。映像が一瞬止まる (`waiting`)・遅れを取り戻そうと先へ飛ぶ (`seeking`) たびに組み直すので、届き方が揺れる回線で起きていた
- 映像の時刻が 40 ms 以上動かないまま音だけ進んで組み直したら (再生の途中で止まったときも)、映像が動き出すまで音を予約しない。WebKit は、バッファが空になって映像が止まっても
  `waiting` を出さず `readyState` を 3 のままにすることがあり、そのまま予約し続けると 80 ms 鳴っては組み直すのを繰り返していた
- `<video>` は消音にし、使う人の消音は画面が持つ (`player.silenced`。バックグラウンドの戻しもこれを見る)
- 別に鳴らせなくなったら再生は止めず `<video>` の音に戻す (音量のつまみは効かないと注意を出す)
- **制約:** PCM は過去 30 秒・16 MiB まで (5.1ch なら約 14 秒) なので、それより前へ戻る・長く止めると音が出ないことがある。
  追いつき再生の間は音程も変わる。WebKit の端末では CPU・メモリが増える

### 互換モード (エンコードしたものも canvas に描く)

**`<video>` の再生が止まる端末のための方式です。** テスラの車載ブラウザは、停車中でも `<video>` の
再生を止めます。canvas に描くものは止めないので、互換モードでは**ライブ・追っかけ・録画の観る画面の H.264 / AV1 も
放送のままと同じ worker でデコードして canvas に描きます** (観る画面は[下](#録画の観る画面も-canvas-に描く))。

```
サーバ (変えない) → WebSocket (0x00 init / 0x01 媒体。fMP4) → worker ┬→ moof/trun → WebCodecs (VideoDecoder) → 2D
                                                                     └→ AAC は ADTS ヘッダを付けて / Opus は OpusHead で → WASM → 画面 → Web Audio (時計)
```

- **サーバは変えません。** 届くものはエンコードする経路と同じ fMP4 で、画面が MSE ではなく放送のまま描くエンジン
  (`RawEngine` の `fmp4`。`raw/fmp4.ts`) へ流すだけ。worker は作るときに何を受け取るか (`RawInput`) を決める
  (描く先の canvas の使い方が WebGL2 と 2D で違うので途中で替えない)
- **ボックスは自前で読みます** (`ts/fmp4.ts` の `readInit` / `readFragment`)。moov の avcC / hvcC / av1C / esds / dOps (hvcC は、サーバが段を下げた H.265 の長さを数える `server/pace.ts` と、キーフレームを待つ `ts/key-gate.ts` のため。互換モードでは描かない) と、
  moof の tfdt / trun。中身の在りかは moof の先頭から数える (`+default_base_moof`)
- **映像は VideoDecoder** (`description` に avcC / av1C)。デコードできた VideoFrame は**描いたらすぐ閉じる**
  (持つとデコーダのフレームの置き場が尽きる。[デコードしたフレームを持つ数](#デコードしたフレームを持つ数))。圧縮のまま
  持っておき、番の 0.3 秒前に渡すのは MPEG-2 と同じ。コマの時刻が飛んだら (サーバが詰まった客に媒体を捨てた) 次のキーフレームまで捨てる。
  デコーダがエラーを返したら開き直してキーフレームから入り直し、4 回続けてエラーなら打ち切る
- **描く大きさは pasp (画素の縦横比) を掛けた幅** (1440x1080 の SAR 4:3 なら 1920 幅。`Fmp4Track.displayWidth`)。
  VideoFrame の見せる大きさは使いません。Safari は画素の数のまま返し (H.264 の SAR も `displayAspectWidth` も見ない)、
  AV1 は映像の中に縦横比を持たないので、4:3 に縮んで出ます。pasp が無ければフレームに合わせる
- **音は MPEG-2 と同じ WASM。** AAC は esds の AudioSpecificConfig から ADTS ヘッダを組んで付ける (`adtsHeader`)。
  Opus は dOps を OpusHead に書き換えて Opus のデコーダ (`opus_open`) へ渡す (端末に保存した Matroska はもともと OpusHead)。H.264 の WASM のデコーダと dav1d の WASM は作りません
- **時計は放送のままのときと同じ** (鳴っている音。`playout.ts`)。時刻は MP4 の物差し (0 から数え、一周しない) で、
  字幕・時計の通知も同じ物差しで届く
- **間に合っているか** (`budget.ts`) は、放送のままのときと同じく 1 コマの時間では判じない。GPU の経路は詰まっていなくても
  数コマぶん溜めることがある。VideoDecoder の詰まり (`decodeQueueSize` が窓の間ずっと
  3 枚以上) と、映像の遅れ (0.25 秒)、捨てたコマ (出すはずのコマの 15% 以上) を同じく 3 秒続いたかで数える
- **速さは等速だけ。** ライブは止めて再開は放送の今から (戻れるシークバーも追っかけの速さも出ない)
- **追っかけは放送の今を追わない** (`RawEngine` の `chase`、`playout.ts` / worker の `follow`)。溜まっても飛ばず、
  止めて再開は止めた所から。シークバーは出すが、動かすといつもリクエストし直す (手元に持っているのは先だけ)。
  サーバは倍速で送り込んでくるので、圧縮のまま持つのは **120 秒か 120MB の小さいほうまで** (`raw/fmp4.ts` の `FOLLOW_AHEAD_MOST`。120MB は MSE の `BUDGET` と同じ)。
  超えたら受け取るのをやめ (`full`)、手元が 5 秒を切ったらいまの位置からリクエストし直す (`REFILL`)。
  描けなくなったら、MPEG-2 をデコードできればそちらに替え、できなければ理由を出して止まる (ライブと同じ)

**オン/オフは端末ごと** (再生の設定 (⚙) の「互換モード」。`canvas-video.ts`)。localStorage のキー 1 つ
(`canvas-video` = `on` / `off` / 無し) で、**明示した値が勝ちます**。無ければ UA に `Tesla/<数字>` が
ある端末はオン、それ以外はオフ (判定は画面だけ。サーバは UA を見ない)。同じ項目に、この端末で
H.264 / AV1 が使えるか (`VideoDecoder.isConfigSupported`) と、テスラの印があるかを出します。切り替えたらページを読み直します。

**運転中の注意を一度だけ出します** (`canvas-drive-notice`)。⚙ でオンにしたとき (確かめる窓。取消できる) と、
UA の既定でオンになっている端末で初めて canvas で再生する前 (「了解」を押すまで再生を始めない)。
位置情報で止める仕組みは作りません。

**打ち切るときも `<video>` には戻りません** (テスラでは止まってしまう)。

|                                                                               | どうするか                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| この端末でデコードできない形式                                                | コーデックのメニューに「(再生できません)」と出して選ばせない。選んでいた形式がデコードできなければデコードできるほうへ (AV1 → H.264)、どちらも駄目なら MPEG-2、それも駄目なら「再生できる形式がありません」 |
| 描いている途中で打ち切った (間に合わない・デコーダが失敗し続ける・音が来ない) | MPEG-2 で描けるならそちらへ (断り書きに理由)。無理なら理由を出して止まる                                                                                                                                    |
| MPEG-2 をやめた                                                               | エンコードしたものを canvas に描く (互換モードでなければ `<video>`)                                                                                                                                         |

VideoDecoder は **https か localhost でしか出てきません。** http で開いた LAN では
H.264 / AV1 とも使えず、MPEG-2 で描きます。互換モードの自動は AV1 → H.264 → MPEG-2 の順です ([どの形式で流すか](#どの形式で流すか))。
E2E (`tests/e2e/38-live-compat`) は偽 ffmpeg が本物の H.264 + AAC・AV1 + Opus の fMP4 を流し、描くところまで
見ます (H.264 は走らせている Chromium の VideoDecoder がデコードできるときだけ)。

#### 録画の観る画面も canvas に描く

**互換モードの観る画面 (`/watch/<id>`) は `<video>` を使わず、`/api/recordings/<id>/stream` を fetch で読んで同じエンジンへ流します**
(`canvas-player.ts`。リクエストの仕方は `<video>` でその場で流すとき (`remux-player.ts`) と同じ。[library.md](library.md#何で観るかはサーバが出せるものから画面が選ぶ))。

**互換モードでなくても、MPEG-2 で観るときは同じ経路で描きます** (`ts/playback.ts` の `pickOffer` が `raw` を返す)。エンコード済みの無い録画を家の中の
「自動」で開いたときと、元の TS が残っている録画でコーデックのメニューから MPEG-2 を選んだときです。下の決まり (時刻・飛ぶ・終わり・
先へ読みすぎない・等速だけ) はそのまま効きます。CM スキップ・字幕・データ放送・続きから・切り抜き・音声の選び直し (リクエストし直さない) も互換モードと同じです。

- 並べるのは、サーバが元の TS を流せて (`offers` に `raw`)、この端末でデコードできるとき (`raw/support.ts`) だけ。元の TS を消した録画と、
  前のバージョンで CM を切ってエンコードした録画 (時刻が合わない) には並ばない
- デコードが間に合わなくなったら、その画面を開いている間は MPEG-2 を外し、自動と同じ決め方で `<video>` に戻す (断り書きに理由)。
  MPEG-2 を選び直せばまた試す
- 端末に保存したもの (エンコード済み) とは関係しない。保存したものを持っていても、MPEG-2 を選べばサーバから元の TS を流す

```
/stream?codec=h264|av1&from= (fMP4。時刻はページの物差し) ─→ ボックスで割る (Fmp4Splitter) ─┐
/stream?codec=mpeg2&from=    (元の TS。X-Denpa-Origin)  ────────────────────────────────┴→ RawEngine (worker・Web Audio)
```

- **どれで描くか** (`ts/playback.ts` の `pickCanvas`)。サーバから使えるのは流すもの (fMP4 と元の TS) だけで、ファイルそのまま
  (Matroska) は使わない (端末に保存したものは下)。自動はエンコード済みと同じ形式の詰め替え (サーバは軽い) → ライブの互換モードと同じ順 (変換の AV1 → H.264 → MPEG-2) で、
  この端末で描けるもの。コーデックのメニューは「自動・AV1・MPEG-2」(録画が出せるものだけ。描けない形式は押せない)
- **時刻はページの物差し。** fMP4 はサーバが物差しのまま書いてくる。元の TS は放送の PTS なので、応答の
  `X-Denpa-Origin` (物差しの 0 にあたる PTS) を引いて一周の中で取る (`ts/seek.ts` の `sinceHead`)。字幕
  (`captions.json`)・チャプター (CM スキップ)・データ放送・続きの位置はこの位置で引く (40ms ごとの刻み)
- **決め方は追っかけと同じ `follow`** (`playout.ts`)。止めたら位置を保ってそこから再開し、溜まっても今へは飛ばない。
  録画のために足したのは次の 2 つ。
  - **飛ぶ** (シークバー・← →・前/次のチャプター・CM スキップ・続きから)。持っているものを捨てて、飛び先からリクエストし直す。
    サーバは飛び先の少し手前 (キーフレーム・1 秒前) から流すので、**手前のコマはデコードするだけで描かず** (worker の `floor`)、
    音も飛び先から鳴らす。描けるまでは前の映像のまま (`<video>` のような蓋 (`cover`) は要らない)
  - **終わり** (`finish`)。末尾まで読んだら、バッファが足りなくても残りを鳴らし、鳴らしきったら止まる (`ended`)
- **先へ読みすぎない。** 手元の音が fMP4 は 30 秒、元の TS は 10 秒を超えたら読むのを待つ
  (fetch のストリームが詰まり、サーバも送るのを待つ)。デコーダを読み込み終えるまではバイト数 (8MB) で区切る。それでも
  溢れたら (worker が `full`) いまの位置からリクエストし直す
- **速さは等速だけ** (メニューを出さない)。切り抜き・小窓・バックグラウンド再生 (`<audio>` を通す) はライブと同じ仕組み
- 切れたら観ていた位置からリクエストし直す。混んでいて断られたら (503)、変換させずに描けるもの (詰め替え・MPEG-2) を勧める
- **描けなくなったらライブと同じ順で移る** (断り書きに理由)。どれも無理なら理由を出して止まる。**`<video>` には戻らない**
- **端末に保存したもの (オフライン) も canvas に描く** (`mkv-source.ts` → `raw/mkv.ts`)。保存してあるのはエンコード済みの
  Matroska で、**fMP4 に組み直さず worker がそのまま読み**、読んだコマを fMP4 の経路 (`Fmp4Video`) へ渡す
  (`ts/mkv-media.ts` が Tracks の CodecPrivate (avcC / av1C / AudioSpecificConfig / OpusHead) とコマを読む)。
  - 飛ぶ位置は Matroska の **Cues** から引く (SeekHead が在りかを言う)。先頭 (最初の Cluster まで) に飛び先の手前の
    Cluster からを繋いで、`Blob.stream` で流す。手前のコマは描かない (`floor`)。Cues が無ければ先頭から
  - Matroska のコマは見せる時刻しか持たないので、デコードする順の時刻は、先の 4 コマの見せる時刻のうちまだ使っていない
    いちばん早いものを 1 つずつ使い、4 コマぶん手前にずらして作る (H.264 の B フレーム。`raw/mkv.ts`)
  - 音は選んだ 1 本 (音声のメニューはトラックの名前 → 言語 → 連番)。選び直すといまの位置から読み直す
  - 描けない形式か読めなければ、サーバから流すものへ。オフラインなら理由を出して止まる

E2E (`tests/e2e/40-watch-compat` と `40-watch-compat-long`) は、偽 ffmpeg が作り置きの fMP4 をリクエストされた位置から並べて出すもの (`fmp4-out.ts`) と、
偽の放送の MPEG-2 をそのまま描き、元の TS の位置が物差しに直っているかを見る。飛ぶ・CM スキップ・字幕・止めて再開は、
長い録画のふりをして (`fmp4-clip.ts`) 見る。

## データ放送の統合

**デコードする側も描く側も自前です。映像は denpa が持つ。** 2026-10 まで otya128/web-bml を使っていた経緯は
[stream-history.md](stream-history.md#web-bml-を使っていた頃)。

運び方は衛星のロゴと同じ DSM-CC で、共通のところは `packages/arib/src/dsmcc.ts` (ロゴは `ts/logo-dsmcc.ts`)、データ放送の読み方は `packages/arib/src/bml.ts`。
モジュールの中身 (multipart) を切るのも自前 (`packages/arib/src/multipart.ts`)。TS を直に読むので psisiarc も要らない。

渡す形式 (`ResponseMessage`) は web-bml の取り決めを写して `packages/arib/src/bml-protocol.ts` に置いた。
録画の隣の `.bml.jsonl` がこの形式で残るので、**名前と意味は変えない** (足すのはよい)。

| 型                               | 中身                                                   |
| -------------------------------- | ------------------------------------------------------ |
| `pmt`                            | データ放送の component (PID・componentId・BXML の情報) |
| `moduleListUpdated`              | どのモジュールが何バイトか (DII)                       |
| `moduleDownloaded`               | 揃ったモジュール。ファイルごとに base64 と MIME        |
| `esEventUpdated` / `currentTime` | イベントメッセージ・NPT・放送の時刻                    |
| `programInfo`                    | 局の番号と番組 (denpa が DB から作る)                  |

```
エージェント → denpa ┬→ ffmpeg ┬→ fMP4 → MSE          (映像・音声)
                     │         └→ mkv  → デコードする → canvas (字幕)
                     └→ BmlDecoder → 組み立て済みモジュール → 画面のエンジン (src/lib/bml/)
```

ffmpeg は 1 本のまま、チューナーも 1 つのまま。

### いま入っているところ

デコードする側は `server/databroadcast.ts`、描く側の入れ物は `components/player/DataBroadcast.svelte`。
1 局に絞った TS の写しを `BmlDecoder` へ分け (`Session.tap`)、出てきたものを
`CHANNEL.data` (0x30) に JSON で載せます。覚えておくぶんは `ts/carousel.ts`。

実機の録画 (1 局に絞った約 40 秒ぶん) で、揃ったモジュールは 16 個・約 1.4MB、速さは 128 MB/s (放送の 17 Mbit/s に対して**1 コアの 1.7%**)、
繋いできた人に配り直すぶんは 18 個・2MB。

**リクエストされてからデコードします。** 見ている人のほとんどは押さないので、画面から
`{ type: 'data', on: true }` が来たときだけ回し、誰も出していなければ畳みます。引き換えに、押してから出るまで
カルーセルが一周するのを待ちます (大きいモジュールほど間隔が空く)。常に受信する端末は、選局したらすぐリクエストします ([常に受信する端末](#常に受信する端末))。

決めたことは次の 4 つです。

- **`pcr` は出さない。** 毎秒 50 個ほど来るうえ、denpa では映像そのものが時計です
- **`programInfo` はデコードする側から出さない。** denpa は自前の番組表から作るほうが正確で安い
  (`Session.programInfo`)。描く側は局の番号をこれで知ります (`arib-dc://` の名前を解決する・NVRAM を局ごとに分ける)。
  中継の番号 (`transportStreamId`) だけは、絞るときに読む PAT の先頭から読み取ります (`ServiceFilter`)。
  テレ朝の TVer リンクは `browser.getProgramID(4)` でこれを取って TVer のサーバへ送るので、`null` のままだと
  「情報を取得することができませんでした。[エラーコード:DT-RE]」で断られます
- **`pmt` は変わったときだけ。** モジュールも同じバージョンは配り直しません (カルーセルは回り続け、バージョンが上がらなくても同じものが何度も揃う)
- **デコードする側がエラーを返しても映像は止めない。** 投げ返すと TS を送り込んでいるところごと落ち、映像まで出なくなります

### 描く側 (`src/lib/bml/`)

**denpa が作る `ResponseMessage` をそのまま受け取る。** Svelte から切り離してあり、画面の入れ物は
[DataBroadcast.svelte](../src/lib/components/player/DataBroadcast.svelte) が持つ。

```ts
const bml = createBml({
  root,
  fonts,
  ip,
  store,
  receiver,
  clock,
  onVideoRect /* ほかは bml/engine.ts の型 */,
});
bml.feed(message); // ← packages/arib/src/bml.ts が出すものをそのまま
bml.key(code, down); // AribKeyCode (20 が d)
bml.listens("DataButtonPressed");
bml.destroy();
```

外のライブラリは使わない。中継を呼ぶ `relay.ts` だけは SvelteKit の `$app/paths` を読み、画面 (`DataBroadcast.svelte`・`HybridcastFrame.svelte`) から使う。

  (データ取得中が下りる) まで映像のままにする。`visibility` では隠せない。エンジンは描く要素ごとに BML の `visibility` を写すので、
  子の visible が親の hidden を打ち消す
- 切り分けのために `data-showing` / `data-receiving` / `data-handed` を外へ出してある
  (「押しても何も出ない」が、届いていないのか描かれないのかを外から見分けるため)
- **文字は EUC-JP の符号として扱う** (`charCodeAt`・`fromCharCode`・大小)。TBS・テレ東が `String.fromCharCode(0xA1A1〜)` を、
  MX が `charCodeAt` を EUC の範囲と比べる書き方を使っていた。数は整数 (割り算は切り捨て)、Date は日本の時刻
- **メインスレッドを続けて使うのは 1 つの仕事で 5ms まで** ([budget.ts](../src/lib/bml/budget.ts))。スクリプト・描き直し・Promise の続きは
  全部この下で動かす。「仕事」はブラウザのタスク 1 つと、それに続くマイクロタスク全部。マイクロタスクで
  入り直しても区切りは始め直さない (始め直すと、マイクロタスクで回り続ける文書でタブごと固まる)。区切りで明け渡しても
  休みなく回り続ける文書 (10 秒のうち 4 割を超えて動く) は止めて、ログに残す

`browser.*` は放送が呼ぶ 53 種を全部持ち、動かせないもの (予約・PPP・外のアプリ) は規格どおり失敗 (NaN / null / 0) を返す。
Hybridcast の起動は画面に任せる ([Hybridcast](#hybridcast))。選局 (`epgTune`) も画面に任せる
(ライブは局の一覧から探して切り替え、録画は失敗を返して「録画の再生中は選局できません」と知らせる)。
録画では再生位置から放送の時刻を出して渡す (`clock`)。

**移れない文書へ移ろうとしても、今の文書のまま失敗 (NaN) を返す。** `launchDocument` は名前を先に
確かめ、別の局の `arib-dc://`・ftp・PMT や DII に無いモジュールなら、今の文書を捨てずに
NaN を返す (放送のアプリはこれを見て「接続できません」などを自分で出す)。先に今の文書を捨てると、NHK の入口は `invisible` のまま
d を待つ文書なので、データ放送が閉じたように見える。DII には載っているがまだ届いていないモジュールは、待ってから移る。

**通信の文書 (http・https) へも移る** (TR-B14 の通信コンテンツ)。`launchDocument("https://…")` は
文書を中継 (`/api/bml/proxy`、[双方向 (通信系コンテンツ) プロキシ](#双方向通信系コンテンツプロキシ)) で取るまでスクリプトを待たせ、取れたら今の文書を捨てて移る。
双方向がオフ・中継が断った・相手が 2xx 以外・BML でない (`text/X-arib-bml` でも先頭に `<bml` も無い)
なら NaN を返して今の文書のまま。

|            |                                                                                                                                                                                                                                                                                          |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 中の名前   | 相対の名前 (画像・CSS・script・次の文書) は文書の URL から解決し、同じ中継で取る。`arib-dc://` は放送のものとして引く (放送へ戻れる)。`~/` は放送の部品を指す書き方なので、通信の文書からは使えない                                                                                      |
| 今どちらか | `getBrowserStatus("TerrP", "IRDState", …)` は、放送の文書なら `Broadcast` が 1、通信の文書なら `Link` が 1 (もう片方は 0)。局のスクリプトはこれで BinaryTable などの置き場を選ぶ。両方を 1 にすると、通信の文書で放送のモジュールの名前を作り、それを URL として取得しようとして失敗する |
| 覚えておく | 画像・CSS・script は 64 個・8MB まで覚え、長く使っていないものから捨てる。今の文書が使っているものは捨てない。文書そのものは移るたびに取り直す (投票の結果などを古いバージョンで出さない)。取れなかった画像は覚えて取り直さない                                                          |
| NVRAM      | 通信の文書から使えるのは `nvram://local_web/` と、受信機の設定 (`receiverinfo/`) を読むことだけ。放送の文書が覚えたもの (同意・地域など) を外から来た文書に渡さない                                                                                                                      |
| 押さえる   | `lockModuleOnMemory` はカルーセルのモジュールだけ。通信の文書にいる間は PMT・DII が変わっても入口へ出直さない (データイベントの「入口へ戻る」は従う。PMT から入口の部品 0x40 が消えたら閉じる)                                                                                           |
| CSP        | 変えない。取るのは同じオリジンの中継で (`connect-src 'self'`)、画像は今までどおり blob: に作り直す                                                                                                                                                                                       |

まだ無いもの: NPT (PCR を送っていないので、時刻指定のイベントメッセージと NPT の TimerFired は起きない)。

### 常に受信する端末

**受信するのと開くのは別のこと。** 再生の設定 (⚙) の「データ放送を常に受信」(ライブと録画の観る画面で同じ 1 つ) をオンにした端末
(`components/player/data-receive.ts`。localStorage の `player-data-always` に端末ごとに覚える。既定はオフ) は、局を映している間はいつもサーバに
`{ type: 'data', on: true }` をリクエストし、開く (d) 前からエンジンを動かします。テレビが d を押す前から入口を裏で動かしているのと同じです。

番組の側から「データ放送を開いて」と受信機に求める合図は ARIB に無く、番組に合わせた誘導 (「d ボタンで参加」など) は、
イベントメッセージ・モジュールの更新・時刻を受けた文書が自分で描くものです。なので、**文書が自分で出したものはそのまま映像に重ねます**
(映像を小窓へ寄せる文書なら、開いていなくても寄る)。受信していない端末はこれに応えられません。

|                      |                                                                                                                                                                                    |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 入口を始めるか       | データ符号化方式記述子の `auto_start_flag` (TR-B14 第二分冊 2.1.4・TR-B15 第一分冊 5.1.5) がある入口だけ、開く前から始める。無い入口は開いたら始める (エンジンの `opened`・`open`) |
| 開くまで渡さないもの | リモコン (右の列に出さない)・キー・d。選局 (`epgTune`) と Hybridcast の起動は断る (文書には失敗を返す)。勝手に局が替わったり外のアプリが開いたりしない                             |
| 出し方               | 揃うまで映像のまま (開いたときの 8 秒の見切りはしない)。「データ取得中…」も出さない                                                                                                |
| 開く                 | エンジンは作り直さず、出す操作を d の 1 押しとして届ける (今までと同じ)。カルーセルを待たないぶん早く出る                                                                          |
| 閉じる               | エンジンは捨てず、入口から出直させる (`reset`。待機の状態へ戻す)。Hybridcast のアプリは閉じる                                                                                      |
| 帯域                 | 選局のたびに覚えているぶん (実機で約 2MB) と、その後の更新ぶん。デコードは誰かが受信している間セッションに 1 つ (人数では増えない)                                                 |

追っかけと、録画に譲っている間は局を映していないのでリクエストしません (開いていれば今までどおり)。追っかけはもともとデータ放送を出しません。

**録画の観る画面も同じ決まりです。** 録画のデータ放送はサーバのデコードではなく、エンコードするときに取り出した変化ログ
(`server/recorded-bml.ts` の `.bml.jsonl`) を再生位置に合わせて流す経路ですが、常に受信する端末は開く前から変化ログを取得して流し、
入口の文書を裏で動かします (行が出るのはデータ放送のある録画だけ)。開くまで渡さないもの・開く・閉じるはライブと同じで、
文書からの選局は開くまで黙って断ります (「録画の再生中は選局できません」と知らせるのは開いているときだけ)。

- **戻った (シークで巻き戻した) ら、エンジンを作り直してその位置まで積み直す** (`ts/data-timeline.ts` の `feedFor`。今までと同じ)。
  開いているかは持ち越し、入口から出直す。開いていれば出す操作を d の 1 押しとして届け直し、開いていなければ裏で動かすだけ
- **先へ飛んだ (シーク・CM 飛ばし) ときは、その間の変化をまとめて足す** (作り直さない。文書は続きから動く)

## 双方向（通信系コンテンツ）プロキシ

放送局の通信系サーバは受信機の専用ネットワークスタックが前提で、CORS ヘッダを返さない。
そこで **SvelteKit サーバが中継する** (中身は [server/bml-network.ts](../src/lib/server/bml-network.ts))。

| エンドポイント     | BML の API                                                        | 何をする                                                  |
| ------------------ | ----------------------------------------------------------------- | --------------------------------------------------------- |
| `/api/bml/proxy`   | `launchDocument("https://…")` と、その文書の中の画像・CSS・script | GET して中身をそのまま返す                                |
| `/api/bml/post`    | `transmitTextDataOverIP`                                          | POST してレスポンスをそのまま返す                         |
| `/api/bml/confirm` | `confirmIPNetwork`                                                | 相手の 443 番へ繋がるか (ICMP はコンテナの中から送れない) |

**「送る」は応募・投票のためだけの API ではない。** 放送のアプリは `isIPConnected` の申告を信じない。NHK は送る API へ一度送ってみて、
返らなければ「インターネットに接続されていません」と案内する (`confirmIPNetwork` は呼ばない)。通さないと、双方向をオンにしていても
オフと同じ画面になる。

**既定はオン。** テレビと同じく、データ放送の通信の項目 (お知らせ・応募・投票・利用状況の調査など) が開く。引き換えに、応募や投票、
視聴の記録 (NHK の「利用調査」など) が放送局へ送られうる。同意を取るのは放送の文書で、denpa は通すだけ。
設定の「受信」の「データ放送」(`/settings/reception#broadcast`) の説明にこのことを出し、「双方向 (通信系コンテンツ) を使う」を
切ればこの API は 403 を返し、画面側も `isIPConnected` に 0 を返す。録画の再生では通信しない。
既定がオフだった頃にこの設定を保存した人は、保存した値 (オフ) のまま変わらない。

### 局ごとのドメイン表は持たない

「いま映している局のドメインだけ許す」には、局とドメインの対応表が要る。**その表は必ず古くなり**、新しい局や引っ越した先で
黙って繋がらなくなる (放送側の不調と見分けが付かない)。代わりに繋ぎ先ではなく繋ぐ範囲を縛る。危ないのは放送局以外に繋ぐことではなく、
**denpa のサーバが内側に繋ぐこと** (SSRF) だから。

|          |                                                                                                                                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| メソッド | GET と POST。中身は組み立てない。描く側が `Denbun=…` まで作って渡してくるので、`application/x-www-form-urlencoded` として素通しし、レスポンスもデコードせずに返す                                                                                                                     |
| 相手     | **公開アドレスのみ**。私設・ループバック・リンクローカル (クラウドのメタデータ)・CGNAT・マルチキャストは断る。IPv6 は公開のユニキャスト (2000::/3) だけで、IPv4 を埋め込んだ NAT64・6to4 は中の IPv4 で見る                                                                           |
| ポート   | 80・443 と 8080・8443 だけ。公開アドレスでも Web 以外のサービスへは繋がない                                                                                                                                                                                                           |
| 仕組み   | http と https。`file:` などへ逃がす経路は塞ぐ                                                                                                                                                                                                                                         |
| 見方     | 名前ではなく引いた先で見る。`localhost` の別名や、内側を指す公開の名前は綴りでは見分けられない。名前は `BML_DNS` で引く。家庭の DNS フィルタが局のドメインを 0.0.0.0 に落とすと、上の防御が正しく断ってしまう ([config.md](config.md))                                                |
| 追いかけ | 3 回まで。行き先ごとに確かめ直す (1 回目が公開でも、飛ばされた先が内側のことがある)                                                                                                                                                                                                   |
| 大きさ   | 4MB / 待ち 10 秒 (追いかけるぶんと本文を読み終えるまでを含めた全体) / 同時に 32 本まで (あふれたら待たせずに断る)                                                                                                                                                                     |
| 持ち物   | 何も渡さない (cookie も認証も、User-Agent も)。denpa の資格情報も、端末や利用者を見分けるものも外へ出ない。放送の文書が自分で本文に入れたものは通る (テレビと同じ)。User-Agent で断る局が出たら `denpa/<バージョン>` と名乗る (実在の受信機は名乗らない)                              |
| 証明書   | 確かめない。放送局の通信系サーバは証明書の鎖を最後まで送ってこないことがあり、確かめるとフジの `tvid-sha1.tver-tech.co.jp` が `unable to get local issuer certificate` で失敗する (`doRequest`)。資格情報は何も乗せず、素の http も通しているので、確かめないことで増える危険は小さい |
| 返し方   | 相手の形式のまま返し、`sandbox` の CSP と `nosniff` を付ける (直に開かれても denpa のオリジンの文書にしない)。fetch・XHR 以外の読み込み (ページとして開く・`<img>` など。`sec-fetch-dest` で見る) は繋ぐ前に 403                                                                      |
| 記録     | 断ったものは何に繋ごうとしたかを残す                                                                                                                                                                                                                                                  |
| 使える人 | denpa の画面を使える人だけ (信頼するネットワーク・ログイン・アクセストークン。`hooks.server.ts`)                                                                                                                                                                                      |

## Hybridcast

**データ放送が起動を求めたら、denpa の中で開く。受信機の API は用意できる範囲だけ。**

データ放送 (BML) と違い、**アプリは放送波で送られていません**。
放送波で届くのは AIT という表だけで、中身は放送局のサーバから HTTPS で取得します。

```
PMT ─ ES に application_signalling_descriptor (0x6F) ─→ その PID に AIT
AIT ─ transport_protocol_descriptor        (URL の先頭)
    └ simple_application_location_descriptor (その先の経路)  →  アプリの URL
```

[packages/arib/src/ait.ts](../packages/arib/src/ait.ts) は表を読むだけです。**押されなくても読みます** (デコードする量が無いうえ、押すまで在ることが
分からないのでは出したいものが出せない)。載っていない局では PMT に印が無いので、AIT を待つこともしません。

見つけたら、操作バーの下の段に**別のタブで開くボタン**を出します (受信機の API が無いので、多くはそのままでは動きません)。
URL の先頭が http(s) でないアプリは出しません (`javascript:` などをボタンから開かせない)。
denpa の中で開くのは、データ放送が `startAITControlledApp` で起動を求めたときです。

### 開くまで

```
データ放送 ─ getBrowserSupport("ARIB", "AITControlledAppEngineFunction", …) → 1 (開けるときだけ)
          ─ startAITControlledApp(…) → 画面が AIT のアプリを開く
画面 ─ アプリの HTML を中継で取得 (/api/bml/proxy)
     ─ 先頭に <base href="アプリの中継の URL"> と差し込み (src/lib/hybridcast/shim.ts) を入れる
       (後ろに、データ放送の Greg・NVRAM を使わせる compat.ts を束ねて入れる。vite.config.ts の ?inject)
     ─ sandbox="allow-scripts" の iframe (/api/bml/hybridcast) へ postMessage で渡し、document.write で開く
アプリ ─ 配信元の画像・script・CSS は <base> から中継 (/api/bml/hc/…) を通して取得
       ─ fetch・XMLHttpRequest・受信機の記憶・受信機 API は postMessage で画面へ
```

- **開けるのは**双方向がオンで、AIT にアプリがあり、データ放送を開いているときだけ。それ以外 (常に受信しているだけのときも) は AIT の問い合わせ
  (`AITControlledAppEngineFunction`・`AITTransferMethod`・`AITTransportMethod`・APIGroup の
  `AITControlledApp.Start`) に 0 と答え、`startAITControlledApp` は失敗を返す (行き先のボタンだけが残る)。
  **開けないのに 1 と答えてはいけません。** BML が起動を求めてきて、そのまま返らなくなります
- **電波に AIT を載せない局もある** (NHK)。PMT に印が無く、データ放送が `AITTransportMethod` の XML・HTTP を訊いてくる。
  双方向がオンでデータ放送を開いていれば、これと `AITControlledAppEngineFunction`・`AITControlledApp.Start` に 1 と答え
  (電波の表で運ぶ `AITTransferMethod` は 0)、`startAITControlledApp` に渡された http(s) の URL を XML の AIT として
  中継で取り、そこにあるアプリを開く (`hybridcast/xml-ait.ts`。ETSI TS 102 809 の形式)。文書には取得し始めた時点で 1 を返す (開く手立てがあるので、上の決まりには反しない。URL を渡されなければ失敗を返す)。
  取れなかったときは `[bml] XML の AIT を読めませんでした` をコンソールに出して、データ放送のまま。
  **XML の AIT を渡せるのは放送の文書だけ**です。通信の文書 (http・https から取った文書) には、XML の AIT の問い合わせに 0 と答え、
  `startAITControlledApp` に URL を渡されても失敗を返す。開いたアプリは局の NVRAM を読み書きできるので、
  外から来た文書が選んだアプリにそれを渡さない (通信の文書に局の NVRAM を使わせないのと同じ決まり)。電波の AIT にあるアプリは通信の文書からも開ける
- **開くのは AIT にある行き先だけ。** 電波に AIT があれば、文書が渡した引数に URL があっても使いません
  (XML の AIT の URL として使うのは、電波に AIT が無いときだけ。その場合も開くのは XML の AIT にある行き先)。数の引数は
  どのアプリかの手がかり (organisation_id と application_id が合うもの → application_id が合うもの →
  autostart のもの → 先頭)
- 何を訊かれたか (`getBrowserSupport` の AIT の問い合わせと `startAITControlledApp` の引数) はブラウザの
  コンソールに `[bml]` で出します。局が何を見て案内を出し分けているかを見るためです
- **アプリは denpa を通して読ませる** (`server/hc-relay.ts`)。NHK のアプリは `http://hc.nhk.or.jp/` にあり、
  そこは https に応じないので、https の画面からは script が Mixed Content として止められる。https のアプリも通す。
  配る script の `location.href = …` などを差し込みへ向けるため (元のサーバから直に読ませると書き換えられず、
  アプリが移るときに iframe ごと外へ行こうとして「This content is blocked」で止められる。NHK の「番組表」は https)。開くときにトークンをもらい
  (`POST /api/bml/hc`。ログインした人だけ)、`<base>` と HTML に直に書かれた配信元の URL を `/api/bml/hc/<トークン>/…`
  へ書き換える。後から作られる要素の URL は差し込みが書き換え、fetch・XHR は元の行き先に戻して今までどおり中継で取る。
  - 中継はログインを見ない (使い捨てのオリジンの iframe からの読み込みには cookie が付かない)。トークンは推測できない乱数で、
    配信元 1 つに結びつき、6 時間で切れる
  - 取り方の決まりは `/api/bml/proxy` と同じ。返すものには `sandbox` の CSP と `nosniff` を付け、直に開かれても
    denpa のオリジンの文書にしない

### 画面

- アプリは映像の上に重ねて、1920x1080 で組ませて枠に合わせて伸ばします (`HybridcastFrame.svelte`)。開いている間は BML を隠します
- **戻る (Backspace・x・リモコンの戻る) と d で閉じて**データ放送へ戻ります
- 色ボタン (r・g・b・y) は受信機のキー (keyCode 403〜406)、矢印・決定・数字はそのまま渡します
  (`KeyEvent.VK_*` と、素の名前の `VK_*` も用意。NHK のアプリは `case VK_LEFT:` と書く)
- アプリが `<object type="video/broadcast">` を置けば、放送の映像をその場所へ縮めて出します。
  **映像はアプリの上に重ねます** (テレビは映像を object の場所に描く。アプリは枠の周りを塗るので、下に敷くと隠れる)。
  無ければ全面、`stop()`・`release()` を呼んだときと、object が見えない (`visibility: hidden`) ときは出しません

### できること・できないこと

| 機能                                     | denpa |                                                                                                                                                                                                                   |
| ---------------------------------------- | ----- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 放送の映像の表示と縮小                   | ○     | `video/broadcast` の object (`bindToCurrentChannel`・`stop`・`setFullScreen`・`currentChannel`・`programmes`)                                                                                                     |
| いまの局と番組                           | ○     | 放送の programInfo と局の一覧から。`navigator.receiverDevice.getCurrentChannel()`・`getCurrentProgram()`                                                                                                          |
| 選局                                     | △     | データ放送の `epgTune` と同じ範囲 (局の一覧にある局だけ)。局が変わるとアプリは閉じる                                                                                                                              |
| 字幕の表示の切り替え                     | ○     | `getCCStatus`・`setCCStatus`                                                                                                                                                                                      |
| 受信機の記憶 (`localStorage`)            | ○     | 配信元のオリジンごとに覚える (`denpa_hybridcast_<オリジン>`。JSON で 256K 字まで。テレビの 256KB に合わせた)。denpa のほかの記憶とは混ぜない                                                                      |
| データ放送の Greg と NVRAM               | ○     | `navigator.bmlCompat.browserPseudo` (`Greg`・`readPersistentArray`・`writePersistentArray`・`checkAccessInfoOfPersistentArray`)。データ放送と同じもの。NVRAM は放送の文書と同じ領域で、起動した局から見える分だけ |
| データ放送へ戻る                         | ○     | `navigator.applicationManager.launchDataBroadcastingBrowser`。アプリを閉じる (戻る先の部品は選べない)                                                                                                             |
| 番組の変わり目                           | △     | `receiverDevice.streamEvent` の番組が変わったことだけ知らせる。放送のイベントメッセージは届けない                                                                                                                 |
| アプリの通信 (`fetch`・`XMLHttpRequest`) | ○     | 中継を通す。GET (HEAD も GET で取る) と POST だけ。POST の形式はフォーム・JSON・文字だけ                                                                                                                          |
| 受信機 ID・証明書・機種                  | ×     | 持たない。`getReceiverId` などは null                                                                                                                                                                             |
| WebSocket・EventSource・sendBeacon       | ×     | 差し込みで中継へ渡せないので使えない                                                                                                                                                                              |
| 同期の XMLHttpRequest                    | △     | 非同期で返す                                                                                                                                                                                                      |
| cookie                                   | ×     | 持たない。`document.cookie` は空                                                                                                                                                                                  |
| DRM 付きの動画                           | ×     | ライセンスサーバが受信機を見る                                                                                                                                                                                    |
| スマホ連携 (Hybridcast Connect)          | ×     | 家の LAN にエンドポイントを開けることになるので作らない                                                                                                                                                           |
| 録画の再生中                             | ×     | データ放送の通信と同じく放送中だけ                                                                                                                                                                                |

受信機 API の名前は IPTVFJ STD-0010 の本文で確かめていません。差し込みは用意していない名前の呼び出しにも
null (使えない) を返し、何を呼ばれたかをコンソールに `[hybridcast] … は使えません` で出します。
本物の放送でここを見て、要るものを足していきます。

### 受信機の名乗り

アプリの中の `navigator.userAgent` には `Hybridcast/1.0 (;;;;;)` を足します。NHK のアプリは、これが無いと
PC 向けの案内のページ (`www.nhk.or.jp/hybridcast/`) へ移り、Hybridcast のトップを出しません。
**メーカー・機種などは空です。** 中継は今までどおり UA を送りません。受信機 ID・証明書も持ちません。
そのため、受信機を確かめるアプリ (メーカーや機種を見る・証明書を求める・会員や視聴の記録を受信機に結ぶ) は動きません。
**denpa 側の努力では越えられないので、作り込みません。**

### 安全のための作り

|                        |                                                                                                                                                                                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| オリジン               | iframe は `sandbox="allow-scripts"` (`allow-same-origin` は付けない)。入れ物 (`/api/bml/hybridcast`) も CSP の `sandbox allow-scripts` を返すので、URL を直に開いても使い捨てのオリジンになる。denpa の cookie・localStorage・画面には触れない              |
| 繋ぐ                   | 入れ物の CSP で `connect-src 'none'`。アプリの通信は差し込みが画面へ渡し、画面が中継で取得する。中継の決まりはデータ放送と同じ。denpa 自身 (内側) へは中継が断る                                                                                            |
| 読み込む               | アプリの配信元の script・画像・CSS は中継から、ほかの配信元のもの (フォント・動画など) は直に (`*`)。フォームの送信・入れ子の iframe・worker・ポップアップ・上の画面を移すことはできない                                                                    |
| 残る危険               | ほかの配信元から読むものは中継を通らないので、アプリ (とアプリが読む外の script) は利用者のブラウザから LAN の中や localhost へ GET を送れる (レスポンスは読めない)。読み込む先のサーバには利用者の IP が見える。テレビのブラウザと同じで、ここは受け入れる |
| 受け取る               | 画面は postMessage の送り元が自分の iframe であることと、形式を確かめる (`frameMessage`)。選局は denpa が許した範囲だけ                                                                                                                                     |
| srcdoc・blob: にしない | それだと denpa の画面の CSP を受け継ぎ、放送局の script が動かない。緩めると denpa の画面の CSP の意味がなくなる。denpa の画面の CSP は `frame-src 'self'` を足しただけ                                                                                     |
| 送られる情報           | アプリが自分で送るもの (視聴の記録・いまの番組など) は通る。テレビと同じ。双方向をオフにすれば起動しない                                                                                                                                                    |
