# 放送波ストリーミングシステム 構成設計

> **映像・音声・字幕 (第1〜2段階) が入っています。** 残っているのはデータ放送だけです
> (低遅延の追い込みは[採用しないことにしました](#webrtc--whep-による低遅延化--不採用))。
> どこまで入っているかは [§4](#4-実装の順序) を見てください。
> [roadmap.md](roadmap.md) の「ライブ視聴の残り」に対応します。

最終更新: 2026-08-08

---

## 1. 前提

| 項目 | 内容 |
| --- | --- |
| デプロイ形態 | **セルフホスト（1ユーザー = 1サーバ）** |
| アプリ | SvelteKit 単一アプリ（配信・視聴の両方を担当） |
| 入力ソース | 放送波 MPEG-TS（ISDB-T / ISDB-S） |
| 目標コーデック | AV1 + Opus |
| 必須機能 | ARIB字幕、データ放送（双方向含む）、複数音声・映像ストリーム |
| 非機能要件 | 低遅延 |

セルフホスト前提であることから、以下は**設計上の考慮から外す**:

- NVRAM のマルチユーザー分離（受信機 = サーバ = ユーザーが 1:1:1 で対応するため）
- ユーザーごとの地域設定・リモコン設定の分離
- 通信系コンテンツのプロキシにおけるユーザー識別

## 2. 全体構成

```
┌─────────────────────────────────────────────────────────────────┐
│ チューナー (エージェント)                                     │
└────────────────────────────┬────────────────────────────────────┘
                             │ MPEG-TS (チャンネル丸ごと)
                             ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ            │
              │  ・1局に絞る (ServiceFilter)  │
              │  ・プロセス管理／再起動        │
              │  ・WebSocket ハブ             │
              │  ・BML通信系プロキシ           │
              └───┬──────────────────────┬───┘
                  │ 1局ぶんの TS          │ (押した人が居るときだけ)
                  ▼                      ▼
     ┌───────────────────────────┐  ┌──────────────────┐
     │ ffmpeg + libaribcaption   │  │ BmlDecoder       │
     │  ├→ pipe:1 fMP4 (映像音声) │  │ カルーセルを     │
     │  └→ pipe:3 mkv (字幕の絵) │  │ 組み立てる       │
     └─────────────┬─────────────┘  └────────┬─────────┘
                   └───────────┬─────────────┘
                               ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ (配る)     │
              └──────────────┬───────────────┘
                             │ WebSocket (メディア + サイドチャネル)
                             ▼
              ┌──────────────────────────────┐
              │   ブラウザ (SvelteKit client) │
              │  ・MSE 直接        → 映像音声 │
              │  ・canvas 重ね     → 字幕     │
              │  ・web-bml         → データ放送│
              └──────────────────────────────┘
```

**映像と字幕は同じ ffmpeg の2つの出口。** 別々に起こすと時刻が揃わないため
（[§5.2](#52-字幕sub2video)）。データ放送を入れるときは、絞った TS をもう一方へ
分ける（`tee` は要らない — 分けるのは denpa の中）。

### 設計上の中核

**メディアとメタデータは同じコンテナに載らない。** ARIB字幕（B24 PES）もデータ放送（DSM-CC カルーセル + PSI/SI）も、fMP4 / WebM には規格上入れられず、ffmpeg も GStreamer も扱えない。したがって:

> **サイドチャネル用の WebSocket を 1 本用意し、字幕とデータ放送を同じ経路に相乗りさせる。**

これは迂回路ではなく、本システムの主要な設計要素である。

### 字幕はサーバで絵にする

**ブラウザに B24 を渡さない。** サーバ側で libaribcaption に描かせ、**絵と時刻だけ**を送る。

放送に絵は流れてこない。乗っているのは文字と「どこに・どの大きさで・何色で・背景の箱つきで」という指定で、テレビはそれを見て毎回自分で描いている。`-sub_type bitmap` はその描画を libaribcaption にやらせたもので、**それが「放送どおりの字幕の絵」**になる。

この経路は**録画側で実装・実測済み**（[encode.md「字幕は PGS 1本だけ」](encode.md#字幕は-pgs-1本だけ)、`src/lib/server/subtitle.ts`）。live で変わるのは出口だけで、`.sup` に書く代わりに WebSocket へ流す。

| | サーバで描く（採用） | ブラウザで描く（aribb24.js） |
| --- | --- | --- |
| 外字 (DRCS) | そのまま絵になる | 実装依存 |
| 位置・背景の箱・点滅 | 放送どおり | 実装依存 |
| 録画との見た目 | **完全に同じ**（同じ描画系） | 別実装なので揃わない |
| 帯域 | **変わった枚だけ送る**ので映像の隣では誤差（[§5.2](#52-字幕sub2video)） | 数百バイト／字幕 |
| サーバ負荷 | **映像と同じ ffmpeg の出口が1つ増えるだけ**（実測では埋もれた） | なし |
| クライアント側の自由度 | 拡大は画像の拡大になる | 文字サイズを変えられる |
| 持つコード | 出口だけ（録画と共通） | 字幕ライブラリ1本 |

出す時刻は[§5.4](#54-時刻同期)。**絵に添えられた時刻にそのまま置く** — 映像と同じ
ffmpeg が付けたものなので、受け側の再生位置と直に比べられる。

### 送るのは PGS ではなく PNG

録画側は同じ絵を PGS にしている。live でもそのまま送りたくなるが、**ブラウザに PGS の
デコーダが無い**。自分で書くことになるうえ、PGS は色を YCrCb 限定レンジでしか持てないので、
サーバで変換したものをクライアントで戻す往復が入る。あの変換は mkv に入れるための
制約であって、live には無い。PNG なら `createImageBitmap()` に渡すだけで済む。

**組ませるのは ffmpeg。** 設計では denpa が切り抜き・256色化・パレット PNG の組み立てまで
やることにしていたが、**実機で測ったら ffmpeg に畳ませるほうが速かった**
（[§5.2](#52-字幕sub2video)）。`pgs.ts` の `quantize` も `logo-palette.ts` も使っていない。

## 3. コンポーネント選定

| 役割 | 採用 | ★ | 備考 |
| --- | --- | --- | --- |
| エンコード | FFmpeg（将来 QSVEncC/NVEncC/VCEEncC） | — | CLI パイプラインで差し替え可能 |
| 字幕の描画 | xqq/libaribcaption | 127 | `-sub_type bitmap` + sub2video。録画側と同じ。denpa の ffmpeg は `--enable-libaribcaption` で組んである |
| データ放送 | otya128/web-bml | 246 | BMLブラウザ。**描画側だけ借りる** — 解く側は自前 ([§5.6](#56-データ放送の統合)) |
| 再生 | MSE 直接 / Vanilagy/mediabunny | 6,846 | AV1+Opus fMP4 |

★は 2026-08-02 時点。日本の放送関連ツールはスター数が2桁だが**代替が存在しない**ため、数値で評価しないこと。

**TS 整形の `tsreadex` は入れかけて外した。** 挟む理由として挙げたものが、どれも
ffmpeg 単体で足りた（[§4](#tsreadex-は挟まない)）。

**mpegts.js と aribb24.js は使わない。** どちらも「H.264 + MPEG-TS をブラウザで直接再生し、
字幕も TS の中から拾う」構成のための部品で、fMP4 + サイドチャネルにすると出番が無くなる。
段階を踏むために一度その構成を通す案もあったが、**字幕の経路が録画側で先に完成した**ため、
捨てることになるコードを書く理由が無くなった。

## 4. 実装の順序

作るものは1つ。難所は「AV1 のリアルタイムエンコード」だけに絞れているので、そこだけ逃げ道を用意する。

1. **メディア経路** — `ffmpeg → fMP4 → WebSocket → MSE`。まず映像音声だけ出す — **入っています**
2. **字幕** — 同じ ffmpeg の2つ目の出口からサイドチャネルへ流し、canvas に重ねる — **入っています**
3. **データ放送** — 1局に絞った TS の写しを自前の `BmlDecoder` で解き、組み立て済みのモジュールをサイドチャネルへ — **解くところまで入っています** ([§5.6](#56-データ放送の統合))
4. ~~**低遅延の追い込み（任意）**~~ — **やめました。** 縮むのは受け側の貯め (0.2秒〜) だけで、
   開いてから映るまではむしろ伸び、「止めた所から見られる」「5分戻れる」を捨てることになる
   （[§6](#webrtc--whep-による低遅延化--不採用)）

**コーデックは段階ではなく設定にする。** AV1 が回らない環境・Safari では H.264 + AAC に
切り替える。エンコーダとコンテナ以外は共通なので、字幕もデータ放送もそのまま動く。

### 入っているもの

| | |
| --- | --- |
| 画面 | `/live`。左に映像、右にチャンネル。**前回見ていた局から開く** |
| 焼き方 | **H.264 + AAC / AV1 + Opus を見ながら選べる**（[§5.1](#51-エンコード)）。`src/lib/server/live.ts` |
| 運び方 | WebSocket 1本。多重化の頭は [§5.3](#53-websocket-プロトコル) のまま |
| チューナー | 優先度 **9**。録画 (10) にだけ譲り、番組表もロゴもスキャンも蹴る |
| 相乗り | 同じ局を2人で見ても、チューナーも ffmpeg も1つ |
| 畳み方 | **見ている人が0になったら離す**。接続そのものが在席の印 |

**相乗りの単位は局とコマ数と音声と焼き方、そして字幕。** 1本の物理チャンネルに複数の局が
乗っていて、ffmpeg には局を名指しさせている（下記）ので、出てくる絵が局ごとに違う。
コマ数も同じで、国内アニメを見ている人と実写を見ている人では違う。音声も同じで、
二カ国語を主音声で見ている人と副音声で見ている人は別のものを焼いている。
**何本目の字幕かも同じ** — 字幕は映像と同じ ffmpeg が焼くので（[§5.2](#52-字幕sub2video)）、
選び直せば別のものになる。チューナーはエージェント側で相乗りになるので、増えるのは ffmpeg だけ。

### 多重音声はサーバで1本に決める

**「多重音声」と呼ばれるものは中身の違う2通りある。** 見ている人にとってはどちらも
「音声を選ぶ」1つの操作でしかないので、**平らに並べて1つの一覧に見せる**
（`arib.audioTracks`）。

| | 中身 | 分け方 |
| --- | --- | --- |
| デュアルモノ | 音声は**1本**。左に主音声・右に副音声（二カ国語・解説放送） | `-af pan=stereo\|c0=c0\|c1=c0`（副音声は `c1`） |
| 複数の音声 | 音声そのものが**2本以上** | `-map 0:p:<局>:a:<何本目>` |

デュアルモノは1本から3つ（主・副・主+副）出てくる。テレビの「音声切換」と同じ3択。

**選ぶのはサーバ側。** 音声を全部まとめて送ってブラウザで切り替える手もあるが、
MSE は1つの器に複数の音声を入れた fMP4 を、ブラウザによっては切り替えられない
（`audioTracks` の実装がまちまち）。焼くときに1本に決めてしまえば、どのブラウザでも
同じように鳴る。代償は**選び直しが焼き直しになる**こと — チャンネルは変わらないので
チューナーは掴んだままで、かかるのは焼き始めのぶんだけ。

**選べるものは繋いだあとでないと分からない。** 二カ国語の映画が終わればステレオに
戻るので、局の一覧からは決められない。選局のたびに現物を `tuned` に載せて送る。
覚えていた合言葉が選べなくなっていたら先頭に落とす（`arib.pickTrack`）— 落とさないと
番組が変わった瞬間に音が出なくなる。

### 追っかけ再生とライブは別物

止めて見ていたり、帯を戻したりして**わざと遅れて見ている**状態を、ライブと分けて持つ。

| | ライブ | 追っかけ |
| --- | --- | --- |
| 大きく離れたら | **跳んで詰める**（別のタブから戻ったとき） | **跳ばない**（見ようとしていた場面が飛ぶ） |
| 速さ | 自動（1.05倍まで） | **選べる**（1 / 1.25 / 1.5 / 2倍） |
| 追いついたら | — | **自分でライブに戻る** |

**分けていなかった頃は、止めて再開すると勝手に放送の今へ跳んでいた。**
`pacing` が「大きく離れた」としか見ておらず、それが「別のタブから戻ってきた」なのか
「わざと遅れて見ている」なのか区別できていなかった。8秒より長く止めると戻れないので、
「止めた所から見られる」と謳っておきながら実際には効いていない。

**追いついたら自分で戻すのが要る。** 戻さずに選ばれた速さのまま進むと放送を追い越し、
溜まりを使い切って止まる。実機で 15.8 秒遅れから2倍で追わせると、14.9 秒で追いついて
速さが 1 に戻った。

### 開いてから絵が出るまでの内訳

実機（PT3 + `earth_pt3`）で割った。**チューナーが温まっていれば ≈0.89 秒**、
冷えていれば頭に選局の 0.66 秒が付く。

| | |
| --- | --- |
| 画面が動き出して札を取り、WebSocket が繋がるまで | 160ms |
| ffmpeg の立ち上がり（固定） | 530ms |
| 放送の I フレーム待ち | **0〜501ms**（GOP はちょうど 501ms） |
| **貯めてから始める**（`pacing.ts` の `FLOOR`） | **200ms**（0.4秒だったのを半分に。ただし下の「覚えておく」） |
| MSE に入れて1枚映るまで | 40ms |

**貯める量はこちらの都合で動かせる唯一のところ。** 再生を始める条件は
「貯まった尺 ≧ 貯める量」で、電波は実時間で届くのだから、0.4 秒貯めるには
0.4 秒かかる。0.2 秒 = 塊4つぶん（サーバは 0.05 秒ずつ出す）まで下げた。
**足りずに止まったら 0.6 ずつ増える**ので、荒れる経路では自分で伸びる — 迷ったら
小さいほうから始めてよい。

### 一瞬止まって遅延が増えていく

実機で「宅内なのに一瞬止まり、そのたびに遅れが増えて戻らない」が出ていた。
順に切り分けたもの:

| 見たところ | 結果 |
| --- | --- |
| エージェントの環が溢れていないか | 6分の視聴 + 番組表3本の同時取得で **0回** |
| 送り出しが途切れていないか（入口=TLS を通した素の WebSocket で受ける） | H.264 25分 = 25,405個 / 2.3GB、中央 43ms・p95 130ms・p99 194ms、**0.5秒以上の間は0回**。AV1 4分も同じく0回（中央 34ms） |
| 流量が足りていないか | 高校野球で H.264 **14.5 Mbit/s**、AV1 **6.6 Mbit/s**。`-maxrate 8M` で 8.4 Mbit/s まで削った |
| 削っても直らない | 手元のブラウザ（入口込み・8.4 Mbit/s）で8分に**10回、ちょうど60秒ごと** |

**周期が揃っている時点で電波の混み具合ではない。** 遅延の推移を見ると毎回
「3.1秒 → 1.05倍で詰めて 0.3秒 → 止まる」で、**縮める先をいつも `FLOOR` に
していた**のが原因だった。そこでは止まると分かっている高さへ、律儀に毎回
戻っていた。

**止まった高さのすぐ上を、次の下限にする**ようにした（`pacing.ts` の `PROBE`）。
焼き方を一切触らずにこうなった:

| | 途切れ | 遅延 中央 | 遅延 最大 |
| --- | --- | --- | --- |
| 直す前 | 8分に10回 | 1.4秒 | 3.2秒 |
| 下限を覚える | 8分に5回 | 0.7秒 | 3.2秒 |
| 下限を下げ直すまでを2分→10分 | 10分に3回（最後の6分は0回） | 0.9秒 | 1.1秒 |
| `-maxrate` を外す | **10分に1回** | **0.6秒で平ら** | **0.7秒** |

`-maxrate` は上の見立て違いから入れたもので、**外した**。宅内なら帯域は余って
いるので削って得るものが無く、削るのは動きの多い場面の絵のほうになる。
細い経路のためには AV1 を選ぶ道がある。

### 絵だけが遅れる（音と字幕は合っている）

上の直しのあと、実機で別の症状が出た。**音と字幕は合っているのに絵だけ遅れ、
開き直すと直る。**

字幕は再生位置（`currentTime`）に合わせて貼っており、その再生位置は**音が刻んで
いる時計**なので、音と字幕が合うのは当たり前。**絵だけが遅れるなら、遅れているのは
復号**で、運び方でも貯め方でもない（どちらが遅れても時計ごと遅れる）。しかも
ブラウザは遅れたまま出し続けて勝手には戻さないので、**開き直すまで溜まる**。
**遅延の数字にも出ない** — あれは放送の今と再生位置の差なので、絵が何コマ遅れて
出ていても変わらない。

`requestVideoFrameCallback` は「いま画面に出した絵」の時刻をくれるので、再生位置
との差がそのまま「絵だけの遅れ」になる。0.15秒（口の動きのずれが分かりはじめる
手前）を超えたら**その場へ跳び直す** — 開き直しと同じことを、繋ぎも溜まりも
そのままでやる（`live-player.svelte.ts` の `unslip`）。3秒に1回まで。

**跳んで起きた詰まりは数えない。** 跳べば復号器は読み込み直しになって必ず
`waiting` が上がるので、数えると絵を直すたびに貯める量が増える。

切り分けのために画面へ「コマ落ち」と「絵の直し N回」を出している。運び側
（途切れ）と復号側（この2つ）が別々に読めるようにするため。

### 落ち着いた高さは覚えておく

上の下限は**端末に覚えさせている**（`live-player.svelte.ts` の `FLOOR_KEY`)。
開くたびに 0.2 秒から始めていた頃は、**開いて30秒以内に必ず1回止まって**いた —
0.2 秒はどの経路でも足りないので、毎回そこから当たりを探し直すことになる。

置き場が端末なのは、これが**経路の性質**だから。同じ人でも宅内の PC と出先の
タブレットでは別の値になる（続きの位置 `resume_ms` をサーバに置いているのとは
逆の理由）。長く無事なら少しずつ下げて試し直すので、宅外から帰ってくれば戻る。

**帰ってきたときのために、捨てる口も出してある**（`live-player.svelte.ts` の
`relearn`）。自分で下がるとはいっても **10分ごとに 0.3 秒ずつ**（`FORGET`）なので、
線を繋ぎ替えた直後は前の経路の値のまま余計に遅れて見ることになる。押すと覚えた
ものを消し、貯めているぶんも下限まで詰めて放送の今へ戻す。**覚えているものが
あるときだけ出す** — まっさらな端末には捨てるものが無い。

低すぎる側に外れたぶんは放っておいてよい。止まればその場で上がる。

冷えているときの選局 0.66 秒の中身：

| | |
| --- | --- |
| 頼んでから選局の ioctl を出すまで | 42ms |
| **復調器がロックするまで** | **320ms**（実測 319〜323ms。ISDB-T の OFDM フレームは約 205ms） |
| ドライバが TS を出しはじめるまで | 0〜7ms |
| ロックしてから denpa の1バイト目まで | 240ms（PAT 60ms → PMT 110ms → **ECM 50〜250ms** → カードの往復） |

**削れたのは 160ms だけだった。** 画面が繋いでくる前にサーバ側で焼きはじめる
（`server/live.ts` の `warm`）と、その 160ms が ffmpeg の 530ms と重なる。開く局は
ページを組む時点で決まっているので、待たずに始められる。

> **PSI を先に流す手は外した。** ffmpeg は入口で PAT と PMT を待つので、前に開いた
> ときの PAT/PMT を取っておいて先に流せば、選局を待つ 0.66 秒に入口の仕事を重ねられる。
> 単体で測ると効いていた（888ms → 707ms、ばらつきも 342ms → 77ms）。
>
> **実機では切り替えが壊れた。** 電波が来るより先に ffmpeg が入口を読み終えてしまい、
> `-map 0:p:<局>:v:0` がその時点の情報で解決できずに**そのまま終了する**：
>
> ```
> Failed to set value '0:p:24632:v:0' for option 'map': Invalid argument
> Error opening output files: Invalid argument
> ```
>
> 測ったときは選局済みで、呼び水の直後に本物が来ていた。**効くはずの場面
> （選局に 0.66 秒かかるとき）でだけ壊れる**ので、測っているときには見えなかった。

> **同じ落ち方が、先出しとは無関係にも起きていた。** 局が3つ相乗りしている TS
> （実機の tvk / T15。tvk1・2・3 + ワンセグ + データで、局ごとに14本以上の
> ストリームがある）では、`-probesize 400000` が足りず `-map 0:p:24632:v:0` を
> 解決できないまま ffmpeg が降りる。**渡す前に1局へ絞って直した**（下の
> 「渡す前に1局へ絞る」）。

### 渡す前に1局へ絞る

ffmpeg は名指しした局を `-probesize` のぶん読む間に見つけられなければ、
**そのまま終了する**。わざと probesize を下げて T15 で測ったもの（3回ずつ）:

| probesize | 丸ごと渡す | 1局に絞る |
| --- | --- | --- |
| 20KB | **0/3 通る** | 3/3 |
| 50KB | **0/3 通る** | 3/3 |
| 120KB | **1/3 通る** | 3/3 |
| 400KB | 3/3 | 3/3 |

**絞れば 20KB でも通る。** 録画と同じ `ServiceFilter` を通すだけで、ffmpeg が
受け取るのは局が1つだけの TS になる。局を探す仕事が消えるので `-probesize` は
**400KB → 20KB**。字幕側も同じ。

そこまで下げてよいかは、6回ずつ測って決めた:

| probesize | 最短 | 中央 | 通った |
| --- | --- | --- | --- |
| 100KB | 474ms | 839ms | 6/6 |
| **20KB** | **441ms** | 752ms | 6/6 |

**中央値の差はばらつき**（放送の GOP 待ち 0〜501ms）で、**最短どうしの 33ms が
固定の費用**。絞った TS の PAT は最初のパケットから入っているので、探すものが無い。

> **削ったぶん、コマ数は読み切れなくなる。** ffmpeg は時間の刻み（90kHz）から
> でたらめな値を起こすことがあり、x264 は黙って受けるが **SVT-AV1 は突っぱねる**
> （`The maximum allowed frame rate is 240 fps`）。実機で 20KB のまま AV1 を選ぶと
> **0/3**、上限（`-fpsmax`）を付けると **3/3** 通った。
>
> **固定（`-r`）ではなく上限にする。** 固定すると、放送が本当に 59.94p だったとき
> （720p の局）にコマを落とす。上限なら、まともな値のときは何も起きない。

名指し（`0:p:<局>`）はそのまま残す。絞ったものに万一違う局が入っていたら、
**黙って別の局を映すより、そこで落ちるほうがいい**。

**量はほとんど減らない。** 実測は tvk で 17.6 → 16.8 Mbit/s、日テレで
17.3 → 14.5 Mbit/s。相乗りしている局は**同じ ES を指している**ことが多いので
（tvk1/2/3 は同じ中継を流している）、落ちるのは他局ぶんの表と詰め物だけ。
狙いは量ではなく、**ffmpeg に局を探させないこと**。

**黙って黒くなることもなくなった**。ffmpeg が降りたらその場で
「映像を出せませんでした」を出す（下の「焼けなくなったら、その場で言う」）。

### 焼けなくなったら、その場で言う

ffmpeg が降りても何も伝えていなかった頃は、画面には**前の絵が貼られたまま6秒たって
黒くなる**だけだった（`live-player.svelte.ts` の `HOLD_MOST`）。見た目は
「切り替えに6秒かかった」で、実際には失敗しているのに、そうとは分からない出方をする。

2つ直した。

- **終わりを ffmpeg の終了で見る。** 汲み出しは相手が死ねばすぐ終わるが、
  **流し込みは終わらない**（書き込み先が閉じても例外にならないことがあり、放送は
  止まらないので回り続ける）。3つ揃うのを待っていると、死んだことに永久に気づかない
- **畳んだセッションを掴んだままにしない。** 繋いでいる側は同じものを指したままなので、
  同じ局を選び直しても「もう見ている」と見なされて何も起きず、**「やり直す」を
  押しても直らなかった**

**放送が止まっているだけのときは、そう言う。** エージェントの言い分
（「電波が来ていないか、その周波数に放送がありません」）は言い切りとしては正しいが、
**アンテナや配線を疑う文面**になる。実機で「T27 がときどき同期しない」として出たものは、
調べると **NHK総合が保守の晩に停波していた**だけだった:

| | |
| --- | --- |
| 48時間で同期しなかったチャンネル | **T27 だけ**、10回 |
| その時刻 | 01:04〜02:54 JST |
| 番組表が言う T27 の状態 | **00:11〜05:00 が「放送休止」** |
| 窓の外で開いたとき | 一発で通り、5秒で 11.3MB |

同じ NHK でも Eテレ（T26）は休止がほぼ毎晩4〜5時間あるのに一度も失敗していない。
**総合は送信機ごと止め、Eテレは搬送波を出したまま**、ということ。

番組表を持っているのは denpa だけ（エージェントは知らない）なので、言い換えられるのは
こちら側。**同期しなかったときだけ**言い換える — 塞がっていたときや ffmpeg が降りた
ときに「放送休止です」と出すと、今度はこちらが嘘をつく（`server/live.ts` の `whyNotTuned`）。

残りは全部、放送か機材か ARIB の都合：

- **ロックの 320ms はチップの物理時間。** ドライバを替えても同じ
  （`dvb_override_tune_delay` を 1ms にして試すと、DVB core が同期の途中で
  周波数を振り直すぶん **451ms に悪化**した。あの値は「諦めるまでの猶予」で、
  ロックの検出間隔ではない。検出はこちらが 10ms 間隔で直に読んでいる）
- **ロック後の 240ms はスクランブル解除。** ECM が来るまで鍵が作れない
- **I フレーム待ちは放送の GOP。** MPEG-2 は I フレームからしか復号を始められない
- **符号器は道の上に居ない。** `-tune zerolatency` は B フレームも先読みも作らない。
  インタレ解除・音声・塊の細かさを外しても縮まなかった（実測）

器を作り直すと `<video>` は何も映さなくなるので、そのままだとその間ずっと真っ黒になる。

器を捨てる前に1枚だけ canvas へ写して重ね、**次の絵が実際に出た時点で剥がす**
（`requestVideoFrameCallback`。`play()` が返っただけではまだ何も映っていない）。
待ち時間そのものは変わらないが、黒い画面を見せずに済む。絵は止まって見えるが、
それは正しい — 実際に止まっている。

貼りっぱなしを避ける上限（6秒）を置く。**壊れているのに動いて見えるのがいちばん悪い。**

**まず H.264 + AAC で通した。** 狙いは AV1 + Opus だが、実機に HW エンコーダが
無く（`ffmpeg -hwaccels` が空）、CPU も AVX-512 を持たない世代（Xeon E5 v4）なので
ソフトウェアの AV1 は賭けだった。**難所を1つに絞る**ため、確実に出るほうから始めた。
**いまは両方入っていて、見ながら選べます**（[§5.1](#51-エンコード)）。

### `tsreadex` は挟まない

一度は入れかけたが、**挟む理由として挙げたものが、どれも ffmpeg 単体で足りた**。

| 欲しかったもの | 結論 |
| --- | --- |
| デュアルモノ分離 | ffmpeg で足りる。**録画と同じ見分け方**（番組表の音声情報）で、選ばれた側を両耳へ配る（上記）。録画は左右を2トラックに分けるが、ライブは器が1つなので片方を採る |
| 局の選び分け | ffmpeg で足りる。`-map 0:p:<局>:v:0`。実機で確認済み |
| 音声・字幕が消えたときに無音を挿す | tsreadex にしかできない。ただし**実害を確認していない** |
| `aac: Input buffer exhausted` | **そもそも直らない**。壊れた AAC フレームの修復は tsreadex の仕事ではない |

イメージに1つ足す代償に対して、いま得られるものが最後の2行しかない。**3行目の実害を
実際に踏んだら**入れる。

### 局は名指しで選ぶ

**1本の物理チャンネルに複数の局が乗っている。** `-map 0:v:0` は「最初に見つけた映像」
でしかないので、MX2 を選んでも MX1 の絵が出うる。実機の T26 を調べると局が4つ
（Eテレ1/2/3 と**ワンセグ**）並んでいて、ワンセグは 320x180 の H.264 — それを掴む目まである。

`-map 0:p:<局>:v:0` なら選んだ局の中から選ぶ。選局の指示に局まで載せているのは
このためでもある（コマ数の判定と共用）。

### 入口が1つ増えている

**bun の `node:http` は WebSocket の握手ができない。** `upgrade` は上がるのに、
渡される socket に書いても相手に1バイトも届かない（`write()` は true を返し、
コールバックも成功と言う。`_handle` が空）。adapter-node はその上に居るので、
そのままでは通らない。

`svelte-adapter-bun`（[Bun 公式が案内している](https://bun.com/guides/ecosystem/sveltekit)）
にも替えてみたが、**今の SvelteKit では動かない**。あちらは kit の生成物を正規表現で
4か所書き換えて `websocket` フックを挿し込む作りで、`get_hooks` が別チャンクへ
出るようになったため2か所が当たらず、`Bun.serve` に `websocket` が渡らない
（`To enable websocket support, set the "websocket" object` で 500）。

そこで **`Bun.serve` を前に置き、WebSocket だけそこで受ける**（`server.js`）。

```text
ブラウザ ──→ Bun.serve (公開ポート)
                ├ /api/live/socket → WebSocket をここで受ける
                └ それ以外          → 127.0.0.1 の adapter-node へ中継
```

**取るのは WebSocket だけ。** 録画の配信（Range 要求）も認証も SSE も、Pod 入れ替え時に
録画が終わるまで居座る仕掛けも adapter-node に乗っているので、触らないのがいちばん安い。
`Host` はそのまま渡す — 書き換わると CSRF 判定が自分の origin と食い違い、フォーム送信が
全部弾かれる（denpa は名前を2つ持っていて `ORIGIN` で固定できない）。

**開発サーバ（`bun run dev`）ではライブが繋がらない。** vite が持つのは `node:http` で、
上の理由で握手できないため。確かめるときは `bun run build && bun ./server.js` を使う。

### 繋ぐときの認証

**ブラウザは WebSocket の握手に `Authorization` を付けてくれない。** ベーシック認証で
守っている denpa では、そのままだとチューナーを掴む口が素通しになる。

画面が先に `POST /api/live/ticket` で**使い捨ての札**を取り、それを URL に付けて繋ぐ。
札の発行は普通の HTTP なので、ベーシック認証も OIDC も信頼した網もそのまま効く。
**1回使ったら消す**（URL は履歴にもログにも残るため）。寿命は30秒。

## 5. 実装詳細

### 5.1 エンコード

**いま回している形は `src/lib/server/live.ts` の `encodeArgs` にあります。** 1本の
ffmpeg が映像と音声を1つの pipe へ多重化し、`Fmp4Splitter` が `moof`+`mdat` ごとに
割って WebSocket へ流します。

```bash
ffmpeg -nostats -fflags nobuffer -probesize <小さく> <字幕の入口> -i pipe:0 \
    -vf <インタレ解除> \
    -map 0:p:<局>:v:0 -fpsmax <上限> <映像の焼き方> \
    -map 0:p:<局>:a:<何本目> [-af pan=...] <音声の焼き方> \
    -f mp4 -movflags +empty_moov+default_base_moof \
    -frag_duration 50000 -flush_packets 1 pipe:1 \
    <字幕の出口 → pipe:3>
```

**値は書きません。形だけです。** 実測した値と理由は `encodeArgs` の説明にあり、
**写すと必ず片方が古くなります** — 実際ここには `-frag_duration` が古いまま残って
いたことがあり、直したあとも `-probesize` と `-preset` と音声の量が同じように
古くなっていました。なぜこの形かは [§4](#入っているもの) にあります。

- **`-copyts` は付けません。** 付けると放送の絶対時刻が mp4 の多重化器まで届き、
  あれが 0 に詰め直すので、受け側から見た 0 の意味が分からなくなります
  （[§5.4](#54-時刻同期)）。付けなければ ffmpeg が入口で1回だけ 0 に寄せ、
  **その寄せが字幕の出口にも同じだけ効きます**
- **`-loglevel` は下げません。** 選べる字幕は入口の見出しから拾っていて、あれは info
  で出ます（[§5.2](#52-字幕sub2video)）。数字の進み具合だけ `-nostats` で止めます
- クライアント側の SourceBuffer は `segments`（既定）で使う。`sequence` は
  「届いた順に詰める」動きなので、1つ取りこぼすと以降ずっとずれる。
  再生位置の面倒（貯めてから出す・離れたら速める）は `src/lib/ts/pacing.ts`

**将来トラックごとに pipe を分けるなら**、`-movflags +frag_every_frame` に戻せます。
1本に多重化している間は使えません（[§4](#入っているもの)）。複数映像も
そのときの話で、いまは映像1本・音声1本に決め打っています。

#### 焼き方は見ながら選べる

画面の操作列から **H.264 / AV1** を選び直せる（`LiveCodec`）。音声と同じで、選び直すと
焼き直しになる（器から作り直し）が、チャンネルは変わらないのでチューナーは掴んだまま。
**局を変えても引き継ぐ** — 絵の中身ではなく「その端末で出るか」の話なので。

**落ちこぼれない。** 設計では「ソフトウェアの AV1 は厳しい」としていたが、実機
（Xeon E5-2696 v4 / 44スレッド / HW エンコーダ無し）で 1080i を解いて 60 コマ/秒という
いちばん重い形を通しても、**焼けた尺が実時間に付いていった**。コア数で間に合っている。
代償は立ち上がりが 0.45 秒ぶん遅いことで、既定は H.264 のまま — **どの端末でも出る**
ほうから始める。**実測は `videoArgs` の説明に**（[§5.1 冒頭](#51-エンコード) と同じ理由で、
値はここに写しません）。

**量については、まだ何とも言えない。** どちらも品質を指定して焼いている
（ビットレートを決めていない）ので、出てくる量は場面で動く。実測も揃わなかった。

**音声は AV1 のとき Opus、H.264 は AAC。どちらも 256k** — 元の放送（AAC 256kbps）
に合わせた値で、録画側も前から `libopus -b:a 256k`。

#### 役割を分ける — H.264 は「速く」、AV1 は「小さく」

H.264 は**量を捨てて速さを採る**（`-preset ultrafast`、画質は既定のまま）。
**画質を上げると必ず遅くなる** — 最初の1枚が太り、書き出すのに時間がかかるため。
`-crf` を付けないのが最速で、**出てくる絵は今までと同じ**（同じ crf 23）。増えるのは
量だけで、同じ画質を `ultrafast` で出すと 3 倍になる（実測は `videoArgs`）。
そのぶん**宅内向けの値**になるので、宅外から見るときは AV1 を選ぶ。

> **戻れる幅はバイト数でも切る。** 5分（`KEEP`）は「毎秒 3Mbit なら 110MB」の
> つもりの値だった。速さを採ったぶん太った流れで5分持つと `appendBuffer` が
> `QuotaExceededError` で落ちて**そこから絵が出なくなる**。受け取っている速さから
> 120MB に収まる長さを出して、時間と小さいほうで切る（`live-player.svelte.ts`）。

`lookahead=0` が要る。SVT-AV1 は既定で先を読むぶん貯めるので、付けないとその貯めが
そのまま遅れになる。preset 12 を採る（13 は目に見えて粗く、10 は間に合わない）。

> **付けてもまだ溜め込む。** 電波が届いてから mp4 の塊が出るまでが H.264 の数倍かかり、
> 低遅延指定（`pred-struct=1`）は**実時間に間に合わなくなる**（出口が 6秒 → 22秒 と
> 離れていった）。**AV1 を選ぶと放送の今から1秒ぶん離れる**ので、切り替えにもそう書いてある。

**受け取れない端末では H.264 に戻す。** `MediaSource.isTypeSupported` が false なら
その場で戻して、戻した理由を画面に出す。黙って別の形にすると、なぜ切り替えが
効かないのか分からない。

HW エンコーダのある機材なら `av1_nvenc`（RTX40以降）/ `av1_qsv`（Arc・Meteor Lake 以降）/
`av1_amf`（RDNA3以降）に載せ替えられる。

### 5.2 字幕（sub2video）

**映像と同じ ffmpeg が焼く。出口を2つ持つ**（`src/lib/server/captions.ts`）。

```bash
ffmpeg <上の映像の形と同じ> \
    -sub_type bitmap -canvas_size 1920x1080 -font '<丸ゴシック>' -i pipe:0 \
    ... pipe:1 \
    -filter_complex '[0:p:<局>:s:<n>]null[s]' -map '[s]' -fps_mode passthrough \
    -c:v png -pix_fmt rgba -cluster_time_limit 1 -cluster_size_limit 1 \
    -flush_packets 1 -f matroska pipe:3
```

**ここも形だけです**（[§5.1](#51-エンコード) と同じ理由）。値と実測は
`captionInput` / `captionOutput` の説明にあります。

- 字幕をフィルタの入力にすると、字幕1枚ごとに映像フレームになる（sub2video）。
  **通す先は何でもよい**ので `null` にしてある — 通すこと自体が目的
- `-canvas_size` は必須。指定が無いと libaribcaption は 1440x1080 (PROFILE_A) とみなすので、
  1920x1080 の放送では字幕だけ横に伸びる
- **局を名指しする。** 映像と同じ理由（1本の物理チャンネルに複数の局が乗っている）
- **Matroska で受ける。** 時刻をコマと一緒に運ばせるため（下の「時刻はコマに付けて運ぶ」）

#### 1本にしたのは、時刻を揃えるため

以前は映像を作らない ffmpeg をもう1本、同じチャンネルに当てていた。**そうすると時刻が
揃わない。** ffmpeg は入口で時刻を 0 に寄せ直すが、その寄せ幅は**プロセスごとに違う** —
別々に起こした2本は焼き始めの鍵フレームがずれるので、出てきた時刻どうしを突き合わせても
意味を持たない。`-copyts` で放送の絶対時刻を保っても駄目で、**mp4 の多重化器がその時刻を
0 に詰め直す**（`-avoid_negative_ts disabled` も `-muxdelay 0` も `-output_ts_offset` も
効かない。実機で確認）。

1本にすれば**入口の寄せが1回だけになって両方の出口に効く**。実機で突き合わせると 1ms 以内で
一致し、費用も埋もれた（実測は `captions.ts`）。

引き換えに、**音声や焼き方を選び直すと字幕も焼き直し**になる（前は局ごとに1本だったので
途切れなかった）。字幕は次が来るまで出しっぱなしのものなので、焼き直しの間はサーバが
最後の1枚を配り直して繋ぐ。

> **字幕を持たない放送はある**（ショッピングやサブチャンネル）。そこに `[0:p:X:s:0]` を
> 頼むと ffmpeg は**組み立ての時点で降りて、映像も出ない**。そうと分かったら
> 字幕なしで焼き直し、その局は15分覚えておく（`server/live.ts` の `captionless`）。

#### 時刻はコマに付けて運ぶ

生の PNG を並べただけ（`image2pipe`）では時刻が乗らない。**器に入れて運ばせる** —
Matroska を選んだのは、必要なところだけなら小さいから（`src/lib/ts/mkv.ts` が読むのは
`TimestampScale` / `Cluster > Timestamp` / `SimpleBlock`（と `BlockGroup > Block`）だけ）。
NUT はコマの見出しを組み立てるのに表の復元が要り、mp4 は PNG を入れられない。

塊の上限を最小（`-cluster_time_limit 1` / `-cluster_size_limit 1`）にして、1枚ごとに
書き出させる。溜められるとそのぶん遅れる。

**別の口と組にしない。** 以前は `showinfo` に時刻と「空かどうか」を標準エラーへ喋らせ、
その行と標準出力の PNG を来た順に1対1で組にしていた。**数が合わない** — フィルタを通った枚が
そのまま出てくるとは限らないので（同じ時刻の枚は多重化のところで落ちる）、**別々の口から
来るものを位置で突き合わせている限りずれ得る**。一度ずれたら戻らず、字幕が出た枚に1つ前の
「空」が当たって**消す**に化け、「字幕が遅れて固まって出る」という報告そのままの出方をする
（実測は `captions.ts`）。外したぶん ffmpeg の標準エラーも静かになった（40秒で 383行 → 109行）。

#### PNG は ffmpeg に組ませる

設計では生の RGBA を受け取って、denpa が切り抜き・256色化・パレット PNG の組み立てまで
やることにしていた。**実機で測ったら、ffmpeg に PNG まで畳ませるほうが速かった**
（生のほうが遅いのは書く量が桁違いだから。256色に落とすと半分になるが CPU を4倍払う。
実測は `captions.ts`）。denpa 側の切り抜き・色数落とし・PNG 組み立ては、まるごと要らなく
なった（`crop` / `quantize` / `logo-palette` を使う話は無し）。

送るのは画面まるごとの PNG で、受け側は映像と同じ枠に敷いて引き伸ばすだけ。
**切り抜きは要らなかった** — PGS には1秒あたりに送れる量の決まりがあるので録画側では
切っているが、こちらにその縛りは無い。

#### 変わったときだけ送る

**sub2video は同じ絵を何度も出す。** 一本化してからは映像のコマが心拍になるので出てくる
枚数はさらに増えるが、**中身が変わっているのはごく一部**なので、同じ絵は配り直さない。

空の枚（全部透明）も**そのまま送る**。重ねれば消えるので、「消す」に置き換える必要が無い
（[§5.3](#53-websocket-プロトコル) の `0x21` を使わずに済む）。

#### 焼き方ごとに分かれる

一本化したので、**字幕は焼き方（コマ数・音声・コーデック・何本目の字幕か）ごとに
分かれる**。音声を選び直すと字幕も焼き直しになり、同じ局を別の音声で見ている2人は
別々に字幕を描くことになる。

**その代わり、TS をもう一度もらう必要が無くなった。** 別建てだった頃は字幕のために
エージェントから TS を2本目としてもらっていて（ロゴ集めと同じ取引 — [agent.md](agent.md)）、
チャンネルを変える一瞬だけチューナーが1本余分に要った。地上波は2本しかないので、
番組表集めが1本使っているとそこで断られていた（実機で
`[captions] GR:T15: チューナーに空きがありません`）。**その経路ごと無くなった。**

> **字幕が1枚も来ない番組がある。** 絵は描くものがあったときだけ出るので、本編に字幕が
> 無ければ0枚になる（録画側の実測でも同じ）。何も来ないことは異常ではない。
>
> **ボタンを出すかどうかは、届いた枚数では決めない。** 放送が字幕を持っているかは
> ffmpeg の入口の見出しに出ているので、1枚も来ていなくても分かる（`TrackList`）。
> 届いてから出していた頃は、**間隔の空く番組を開くとボタンが出なかった**
> （実機の「みんなの手話」。番組表には [字] と出ているのに出ない）。
> 持っていない放送では出さない — 押しても何も起きない操作を並べない。

### 5.3 WebSocket プロトコル

単一接続で全チャネルを多重化する。

```
[1 byte: channel][8 bytes: 時刻 (90kHz, BE)][payload...]

channel:
  0x00  video init segment (ftyp + moov)
  0x01  video media  (moof + mdat)
  0x10  audio init segment
  0x11  audio media
  0x20  字幕の絵     [2:x][2:y][2:w][2:h][PNG...]
  0x21  字幕を消す   (中身なし) ※いまサーバは送らない
  0x30  PSI/SI + データカルーセル (.psc chunk)
  0x40  制御 (チャンネル切替、EPG更新通知 等)
```

- init セグメントは接続直後に必ず送る（再送用にサーバ側で保持）
- MSE はバイト列をそのまま `appendBuffer()` に投げられるため、映像音声のパースは不要
- 字幕の座標は `-canvas_size` の座標系。表示側の拡大率に合わせて canvas を伸ばす
- **頭の時刻は「焼いた mp4 の物差し」。** 受け側の `video.currentTime` と直に比べられる
  （[§5.4](#54-時刻同期)）。映像も音声も字幕も同じ ffmpeg が焼いているので揃う
- 途中から入ってきた視聴者のために、**いま出ている字幕はサーバが1枚だけ保持して再送する**

### 5.4 時刻同期

| 対象 | 方法 |
| --- | --- |
| 映像・音声 | fMP4 の timescale で自動的に整合 |
| 字幕 | **添えられた時刻に置く。** 映像と同じ ffmpeg が付けた mp4 の物差し |
| データ放送 | カルーセルは時刻同期不要（PMT/TOT/EIT の更新に追従） |

**いまは測っていません。** 字幕のコマに時刻が付いてくるので、受け側は再生位置と
比べて「追い越していない中の最後の1つ」を出すだけです（`ts/captions.ts`）。
揃うのは、映像と字幕を**同じ ffmpeg で焼いている**からです（[§5.2](#52-字幕sub2video)）。

#### そこへ来るまでに3回外しました

**どれも「別々の ffmpeg の出口どうしを突き合わせて測る」ことをしていました。**

| 使った基準 | 実測のずれ |
| --- | --- |
| mp4 の 0（＝焼かれた1コマ目のつもり） | **2.4秒**。多重化器が 0 に合わせるのは probe の間に溜まった**音声** |
| 焼いている絵の時刻（映像側の `showinfo`） | **5秒**。フィルタは符号器より先を走る |
| 字幕側の `showinfo` が言う放送時刻 | **1秒ほど遅れる**。行と絵の数が合わず、組がずれる（[§5.2](#52-字幕sub2video)） |

諦めて「時刻ではなく**待たせる量**を渡す」ことにしましたが、**そちらも3回外しました。**
値ではなく、見方の間違いです。

| | 何を見落としたか | 出た症状 |
| --- | --- | --- |
| 1回目 | **映像も先送りされている**ことを忘れ、字幕の先回りだけを見た | 0.5 秒待たせ、字幕が遅れた |
| 2回目 | 両方の差は採ったが、**焼く手間がそれを食う**ことを数え落とした | 0.42 秒待たせ、まだ遅れた |
| 3回目 | 待たせる量は 0 にしたが、**置く先を「届いている映像の端」にしていた** | 貯めているぶん（0.2 秒）遅れた |

1回目で「4局とも差は 7ms に収まる」と見えたのは**確かめになっていませんでした** —
字幕と映像の先回りは局ごとに同じ方向へ動くので、片方だけ見ても揃って見えます。

**測って詰めることはできませんでした。** 焼いた mp4 の中身がどの放送時刻に当たるかは
多重化器が握っていて外から見えず、別々に起こした ffmpeg は焼き始めの鍵フレームが
0〜0.5 秒ずれます。装置を5通り作って -60〜+450ms とばらけ、同じ局を2回測って 150ms
動きました。**測れないものを測ろうとしていました。**

#### 直したのは測り方ではなく、作り

**1本の ffmpeg に両方を焼かせれば、入口の寄せが1回で済んで時刻が揃います**
（[§5.2](#52-字幕sub2video) に実測。1ms 以内で一致）。そうすると測るものが無くなります。

`-copyts` は**外しました**。付けると放送の絶対時刻が mp4 の多重化器まで届き、
あれが 0 に詰め直すので受け側から見た 0 の意味が分からなくなります（実機では
`Assertion next_dts <= 0x7fffffff failed at libavformat/movenc.c` で**映像ごと落ちも
しました** — 放送時刻は 32bit に収まりません）。

**貼り直すのは、映した1枚ごと**（`live-player` の `follow`）。届いた塊に相乗りして
いた頃は 0.05 秒刻みでしか貼り直さず、**遅れる方向にだけ** 0〜50ms ずれていました。

**焼き直しのたびに、待たせている字幕は捨てます。** 音声や焼き方を選び直せば mp4 の
時刻は 0 から数え直しになるので、前の時刻で待たせているものはどれも合いません
（`live-player` の `forget`）。

### 5.5 放送そのまま（MPEG-2）は出せない

**ブラウザに MPEG-2 の復号器が無い。** Chromium 151 で実際に聞いた結果:

| 聞き方 | `mp2v` / `mpeg2video` | `avc1` | `av01` | `vp09` | AAC |
| --- | --- | --- | --- | --- | --- |
| `MediaSource.isTypeSupported` | **×** | ○ | ○ | ○ | ○ |
| `VideoDecoder.isConfigSupported` | **×** | ○ | ○ | ○ | ○ |

（`video/mp2t` そのものは ○ だが、これは**中身が H.264 の TS** の話。放送の
MPEG-2 を入れても出ない）

つまり「焼かずにそのまま送る」を画面で出すには、**WASM で復号器を持ち込む**しかない
（libmpeg2 相当。音声の AAC はブラウザにあるのでそのまま使える）。得るものは大きい —
ffmpeg の立ち上がり 0.5〜0.7 秒が丸ごと消え、サーバの CPU も 350〜470% からほぼ 0 に
なる。**遅延も、焼くのに掛かっているぶん（電波が届いてから塊が出るまで。実測は
`server/live.ts` の `videoArgs`）が丸ごと落ちる** — 残るのは受け側の貯め（`ts/pacing.ts` の
`FLOOR` から始まる貯め）だけになる。**TVTest 並みに手が届くのはこの道だけ。**

払うものも大きい:

- **帯域が増える。** 1局に絞った生の TS は実測 14.5〜16.8 Mbit/s で、中身によらずほぼ
  一定。焼いたものは形と場面で動き（AV1 なら数分の1まで、速さを採った H.264 では
  半分程度まで。実測は `videoArgs`）、**宅外から見ることを考えるとここがいちばん重い**
- 端末の CPU と電池（特に携帯）
- **MSE をやめることになる。** 貯め方・追っかけ再生・5分戻れる仕組みは全部 MSE の
  `buffered` に乗っている。自前の復号器だと、時刻合わせも溜め方も巻き戻しも書き直し。
  1080i の解除もシェーダで自前になり、いまの `bwdif` より落ちる

やるなら **LAN のときだけ生、宅外は焼く**という分け方になる（`TRUSTED_NETWORKS` で
既に見分けている）。**まだ入っていない。**

### 5.6 データ放送の統合

web-bml は Node.js サーバ + ブラウザクライアント構成（既定ポート 23234）。
セルフホスト前提なので、NVRAM は web-bml の既定実装（サーバローカル保存）をそのまま使う。

**映像は denpa が持つ。web-bml からは「解く側」だけを借りる。**

素直に「サイドカーとして起動して iframe で抱える」をやると**映像を出すプレイヤーが
2つ**になる。web-bml が受け取るのは Mirakurun / EPGStation / TSファイルで、
**自前の ffmpeg で HLS を作って自分の `<video>` に映す**ためで、そうすると
denpa 側の貯め方も字幕も焼き方の切り替えも、その画面では使われない。HLS の遅延は
数秒なので、denpa の 0.6秒 の絵に重ねることもできない。

**借りるのは描画側と、渡す形の取り決めだけ。解く側は自前です。**

一度は解く側 (`server/decode_ts.ts`) も借りました。あれは TS を流し込む Node の
ストリームで、**組み立て終わったモジュール**を `sendCallback` で吐きます。ただし
998行のうち **denpa が通るのは3割** (DSM-CC と PMT の記述子) で、残りは
EIT/SDT/NIT や字幕の PES — どれも denpa に自前のものがあります
(`ts/eit.ts` / `ts/psi.ts` / 字幕は ffmpeg が絵にする)。その3割のために
`@chinachu/aribts` (2.3MB) を抱えることになるので、書き直しました。

**運び方は衛星のロゴと同じ DSM-CC で、denpa は既に持っていました**
(`ts/logo-dsmcc.ts`、DII を読んで DDB を揃える)。共通のところを `ts/dsmcc.ts` に
括り出し、データ放送の読み方だけを `ts/bml.ts` に足しています。

**渡す形は借りたまま** (`server/ws_api.ts` の `ResponseMessage`)。描画側との契約なので、
自前で詰めても**食い違えば型検査が止めてくれます**:

| 型 | 中身 |
| --- | --- |
| `pmt` | データ放送の component (PID・componentId・BXML の情報) |
| `moduleListUpdated` | どのモジュールが何バイトか (DII) |
| `moduleDownloaded` | 揃ったモジュール。**ファイルごとに base64 と MIME** |
| `esEventUpdated` / `currentTime` | イベントメッセージ・NPT・放送の時刻 |

**psisiarc は要らない。** TS を直に読むので、間に挟むものがありません。

```
エージェント → denpa ┬→ ffmpeg     → fMP4 → MSE          (映像・音声)
                     ├→ ffmpeg     → mkv  → canvas       (字幕の絵)
                     └→ BmlDecoder → 組み立て済みモジュール → web-bml の描画側
```

ffmpeg は1本のまま、チューナーも1つのまま、遅延も 0.6秒 のまま。

### いま入っているところ

**解いてサイドチャネルに流すところまで入っています** (`server/databroadcast.ts`)。
描画側はまだです。

1局に絞った TS の写しを `BmlDecoder` へ分け (`Session.pump`)、出てきたものを
`CHANNEL.data` (0x30) に JSON で載せます。覚えておくぶんは `ts/carousel.ts`。

実機の録画 (1局に絞った 79MB = 約40秒ぶん) で測ったもの:

| | |
| --- | --- |
| 出てきた知らせ | `moduleDownloaded` 16 / `currentTime` 13 / `moduleListUpdated` 3 / `pmt` 1 |
| 揃ったモジュール | 16個・約 1.4MB (application / image / text / audio) |
| 速さ | 128 MB/s。放送の 17 Mbit/s に対して**1コアの 1.7%** |
| 繋いできた人に配り直すぶん | 18個・2MB |

**借りていた `decodeTS` と突き合わせて、揃うモジュール16個・ファイル数・バイト数・
種別まで完全に一致しました。** 違うのは出さないものが2つあることだけです
(下の「決めたこと」)。

**頼まれてから解きます。** 解くこと自体は 1.7% と安いのですが、**見ている人の
ほとんどは押さない**ものなので、全員のぶんを解き続ける理由がありません。画面から
`{ type: 'data', on: true }` が来たときだけ回し、誰も出していなければ畳みます。

引き換えに、**押してから出るまでカルーセルが一周するのを待ちます**。放送は同じ
ものを何度も回しているので待てば揃いますが、大きいモジュールほど間隔が空きます。

決めたことが4つ:

- **`pcr` は出さない。** 毎秒50個ほど来るうえ、denpa では**映像そのものが時計**です
- **`programInfo` は解く側から出さない。** 借りていた側は EIT/SDT/NIT を読んで
  組み立てていましたが、denpa は**自前の番組表を持っている**ので、そちらから作る
  ほうが正確で安い (`Session.programInfo`)。**これが無いと画面が出ません** —
  描く側は入口の BML を開く前に `getProgramInfoAsync()` で待つ作りなので、
  モジュールが全部揃っていても待ち続けます (実機で踏みました)
- **`pmt` は変わったときだけ。** 放送は同じ表を何度も送ります。モジュールも
  「同じ版を配り直さない」で止めています (カルーセルは回り続けるので、版が
  上がっていなくても同じものが何度も揃う)
- **解く側が転んでも映像は止めない。** データ放送は映像の付け足しなので、転んだら
  そこで諦めて映像は流し続けます。**投げ返すと TS を送り込んでいるところごと落ちて
  映像まで出なくなります** (作りものの放送で実際に落ちました)

### 残っているのは、描画側をどう抱えるか

**繋ぎ口はぴったり合っている。** `client/bml_browser.ts` の `BMLBrowser` は、
denpa が既に作っている `ResponseMessage` をそのまま食べる:

```ts
const browser = new BMLBrowser({
    containerElement,        // BML を描く場所
    mediaElement,            // 映像が居る入れ物。**denpa の <video> をそのまま渡す**
    videoPlaneModeEnabled,   // BML が指す位置に映像を置き直すか
});
browser.emitMessage(msg);    // ← ts/bml.ts が吐くものをそのまま
browser.destroy();
```

**映像は渡すだけ。** `VideoPlayer` の実装 (`client/player/*.ts`) は向こうの
単体ページ (`client/index.ts`) が hls.js / mpegts.js で自前再生するためのもので、
**`BMLBrowser` は受け取らない**。denpa の絵はそのまま、上に BML が載る。

自分で書き直す道は無い。ES2 の処理系まで抱えることになる (下の実測)。

#### どれだけ持ち込むことになるか

`BMLBrowser` から実際に辿れるものを数えた (2026-08-10 時点):

| | |
| --- | --- |
| ファイル | **46個・1,237 KB** の TypeScript (置いたあとは 44個 — `js_interpreter.ts` を自前に差し替え、README を足したため。数え直すのは [vendor-web-bml.ts](../.github/vendor-web-bml.ts)) |
| 大きいもの | `es2/index.ts` 200KB / `jis_to_unicode_map` 122KB / `es2_dom_binding` 122KB / `unicode_to_jis_map` 121KB / `interface/DOM` 90KB / `romsound_data` 84KB / `content` 68KB / `browser` 56KB |
| 外から引くもの | **4つだけ** — `buffer` / `crc-32` / `css` (otya128 のフォーク) / `fast-xml-parser` |
| ほかに要るもの | `JS-Interpreter/interpreter.js` (117KB) と `acorn.js` (68KB)。`public/default.css` (9KB) と `default_c.css` (5KB) |

**koa・react・hls.js・mpegts.js は引かない。** あれらは向こうの package.json に
並んでいるだけで、`BMLBrowser` の木には入っていない (サーバと単体ページのもの)。

引っかかるのは1箇所だけ。`js_interpreter.ts` が
`require("../../JS-Interpreter/interpreter")` を使い、その中が**大域の `acorn`** を
見る。向こうは webpack の `ProvidePlugin` で入れているので、Vite で組むなら
同じことをする必要がある。

**フォントは別の話。** BML は丸ゴシックを指してくるので、向こうは Kosugi /
KosugiMaru を 4.4MB ぶん抱えている。積むかどうかは持ち込み方とは独立に決める。

#### 3つの道

| 道 | 良いところ | 引き換え |
| --- | --- | --- |
| **A. npm の git 依存** (`github:otya128/web-bml`) | 更新が `bun update` で済む。ファイルを抱え込まない | **`exports` が無く `main` は生の TS**。node_modules の TS を Vite に組ませる設定が要る。入れるだけで**使わない25個の依存も落ちてくる** (koa・react ほか)。型は追えるが `acorn` の大域は自分で用意 |
| **B. webpack の束を Dockerfile で組む** | 向こうのビルド設定 (`acorn` も `buffer` も) をそのまま使える。denpa 側の依存は**増えない**。ffmpeg や chapter_exe と同じやり方 | **型が切れる** (`window` 越しになるので `any`)。像を焼くのに node と npm が要り、25個の依存も落ちる。`ResponseMessage` の食い違いを**型検査が見張れなくなる** — 解く側を自前にした利点が半分消える |
| **C. 借りものとして置く** (`src/lib/vendor/`。解く側と同じ) | Vite が他と一緒に組む。**型が最後まで通る**。増える依存は4つだけ。網の要らないビルド | **1,237 KB・46ファイル**をリポジトリに抱える。更新は取り直し。`acorn` の大域と `css` フォーク (git tarball) は自分で面倒を見る |

**C を採った。** 決め手は型で、`emitMessage(msg: ResponseMessage)` の食い違いを
検査で止められるかどうかがそのまま「解く側を自前にした意味」に効く。A は
`exports` が無い時点で結局 node_modules の中を名指しすることになり、抱えないぶんの
利点が薄い。B は依存が増えないのが魅力だが、型が切れるのと像の焼き時間が伸びるのが
重い。

**1,237 KB は置いてある元のほうで、束になると 700KB。** 読むためではなく
置くためのもので、biome の整形・検査からは
`!src/lib/vendor` で外れる (解く側と同じ扱い)。型検査も1行目の `@ts-nocheck` で
外してあるが、**denpa 側は効いたまま** — `ts/bml.ts` が `ResponseMessage` に無い物を
入れれば `bun run check` が止める。

#### 入れたあと

**押されるまで 700KB を取りに行かない。** `import()` で分けてあるので
(`components/player/DataBroadcast.svelte`)、d ボタンを押した人だけが落とす。
どのみち押してからカルーセルが一周するのを待つので、そこに紛れる。

| | |
| --- | --- |
| 束 | 700KB (gzip 前)。**押すまで落ちてこない** |
| フォント | **字幕を焼いているのと同じ `rounded-mplus-1m-arib`**。BML が要る**等幅・丸ゴシック・ARIB外字**を1本で満たす (借りている側の Kosugi 4.4MB は外字を持たない)。像には ttf と woff2 を置き、`/api/font` で配る |
| 覚えるもの | NVRAM は**端末の** localStorage。`denpa_bml_denpa_nvram_` で他と混ざらないようにしてある |
| 郵便番号 | 設定画面から入れて、器を作る前に NVRAM へ写す (`nvram://receiverinfo/zipcode`)。**放送はこれで天気・地域のニュース・防災情報の場所を決める** — 入れないと「郵便番号が正しく設定されていません」と出る。置き場をサーバにしてあるのは、家の場所が端末では変わらないから |
| リモコン | 十字・決定・戻る・数字・色をそのまま渡す (`keyCodeToAribKey`)。**`d` だけ渡さない** — 出し入れに使うので、渡すと抜けられなくなる。**指で押すぶんは自前** (`components/player/Remote.svelte`) で、映像の上ではなく右の列に置く — 放送の画面は枠を下まで塗り潰すので、重ねると押すものが埋もれる |

**映像の入れ物は、描く場所の親にしてはいけない。** 借りている側は BML の文書を
組むときに `mediaElement` を動かすので、その中に `containerElement` が居ると
`appendChild ... contains the parent` で転ぶ。denpa では映像だけを
`<div>` に入れて、データ放送はその**兄弟**に置いている。

**描く場所は毎回作り直す。** 借りている側は渡された要素に**閉じた影**
(`attachShadow({ mode: "closed" })`) を張る。影は外せないので、同じ要素を
渡し直すと2度目で転ぶ — 消して出し直すと出なくなる、という壊れ方をする。

閉じた影なので、**外から中身は見えない**。切り分けのためだけに
`data-showing` / `data-receiving` / `data-handed` を外へ出してある
(ここに1日使った)。

##### 借りものが持っていないぶん

**`BMLBrowser` は画面の器を持っていない。** 向こうの単体ページ
(`client/index.ts`) がやっていたことは、借りていない以上こちらでやることになる
— d を渡す・映像を戻す・枠に合わせる・データ取得中を出す・郵便番号を渡す。
**どれも抜けると「押しても何も出ない」形で壊れる** — 実機で全部踏んだ。

**中身は[借りものの README](../src/lib/vendor/web-bml/README.md#借りていないぶんこちらでやること)に
1箇所だけ置いてある。** ここと両方に書いていた頃は、増えたときに片方だけ
「3つ」のままになった。

**局を変えたら作り直す。** 借りている側は一度に一つの放送しか持てない
(カルーセルも覚えるものも局ごと) し、**前の局の文書が映像を掴んだまま**になる。

Vite で組むために2つだけ面倒を見ている。**借りものは書き換えていない。**

- `import css from "../public/default.css"` を**文字列として**読ませる
  (`vite.config.ts` の `denpa:bml-css`。向こうは webpack の `asset/source`)
- `js_interpreter.ts` は写さず、denpa の1行に差し替える (向こうの README が
  「未使用」と言っている道で、素の ESM に `require` は無い)

### 5.7 双方向（通信系コンテンツ）プロキシ

放送局の通信系サーバは受信機の専用ネットワークスタックを前提としており、CORS ヘッダを返さない。
そのため **SvelteKit サーバが中継する** (中身は
[server/bml-network.ts](../src/lib/server/bml-network.ts))。

| 口 | BML の API | 何をする |
| --- | --- | --- |
| `/api/bml/proxy` | `browser.Ureg` 系の取得 (`get`) | GET して中身をそのまま返す |
| `/api/bml/post` | `transmitTextDataOverIP` | POST して返りをそのまま返す |
| `/api/bml/confirm` | `confirmIPNetwork` | 相手の 443 番へ繋がるか (ICMP は器の中から撃てない) |

#### 「送る」は応募・投票のためだけの口ではない

最初は「正規受信機以外からの送信は想定外」として `transmitTextDataOverIP` を
**渡さなかった**。それでは足りなかった。

**放送のアプリは `isIPConnected` の申告を信じない。** NHK は送る口へ一度投げてみて、
返らなければ「インターネットに接続されていません」と案内する (実機で確認。
`confirmIPNetwork` は呼びに来もしない)。渡さないと借りものは「その機能は無い」と
答えるので、**双方向を入れていても入っていないのと同じ画面**になっていた。

中身は組み立てない — 借りものが `Denbun=<EUC-JP か Shift_JIS を %xx にしたもの>` まで
作ってから渡してくるので、denpa は `application/x-www-form-urlencoded` として素通しし、
返りも解かずに返すだけ。

**既定オフ。** 設定画面の「データ放送の双方向」を入れるまで、この口は 403 を返し、
画面側も `isIPConnected` に 0 を返す。**そのとき放送のアプリが出す「インターネットに
接続されていません」は事実の通り**で、消したければ入れる。web-bml 系の実装も同じ方針
（TVTDataBroadcastingWV2:「通信機能は既定では無効であり、その場合すべての外部への
リクエストはブロックされます」）。

#### 局ごとのドメイン表は持たない

「いま映している局のドメインだけ許す」には、局とドメインの対応表を抱えることになる。
**その表は必ず古くなり**、新しい局や引っ越した先で黙って繋がらなくなる — しかも
「繋がらない」は放送側の不調と見分けが付かない。

代わりに**繋ぎ先ではなく繋ぐ範囲**を縛る。危ないのは「放送局以外に繋ぐこと」ではなく、
**denpa のサーバが内側に繋ぐこと** (SSRF) だから。

| | |
| --- | --- |
| 手 | GET と POST。**中身は組み立てない** — 放送のアプリが作ったものを素通しするだけ |
| 相手 | **公開アドレスのみ**。私設・ループバック・リンクローカル (雲のメタデータ)・CGNAT・多重放送は断る |
| 仕組み | **http と https**。`file:` などへ逃がす道は塞ぐ |
| 見方 | **名前ではなく引いた先で見る** — `localhost` の別名や、内側を指す公開の名前が綴りでは見分けられない |
| 追いかけ | 3回まで。**行き先ごとに確かめ直す** (1回目が公開でも、飛ばされた先が内側のことがある) |
| 大きさ | 4MB / 待ち 10秒 |
| 持ち物 | **何も渡さない** (cookie も認証も)。denpa の資格情報が外へ出ない |
| 記録 | 断ったものは**何に繋ごうとしたか**を残す |

#### 動作範囲の現実的な想定

| 種別 | 可否 |
| --- | --- |
| dボタン、ページ遷移、地域選択、クイズ選択肢 | ○ 受信機内で完結するため動作 |
| NVRAM への保存・読み出し | ○ web-bml に実装あり |
| 通信系コンテンツの取得（HTTP GET） | ○ 中継口経由 (既定は切) |
| 応募・投票などのデータ送信（HTTP POST） | ○ 中継口経由 (既定は切)。**繋がっているかの判定もここを通る** |

### 5.8 Hybridcast

**在ることは言う。動かさない。**

データ放送 (BML) と決定的に違うのは、**アプリが電波に乗っていない**ことです。
乗っているのは **AIT** という表だけで、中身は放送局のサーバから HTTPS で取ります。

```
PMT ─ ES に application_signalling_descriptor (0x6F) ─→ その PID に AIT
AIT ─ transport_protocol_descriptor        (URL の頭)
    └ simple_application_location_descriptor (その先の道)  →  アプリのURL
```

つまり denpa がやってきた「電波を解く」仕事は**ほとんど要りません**
([ts/ait.ts](../src/lib/ts/ait.ts) は表を読むだけ)。**押されなくても読みます** —
解く量が無いのと、「押すまで在ることが分からない」では出したいものが出せない
ためです。載っていない局では**PMT に印が無いので AIT を待つこともしません**。

見つけたら、操作列に**別のタブで開くボタン**を出します
(`components/player/Remote.svelte` の隣ではなく、d ボタンの隣)。**d と同じ形には
しません** — あちらは denpa の中で開くもの、こちらは外へ出ていくもので、
押した結果がまるで違います。

#### 動かさないのは、越えられない壁が3つあるから

1. **受信機の API は、アプリのページの中に無いと意味がない。** Hybridcast の
   アプリは `hcApp` などの API を呼びます (放送の映像面の制御・いまの局と番組・
   受信機の記憶・スマホとの連携)。放送局のサーバから来るページは別オリジン
   なので、iframe に入れても**中に手を入れられません**。同一オリジンに見せるには
   URL を全書き換えして中継したうえで、**IPTVFJ STD-0010/0011 の API を実装する**
   ことになります — 仕様1本ぶんの仕事です
2. **放送局のサーバが、認証された受信機を期待している。** 受信機の証明書や
   識別子を見るものが多く、**素性を偽って通す気はありません**
3. **映像は DRM 付き。** MPEG-DASH + Widevine/PlayReady で、ライセンスサーバが
   また端末を見ます

**2番は denpa 側の努力では越えられません。** そこが越えられない以上、
1番に仕様1本ぶんを注ぎ込む理由がありません。

#### できないものを、できる顔で出さない

借りている BML ブラウザは `AITControlledApp.Start` に **0 (できない)** と
答えます。実機の NHK はこれを聞きに来ていて、その答えでデータ放送側の
「Hybridcast」ボタンを死なせています。**ここを 1 にしてはいけません** —
BML が起動を頼んできて、そのまま返らなくなります。

## 6. 技術選定の記録（採用しなかったもの）

### ブラウザ側での字幕デコード（aribb24.js）— 不採用

B24 をそのままブラウザへ送り、`feedB24(payload, pts, dts)` に食わせる構成。
クライアントで完結しプロセスも増えないが、**録画と live で描画系が二重になる**。
サーバで描けば見た目が完全に一致し、外字も背景の箱も放送どおりに出る。
帯域は変わった枚だけ送るので、映像の隣では無視できる（[§5.2](#52-字幕sub2video)）。

**サーバ負荷を理由に戻す道はほぼ消えた** — 映像と同じ ffmpeg の出口が1つ増えるだけで、
実測では焼く手間に埋もれる。戻すとしたら描画系を二重に持つ側の理由がいる。
**サイドチャネルの形は変わらない**（B24 を 0x20 で流すだけ）。

### H.264 + MPEG-TS + mpegts.js で先に全機能を通す — 不採用

前例が豊富（KonomiTV / web-bml と同一構成）で、段階を踏む案として有力だった。
**字幕の経路が録画側で先に完成した**ため、あとで捨てるコードを書く理由が無くなった。
Safari や AV1 非対応環境のための H.264 fallback は、段階ではなく**コーデックの設定**として残す。

### GStreamer — 不採用

当初は「tsdemux の private pad で B24 を映像と同一クロック上で取得でき、tee が不要になる」ことを理由に有力視した。**データ放送要件の追加によりこの論拠は失効**（データ放送も TS をもう一方へ分けて読むため tee は必須）。

残る比較では ffmpeg が優位:

- web-bml 自体が ffmpeg 前提（`FFMPEG` 環境変数、既定形式 `h264-mpegts`）
- tsreadex / psisiarc / tsreplace / KonomiTV も同様の CLI パイプライン形
- QSVEncC / NVEncC / VCEEncC が使える（GStreamer からは不可）
- GStreamer は ARIB/ISDB の知識・前例ゼロ
- 放送波の不安定さ（解像度変化、ステレオ⇄デュアルモノ）は tsreadex が吸収済み
- AV1 over WebRTC は MediaMTX 経由で取得可能
- **libaribcaption を組み込める**（`--enable-libaribcaption`。字幕の描画をそのまま使える）

### WebRTC / WHEP による低遅延化 — 不採用

設計では「低遅延の追い込み（任意）」として MediaMTX 経由の WHEP を候補に置いていた。
**入れない。**

**縮むのは待っている間だけで、開いてから絵が出るまではむしろ伸びる。**
いま遅れている 0.5〜1.0 秒のうち、WHEP が持って行けるのは受け側の貯め
（`ts/pacing.ts`。宅内で 0.2〜0.9 秒）だけ。焼くのに掛かっているぶんは
**符号器の中の話なので運び方を変えても消えない**（[§5.1](#51-エンコード)）。
代わりに、開くたびに **ICE と DTLS の往復**が増える。**押してから映るまでが
いちばん効く場面**（テレビと同じに使う）で、そこが遅くなる取引になる。

払うものも大きい:

| | いま（WebSocket + MSE） | WHEP にすると |
| --- | --- | --- |
| 積むもの | Bun.serve の WebSocket 1本 | **MediaMTX がもう1プロセス**（+ SFU の設定・鍵・NAT） |
| 字幕・データ放送 | **同じ1本に相乗り**（[§5.3](#53-websocket-プロトコル)） | 別建て（DataChannel を自分で組む） |
| 追っかけ・5分戻れる | MSE の `buffered` がそのまま | **全部書き直し**（WebRTC に `buffered` は無い） |
| 止めて見る | そのまま | 溜めが無いので**追い越されて終わる** |
| 音声・焼き方の選び直し | 焼き直して繋ぎ直すだけ | 交渉からやり直し |

**「止めた所から見られる」と「戻れる」は、貯めているから成り立っている。**
低遅延はその貯めを削ることなので、**同じものの両端**にある。**貯めを削れる幅は
そもそも経路が決めている** — 実測では 0.2 秒では止まり続け、落ち着いたのは
0.9 秒だった（上の「一瞬止まって遅延が増えていく」）。1秒足らずを削るために
その2つを捨てるのは、テレビとして使う道具では割に合わない。

**本当に縮めたいなら、道ではなく焼くのをやめるほうが効く**（[§5.5](#55-放送そのままmpeg-2は出せない)）。
そちらは符号器のぶんが丸ごと落ちるので桁が違う。**WHEP を考えるのは、その道を
通ったあとでいい。**

> **ffmpeg の WHIP muxer も同じく使わない。** 音声 Opus・映像 H.264 固定かつ
> experimental で、AV1 が使えない。仮に WebRTC を通すことになっても MediaMTX 経由になる。

### MPEG-TS への AV1 多重 — 保留

AOM 公式仕様（AOMediaCodec/av1-mpeg2-ts、stream_type 0x06 + format_identifier `AV01`）は存在するが、
FFmpeg は PR、GStreamer は WIP 段階。ブラウザ側デマクサも存在しない。継続監視する。

### Media over QUIC — 低遅延化の候補

字幕・データ放送を第一級のトラックとして扱える唯一の選択肢だが、IETF ドラフト段階。

| --- | --- | --- |

| web-bml の通信機能 | 実装の有無・範囲を未確認 | ソース（`client/`, `documents/`）で要確認 |
| カルーセル初期表示 | 数秒周期の繰り返し送出のため初期表示に数秒かかる | 仕様上の制約。低遅延要件とは別軸として扱う |
| BML のレイアウト | 映像プレーンの座標系前提 | 字幕と共通のオーバーレイ層を作り、リサイズ追従を一元化 |
| 規約面 | 通信系サーバへの非受信機アクセス | 個人の視聴環境の範囲に留める |
