# 放送波ストリーミングシステム 構成設計

> **映像・音声・字幕・データ放送 (第1〜3段階) が入っています。** 低遅延の追い込みは
> [やめました](#webrtc--whep-による低遅延化--不採用)。
> どこまで入っているかは [§4](#4-実装の順序) を見てください。

---

## 1. 前提

| 項目 | 内容 |
| --- | --- |
| デプロイ形態 | **セルフホスト（1ユーザー = 1サーバ）** |
| アプリ | SvelteKit 単一アプリ（配信・視聴の両方を担当） |
| 入力ソース | 放送波 MPEG-TS（ISDB-T / ISDB-S） |
| 目標コーデック | AV1 + Opus |
| 必須機能 | ARIB字幕、データ放送（双方向含む）、複数音声・映像ストリーム |
| 非機能要件 | 低遅延 |

セルフホストなので、以下は**設計で考えない**:

- NVRAM のマルチユーザー分離（受信機 = サーバ = ユーザーが 1:1:1）
- ユーザーごとの地域設定・リモコン設定の分離
- 通信系コンテンツのプロキシにおけるユーザー識別

## 2. 全体構成

```
┌─────────────────────────────────────────────────────────────────┐
│ チューナー (エージェント)                                     │
└────────────────────────────┬────────────────────────────────────┘
                             │ MPEG-TS (チャンネル丸ごと)
                             ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ            │
              │  ・1局に絞る (ServiceFilter)  │
              │  ・プロセス管理／再起動        │
              │  ・WebSocket ハブ             │
              │  ・BML通信系プロキシ           │
              └───┬──────────────────────┬───┘
                  │ 1局ぶんの TS          │ (押した人がいるときだけ)
                  ▼                      ▼
     ┌───────────────────────────┐  ┌──────────────────┐
     │ ffmpeg                    │  │ BmlDecoder       │
     │  ├→ pipe:1 fMP4 (映像音声) │  │ カルーセルを     │
     │  └→ pipe:3 mkv (字幕)     │  │ 組み立てる       │
     └─────────────┬─────────────┘  └────────┬─────────┘
                   └───────────┬─────────────┘
                               ▼
              ┌──────────────────────────────┐
              │   SvelteKit サーバ (配る)     │
              └──────────────┬───────────────┘
                             │ WebSocket (メディア + サイドチャネル)
                             ▼
              ┌──────────────────────────────┐
              │   ブラウザ (SvelteKit client) │
              │  ・MSE 直接        → 映像音声 │
              │  ・canvas に描く   → 字幕     │
              │  ・自前のエンジン  → データ放送│
              └──────────────────────────────┘
```

**映像と字幕は同じ ffmpeg の2つの出口。** 別々に起こすと時刻が揃わない
（[§5.2](#52-字幕)）。データ放送へは、絞った TS を denpa の中で分ける
（`tee` は要らない）。

### 設計上の中核

**メディアとメタデータは同じコンテナに載らない。** ARIB字幕（B24 PES）もデータ放送（DSM-CC カルーセル + PSI/SI）も、fMP4 / WebM には規格上入れられず、ffmpeg も GStreamer も扱えない。そこで:

> **サイドチャネル用の WebSocket を 1 本用意し、字幕とデータ放送を同じ経路で一緒に送る。**

迂回路ではなく、この設計の柱。

### 字幕はサーバでデコードして、描くのは受け側

**置き場所を決めるところまではサーバで、描くのはブラウザ (とテレビのアプリ) で。** 送るのは
「どの字を・どこに・どの大きさで・何色で」まで決めた**文字の配置** (JSON。[api.md](api.md#字幕の文字の配置))。

放送で字幕の画像が流れてくるわけではない。テレビは文字と配置の指定から毎回描いている。以前はその描画を
libaribcaption にやらせ、画像 (PNG) を配っていた。libaribcaption は「デコードする (decoder)」と
「描く (renderer)」が分かれていて、置き場所・大きさ・色・外字の置き換えはデコードする側で決まる。
**デコードする側を TypeScript に写して** (`src/lib/ts/b24caption.ts`) サーバで回し、描く側だけを受け側に移した。

| | 画像を配る (前) | 文字の配置を配る (いま) | ブラウザで B24 をデコードする (aribb24.js) |
| --- | --- | --- | --- |
| 置き場所・色・外字の置き換え | libaribcaption | **libaribcaption と同じ計算** (写した) | 実装依存 |
| 全画面での字 | 1920x1080 の画像の拡大 | **画面の画素で描く** | 画面の画素で描く |
| 帯域 | 1枚 20〜50KB の PNG | 1枚 数百バイト〜1KB ([§5.2](#52-字幕))。字にできない外字があれば1字 3.5KB ほど足す | 数百バイト |
| サーバ負荷 | 字幕を描いて PNG に組む | 写してデコードするだけ | なし |
| 持つコード | 出口だけ | デコードする側 (表は libaribcaption から写したものを手で持つ) と描く側 | 字幕ライブラリ1つ |
| テレビのアプリ | 画像を重ねるだけ | 描く側を Kotlin で持つ (denpa-tv 0.16.0 から) | 同上 |

外字 (DRCS) は置き換え表で字にできるものは字に、できないものは画像で送り、受け側が字の枠いっぱいに引き伸ばす。
放送の外字は 16〜36 画素の白黒の画像で、そのまま伸ばすと1点が 4x4 の階段になる (なめらかに伸ばしても階段がぼやけて残る)。
**サーバで斜めを丸めた濃淡の画像にしてから送る** (`src/lib/ts/drcs-smooth.ts`。水増しされた行・列を畳み、Scale2x で斜めを
細かくし、4x4 ずつ平均して縁に中間の濃さを付ける。16 階調・一辺 64〜256)。libaribcaption で描いていた頃は同じことを
パッチで当てていた (#554) が、描くのを受け側に移したとき (#586) に落ちていたのを、ここへ移した。録画には放送の字幕がそのまま入る (`S_ARIBSUB`) ので同じ描き方で観られる。
ずっと前にエンコードしたもの (PGS の画像が入っている) の字幕はもう読まない。画像で送る経路 (PNG・PGS・libaribcaption) は外した。

時刻は字幕に添えられたものをそのまま使う。映像と同じ ffmpeg が付けたので、受け側の
再生位置と直に比べられる（[§5.4](#54-時刻同期)）。

## 4. 実装の順序

**映像音声 (`ffmpeg → fMP4 → WebSocket → MSE`) → 字幕 (同じ ffmpeg の2つ目の出口から
サイドチャネルへ) → データ放送 (1局に絞った TS を自前の `BmlDecoder` でデコードする。[§5.6](#56-データ放送の統合))
の順に入れ、どれも入っています。** 4段目の低遅延の追い込みはやめました。縮むのは受け側の
貯め (0.2秒〜) だけで、開いてから映るまではむしろ伸び、「止めた所から見られる」「5分戻れる」を
捨てる ([§6](#webrtc--whep-による低遅延化--不採用))。

**コーデックは段階ではなく選択にする。** 既定は H.264 + AAC (どの端末でも再生できる) で、
AV1 + Opus はプレイヤーの画質メニューで選ぶ。エンコーダとコンテナ以外は共通なので、字幕もデータ放送もそのまま動く。

### 入っているもの

| | |
| --- | --- |
| 画面 | `/live`。左に映像、右に局の一覧。前回見ていた局から開く |
| エンコード方式 | H.264 + AAC / AV1 + Opus を見ながら選べる（[§5.1](#51-エンコード)）。`src/lib/server/live.ts` |
| 運び方 | WebSocket 1本。多重化の頭は [§5.3](#53-websocket-プロトコル) のまま |
| チューナー | 優先度 **9**。録画 (10) にだけ譲り、番組表・ロゴ・スキャンからは取り上げる |
| 共有 | 同じ局を2人で見ても、チューナーも ffmpeg も1つ |
| 変換せずに送る | **エンコードせずに送れる**（画質の切り替えで MPEG-2 を選ぶ。端末ごとに覚える）。[§5.5](#55-放送そのままmpeg-2を送る) |
| 畳み方 | **見ている人が0になったら離す**。接続そのものが在席の印 |
| 画面の外へ | `GET /api/services/<id>/live` で同じものを HTTP で流す（同じ取り合い・共有。字幕・データ放送は載せない。[api.md](api.md)） |

**共有の単位は局・音声・エンコード方式・字幕。** 1つの物理チャンネルに複数の局が入っていて、
ffmpeg には局を名指しさせている（下記）ので、映像は局ごとに違う。二カ国語を主音声で
見る人と副音声で見る人も別のものをエンコードする。字幕も映像と同じ ffmpeg がエンコードするので
（[§5.2](#52-字幕)）、何本目を選ぶかで別になる。チューナーはエージェント側で
共有され、増えるのは ffmpeg だけ。

### 多重音声はサーバで1本に決める

**「多重音声」には中身の違う2通りがある。** 見る人にはどちらも「音声を選ぶ」操作なので、
1つの一覧に平らに並べる（`arib.audioTracks`）。

| | 中身 | 分け方 |
| --- | --- | --- |
| デュアルモノ | 音声は1本。左に主音声・右に副音声（二カ国語・解説放送） | `-af pan=stereo\|c0=c0\|c1=c0`（副音声は `c1`） |
| 複数の音声 | 音声そのものが2本以上 | `-map 0:p:<局>:a:<何本目>` |

デュアルモノは1本から3つ（主・副・主+副）出てくる。テレビの「音声切換」と同じ3択。

**選ぶのはサーバ側。** 音声を全部送ってブラウザで切り替える手もあるが、複数の音声を
入れた fMP4 を MSE で切り替えられないブラウザがある（`audioTracks` の実装がまちまち）。
エンコードするときに1本に決めれば、どのブラウザでも同じに鳴る。代償は選び直しが再エンコードに
なることだが、チューナーは確保したままで、かかるのはエンコードし始めのぶんだけ。

**選べるものは繋いだあとでないと分からない。** 二カ国語の映画が終わればステレオに
戻るので、局の一覧からは決められず、選局のたびに現物を `tuned` に載せて送る。
覚えていた合言葉が選べなくなったら先頭に落とす（`arib.pickTrack`）。落とさないと
番組が変わった瞬間に音が消える。

### 追っかけ再生とライブは別物

止めたりシークバーを戻したりして**わざと遅れて見ている**状態を、ライブと分けて持つ。

| | ライブ | 追っかけ |
| --- | --- | --- |
| 大きく離れたら | 飛んで詰める（別のタブから戻ったとき） | 飛ばない（見ようとしていた場面が飛ぶ） |
| 速さ | 自動（1.05倍まで） | 選べる（1 / 1.25 / 1.5 / 2倍） |
| 追いついたら | — | 自分でライブに戻る |

分けていなかった頃は `pacing` が「別のタブから戻った」と「わざと遅れて見ている」を
区別できず、8秒より長く止めて再開すると放送の今へ飛んでいた。

**追いついたらライブに戻す。** 選ばれた速さのまま進むと放送を追い越し、溜まりを
使い切って止まる。実機で 15.8 秒遅れから2倍で追わせると、14.9 秒で追いついて
速さが 1 に戻った。

録画中の録画を頭から観る `/chase/<id>` も同じ仕組みで流す（`server/chase.ts` が伸びる元のTSを
追い読みする。チューナーは使わない。[app.md](app.md#画面)）。ここでいう「追っかけ」とは別の話。

### 開いてから映像が出るまでの内訳

実機（PT3 + `earth_pt3`）で割った。**チューナーが温まっていれば ≈0.89 秒**、
冷えていれば頭に選局の 0.66 秒が付く。

| | |
| --- | --- |
| 画面が動き出してチケットを取り、WebSocket が繋がるまで | 160ms |
| ffmpeg の立ち上がり（固定） | 530ms |
| 放送の I フレーム待ち | 0〜501ms（GOP はちょうど 501ms） |
| **貯めてから始める**（`pacing.ts` の `FLOOR`） | 200ms（0.4秒だったのを半分に。ただし下の「覚えておく」） |
| MSE に入れて1枚映るまで | 40ms |

**貯める量はこちらの都合で動かせる唯一のところ。** 再生は「貯まった尺 ≧ 貯める量」
かつ「映像を出せるようになっている」（下の「貯まっただけでは始めない」）で始まる。
電波は実時間で届くので、0.4 秒貯めるには 0.4 秒かかる。0.2 秒 = 塊4つぶん
（サーバは 0.05 秒ずつ出す）まで下げた。足りずに止まれば 0.6 ずつ増え、荒れる経路では
自分で伸びるので、小さいほうから始めてよい。

#### 選局の 0.66 秒と、削れなかったもの

冷えているときの選局 0.66 秒の中身:

| | |
| --- | --- |
| リクエストしてから選局の ioctl を出すまで | 42ms |
| **復調器がロックするまで** | 320ms（実測 319〜323ms。ISDB-T の OFDM フレームは約 205ms） |
| ドライバが TS を出しはじめるまで | 0〜7ms |
| ロックしてから denpa の1バイト目まで | 240ms（PAT 60ms → PMT 110ms → ECM 50〜250ms → カードの往復） |

**削れたのは 160ms だけだった。** 開く局はページを組む時点で決まっているので、画面が
繋いでくる前にサーバ側でエンコードし始める（`server/live.ts` の `warm`）。その 160ms が
ffmpeg の 530ms と重なる。

> **PSI を先に流す手は外した。** 前に開いたときの PAT/PMT を先に流し、選局待ちの 0.66 秒に
> ffmpeg の入口の仕事を重ねる手で、単体では効いた（888ms → 707ms、ばらつき 342ms → 77ms）。
> 実機では、電波より先に入口を読み終えた ffmpeg が `-map 0:p:<局>:v:0` を解決できずに
> 終了し、切り替えが壊れた（`Failed to set value '0:p:24632:v:0' for option 'map'`）。測ったときは
> 選局済みだったので見えなかった。同じ落ち方は局がいくつも入っている TS（tvk / T15）でも起き、
> [渡す前に1局へ絞る](#渡す前に1局へ絞る)で直した。

削れなかった残りは、放送か機材か ARIB の都合:

- **ロックの 320ms はチップの物理時間。** ドライバを替えても同じ。
  `dvb_override_tune_delay` を 1ms にすると、DVB core が同期の途中で周波数を
  振り直して 451ms に悪化した。あの値は「諦めるまでの猶予」で、ロックの検出間隔
  ではない（検出はこちらが 10ms 間隔で直に読んでいる）
- **ロック後の 240ms はスクランブル解除。** ECM が来るまで鍵が作れない
- **I フレーム待ちは放送の GOP。** MPEG-2 は I フレームからしか復号を始められない
- **エンコーダは遅れの原因ではない。** `-tune zerolatency` は B フレームも先読みも作らない。
  インタレ解除・音声・塊の細かさを外しても縮まなかった（実測）

### 一瞬止まって遅延が増えていく

宅内なのに一瞬止まり、そのたびに遅れが増えて戻らなかった。エージェントのリングバッファ
（6分視聴 + 番組表3本で溢れ 0回）・送り出し（H.264 25分で 0.5秒以上の間 0回）・流量
（`-maxrate 8M` で 8.4 Mbit/s まで削っても8分に10回）と順に外して、残ったのは**ちょうど60秒ごと**という周期だった。

周期が揃うなら電波の混み具合ではない。遅延（ここでは手元の貯まり。[「遅延」は2つある](#遅延は2つある)）
は毎回「3.1秒 → 1.05倍で詰めて 0.3秒 → 止まる」で、縮める先をいつも `FLOOR` にしていたのが原因だった。

**止まった高さのすぐ上を次の下限にする**（`pacing.ts` の `PROBE`）と、エンコード方式を触らずにこうなった:

| | 途切れ | 貯まり 中央 | 貯まり 最大 |
| --- | --- | --- | --- |
| 直す前 | 8分に10回 | 1.4秒 | 3.2秒 |
| 下限を覚える | 8分に5回 | 0.7秒 | 3.2秒 |
| 下限を下げ直すまでを2分→10分 | 10分に3回（最後の6分は0回） | 0.9秒 | 1.1秒 |
| `-maxrate` を外す | **10分に1回** | **0.6秒で平ら** | **0.7秒** |

`-maxrate` は見立て違いで入れたもので、外した。宅内なら帯域は余っていて、削られるのは
動きの多い場面の画質になる。細い経路には AV1 を選ぶ手がある。

### 映像だけが遅れる（音と字幕は合っている）

開き直すと直る、映像だけの遅れが出た。字幕は再生位置（音が刻む時計）に合わせて貼って
いるので、**映像だけが遅れるなら遅れているのはデコード**で、運び方でも貯め方でもない。
ブラウザは遅れたまま出し続けるので開き直すまで溜まり、放送との差の数字にも出ない。

`requestVideoFrameCallback` の `mediaTime` と再生位置の差が「映像だけの遅れ」になる。0.1秒（口の動きの
ずれが分かりはじめるところ）を超えたらその場へ飛び直す（`live-player.svelte.ts` の `unslip`。3秒に1回まで）。
飛べば必ず `waiting` が上がるが、飛んで起きた詰まりは数えない。数えると映像の遅れを直すたびに貯める量が増える。

#### 測れないこともある

`mediaTime` はコンポジタへ渡した時点のコマの時刻。Windows の Chrome / Edge は映像を別の面（DirectComposition の
overlay）に出すので、**面のほうが遅れても数字に出ない**。実機では「映像と音がずれるのに飛び直しが一度も出ない」
形で出た（ソフトウェア合成の Chromium で 18,000 コマ測っても遅れは最大 0.058 秒で、再現しない）。
そこで途切れのたびにも飛び直す。元手は1コマぶんで、映像が止まった直後なので目立たない。

**コマ落ちは合図にしない。** Windows Edge (152) では落ち着いたあとも絶えず 5.6% 落ち、合図にすると
飛び続ける（90秒に 31回。途切れだけなら 1回。飛ぶたびに音が 0.02 秒飛ぶ）。飛ぶせいで落ちが増えるのではない。

画面の「コマ落ち」「映像の遅れ 最大」「映像の遅れを補正 N回」は、運び側（途切れ）とデコード側を分けて読むためのもの。
「映像の遅れ 最大」が 0 のままなのに映像と音が合わないなら、遅れているのは面のほう。

### 「遅延」は2つある

画面に出す2つは**意味が違います**。

| 出す名前 | 何の差 | 入っているもの |
| --- | --- | --- |
| **放送から N秒** | 隣に置いたテレビが映すはずの時刻と、いま映しているコマの差 | 端から端まで（ffmpeg のエンコード・回線・手元の貯まり） |
| **貯まり N秒** | `buffered.end - currentTime` | 手元にあと何秒ぶん持っているかだけ |

長いこと後者しか出しておらず、詰める作業をするのに上流でどれだけかかっているかが見えなかった。

#### 結びつけ方

放送の PCR と映像の PTS は同じ時計で打たれている。**PCR をサーバが受け取った時刻と組にして覚えれば**
（[ts/clock.ts](../src/lib/ts/clock.ts) の `BroadcastClock`）、「このコマは隣のテレビなら何時何分に映るか」が
サーバの時計の上で言える。エンコードしたものの物差しへは、ffmpeg が入口で 0 に寄せたぶん
（入口の `Duration: N/A, start: 72575.147089`）を引くだけ。

- **遅れて読んだ組は採らない。** `受け取った時刻 − PCR` がいちばん小さい組を採る。PCR とサーバは別の水晶
  なので 30秒ごとに選び直す（直前の区切りのぶんも残して比べる）
- **端末の時計は当てにしない。** 通知にサーバの時計を添えて差を覚え、以降はサーバの時計の上で数える
  （LAN の片道は 1ms 未満）。時計の絶対値は要らず、サーバの NTP がずれていても数字は変わらない
- チューナーの中とエージェント→サーバの時間は入らない（測っていない。同じ機械の中なら小さいはず）

**放送の時刻 (TDT/TOT) とは組にしない。** 以前は TDT と組にしていたが、TDT は局ごとに固定でずれている。
NTP で合わせたサーバの時計と突き合わせると、11局（地上波9・BS 2）で -0.72秒（フジ）〜
+0.90秒（tvk）の 1.6秒幅。負の値もあるので秒未満の切り捨てでは説明が付かず、何本待っても寄らない（2026-09-26 実測）。
T26 と T15 で「放送から」が 1.3秒違って見えていたのは、ほぼこのずれだった
（[data.md](data.md#時刻合わせ-tdt--tot-は持たない) と同じ結論）。

出口の寄せ幅が入口の `start:` と同じことも確かめた（録画を切り出してライブと同じ引数で
エンコードし、`-debug_ts` と fMP4 を突き合わせて差 2ms）。映像は音声より 0.5秒ほど遅れて始まるが、頭は同じフレームで埋まり、
映像だけ 0 に詰められることは無い（[encode.md](encode.md#頭の音声だけの区間はずらさずに捨てる) の件は
Matroska を読むプレイヤーの話で、MSE ではない）。

#### 貯まりより小さく出ることはある

**テレビも PTS まで待って映す。** 放送の映像は着いてから映すまで 0.41〜0.50秒（音声は 0.12〜0.15秒）
待たせる作りで、着いた端からエンコードする denpa はそのぶん先回りできる:

```text
放送から = エンコードの完了 + 回線 + 貯まり − (テレビが待つぶん 0.4秒ほど)
```

貯まりより小さい値はおかしな値ではない。待つぶんはどの局もほぼ同じなので、局どうしの比較には使える。

### 貯まっただけでは始めない（音だけ先に出る）

**局を変えると、音が先に出て映像が遅れて始まっていた。** MSE を作り直した直後はデコーダが立ち上がって
おらず、重ねてあるのは前の局の静止画（`freeze`）なので、映像が止まったまま新しい局の音が鳴る
（Windows Edge で選局を繰り返すと、音から1枚目まで中央 41ms・最大 1043ms）。貯まりの長さだけで `play()` を
呼んでいたためで、`readyState` が `HAVE_CURRENT_DATA` に上がるまで待てば一緒に始まる（`live-player.svelte.ts` の `canStart`）。

ただし待ちきりにはしない。映像の無い放送やデコードの失敗で音まで出なくなるほうが困るので、1.5秒で諦めて音だけ先に出す。

#### 新しい局の1枚目が少し止まるのは、直さない

代わりに、新しい局の1枚目が 150ms ほど止まって見える（実機で 135〜174ms）。**意図した姿で、不具合ではない。**
止まっている間は貯まりが `target`（最短 0.2秒）に届くのを待っていて、止まって見える長さ ≒ 貯める量。

変えられるのは、その間に何を見せるかだけ。前の局の映像（音は新しい局）ではなく、新しい局の1枚目（音はまだ
出ない）を採る。見えるものと聞こえるものが食い違わないからで、前のやり方は「映像と音がずれている」と報告された。

### 落ち着いた高さは覚えておく

上の下限は**端末に覚えさせている**（`live-player.svelte.ts` の `FLOOR_KEY`)。
毎回 0.2 秒から始めていた頃は、どの経路でも足りずに開いて30秒以内に必ず1回止まり、
そこから当たりを探し直していた。

置き場が端末なのは、これが経路の性質だから。同じ人でも宅内の PC と出先の
タブレットでは値が違う（続きの位置 `resume_ms` をサーバに置くのとは逆の理由）。
長く無事なら少しずつ下げて試し直すので、宅外から帰ってくれば戻る。

戻るのは 10分ごとに 0.3 秒ずつ（`ts/pacing.ts` の `FORGET` / `PROBE`）なので、線を繋ぎ替えた
直後は前の経路の値のまま余計に遅れる。そのために**覚えたものを捨てるボタンも出してある**
（`live-player.svelte.ts` の `relearn`）。押すと覚えたものを消し、貯めているぶんも下限まで
詰めて放送の今へ戻す。覚えているものがあるときだけ出す。

低すぎる側に外れたぶんは放っておいてよい。止まればその場で上がる。

### 渡す前に1局へ絞る

**1つの物理チャンネルに複数の局が入っている。** `-map 0:v:0` は「最初に見つけた映像」でしかないので、
MX2 を選んでも MX1 の映像が出うる（実機の T26 は Eテレ1/2/3 とワンセグの 320x180 H.264 が並ぶ）。
`-map 0:p:<局>:v:0` で局を名指しする。

名指しだけでは足りない。ffmpeg は名指しした局を `-probesize` のぶん読む間に見つけられなければ
そのまま終了する。3局が入っている T15 で probesize を下げて測ったもの（3回ずつ）:

| probesize | 丸ごと渡す | 1局に絞る |
| --- | --- | --- |
| 20KB | 0/3 通る | 3/3 |
| 50KB | 0/3 通る | 3/3 |
| 120KB | 1/3 通る | 3/3 |
| 400KB | 3/3 | 3/3 |

録画と同じ `ServiceFilter` を通して局が1つだけの TS を渡せば、局を探す仕事が消える。映像だけをエンコードしていた
頃は 20KB まで下げていた（100KB との差は最短どうしで 33ms。これが固定費で、中央値の差は GOP 待ちのばらつき）。
**いまは字幕も見つけさせるので 100KB。**

- **量はほとんど減らない**（tvk 17.6 → 16.8、日テレ 17.3 → 14.5 Mbit/s）。同じ TS に入っている局は同じ ES を指していることが
  多く、落ちるのは他局の表と詰め物だけ。狙いは ffmpeg に局を探させないこと
- **名指しは絞ったあとも残す。** 万一違う局が入っていたら、黙って別の局を映すより落ちるほうがいい
- **コマ数は `-fpsmax` で上限を言う。** probesize が小さいと ffmpeg がでたらめなコマ数を起こすことがあり、
  SVT-AV1 は突っぱねる（20KB のまま AV1 で 0/3、上限を付けて 3/3）。固定（`-r`）では本当に 59.94p の局
  （720p）でコマを落とす
- ffmpeg が降りたら、その場で「映像を出せませんでした」を出す（[下](#エンコードできなくなったらその場で言う)）

### エンコードできなくなったら、その場で言う

切り替えの間は前の映像を貼る。MSE を作り直すと `<video>` は何も映さないので、捨てる前に1枚だけ canvas へ
写して重ね、次の映像が実際に出た時点で剥がす（`requestVideoFrameCallback`。`play()` が返っただけではまだ
映っていない）。貼りっぱなしを避ける上限は6秒（`live-player.svelte.ts` の `HOLD_MOST`）。**壊れているのに
動いて見えるのがいちばん悪い。**

ffmpeg が降りても何も伝えていなかった頃は、前の映像のまま6秒たって黒くなるだけで、失敗が「切り替えに6秒
かかった」に見えた。直したのは2つ:

- **終わりを ffmpeg の終了で見る。** 流し込みは書き込み先が閉じても終わらないことがあり、3つ揃うのを
  待つと死んだことに永久に気づかない
- **畳んだセッションを持ったままにしない。** 同じ局を選び直しても「もう見ている」と見なされ、「やり直す」が効かなかった

**放送が止まっているだけのときは、そう言う。** エージェントの「電波が来ていないか、その周波数に放送が
ありません」は、アンテナや配線を疑わせる。実機の「T27 がときどき同期しない」は、48時間の失敗10回が
すべて 01:04〜02:54 で、番組表の「放送休止」（00:11〜05:00）の中だった。NHK総合は保守の晩に送信機ごと
止める（Eテレは搬送波を出したままで一度も失敗していない）。番組表を持つのは denpa だけなので、
同期しなかったときだけ「放送休止です」に言い換える。塞がっていたときや ffmpeg が降りたときに
出すと、今度はこちらが嘘をつく（`server/live.ts` の `whyNotTuned`）。

### 録画に譲る

**ライブは録画にだけ譲る**（`config.priority`）。エージェントは録画から見て弱い相手（ライブを含む）しか
いないチューナーも使ってよいものとみなし、要れば取り上げる（[agent.md](agent.md#選ぶ順の約束)）。予約表で通した組を
録れるようにするためで、代わりに**ほかのチューナーが空いていてもライブがチューナーを取り上げられることがある。**

取り上げられたときの動き（画面もテレビのアプリも同じ）:

1. **まず同じ局をリクエストし直す。** 約束どおり使ってよいチューナーが空いていればそこに入り、見ているものは変わらない
   （切り替えの一瞬だけ前の映像のまま止まる）
2. **リクエストし直しても入れなかったときだけ、チューナーを取り上げた録画の追っかけに切り替える**（録れているところの少し手前から）。
   通知は「録画のためチャンネルを切り替えました: <番組名> (録画中を再生しています)」で、隣に「ライブに戻る」
3. 「ライブに戻る」はリクエストし直しを試す。まだ録画がチューナーを塞いでいれば追っかけに戻り、
   「録画が終わるまでライブは見られません (<終了時刻>)」と言う

同じチャンネルの録画は選局を共有する（チューナーは増えない）ので、取り上げられず何も起きない。

**どの録画に取り上げられたかはサーバが読む**（`server/live-yield.ts`）。エージェントは予約を知らないし、取り上げた相手を
教える API も無い。そこでライブはチューナーを確保できた時点で自分の利用者（`live <種別>/<チャンネル>`）がいるチューナーを
`GET /denpa/tuners` から覚えておき、ストリームが途切れたらそのチューナーの利用者にいる `rec <録画ID>` を読む。
1回の選局の利用者は終わるまで同じチューナーにいる約束なので、覚えたチューナーは取り上げられるまで変わらない。

**取り直すのは見ている側。** サーバはチューナーのストリームが（こちらが畳む前に）途切れたらセッションを畳み、
`lost` の通知（チューナーを取り上げた録画を添えて）を送る。セッションの中で取り直してエンコードし続けないのは、再エンコードしたものを
途中から渡すと受け側（MSE・テレビの fMP4）が続きとして読めないため。リクエストし直せば受け側ごと作り直しになる。
画面はいつもの繋ぎ直し（待ちが倍々）に乗せるので、外されては入るを繰り返しても呼び続けない。
HTTP で観ているもの（テレビのアプリ）にはストリームの中で伝えられないので、同じものを通知
（`GET /api/events` の `yielded`。[api.md](api.md#変化の通知-get-apievents)）でも流す。

**入れなかった理由は見分けない。** リクエストし直しが失敗したら、理由が何であれ（ふつうは録画がチューナーを塞いでいる）
追っかけに切り替える。「ライブに戻る」が失敗したときの「録画が終わるまで」も同じで、録画が終わったあとに
別の理由で入れなかったときは文言が外れる。

### `tsreadex` は挟まない

一度は入れかけたが、**挟む理由はどれも ffmpeg 単体で足りた**。

| 欲しかったもの | 結論 |
| --- | --- |
| デュアルモノ分離 | ffmpeg で足りる。録画と同じ見分け方（番組表の音声情報）で、選ばれた側を両耳へ配る（上記）。録画は左右を2トラックに分けるが、ライブはコンテナが1つなので片方を採る |
| 局の選び分け | ffmpeg で足りる。`-map 0:p:<局>:v:0`。実機で確認済み |
| 音声・字幕が消えたときに無音を挿す | tsreadex にしかできない。ただし**実害を確認していない** |
| `aac: Input buffer exhausted` | 直らない。壊れた AAC フレームの修復は tsreadex の仕事ではない |

イメージに1つ足す代償に対して、得られるのは最後の2行だけ。3行目の実害を踏んだら入れる。

### 入口が1つ増えている

**bun の `node:http` は WebSocket の握手ができない**（`upgrade` は上がるが、socket に書いても1バイトも届かない）。
adapter-node はその上にあり、`svelte-adapter-bun` も今の SvelteKit では `websocket` フックを挿し込めない。
そこで `Bun.serve` を前に置き、`/api/live/socket` の WebSocket だけそこで受けて、残りは 127.0.0.1 の
adapter-node へ中継する（`server.js`。試したことと、`Host` をそのまま渡す理由は冒頭の説明に）。

**開発サーバ（`bun run dev`）ではライブが繋がらない**（vite も `node:http`）。確かめるときは `bun run build && bun ./server.js`。

### 繋ぐときの認証

**ブラウザは WebSocket の握手に `Authorization` を付けてくれない。** ログインで
守っている denpa では、そのままだとチューナーを使う API が素通しになる。

画面が先に `POST /api/live/ticket` で使い捨てのチケットを取り、それを URL に付けて繋ぐ。
チケットの発行は普通の HTTP なので、OIDC も信頼したネットワークもそのまま効く。
URL は履歴にもログにも残るので、1回使ったら消す。寿命は30秒。

## 5. 実装詳細

### 5.1 エンコード

**いまの引数は `src/lib/server/live.ts` の `encodeArgs` にあります。** 1本の
ffmpeg が映像と音声を1つの pipe へ多重化し、`Fmp4Splitter` が `moof`+`mdat` ごとに
割って WebSocket へ流します。

```bash
ffmpeg -nostats -fflags nobuffer -probesize <小さく> <字幕の入口> -i pipe:0 \
    -vf <インタレ解除> \
    -map 0:p:<局>:v:0 -fpsmax <上限> <映像のエンコード方式> \
    -map 0:p:<局>:a:<何本目> [-af pan=...] <音声のエンコード方式> \
    -f mp4 -movflags +empty_moov+default_base_moof \
    -frag_duration 50000 -flush_packets 1 pipe:1 \
    <字幕の出口 → pipe:3>
```

**値は書かない。引数の並びだけ。** 実測した値と理由は `encodeArgs` / `videoArgs` の説明にあり、写すと片方が古くなる
（実際ここに写した `-frag_duration`・`-probesize`・`-preset`・音声の量が古いまま残っていた）。

- **`-copyts` は付けない**（[§5.2](#1本にしたのは時刻を揃えるため)）
- **`-loglevel` は下げない。** 選べる字幕は入口の見出し（info で出る）から拾う
  （[§5.2](#52-字幕)）。進み具合の数字だけ `-nostats` で止める
- クライアント側の SourceBuffer は `segments`（既定）で使う。`sequence` は届いた順に
  詰めるので、1つ取りこぼすと以降ずっとずれる。
  再生位置の面倒（貯めてから出す・離れたら速める）は `src/lib/ts/pacing.ts`

トラックごとに pipe を分けるなら `-movflags +frag_every_frame` に戻せる。1本に多重化している間は、映像だけ・
音声だけの塊が交互に並んで MSE が引っかかる（`encodeArgs` の「コマごとに切らない」）。複数映像も
そのときの話で、いまは映像1本・音声1本。

#### エンコード方式は見ながら選べる

画面の操作列から H.264 / AV1 を選び直せる（`LiveCodec`）。音声と同じく、選び直すと
再エンコードになる。**局を変えても引き継ぐ。** 映像の中身ではなく「その端末で出るか」の話なので。

**AV1 でも落ちこぼれない。** 設計では「ソフトウェアの AV1 は厳しい」としていたが、実機
（Xeon E5-2696 v4 / 44スレッド / HW エンコーダ無し）で 1080i をデコードして 60 コマ/秒という
いちばん重い組み合わせでも、エンコードできた尺が実時間に付いていった。コア数で間に合っている。
代償は立ち上がりが 0.45 秒遅いことで、既定はどの端末でも出る H.264 のまま。
実測は `videoArgs` の説明に（[§5.1 冒頭](#51-エンコード) と同じ理由で、ここに写さない）。

量はまだ何とも言えない。どちらも品質を指定してエンコードする（ビットレートを決めていない）ので、
量は場面で動き、実測も揃わなかった。

**音声は AV1 のとき Opus、H.264 は AAC。どちらも 256k。** 元の放送（AAC 256kbps）
に合わせた値で、録画側も前から `libopus -b:a 256k`。

#### 役割を分ける — H.264 は「速く」、AV1 は「小さく」

H.264 は**量を捨てて速さを採る**（`-preset ultrafast`、画質は既定のまま）。
画質を上げると最初の1枚が太り、書き出しに時間がかかるので必ず遅くなる。
`-crf` を付けないのが最速で、画質は今までと同じ（同じ crf 23）。増えるのは
量だけで、同じ画質を `ultrafast` で出すと 3 倍になる（実測は `videoArgs`）。
宅内向けの値なので、宅外から見るときは AV1 を選ぶ。

> **戻れる幅はバイト数でも切る。** 5分（`KEEP`）は「毎秒 3Mbit なら 110MB」の
> つもりの値だった。太ったストリームで5分持つと `appendBuffer` が `QuotaExceededError` で
> 落ち、そこから映像が出なくなる。受け取っている速さから 120MB に収まる長さを出し、
> 時間と小さいほうで切る（`live-player.svelte.ts`）。

AV1 は `lookahead=0` が要る。SVT-AV1 は既定で先読みのぶん貯め、それがそのまま遅れになる。
preset 12 を採る（13 は目に見えて粗く、10 は間に合わない）。

> **付けてもまだ溜め込む。** 電波が届いてから mp4 の塊が出るまでが H.264 の数倍かかり、
> 低遅延指定（`pred-struct=1`）は実時間に間に合わない（出口が 6秒 → 22秒 と
> 離れていった）。**AV1 を選ぶと放送の今から1秒ぶん離れる**（切り替えの画面にはまだ出していない）。

**受け取れない端末では H.264 に戻す。** `MediaSource.isTypeSupported` が false なら
その場で戻し、理由を画面に出す。黙って別の形式にすると、切り替えが効かない理由が分からない。

> **iPhone の Safari は `MediaSource` を持たず、`ManagedMediaSource`（iOS 17.1+）だけがある。**
> 無ければそちらを使う（`ts/media-source.ts`）。`disableRemotePlayback` を立てないと開かない。
> 送り込む頃合いの合図（`startstreaming` / `endstreaming`）は聞かず、ブラウザの刈り取り
> （`bufferedchange`）は `buffered` を毎回読み直すので手当てしていない。**実機では未確認。**
> 出せなかったときも操作列は出したままにしてあり、エンコード方式を選び直して逃げられる。

#### GPU でエンコードする

設定の「GPU」カードでそのコーデックに印があれば、**録画と同じ GPU でエンコードする**（Intel の QSV / VA-API。
引数と決め方は [encode.md「ライブも同じ印で GPU に載る」](encode.md#ライブも同じ印で-gpu-に載る)）。
MPEG-2 を GPU でデコードできる環境ではデコードとインタレ解除も GPU に寄せ、映像の鎖に CPU のフィルタを挟まない。
`-fpsmax`・字幕の出口（`pipe:3`）・音声はそのまま通る（字幕と音声は別のストリームで、`-fpsmax` はコマを間引くだけ）。

**映像を出す前に GPU の ffmpeg が降りたら、ソフトウェアで再エンコードする**（その経路は15分覚えてソフトウェアでエンコードする。
決め方は [encode.md](encode.md#ライブも同じ印で-gpu-に載る)）。画面には断り書きを一行出す（`notice`。
AV1 を出せない端末で H.264 に戻したときと同じ通知）。HTTP のエンドポイント（`sessionStream`）は通知を捨てるので、
アプリには再エンコードが少し遅れて見えるだけ。

NVIDIA / AMD（`av1_nvenc` / `av1_amf`）はまだ試しのエンコードに入れていない。

### 5.2 字幕

**映像と同じ ffmpeg から、字幕をデコードせずに写して受け取る。出口を2つ持つ**（`src/lib/server/captions.ts`）。
デコードして置き場所を決めるのは denpa（`src/lib/ts/b24caption.ts`）、描くのはブラウザ（`components/player/caption-draw.ts`）。

```bash
ffmpeg <上の映像の引数と同じ> -i pipe:0 \
    ... pipe:1 \
    -map 0:p:<局>:s:<n> -c:s copy -cluster_time_limit 1 -cluster_size_limit 1 \
    -flush_packets 1 -f matroska pipe:3
```

**ここも引数の並びだけ**（[§5.1](#51-エンコード) と同じ理由）。値は `captionOutput` の説明にある。

- **写すだけ** (`-c:s copy`)。Matroska には ARIB の字幕がそのまま (`S_ARIBSUB`) 入る
- **局を名指しする。** 映像と同じ理由（1つの物理チャンネルに複数の局が入っている）
- **Matroska で受ける。** 時刻をコマと一緒に運ばせるため（下の「時刻はコマに付けて運ぶ」）
- 受けたコマをデコードして文字の配置にし (`CaptionText`)、0x22 で配る。**デコードして出てくるのは字幕が変わったときだけ**
  (字幕管理データや送り直しは何も出さない) なので、間引く必要も無い

#### 1本にしたのは、時刻を揃えるため

以前は映像を作らない ffmpeg をもう1本、同じチャンネルに当てていた。**それでは時刻が
揃わない。** ffmpeg は入口で時刻を 0 に寄せ直すが、寄せ幅はプロセスごとに違う。
別々に起こした2本はエンコードし始めの鍵フレームがずれ、出てきた時刻どうしを突き合わせても
意味が無い。`-copyts` で放送の絶対時刻を保っても、mp4 のマルチプレクサがその時刻を
0 に詰め直す（`-avoid_negative_ts disabled` も `-muxdelay 0` も `-output_ts_offset` も
効かない。実機で確認）。

1本にすれば入口の寄せが1回で済み、両方の出口に効く。実機で突き合わせると 1ms 以内で
一致した（実測は `captions.ts`）。

引き換えに、音声やエンコード方式を選び直すと字幕も再エンコードになる（前は局ごとに1本だったので
途切れなかった）。字幕は次が来るまで出しっぱなしなので、再エンコードの間はサーバが
最後の1枚を配り直して繋ぐ。

> **字幕を持たない放送はある**（ショッピングやサブチャンネル）。そこに `0:p:X:s:0` を
> 指定すると ffmpeg は組み立ての時点で降り、映像も出ない。そうと分かったら
> 字幕なしで再エンコードし、その局は15分覚えておく（`server/live.ts` の `captionless`）。

#### 時刻はコマに付けて運ぶ

字幕を並べただけでは時刻が乗らないので、**コンテナに入れて運ばせる。**
Matroska は使うところだけなら小さい。`src/lib/ts/mkv.ts` が読むのは
`TimestampScale` / `Cluster > Timestamp` / `SimpleBlock` と `BlockGroup > Block`、それに中身の種類 (`CodecID`) だけ。
NUT はコマの見出しを組み立てるのに表の復元が要り、mp4 は ARIB の字幕を入れられない。

塊の上限を最小（`-cluster_time_limit 1` / `-cluster_size_limit 1`）にして、1枚ごとに
書き出させる。溜められるとそのぶん遅れる。

#### 画像をやめて減ったもの

同じ録画の 103 秒をライブと同じエンコード方式で通すと、CPU は 152 秒 → 101 秒 (1 本あたり 0.5 コア軽い)、字幕に配る量は
1.08 MB → 14.3 KB になった (sub2video が映像のコマごとに 1920x1080 の画像を起こして PNG に組んでいたぶん)。
denpa がデコードする手間は 218 コマで 6ms。

**描くのは受け側の canvas** で、置き場所の計算は libaribcaption のデコーダそのものなので、画像と同じ所に出る。
作り物の字幕と実機の録画 30 枚を、同じ丸ゴシックで描いて画像と画素単位で比べると、墨の外枠は全部 ±1 画素、
色の差は平均 1〜3/255 だった (縁取りの太さで少し違う)。

#### エンコード方式ごとに分かれる

字幕はエンコード方式（音声・コーデック・何本目の字幕か）ごとに分かれる（[共有の単位](#入っているもの)）。
**その代わり TS をもう1本もらわずに済む。** 別建てだった頃は
字幕のためにチューナーの共有をもう1つリクエストし、地上波2台のうち1台を番組表集めが使っていると断られていた
（`[captions] GR:T15: チューナーに空きがありません`）。

> **字幕が1枚も来ない番組はある**（本編に字幕が無ければ0枚。異常ではない）。ボタンを出すかは届いた枚数では
> なく、ffmpeg の入口の見出しで決める（`TrackList`）。届いてから出していた頃は、間隔の空く番組（実機の
> 「みんなの手話」。番組表には [字] と出ている）でボタンが出なかった。持っていない放送では出さない。

### 5.3 WebSocket プロトコル

単一接続で全チャネルを多重化する。

```
[1 byte: channel][8 bytes: 時刻 (90kHz, BE)][payload...]

channel:
  0x00  video init segment (ftyp + moov)
  0x01  video media  (moof + mdat)。音声も同じ fMP4 に入る
  0x02  元の TS      1局に絞った TS そのまま (§5.5)。時刻は 0。init は無い
  0x10  audio init segment   ※いまは使わない (映像と同じ fMP4)
  0x11  audio media          ※同上
  0x20  (空き)       以前の字幕の画像 (PNG)。もう使わない
  0x21  (空き)       以前の「字幕を消す」。もう使わない
  0x22  字幕の文字の配置  JSON (api.md「字幕の文字の配置」)。前の1枚を丸ごと置き換える
  0x30  データ放送   ResponseMessage (JSON。`ts/bml-protocol.ts`)。時刻は 0
  0x40  制御         ここだけ双方向の JSON (選局・追っかけ・データ放送の指示 / tuned・字幕一覧・時計 等の通知)。時刻は 0
```

- init セグメントは接続直後に必ず送る（再送用にサーバ側で保持）
- MSE はバイト列をそのまま `appendBuffer()` に投げられるので、映像音声のパースは不要
- 字幕の座標は字幕の面 (`plane`。ふつう 960x540) の単位。受け側は映像の枠に合わせて伸ばし、画面の画素で描く
- **頭の時刻は「エンコードした mp4 の物差し」。** 映像も音声も字幕も同じ ffmpeg がエンコードするので、
  受け側の `video.currentTime` と直に比べられる（[§5.4](#54-時刻同期)）
- **放送のままの経路（0x02）では、字幕の時刻は放送の PTS そのまま**（受け側の時計が放送の PTS なので。[§5.5](#字幕)）
- 途中から入ってきた視聴者のために、いま出ている字幕はサーバが1枚だけ保持して再送する

### 5.4 時刻同期

| 対象 | 方法 |
| --- | --- |
| 映像・音声 | fMP4 の timescale で自動的に整合 |
| 字幕 | 添えられた時刻（映像と同じ ffmpeg が付けた mp4 の物差し）に置く。出しておく長さ (`duration`) があれば過ぎたら消す |
| データ放送 | カルーセルは時刻同期不要（PMT/TOT と denpa の番組表の更新に追従） |

**いまは測っていません。** 字幕のコマに付いてくる時刻を再生位置と比べ、
「追い越していない中の最後の1つ」を出すだけです（`ts/captions.ts`）。
映像と字幕を同じ ffmpeg でエンコードしているので揃います（[§5.2](#52-字幕)）。

> 「放送から N秒」は遅れを見せるためだけのもので（[「遅延」は2つある](#遅延は2つある)）、
> 映像・音声・字幕を揃えるのには使っていない。

#### そこへ来るまでに3回外した

どれも別々の ffmpeg の出口どうしを突き合わせて測っていた:

| 使った基準 | 実測のずれ |
| --- | --- |
| mp4 の 0（＝エンコードされた1コマ目のつもり） | **2.4秒**。マルチプレクサが 0 に合わせるのは probe の間に溜まった音声 |
| エンコードしているフレームの時刻（映像側の `showinfo`） | **5秒**。フィルタはエンコーダより先を走る |
| 字幕側の `showinfo` が言う放送時刻 | **1秒ほど遅れる**。行とフレームの数が合わず、組がずれる |

「待たせる量を渡す」に替えても3回外した。別々に起こした ffmpeg は鍵フレームが 0〜0.5 秒ずれるので、
測れないものを測っていた。**直したのは測り方ではなく作り**で、1本の ffmpeg に両方をエンコードさせ、測るもの
自体を無くした（[§5.2](#1本にしたのは時刻を揃えるため)）。`-copyts` は効かないうえ、実機で
`Assertion next_dts <= 0x7fffffff failed at libavformat/movenc.c` で映像ごと落ちた（放送時刻は 32bit に収まらない）。

- **貼り直すのは映した1枚ごと**（`live-player` の `follow`）。届いた塊に合わせていた頃は、遅れる方向にだけ 0〜50ms ずれていた
- **再エンコードのたびに、待たせている字幕は捨てる**（`forget`）。mp4 の時刻が 0 から数え直しになるため

### 5.5 放送そのまま（MPEG-2）を送る

**ブラウザでエンコードせずに見られます。** 1局に絞った TS をそのまま
WebSocket に流し、ブラウザが WebAssembly の MPEG-2 デコーダでデコードして WebGL2 で描き、音も
同じ WebAssembly の AAC デコーダでデコードして Web Audio で鳴らします（バックグラウンド再生を入れている間は
`<audio>` を通す。下の「時計とリップシンク」）。**ライブの画質の切り替えで MPEG-2 を選ぶ**と
放送のまま送るようになり、エンコード方式と同じく端末ごとに覚えます（`LAST_COOKIE`。既定は H.264）。

```
エージェント → 1局に絞る ┬→ WebSocket (0x02 元の TS) → worker ┬→ PES → WASM (mpeg2video) → WebGL2 (bob)
                         │                                    └→ ADTS → WASM (aac) ─→ 画面 → Web Audio (時計) [→ <audio>]
                         ├→ ffmpeg (字幕を写すだけ。-copyts) → デコードする → 0x22 文字の配置 (放送の PTS のまま)
                         └→ BmlDecoder → 0x30 データ放送 (エンコードする経路と同じ)
```

**ブラウザに MPEG-2 のデコーダは無い**ので持ち込んでいます。Chromium 151 で実際に聞いた結果:

| 聞き方 | `mp2v` / `mpeg2video` | `avc1` | `av01` | `vp09` | AAC |
| --- | --- | --- | --- | --- | --- |
| `MediaSource.isTypeSupported` | **×** | ○ | ○ | ○ | ○ |
| `VideoDecoder.isConfigSupported` | **×** | ○ | ○ | ○ | ○ |

（`video/mp2t` そのものは ○ だが、これは**中身が H.264 の TS** の話）

得るもの: **ffmpeg の立ち上がり 0.5〜0.7 秒と、エンコードするのに掛かっているぶん**（電波が届いてから
塊が出るまで。実測は `server/live.ts` の `videoArgs`）**が丸ごと消え**、サーバの CPU も
350〜470% からほぼ 0 になります（字幕を描く ffmpeg だけ残る。映像をデコードしないので軽い）。
残る遅れは受け側の貯め（`ts/pacing.ts` の `FLOOR` から始まる貯め）だけです。

#### いつ放送のまま送るか

2つが揃ったときだけ。決めるのは画面です。

| | 誰が見る | 外れたら |
| --- | --- | --- |
| 画質の切り替えで MPEG-2 を選んでいる | 画面 (`LAST_COOKIE` の `raw`) | いつもどおりエンコードする |
| その端末でデコードできる (WebAssembly・worker の WebGL2・AudioContext) | 画面 (`raw/support.ts`) | エンコードしたものをリクエストし、理由を断り書きに出す |

**家の外からでも放送のままで見られます。** 回線が 1局ぶん（下の「払うもの」）出るかは見る人が決める
（放送のままになるのは MPEG-2 を選んだ端末だけ）。足りない回線では貯め直しを繰り返し、音が5秒来なければエンコードしたものへ戻ります。

**http で開いた LAN でも放送のままで見られます。** 音を WebCodecs の AudioDecoder でデコードしていた頃は、
それが安全な繋ぎ（https か localhost）でしか出てこないので http では使えず、iPhone の
Safari には iOS 26 まで AudioDecoder が無かった。iOS 27 の Safari では出てくるのに ADTS の
まま渡すと転び（実機。1枚目の映像のあと「音声を再生できませんでした」）、ADTS の頭を外した AAC と
AudioSpecificConfig を求めているらしい。ブラウザごとの癖を追うより、映像と同じ FFmpeg で
デコードすることにした（1つの経路だけ。AudioDecoder と切り替えない）。WebAssembly の無い端末
（iOS の Gecko など）は「WebAssembly が使えません」と出してエンコードしたものに戻ります。

**放送のままで見ている途中でも、エンコードしたものへ自分で戻ります**（戻したら、その画面を開いている間は
リクエストし直さない — 戻しては諦めるを繰り返すと、そのたびに映像が止まる）:

- デコードするのが間に合わない（下の「間に合わないとき」）
- デコーダが入っていない（`/api/live/mpeg2` が 404）・worker が落ちた
- 映像は出ているのに音が 5 秒来ない・AAC のデコーダが壊れたコマで 20 回続けて転ぶ（1回なら飛ばす）

#### デコーダ

FFmpeg の **mpeg2video のデコーダとフレームの区切りを探す parser、AAC のデコーダだけ**を emscripten で組んだもの
（`wasm/mpeg2/`。互換モードの音のために Opus のデコーダと、それが当てにする swresample も入っている。下の「互換モード」）。AAC の parser は組まない — ADTS の区切りと時刻は JS（`ts/pes.ts` の
`AdtsSplitter`）が付け、デコーダは ADTS の頭を自分で読む。音も映像と同じ worker でデコードする
（1秒ぶんで数 ms と、映像の 1% に届かないので worker を分けるほどではない）。**Dockerfile の `mpeg2wasm` 段で毎回組み**、git には入れません（生成物を
抱えると FFmpeg を上げるたびに差し替えが要り、組んだ手順と中身が食い違っても気づけない）。
FFmpeg はサーバの ffmpeg と同じ版に揃え、emsdk は版で固定しています。置き場はアプリの外
（`/opt/denpa/mpeg2`、`MPEG2_DIR`）で、`/api/live/mpeg2/<名前>` から配ります — 開発と E2E の
compose はソースを `/app` に被せるので、中に置くと隠れます。

| | |
| --- | --- |
| 大きさ | `decoder.wasm` 855KB（brotli 292KB / gzip 364KB）+ 読み込み用の `decoder.mjs` 14KB。**配るときは denpa が縮める**（`Accept-Encoding` を見て brotli か gzip。中身が変わったときに1度だけ縮めて覚える）。AAC を足す前は 474KB（brotli 163KB / gzip 196KB） |
| 速さ（手元の Chromium、ヘッドレス） | BS の 1920x1080i で **90〜97 コマ/秒**、1440x1080i で 110〜130 コマ/秒 — **実時間の3倍** |
| 音の速さ（同じ） | AAC-LC 48kHz の音1秒をデコードして写すのに **ステレオ 256kbps で 1.0〜1.6ms、5.1ch 384kbps で 2.3〜2.9ms**（映像は1秒で 300ms ほど） |
| 組む時間 | 2分ほど（amd64 / arm64 どちらのランナーでも。中身は同じ） |
| **GPU が無いとき** | 描くほうが間に合わない。ソフトウェアの WebGL（SwiftShader）では 1080 の1コマを上げて描くのに 40〜60ms かかり、10〜14 コマ/秒しか出ない — 5秒でエンコードしたものに戻る（下の「間に合わないとき」）。E2E が通るのは映像が小さい（256x144）から |

**スレッドも SIMD も使いません。** スレッド版は SharedArrayBuffer のために COOP/COEP
（`crossOriginIsolated`）を全ページに要求することになり、データ放送の中継やロゴ、別オリジンへ
開く Hybridcast と噛み合いません。SIMD は1割ほどしか変わりませんでした。1スレッドで実時間の3倍
出ているので、払う理由がありません。

#### 時計とリップシンク — 時計は鳴っている音

**鳴っている音を時計にします**（`raw/playout.ts`）。音は途切れると誰でも気づきますが、映像は
1コマ遅れても気づかれにくい。だから音は届いた順に隙間なく Web Audio の時間の上へ予約し、
映像は「いま耳に届いている PTS」を追いかけて、番が来たコマを出します。放送の PTS は音と映像で
同じ時計（PCR）に乗っているので、それで音と映像が合います。

- 「いま耳に届いている PTS」は `AudioContext.getOutputTimestamp()` から出す — 予約している
  位置ではなく**出口までの遅れを引いた位置**。それを performance の時刻と組にして worker へ
  流し（20ms ごと）、worker は組から外挿してコマを選ぶ
- **PCR は受け側では使いません。** 貯めは「届いた音の端 − 鳴っている位置」で見るので、
  放送の時計と手元の時計の対応は要らない（`clock` の通知は「放送から N 秒」を出すのにだけ使う。
  放送のままの経路では ffmpeg の `start:` を引かず PCR をそのまま渡す）
- **PTS は 26.5 時間で一周する**ので、受け側は増え続ける数に伸ばして持つ（`ts/pes.ts` の
  `unwrap`）。字幕と時計の通知も、同じ物差しの近くへ伸ばしてから比べる
- 自動再生で音を断られたら、**壁時計を時計にして映像だけ進め**、「音を出す」を押された時点で
  鳴っている位置のまま音の時計へ移る（`RawEngine.follow`）。逆に音が止められたら（出口が
  外れた・OS に止められた）壁時計へ戻り、映像は止めない

##### `<audio>` を通すとき

**バックグラウンド再生を入れている間と、押して小窓を開いている間は、音を `<audio>` から鳴らします**
（`RawEngine.route`。Safari は除く — そちらは Audio Session を `playback` にする。理由は
[player.md](player.md#裏に回したら止めます)）。GainNode の先を `context.destination` から
`createMediaStreamDestination()` に繋ぎ替え、そのストリームを `<audio>` の `srcObject` に渡すだけで、
予約の仕方も時計の物差し（`context.currentTime`）も変わりません。変わるのは**耳に届くまでの遅れ**です:

- ストリームへ出した音は **Web Audio が組んだその場でストリームに入る** — ページの出口の遅れ
  （`baseLatency + outputLatency`。`latencyHint: 'playback'` で大きめ）は通らず、代わりに `<audio>` の
  出口の遅れが掛かる。ヘッドレスの Chromium で測ると、ストリームに入るのは直に鳴らしたときの
  耳の時刻より **84ms 早かった**（`baseLatency` 23ms + `outputLatency` 72ms = 95ms の大半）
- `<audio>` の出口の遅れはページから読めないので **見込み（`STREAM_OUT` = 30ms）で置く**。
  時計は `getOutputTimestamp()` の組のまま、PTS を `baseLatency + outputLatency − STREAM_OUT` だけ先へずらす
- 見込みは**少なめ**に置く。外れると音が映像より遅れる側に倒れる（人は音が先に来るほうに気づき
  やすい）。上の測りでは、`<audio>` の出口の遅れを L とすると音が映像より L − 19ms 遅れる。
  ずらさなければ逆に音が 84 − L ms 先に来ていた
- オン/オフを切り替えたときは、その差のぶん時計が一度だけ飛ぶ（映像が1〜数コマ止まるか飛ぶ）
- **止める・再開は `<audio>` にも写す。** ロック画面・車の操作・ブラウザの再生中の通知は
  `<audio>` を直に止めるので、それも操作バーに反映する（`RawEvents.remote`）

CSP には掛かりません（`srcObject` は URL を読まない。E2E で `securitypolicyviolation` が出ないことを見ている）。

#### 貯め方

**エンコードする経路と同じ考えで、決め方も同じものを使います**（`pacing.nextTarget`。止まったら伸ばし、
無事が続いたら縮め、止まった高さを覚える）。覚える置き場も同じ（`FLOOR_KEY`）。

- 貯まった音の尺が `target` に届いてから、**放送の今から `target` 手前で**鳴らし始める
- **使い切ったら止まって貯め直す**（止まった回数はエンコードする経路の「途切れ」と同じ数に出る）
- 溜まりすぎ（`target` + 1秒が3秒続く。裏に回ったタブが戻ったとき・時計のずれ）は
  **放送の今へ飛ぶ**。エンコードする経路のように 1.05 倍で詰めることはしません — 音を速めると音程が
  変わる（MSE は保ったまま速めてくれていた）

**貯めるのはデコードする前**です。1080 のフレームは1枚 3MB あるので、貯めのぶんをデコードしたフレームで持つと
1秒で 90MB になる。圧縮のまま（PES）持っておき、**番の 0.3 秒前にデコードします**（1コマ 10ms
前後なので間に合う）。デコードできたフレームはデコーダの中で順番待ちさせ（8枚まで）、番を過ぎたものは
テクスチャに上げずに捨てます（コマ落ちとして数える）。

#### インタレ解除 — bob と、櫛になっていないところは織る

1080i の1コマには時刻の違う2枚（フィールド）が1行おきに入っています。**フィールドごとに
出して、抜けた行はコマの中だけで埋めます**（`raw/render.ts` のシェーダ。色差も同じ）。

- **動きが 60 枚/秒のまま出る**（エンコードする経路の `bwdif` と同じ）。スポーツや流れるテロップが滑らか
- 抜けた行は、**もう片方のフィールドのその行が上下の行の間に収まっていればそのまま使う**
  （織る）。はみ出していれば櫛（2枚の間に動いた）なので、上下の平均で埋める（bob）。
  はみ出しが 8/255 までは雑音として織り、16/255 からは埋める（間はなだらかに混ぜる）
- 前後のコマを持たなくていい。テクスチャ1組で描けて、GPU の手間は誤差

**最初は素の bob（いつも上下の平均で埋める）でしたが、画面がちらつきました。** 上の
フィールドと下のフィールドでは縁になる行が1行ずれるので、交互に出すと**止まっている
テロップの縁が毎秒 30 回上下に揺れる**（bob の宿命）。止まっているところは、どちらの
フィールドの番でも織った同じフレームになるので揺れません。残るのは1行だけの細い横線（上下の
行の間に収まらない）くらいで、放送はインタレの画面でちらつかないよう縦をぼかしてあるので
まず出てこない。前のコマと比べる本当の motion adaptive（テクスチャを2組持つ）は、
これでも気になれば足す

インタレの印の無いコマ（720p など）はそのまま出します。色は HD が BT.709、SD が BT.601
（限定レンジ）。1440x1080 は画素の縦横比を掛けて 1920 幅で描きます。

#### 選局と途切れ

- **局を変えても worker とデコーダは作り直しません**（`reset` で中身だけ捨てる）。デコーダを
  開き直し、**I フレームが来るまで渡さない** — MPEG-2 は I からしかデコードできず、先に P/B を渡すと
  灰色の映像が出る（放送の GOP は 0.5 秒）
- 貯めている間は**新しい局の1枚目を出して待つ**（エンコードする経路の[「新しい局の1枚目が少し止まる」](#新しい局の1枚目が少し止まるのは直さない)と同じ判断）。
  それまでは前の局の最後のフレームが放送のまま描く canvas に残る。エンコードする経路で使う「前の映像を貼る」canvas は
  空にしておく（エンコードしていた頃の古い映像が放送のまま描く canvas の上にかぶさって見えていた）
- 大きく遅れたら（0.5秒）デコードしながら追わずに I フレームまで飛ぶ。止めている間に溜まる圧縮の
  待ちも8秒で切る
- サーバでの共有は局と字幕の単位（音声とエンコード方式では分けない — 音声は全部送って画面が選ぶ）。
  チューナーの使い方・畳み方・`warm` はエンコードする経路と同じ

#### 字幕

**字幕は ffmpeg に写させて、denpa がデコードします**（エンコードする経路と同じ。§2）。映像をデコードしない ffmpeg を
1本起こし（`captions.rawCaptionArgs`）、**`-copyts` で放送の時刻のまま**字幕だけを写させます。CPU は 0.2% ほど。

エンコードする経路で「同じ ffmpeg に両方エンコードさせる」のは、入口で時刻を 0 に寄せる幅がプロセスごとに違う
からでした（[§5.2](#1本にしたのは時刻を揃えるため)）。放送のままの経路の受け側は放送の PTS そのものを
時計にしているので、字幕も放送の PTS のまま出せば突き合わせられます。mp4 のマルチプレクサが 0 に
詰め直す問題は、字幕の出口（Matroska）には無い。実機の録画で、出てきた字幕の時刻が元の TS の
字幕 PES の PTS と 1ms 単位で一致しました（71759.734333 → 71759.734）。**`-copyts` を外すと
合いません** — 映像を出さない ffmpeg は寄せ幅を入口の `start:` と違う値にし（同じ録画で
0.3〜0.7秒）、それを外から知る方法が無い。

**テレビのアプリも同じ字幕を受け取ります**（[api.md](api.md#元のtsの字幕-get-apiservicesidcaptionsget-apirecordingsidcaptions)）。
ライブは放送のままで送るセッションに脇から乗り、字幕 (0x22 の文字の配置) と字幕一覧の通知 (0x40) だけを、
1つずつ頭に長さを付けて HTTP で流します（チューナーは増えない。乗っても畳む判断には数えない）。元のTSの録画と追っかけは、
リクエストされた位置の少し手前から同じ ffmpeg を1本起こします。アプリは Media3 の TS のパーサが 0 に寄せた幅を
足し戻して放送の PTS にし、そこで突き合わせます。

字幕の ffmpeg が転んでも映像は止めません（映像はそもそも ffmpeg を通っていない）。流し込みも
待たせない — 書き込みが捌けていない間に来た塊は字幕の側に渡さない（字幕が1枚欠けることは
ありうるが、映像が止まるよりいい）。

#### データ放送

**変わりません。** 1局に絞った TS の写しを `BmlDecoder` がデコードするのは同じで、描く側は映像の入れ物を
動かすだけ — 放送のまま描く canvas もその入れ物の中にあるので、一緒に動きます。

#### 間に合わないとき

**1コマをデコードする時間の 95 パーセンタイルが1コマの長さの 8 割を超えるか、映像が時計から
0.25 秒以上遅れる**のが、**1秒ごとに数えて5秒続いたら**エンコードしたものに戻します（`raw/budget.ts`）。
1回の重さ（タブを戻したとき・GC・選局の直後）では戻さない — 戻すと再エンコードで 1 秒近く
映像が止まるので、一瞬の詰まりより高くつく。デコードする時間は操作列に「デコード N ms」と出ます。

#### 払うもの

- **帯域。** 1局に絞った元の TS は実測 14.5〜16.8 Mbit/s で、中身によらずほぼ一定
  （エンコードしたものは形式と場面で動き、AV1 なら数分の1まで）。細い回線では放送のままにしないこと
- **端末の CPU と電池。** デスクトップなら1コマ 10ms（1スレッドで実時間の3倍）だが、携帯や
  非力なノートでは電池を目に見えて使う。**既定を H.264 にしてあるのはこのため**
- **MSE に乗っていたものが無くなる:**
  - **止めて再開は放送の今から**（止めた所からは見られない）。5分戻れるシークバー・追っかけの速さも無い。
    1局 15Mbit/s を遡れるだけ持つと 5 分で 600MB になる
  - エンコード方式（H.264 / AV1）の選び直し（エンコードしていない）
  - 5.1ch の番組は頭の2つ（前の左右）だけ鳴らす（下げ方を持っていない）
- インタレ解除はコマの中だけで決める（上）ので、`bwdif` よりは落ちる

#### 実機で確かめること

ヘッドレスの Chromium（GPU 無し・SwiftShader）と偽の放送（`src/lib/ts/synth-av.ts` の小さい
MPEG-2 と無音の AAC）でしか通していません（AAC のデコーダだけは ffmpeg で作ったステレオ・5.1ch・
壊したコマ・途中で形式の変わる ADTS でも確かめた）。本物の GPU・本物の放送で見るべきところ:

- **リップシンク**（`getOutputTimestamp` の遅れの見積もりが Bluetooth などの出口で合っているか）
- 止まっているテロップがちらつかないか、動くところが櫛にならないか（櫛が見えるなら
  織るのをやめる幅 8/255〜16/255 を詰める。ちらつくなら motion adaptive を足す）
- 1080i を実時間でデコードできるか（ノート・古い PC・Firefox / Safari）。「デコード N ms」を見る
- **デュアルモノ**（二カ国語）と**複数音声**の切り替え、**5.1ch** の番組（前の左右が出ているか）
- 長時間（数時間）見て、音の時計と放送の時計のずれで飛び（溜まりすぎ）が何回起きるか
- 携帯・タブレットの電池（MPEG-2 を選んだときにどれだけ減るか）

#### 互換モード — エンコードしたもの (H.264 / AV1) も canvas に描く

**`<video>` の再生が止まる端末のための方式です。** テスラの車載ブラウザは、停車中でも `<video>` の
再生を止めます。canvas に描くものは止めないので、放送のままの MPEG-2 は止まらずに観られていました。
互換モードでは**ライブ・追っかけ・録画の観る画面の H.264 / AV1 も同じ worker でデコードして canvas に描きます**
（観る画面は[下](#録画の観る画面も-canvas-に描く)）。

```
サーバ (変えない) → WebSocket (0x00 init / 0x01 媒体。fMP4) → worker ┬→ moof/trun → WebCodecs (VideoDecoder) → 2D
                                                                     └→ AAC は ADTS の頭を付けて / Opus は OpusHead で → WASM → 画面 → Web Audio (時計)
```

- **サーバは変えません。** リクエストの仕方も届くものもエンコードする経路と同じ fMP4 で、画面が MSE ではなく放送のまま描くエンジン
  （`RawEngine` の `fmp4`。`raw/fmp4.ts`）へ流すだけ。受け取るのは放送のままのときと同じ worker で、作るときに
  何を受け取るか（`RawInput`）を決める（描く先の canvas の使い方が WebGL2 と 2D で違うので途中で替えない）
- **箱は自前で読みます**（`ts/fmp4.ts` の `readInit` / `readFragment`）。moov の avcC / av1C / esds / dOps と、
  moof の tfdt / trun。中身の在りかは moof の頭から数える（`+default_base_moof`）
- **映像は VideoDecoder**（`description` に avcC / av1C）。デコードできた VideoFrame は**描いたらすぐ閉じる**
  （持つとデコーダのフレームの置き場が尽きる。デコードできたフレームと渡したままのフレームを合わせて 6 枚まで）。圧縮のまま
  持っておき、番の 0.3 秒前に渡すのは MPEG-2 と同じ。コマの時刻が飛んだら（サーバが詰まった客に
  媒体を捨てた）次の鍵のコマまで捨てる。デコーダが転んだら開き直して鍵のコマから入り直し、
  4 回続けて転んだら諦める
- **音は MPEG-2 と同じ WASM。** AAC は esds の AudioSpecificConfig から ADTS の頭を組んで付ける
  （`adtsHeader`）。Opus（AV1 と組む）は同じ組み立てに Opus のデコーダを足してデコードする（`opus_open`。
  dOps を OpusHead に書き換えて渡す。Opus のデコーダは swresample を当てにするので、それだけは
  組みに残す）。**H.264 の WASM のデコーダは作りません**（代わりは MPEG-2）。dav1d も WASM にしません
- **時計は放送のままのときと同じ**（鳴っている音。`playout.ts`）。時刻は MP4 の物差し（0 から数え、一周しない）で、
  字幕・時計の通知も同じ物差しで届く
- **間に合っているか**（`budget.ts`）は、1コマの時間では判じない — GPU の経路は詰まっていなくても
  数コマぶん溜めることがある。代わりに VideoDecoder の詰まり（`decodeQueueSize` が窓の間ずっと
  3 枚以上）と、映像の遅れ（0.25 秒）を同じく 5 秒続いたかで数える
- **速さは等速だけ。** ライブは止めて再開は放送の今から（放送のままのときと同じ。戻れるシークバーも追っかけの速さも出ない）
- **追っかけは放送の今を追わない**（`RawEngine` の `chase`、`playout.ts` / worker の `follow`）。溜まっても飛ばず、
  止めて再開は止めた所から（止めている間に届いたぶんも捨てない）。シークバーは出すが、動かすといつもリクエストし直す
  （手元に持っているのは先だけ）。サーバは倍速で送り込んでくるので、圧縮のまま持つのは **120 秒か 120MB の
  小さいほうまで**（エンコードする経路の MSE の `BUDGET` と同じ量）。超えたら受け取るのをやめ（`full`）、手元が 5 秒を
  切ったらいまの位置からリクエストし直す（`REFILL`。その間 1 秒ほど前の映像のまま止まる）。追っかけに MPEG-2 は無いので、
  描けなくなったら理由を出して止まる

**オン/オフは端末ごと**（設定の「互換モードで再生」。`canvas-video.ts`）。localStorage の鍵 1 つ
（`canvas-video` = `on` / `off` / 無し）で、**明示した値が勝ちます**。無ければ UA に `Tesla/<数字>` が
ある端末は入、それ以外は切（判定は画面だけ。サーバは UA を見ない）。同じ項目に、この端末で
H.264 / AV1 が使えるか（`VideoDecoder.isConfigSupported`）と、テスラの印があるかを出します。

**運転中の注意を一度だけ出します**（`canvas-drive-notice`）。設定で入れたとき（確かめる窓。取消できる）と、
UA の既定で入っている端末で初めて canvas で再生する前（「わかりました」を押すまで再生を始めない）。
位置情報で止める仕組みは作りません。

**諦めるとき — `<video>` には戻りません**（テスラでは止まってしまう）:

| | どうするか |
| --- | --- |
| この端末でデコードできない形式 | 画質の切り替えに「この端末では表示できません」と出して選ばせない。選んでいた形式がデコードできなければデコードできるほうへ（H.264 → AV1）、どちらも駄目なら MPEG-2、それも駄目なら「この端末では再生できません」 |
| 描いている途中で諦めた（間に合わない・デコーダが転び続ける・音が来ない） | MPEG-2 で描けるならそちらへ（断り書きに理由）。無理なら理由を出して止まる |
| MPEG-2 を諦めた | エンコードしたものを canvas に描く（互換モードでなければ今までどおり `<video>`） |

VideoDecoder は**安全な繋ぎ（https か localhost）でしか出てきません。** http で開いた LAN では
H.264 / AV1 とも「使えません」になり、MPEG-2 で描きます。AV1 はデコードするのが重いので、互換モードでも既定は H.264 です。
E2E（`tests/e2e/38-live-compat`）は偽 ffmpeg が本物の H.264 + AAC・AV1 + Opus の fMP4 を流し、描くところまで
見ます（H.264 は走らせている Chromium の VideoDecoder がデコードできるときだけ）。箱の読み方は同じ作り置きを単体試験でも読みます。

##### 録画の観る画面も canvas に描く

**観る画面 (`/watch/<id>`) は `<video>` を使わず、`/api/recordings/<id>/stream` を fetch で読んで同じエンジンへ流します**
（`canvas-player.ts`。リクエストの仕方は `<video>` でその場で流すとき (`remux-player.ts`) と同じ。[library.md](library.md#何で観るかはサーバが出せるものから画面が選ぶ)）。

```
/stream?codec=h264|av1&from= (fMP4。時刻はページの物差し) ─→ 箱で割る (Fmp4Splitter) ─┐
/stream?codec=mpeg2&from=    (元の TS。X-Denpa-Origin)  ─────────────────────────────┴→ RawEngine (worker・Web Audio)
```

- **どれで描くか** (`ts/playback.ts` の `pickCanvas`)。サーバから使えるのは流すもの (fMP4 と元の TS) だけで、ファイルそのまま
  (Matroska) は使わない (端末に保存したものは下)。自動はエンコード済みと同じ形式の詰め替え (サーバは軽い) → 変換 (H.264 → AV1) → MPEG-2 の順で、
  この端末で描けるもの。コーデックのメニューは「自動・H.264・AV1・MPEG-2」(録画が出せるものだけ。描けない形式は押せない)
- **時刻はページの物差し。** fMP4 はサーバが物差しのまま書いてくる。元の TS は放送の PTS なので、応答の
  `X-Denpa-Origin` (物差しの 0 にあたる PTS) を引いて一周の中で取る (`ts/seek.ts` の `sinceHead`)。字幕
  (`captions.json`)・チャプター (CM 飛ばし)・データ放送・続きの位置はこの位置で引く (40ms ごとの刻み。
  `<video>` の `timeupdate` と映した1枚ごとの追いかけの代わり)
- **決め方は追っかけと同じ `follow`** (`playout.ts`) — 止めたら位置を保ってそこから再開し、溜まっても今へは飛ばない。
  録画のために足したのは2つ:
  - **飛ぶ** (シークバー・← →・前/次のチャプター・CM 飛ばし・続きから)。持っているものを捨てて、飛び先からリクエストし直す。
    サーバは飛び先の少し手前 (鍵のコマ・1 秒前) から流すので、**手前のコマはデコードするだけで描かず** (worker の `floor`)、
    音も飛び先から鳴らす。描けるまでは前の映像のまま — CM を飛ばしたときも本編の最後のコマが残るので、
    `<video>` のような蓋 (`cover`) は要らない
  - **終わり** (`finish`)。尻まで読んだら、貯めが足りなくても残りを鳴らし、鳴らしきったら止まる (`ended`)
- **先へ読みすぎない。** 手元の音が fMP4 は 30 秒、元の TS は 10 秒 (1 秒 2MB ほどある) を超えたら読むのを待つ
  (fetch のストリームが詰まり、サーバも送るのを待つ)。デコーダを読み込み終えるまではバイト数 (8MB) で区切る。それでも
  溢れたら (worker が `full`) いまの位置からリクエストし直す
- **速さは等速だけ** (メニューを出さない)。切り抜き・小窓・バックグラウンド再生 (`<audio>` を通す) はライブと同じ仕組み
- 切れたら観ていた位置からリクエストし直す (`<video>` で流すときと同じ数)。混んでいて断られたら (503)、変換させずに
  描けるもの (詰め替え・MPEG-2) を勧める
- **描けなくなったらライブと同じ順で移る** — H.264 / AV1 を諦めたら MPEG-2 へ、MPEG-2 を諦めたら描ける H.264 / AV1 へ
  (断り書きに理由)。どれも無理なら理由を出して止まる。**`<video>` には戻らない**
- **端末に保存したもの (オフライン) も canvas に描く** (`mkv-source.ts` → `raw/mkv.ts`)。保存してあるのはエンコード済みの
  Matroska で、**fMP4 に組み直さず worker がそのまま読み**、読んだコマを fMP4 の経路 (`Fmp4Video`) へ渡す
  (`ts/mkv-media.ts` が Tracks の CodecPrivate — avcC / av1C / AudioSpecificConfig / OpusHead — とコマを読む)。
  - 飛ぶ位置は Matroska の **Cues** から引く (SeekHead が在りかを言う)。頭 (最初の Cluster まで) に飛び先の手前の
    Cluster からを繋いで、`Blob.stream` で流す。手前のコマは描かない (`floor`)。Cues が無ければ頭から
  - Matroska のコマは見せる時刻しか持たないので、デコードする順の時刻は先の 4 コマの見せる時刻のいちばん早いものにする
    (H.264 の B フレーム)
  - 音は選んだ 1 本 (音声のメニューはトラックの名前 → 言語 → 連番。`<video>` でコンテナから読むときと同じ)。選び直すと
    いまの位置から読み直す
  - 描けない形式 (この端末の VideoDecoder がデコードできない) か読めなければ、サーバから流すものへ。オフラインなら理由を出して止まる

E2E（`tests/e2e/40-watch-compat`）は、偽 ffmpeg が作り置きの fMP4 をリクエストされた位置から並べて出すもの (`fmp4-out.ts`) と、
偽の放送の MPEG-2 をそのまま描き、元の TS の位置が物差しに直っているかを見る。飛ぶ・CM 飛ばし・字幕・止めて再開は、
長い録画のふりをして (`playback` を差し替え、`stream` は作り置きをリクエストされた位置から並べる。`fmp4-clip.ts`) 見る。

### 5.6 データ放送の統合

**デコードする側も描く側も自前です。映像は denpa が持つ。**

2026-10 までは描く側を otya128/web-bml から借りていた。web-bml は Node.js サーバ + ブラウザ
クライアント構成で、サイドカーとして起動して iframe で抱えると**映像を出すプレイヤーが2つ**になる
(web-bml は自前の ffmpeg で HLS を作って自分の `<video>` に映すので、denpa の貯め方も字幕も
エンコード方式の切り替えもその画面では使われず、0.6秒 の映像に重ねることもできない)。そこで描画側
(`BMLBrowser`) だけを npm から引いて抱えていたが、映像の入れ物を BML の Shadow DOM の中へ移す・
`onclick` を本物の属性のまま DOM に入れる・ES の処理系ごと 700KB ある、といった癖への手当てが
重なったので、自前のエンジン (`src/lib/bml/`) に置き換えて外した。

web-bml のデコードする側 (`server/decode_ts.ts`) も一度は借りたが、998行のうち denpa が通るのは3割 (DSM-CC と PMT の記述子) で、
残りの EIT/SDT/NIT・字幕は自前のものがある (`ts/eit.ts` / `ts/psi.ts` / ffmpeg)。その3割のために
`@chinachu/aribts` (2.3MB) を抱えるより書き直すほうを選んだ。

運び方は衛星のロゴと同じ DSM-CC で、denpa は既に持っていた
(`ts/logo-dsmcc.ts`、DII を読んで DDB を揃える)。共通のところを `ts/dsmcc.ts` に
括り出し、データ放送の読み方だけを `ts/bml.ts` に足した。

渡す形式 (`ResponseMessage`) は web-bml の取り決めを写して `ts/bml-protocol.ts` に置いた。
録画の隣の `.bml.jsonl` がこの形式で残るので、**名前と意味は変えない** (足すのはよい)。
モジュールの中身 (multipart) を切るのも自前 (`ts/multipart.ts`):

| 型 | 中身 |
| --- | --- |
| `pmt` | データ放送の component (PID・componentId・BXML の情報) |
| `moduleListUpdated` | どのモジュールが何バイトか (DII) |
| `moduleDownloaded` | 揃ったモジュール。ファイルごとに base64 と MIME |
| `esEventUpdated` / `currentTime` | イベントメッセージ・NPT・放送の時刻 |

TS を直に読むので、psisiarc も要らない。

```
エージェント → denpa ┬→ ffmpeg     → fMP4 → MSE          (映像・音声)
                     ├→ ffmpeg     → mkv  → デコードする → canvas (字幕)
                     └→ BmlDecoder → 組み立て済みモジュール → 画面のエンジン (src/lib/bml/)
```

ffmpeg は1本のまま、チューナーも1つのまま、遅延も 0.6秒 のまま。

### いま入っているところ

**デコードする側 (`server/databroadcast.ts`) も描画側 (`components/player/DataBroadcast.svelte`)
も入っています。**

1局に絞った TS の写しを `BmlDecoder` へ分け (`Session.pump`)、出てきたものを
`CHANNEL.data` (0x30) に JSON で載せます。覚えておくぶんは `ts/carousel.ts`。

実機の録画 (1局に絞った 79MB = 約40秒ぶん) で測ったもの:

| | |
| --- | --- |
| 出てきた通知 | `moduleDownloaded` 16 / `currentTime` 13 / `moduleListUpdated` 3 / `pmt` 1 |
| 揃ったモジュール | 16個・約 1.4MB (application / image / text / audio) |
| 速さ | 128 MB/s。放送の 17 Mbit/s に対して**1コアの 1.7%** |
| 繋いできた人に配り直すぶん | 18個・2MB |

**借りていた `decodeTS` と突き合わせて、揃うモジュール16個・ファイル数・バイト数・
種別まで完全に一致しました。** 違うのは、出さないものが2つあることだけです
(下の「決めたこと」)。

**リクエストされてからデコードします。** デコードするのは 1.7% と安いのですが、見ている人のほとんどは
押さないので、全員のぶんをデコードし続ける理由がありません。画面から
`{ type: 'data', on: true }` が来たときだけ回し、誰も出していなければ畳みます。

引き換えに、押してから出るまでカルーセルが一周するのを待ちます。放送は同じ
ものを何度も回すので待てば揃いますが、大きいモジュールほど間隔が空きます。

決めたことが4つ:

- **`pcr` は出さない。** 毎秒50個ほど来るうえ、denpa では映像そのものが時計です
- **`programInfo` はデコードする側から出さない。** 借りていた側は EIT/SDT/NIT から
  組み立てていましたが、denpa は自前の番組表から作るほうが正確で安い
  (`Session.programInfo`)。描く側は局の番号をこれで知ります (`arib-dc://` の名前を解決する・
  NVRAM を局ごとに分ける)。
  中継の番号 (`transportStreamId`) だけは、絞るときに読む PAT の頭から拾います
  (`ServiceFilter`)。テレ朝の TVerリンクは `browser.getProgramID(4)` でこれを取り、
  TVer のサーバへ機器の識別子と並べて送ります。`null` のままだと文字の "null" が
  飛んで断られ、画面には「情報を取得することができませんでした。[エラーコード:DT-RE]」
  とだけ出ます (実機で再現。`DT` は dtoken_common、`RE` は返ってきた `e`)
- **`pmt` は変わったときだけ。** 放送は同じ表を何度も送ります。モジュールも
  同じ版は配り直しません (カルーセルは回り続け、版が上がらなくても同じものが何度も揃う)
- **デコードする側が転んでも映像は止めない。** データ放送は映像の付け足しなので、転んだら
  諦めて映像は流し続けます。投げ返すと TS を送り込んでいるところごと落ち、
  映像まで出なくなります (作りものの放送で実際に落ちました)

### 描く側 (`src/lib/bml/`)

**denpa が作る `ResponseMessage` をそのまま食べる。** Svelte から切り離してあり、画面の入れ物は
[DataBroadcast.svelte](../src/lib/components/player/DataBroadcast.svelte) が持つ:

```ts
const bml = createBml({ root, fonts, ip, store, receiver, clock, onVideoRect, onVisible, onReceiving, onLoad });
bml.feed(message);        // ← ts/bml.ts が吐くものをそのまま
bml.key(code, down);      // AribKeyCode (20 が d)
bml.listens('DataButtonPressed');
bml.destroy();
```

依存は持たない。

| | |
| --- | --- |
| 映像 | **動かさない。** object の場所を教えてもらい (`onVideoRect`)、映像の入れ物を style でそこへ寄せる (`placeVideo`)。字幕の canvas は入れ物の中なので一緒に縮む。映像より前に描くものの背景には穴を開ける |
| 文書 | 自前の寛容な XML パーサ → 16 の要素の木 → open な Shadow DOM の中の絶対配置の div。**innerHTML も属性の写しも無い** (字は textContent、見た目は確かめた値を `element.style` に書くだけ。CSP の `style-src` にも頼らない) |
| CSS | 自前で重ね合わせ (単純セレクタ・詳細度・継承・:focus/:active)、確かめた値だけ書く |
| スクリプト | 自前の VM (`vm.ts`)。eval を使わず、CSP の下でそのまま動く。sleep で止まる・launchDocument で打ち切る |
| 字 | TextDecoder (EUC-JP) と、追加記号は b24-tables。DRCS は 1 字を CSS の mask に |
| 内蔵音 | WebAudio で合成 |
| 束 | 押すまで落ちてこない (`import()` で分けてある。どのみちカルーセルの一周を待つので、そこに紛れる) |
| フォント | 丸ゴシックは字幕と同じ Denpa Font (danything/denpa-font)。BML が要る等幅・丸ゴシック・ARIB外字を1つで満たす。イメージにはリリースの woff2 を置き、`/api/font/denpa-font.woff2` で配る。角ゴシックは端末のもの |
| 覚えるもの | NVRAM は端末の localStorage。`denpa_bml_own_` で他と混ざらないようにしてある (web-bml の頃の `denpa_bml_denpa_nvram_…` は読まない。古い端末に残っていても害は無い) |
| 郵便番号・都道府県 | 設定画面から入れて、受信機の設定としてエンジンに渡す (`nvram://receiverinfo/zipcode`・`receiverinfo/prefecture`)。放送はこれで天気・地域のニュース・防災情報の場所を決め、郵便番号を入れないと「郵便番号が正しく設定されていません」と出る。都道府県の番号は ARIB STD-B10 付録G 表G-2 (県域指定) のビットの位置 (北海道は東西、東京都・鹿児島県は島部が別で 1〜50。東京都は 14 で、JIS の都道府県コードとは違う)、未設定は 255 (`src/lib/prefecture.ts`)。郵便番号から都道府県は引かない (表を抱えない)。家の場所は端末で変わらないので、置き場はサーバ。地域符号 (`receiverinfo/regioncode`) は持たず 0 を返す |
| リモコン | 十字・決定・戻る・数字・色・d をそのまま渡す (`aribKey`)。指で押すぶんは自前 (`components/player/Remote.svelte`: 色・十字・決定・戻る・d・数字) で、右の列に置く。放送の画面は枠を下まで塗り潰すので、映像に重ねると埋もれる |
| d ボタン | **テレビと同じ振る舞い。** 出す操作を文書への d の1押しとしても届け (`knock`。日テレ・テレ朝・フジの待機ページはこれでメニューを開く)、返事が無ければ 2.5秒おきに押し直す (TOKYO MX の入口は最初の2秒に受けた d を捨てる)。開いたメニューを閉じてしまう局があるので、押すのは3回まで。出ている間の d は、文書が聞いていれば渡し、聞いていなければ器を閉じる (`pressD`)。右の縦列の d ボタンは放送に渡さず、その場で畳む逃げ道 |

**描く場所は毎回作り直す。** エンジンは渡された要素に Shadow DOM (`attachShadow`) を張る。Shadow DOM は外せないので、
同じ要素を渡し直すと2度目で転び、消して出し直すと出なくなる。

**出すまでは透明にしておく** (`opacity`)。入口の文書はほぼ白紙のまま自分で `invisible` を外して
くるので、本体が揃う (データ取得中が下りる) まで映像のままにする。`visibility` では隠せない —
エンジンは描く要素ごとに BML の `visibility` を写すので、子の visible が親の hidden を打ち消す。

切り分けのために `data-showing` / `data-receiving` / `data-handed` を外へ出してある
(「押しても何も出ない」が、届いていないのか描かれないのかを外から見分けるため。ここに1日使った)。

**局を変えたら作り直す。** カルーセルも覚えるものも局ごとなので、前の局の文書を残さない。

**文字は EUC-JP の符号として扱う** (`charCodeAt`・`fromCharCode`・大小)。9 局 16 本の調査で、
TBS・テレ東が `String.fromCharCode(0xA1A1〜)` を、MX が `charCodeAt` を EUC の範囲と比べる書き方を
使っていた。数は整数 (割り算は切り捨て)、Date は日本の時刻。

**ページを握るのは 1 つの仕事で 5ms まで** ([budget.ts](../src/lib/bml/budget.ts))。スクリプト・描き直し・約束の続きは
全部この下で動かす。「仕事」はブラウザのタスク 1 つと、それに続くマイクロタスク全部 — マイクロタスクで
入り直しても区切りは始め直さない。区切りで手を放しても休みなく回り続ける文書 (10 秒のうち 4 割を超えて
動く) は止めて、ログに残す。2026-10-12 の本番で、モジュールに無い画像を指す object を描くたびに取りに
行き、すぐ「無い」と返って描き直す、がマイクロタスクで回り続けてタブごと固まった (区切りを
マイクロタスクで入り直すたびに始め直していたので効かなかった)。

`browser.*` は放送が呼ぶ 53 種を全部持ち、動かせないもの (AIT・Hybridcast の起動・予約・
PPP・外のアプリ) は規格どおり失敗 (NaN / null / 0) を返す。選局 (`epgTune`) は画面に任せる
(ライブは局の一覧から探して切り替え、録画は失敗を返して「録画の再生中は選局できません」と知らせる)。郵便番号と都道府県は NVRAM に書かず、
受信機の設定として渡す (`receiverinfo/zipcode`・`receiverinfo/prefecture`)。録画では再生位置から放送の時刻を出して渡す
(`clock`)。

まだ無いもの: NPT (PCR を送っていないので、時刻指定のイベントメッセージと NPT の TimerFired は
起きない)・通信コンテンツへの移動 (http の文書)。

### 5.7 双方向（通信系コンテンツ）プロキシ

放送局の通信系サーバは受信機の専用ネットワークスタックが前提で、CORS ヘッダを返さない。
そこで **SvelteKit サーバが中継する** (中身は
[server/bml-network.ts](../src/lib/server/bml-network.ts))。

| エンドポイント | BML の API | 何をする |
| --- | --- | --- |
| `/api/bml/proxy` | `browser.Ureg` 系の取得 (`get`) | GET して中身をそのまま返す |
| `/api/bml/post` | `transmitTextDataOverIP` | POST して返りをそのまま返す |
| `/api/bml/confirm` | `confirmIPNetwork` | 相手の 443 番へ繋がるか (ICMP はコンテナの中から撃てない) |

#### 「送る」は応募・投票のためだけの API ではない

最初は「正規受信機以外からの送信は想定外」として `transmitTextDataOverIP` を
渡さなかった。それでは足りなかった。

**放送のアプリは `isIPConnected` の申告を信じない。** NHK は送る API へ一度投げてみて、
返らなければ「インターネットに接続されていません」と案内する (実機で確認。
`confirmIPNetwork` は呼びに来もしない)。渡さないと描く側は「その機能は無い」と
答えるので、双方向を入れていても入っていないのと同じ画面になっていた。

**既定オフ。** 設定画面の「データ放送の双方向」を入れるまで、この API は 403 を返し、
画面側も `isIPConnected` に 0 を返す。そのとき放送のアプリが出す「インターネットに
接続されていません」は事実の通りで、消したければ入れる。web-bml 系の実装も同じ方針
（TVTDataBroadcastingWV2:「通信機能は既定では無効であり、その場合すべての外部への
リクエストはブロックされます」）。

#### 局ごとのドメイン表は持たない

「いま映している局のドメインだけ許す」には、局とドメインの対応表が要る。
**その表は必ず古くなり**、新しい局や引っ越した先で黙って繋がらなくなる。しかも
「繋がらない」は放送側の不調と見分けが付かない。

代わりに繋ぎ先ではなく繋ぐ範囲を縛る。危ないのは放送局以外に繋ぐことではなく、
**denpa のサーバが内側に繋ぐこと** (SSRF) だから。

| | |
| --- | --- |
| 手 | GET と POST。中身は組み立てない。描く側が `Denbun=…` まで作って渡してくるので、`application/x-www-form-urlencoded` として素通しし、返りもデコードせずに返す |
| 相手 | **公開アドレスのみ**。私設・ループバック・リンクローカル (雲のメタデータ)・CGNAT・多重放送は断る |
| 仕組み | http と https。`file:` などへ逃がす経路は塞ぐ |
| 見方 | 名前ではなく引いた先で見る。`localhost` の別名や、内側を指す公開の名前は綴りでは見分けられない。名前は `BML_DNS` で引く。家庭の DNS フィルタが局のドメインを 0.0.0.0 に落とすと、上の防御が正しく断ってしまう（[app.md](app.md#環境変数)） |
| 追いかけ | 3回まで。行き先ごとに確かめ直す (1回目が公開でも、飛ばされた先が内側のことがある) |
| 大きさ | 4MB / 待ち 10秒 |
| 持ち物 | 何も渡さない (cookie も認証も)。denpa の資格情報が外へ出ない |
| 記録 | 断ったものは何に繋ごうとしたかを残す |

#### 動作範囲の現実的な想定

| 種別 | 可否 |
| --- | --- |
| dボタン、ページ遷移、地域選択、クイズ選択肢 | ○ 受信機内で完結するため動作 |
| NVRAM への保存・読み出し | ○ 端末の localStorage (`src/lib/bml/nvram.ts`) |
| 通信系コンテンツの取得（HTTP GET） | ○ 中継 API 経由 (既定はオフ) |
| 応募・投票などのデータ送信（HTTP POST） | ○ 中継 API 経由 (既定はオフ)。繋がっているかの判定もここを通る |

### 5.8 Hybridcast

**在ることは言う。動かさない。**

データ放送 (BML) と違い、**アプリが電波に乗っていません**。
乗っているのは AIT という表だけで、中身は放送局のサーバから HTTPS で取ります。

```
PMT ─ ES に application_signalling_descriptor (0x6F) ─→ その PID に AIT
AIT ─ transport_protocol_descriptor        (URL の頭)
    └ simple_application_location_descriptor (その先の経路)  →  アプリのURL
```

「電波をデコードする」仕事はほとんど要りません
([ts/ait.ts](../src/lib/ts/ait.ts) は表を読むだけ)。**押されなくても読みます。**
デコードする量が無いうえ、押すまで在ることが分からないのでは出したいものが出せないためです。
載っていない局では PMT に印が無いので、AIT を待つこともしません。

見つけたら、操作列の下の段に**別のタブで開くボタン**を出します。d ボタン (右の縦列) と
同じ見せ方にはしません。あちらは denpa の中で開くもの、こちらは外へ出ていくもので、
押した結果がまるで違います。

#### 動かさないのは、越えられない壁が3つあるから

1. **受信機の API は、アプリのページの中に無いと意味がない。** Hybridcast の
   アプリは `hcApp` などの API を呼びます (放送の映像面の制御・いまの局と番組・
   受信機の記憶・スマホとの連携)。放送局のサーバから来るページは別オリジン
   なので、iframe に入れても中に手を入れられません。同一オリジンに見せるには
   URL を全書き換えして中継し、IPTVFJ STD-0010/0011 の API を実装する
   必要があります。仕様1つぶんの仕事です
2. **放送局のサーバが、認証された受信機を期待している。** 受信機の証明書や
   識別子を見るものが多く、素性を偽って通す気はありません
3. **映像は DRM 付き。** MPEG-DASH + Widevine/PlayReady で、ライセンスサーバが
   また端末を見ます

**2番は denpa 側の努力では越えられません。** なので1番に仕様1つぶんを注ぎ込む理由もありません。

#### できないものを、できる顔で出さない

データ放送のエンジンは `getBrowserSupport` の `AITControlledApp` 系に 0 (できない) と
答えます (`src/lib/bml/browser.ts`)。実機の NHK はこれを聞きに来て、その答えでデータ放送側の
「Hybridcast」ボタンを死なせています。**ここを 1 にしてはいけません。**
BML が起動を求めてきて、そのまま返らなくなります。

## 6. 技術選定の記録（採用しなかったもの）

### ブラウザ側での字幕デコード（aribb24.js）— 不採用

B24 をそのままブラウザへ送り、クライアントでデコードして描く構成。**デコード方法が受け側ごとに別実装になり、
置き場所や外字の置き換えが揃わない** (ブラウザとテレビのアプリで2つ)。いまはデコードするのをサーバ (libaribcaption を
写したもの) に寄せ、受け側は描くだけにしている (比較は [§2 の表](#字幕はサーバでデコードして描くのは受け側))。

### H.264 + MPEG-TS + mpegts.js で先に全機能を通す — 不採用

前例が豊富（KonomiTV / web-bml と同一構成）で、段階を踏む案として有力だった。
**字幕の経路が録画側で先に完成した**ので、あとで捨てるコードを書く理由が無くなった。
H.264 は段階ではなく、既定のコーデックとして残した (Safari や AV1 非対応の端末もそのまま観られる)。

### GStreamer — 不採用

当初は「tsdemux の private pad で B24 を映像と同一クロック上で取れる」ことを理由に有力視した。だが字幕は ffmpeg の
2つ目の出口で同じ時計に乗り（[§5.2](#52-字幕)）、データ放送は denpa の中で TS を分けて自前でデコードするので、
**この論拠は無くなった**。残る比較でも ffmpeg が優位 (字幕は `-c:s copy` で写すだけで済む)。
tsreadex / psisiarc / KonomiTV など周辺も同じ CLI パイプラインの構成で、QSVEncC / NVEncC / VCEEncC も使える。
GStreamer には ARIB/ISDB の知識も前例も無い。

### WebRTC / WHEP による低遅延化 — 不採用

設計では「低遅延の追い込み（任意）」として MediaMTX 経由の WHEP を候補に置いていたが、入れない。

**縮むのは待っている間だけで、開いてから映像が出るまではむしろ伸びる。** WHEP で消せるのは受け側の貯め
（`ts/pacing.ts`。宅内で 0.2〜0.9 秒）だけで、エンコードするのに掛かるぶんはエンコーダの中の話なので運び方では消えない
（[§5.1](#51-エンコード)）。代わりに開くたびに ICE と DTLS の往復が増え、テレビと同じに使うときにいちばん効く
「押してから映るまで」が遅くなる。

| | いま（WebSocket + MSE） | WHEP にすると |
| --- | --- | --- |
| 積むもの | Bun.serve の WebSocket 1本 | MediaMTX がもう1プロセス（+ SFU の設定・鍵・NAT） |
| 字幕・データ放送 | 同じ1本で一緒に送る（[§5.3](#53-websocket-プロトコル)） | 別建て（DataChannel を自分で組む） |
| 止めて見る・追っかけ・5分戻れる | MSE の `buffered` がそのまま | 全部書き直し（溜めが無いので追い越されて終わる） |
| 音声・エンコード方式の選び直し | 再エンコードして繋ぎ直すだけ | 交渉からやり直し |

「止めた所から見られる」「戻れる」は貯めているから成り立ち、低遅延はその貯めを削ることなので、両者は同じものの
両端にある。削れる幅も経路が決め、実測では 0.2 秒では止まり続け、落ち着いたのは 0.6 秒だった
（[一瞬止まって遅延が増えていく](#一瞬止まって遅延が増えていく)）。1秒足らずのためにその2つを捨てるのは割に合わない。
**本当に縮めたいなら、エンコードするのをやめるほうが桁違いに効く**（[§5.5](#55-放送そのままmpeg-2を送る)）。WHEP はその後でいい。
ffmpeg の WHIP muxer も H.264/Opus 固定の experimental で AV1 が使えず、通すなら MediaMTX 経由になる。

### MPEG-TS への AV1 多重 — 保留

AOM 公式仕様（AOMediaCodec/av1-mpeg2-ts、stream_type 0x06 + format_identifier `AV01`）はあるが、
FFmpeg は PR、GStreamer は WIP 段階で、ブラウザ側のデマクサも無い。継続監視する。

### Media over QUIC — 低遅延化の候補

字幕・データ放送を第一級のトラックとして扱える唯一の選択肢だが、IETF ドラフト段階。

## 7. 既知のリスク・未解決事項

| 項目 | 内容 | 対応 |
| --- | --- | --- |
| Safari の AV1 | Opus in mp4 / AV1 が MSE で通らない | 既定の H.264 + AAC で観る (AV1 は画質メニューで選ぶもの) |
| 字幕の拡大 | 画像なので、拡大すると文字も引き伸ばされる | `-canvas_size` は 1920x1080 で固定し、受け側が映像の枠に合わせて伸ばす（放送が 1440x1080 でも表示は 16:9 なので辻褄が合う） |
| データ放送のエンジンの実装範囲 | STD-B24 / TR-B14 / TR-B15 の部分実装 ([§5.6](#56-データ放送の統合) の「まだ無いもの」) | 実際のチャンネルで動作確認。完全互換は期待しない |
| 規約面 | 通信系サーバへの非受信機アクセス | 個人の視聴環境の範囲に留める |

リスクとして挙げていて解決済みになったものは、それぞれの節に実測ごと畳んである。
AV1 の負荷は [§5.1](#51-エンコード)、字幕をエンコードする費用は [§5.2](#52-字幕)、
字幕と映像のズレは [§5.4](#54-時刻同期)。
