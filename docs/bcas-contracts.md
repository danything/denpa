# B-CAS 有料契約の確認と期限切れ通知

更新: 2026-11-07

関連: danything/denpa#2221 / PR #2231、Antigravity 引継書
(`b664cd3a-7fb6-4bb2-b304-db32cf5243f6/handoff.md`)

この文書は、いま実装されている契約確認の仕様と、Antigravity で話していた
「7 日後の期限切れ通知」の現状、および今後の複数 PR 方針をまとめたもの。

## 1. 結論

- 現在の契約確認は、**番組表 (EIT の CA契約情報記述子 0xCB) を B-CAS カードに
  問い合わせる方式**が主。一般のテレビが番組表で契約を判定するのと基本的に同じ。
- ただし 0xCB を流さない局が**実測で存在する** (CS02/04/06 の全局、BS の一部など)。
  そのため **実ストリームの復号テスト**をフォールバックにしている。
  全方式ではなく、局によって使う手段が違う。
- 一方で、DB に 0xCB が無いからといって「放送していない」とは限らない。
  機能を入れる前に取り込んだ番組行は NULL のままなので、生の EIT と DB を分けて見る。
- 「7 日後に切れることを夜に通知する」処理は、**7 日後をカードに問い合わせる部分は
  実装済み**。ただし **7 日前に通知する処理は未実装**で、いまは期限切れになった瞬間だけ
  通知する。
- 7 日後の電波を実際に復号することはできない。できるのは「7 日後の日付をカードに
  聞いて、その日に有効か」を確かめること。

| 第 2 弾 | 予約・番組表の「期限切れ」バッジ、自動録画で契約中の局を優先                                | 実装済み (feature 枝) |

## 3. 現在の仕様

### 3.1 契約確認の流れ

1. EPG 収集時に、有料番組の EIT から `contract_verification` (0xCB の
   `contract_verification_info`) を `programs` に保存する。
2. `checkContracts()` が局ごとに最新の有料番組の `contract_verification` を拾う。
3. あれば B-CAS カードへ `0x90 0x3C` を送り、今日 (MJD) と 7 日後の日付で
   返り値コードを聞く。
4. 返り値コードから契約状態を決める。
   - 今日有効で 7 日後も有効: `subscribed`
   - 今日有効で 7 日以内に切れる: `subscribed` のまま `valid_until` を記録
   - 今日無効で 30 日以内に切れた: `expired`
   - それ以外: `unsubscribed`
5. 0xCB が無い局は、31 日以内に復号テストが成功していれば `subscribed`、
   そうでなければ `unsubscribed`。

**重要:** 現在の「カードのみで判定」という説明は不正確。実際は
「番組表の 0xCB + カードへの 0x90 0x3C」で判定している。0xCB が無い局だけ
復号テストに落ちる。

### 3.2 復号テスト

- 実際にチューナーを開き、TS パケットのスクランブル制御ビットを見る。
- スクランブルが外れていれば `decode_ok = true`。
- 無料番組中はスクランブルが掛からず契約と取り違えるため、対象外。
- 結果は 31 日間だけ契約中の根拠にする (`DECODE_VALID_MS`)。
- 1 局ずつのテストに加え、同じ物理チャンネルの局を 1 回の選局でまとめて
  確かめる「未確認をまとめて復号テスト」がある。
- 復号テストは「いま放送中の番組」しか見られない。7 日後の契約は分からない。

### 3.3 期限切れの記録

- `card_contracts.valid_until` に期限日時 (epoch ms) を入れる。
- 7 日以内に切れる場合も、まだ観られるので `state` は `subscribed` のまま。
- 期限を過ぎてカードが無効と答えたときに `expired` になる。
- `expired` は予約・番組表で「期限切れ」バッジを出し、自動録画の対象から外す。

### 3.4 定期スキャンと Webhook

- `scheduler.tick()` が `CONTRACT_SCAN_INTERVAL` ごとに `scanContracts()` を呼ぶ。
- 既定は **12 時間**。深夜 1 回ではない。
- 前回の状態と比べ、**新たに `expired` になった局だけ**
  `contract.expired` Webhook を送る。
- したがって、7 日前の予告通知は出ない。期限切れ後の通知だけ。

## 4. 「夜に 7 日後を確かめて通知する」の答え

### できること

- 7 日後の日付をカードに聞き、その日に有効かを判定できる。
  これは 0xCB がある局で実装済み (`checkContracts` の `valid(7)`)。
- `valid_until` が 7 日以内なら、その情報を使って 7 日前に通知できる。
  必要なのは通知処理と重複防止だけで、カードへの問い合わせは既にある。

### できないこと

- 7 日後の電波・ECM を今復号することはできない。未来の暗号鍵はまだ届いていない。
- 0xCB が無い CS 局は、7 日後の契約をカードに聞けない。復号テストも
  「いま」しか分からない。
- 無料お試し期間中は、いま復号できても正規契約とは限らない。
  7 日後の日付をカードに聞ける局 (0xCB あり) でしか見抜けない。

### 未実装の部分

1. `valid_until` が 7 日以内の `subscribed` を検出する。
2. `contract.expiring` (仮) を 1 期限につき 1 回だけ通知する。
3. 通知済みを DB に残す。再起動や 12 時間ごとのスキャンで繰り返さない。
4. 深夜に実行する。いまは 12 時間間隔で、時刻の指定がない。

## 5. 契約確認の他の方式

| 方式                 | 何を見るか                                   | 長所                                     | 短所                                         | 状態                           |
| -------------------- | -------------------------------------------- | ---------------------------------------- | -------------------------------------------- | ------------------------------ |
| EIT 0xCB + 0x90 0x3C | 番組表の契約確認情報とカード                 | 選局不要、日付指定で正確、7 日後も分かる | 0xCB を流さない局がある                      | 実装済み。主方式               |
| 復号テスト           | いまの TS のスクランブル                     | 0xCB が無くても判定できる                | チューナーを使う、現在のみ、無料お試しに弱い | 実装済み。フォールバック       |
| ECM 直接確認         | PMT の ECM をカード (0x90 0x34) に渡した結果 | 復号テストより速い、選局は必要           | 現在のみ、無料お試しに弱い                   | 未実装。エージェントに材料あり |
| EIT 0xCB の収集拡大  | p/f 以外の EIT、複数イベント                 | 既存の仕組みだけで対応局を増やせる       | そもそも 0xCB が無い局には効かない           | 一部実装。改善余地あり         |
| EMM 監視             | カード向けの更新メッセージ                   | 契約更新を検知できる                     | 契約の有無を判定する材料ではない             | 実装済み。判定とは別           |
| 手動設定             | 利用者が「契約中」「対象外」を指定           | 自動判定できない局を救える               | 自動ではない、設定の手間                     | 未実装                         |

補足:

- 「普通のテレビは番組表で判定している」という理解は、0xCB を使う限り正しい。
  現在の実装もそこを通っている。差があるのは、0xCB が無い局の扱い。
- PMT の CA 記述子 (0x09) は「スクランブルされている」ことは分かるが、
  「このカードで観られる」ことは分からない。契約判定には使えない。
- B-CAS の標準コマンドに「契約している局の一覧」を返すものは確認できていない。
  0x3C は局ごとの verificationData が必要で、0x34 は ECM が必要。
- EMM はカードを更新するためのもので、契約状態を読み出すものではない。

### 5.1 0xCB が無い局は実在するか

2026-11-07 に kuni1 で、denpa と同じ `EpgReader` を使い、生の EIT を
直接数えた。結果は次のとおり。

| 物理チャンネル | 局                | EIT のイベント数 | 0xCB あり |
| -------------- | ----------------- | ---------------: | --------: |
| BS05:17488     | WOWOW ライブ      |              117 |        97 |
| BS03:17969     | BS アニマックス   |              236 |         0 |
| BS15:16626     | BS10 プレミアム   |              201 |         0 |
| BS21:18256     | WOWOW プラス      |              252 |         0 |
| BS23:18288     | ディズニー ch     |              256 |         0 |
| CS02:24608     | 4 局              |              423 |         0 |
| CS04:28736     | 4 局              |              125 |         0 |
| CS06:28768     | 8 局              |              875 |         0 |
| CS10:24736     | スカチャン 1      |               65 |        65 |
| CS10:24736     | 衛星劇場ほか 4 局 |              251 |         0 |

分かったこと:

- **0xCB を流さない局は実在する。** 同じ物理チャンネル (CS10) の中で
  スカチャン 1 だけが 0xCB を出し、同居する局は出していない。
  これは「読み取り漏れ」ではなく、局ごとの違い。
- **DB の 0 件は、読み取り漏れのことがある。** WOWOW ライブは生の EIT に
  0xCB があるのに、DB は 0 件だった。番組行の最終更新が機能追加の前
  (約 6 時間前) で、EPG の再取得がまだ回っていなかったため。
- したがって、調査では「DB に無い」と「生の EIT に無い」を必ず分ける。
  生の EIT に無い局だけを、復号テストや手動設定の対象にする。

この計測に使った一時スクリプトはリポジトリに入れていない。

### 5.2 事業者単位で表示する場合

「WOWOW、スターチャンネル、ジャパネット、スカパー」のような事業者単位で
契約期限を出せば、すべての局の 0xCB を見なくても済む可能性はある。
ただし、実測では同じ事業者の中でも 0xCB の有無が混在している。

| 事業者           | 0xCB を確認した局              | 0xCB が無かった局                |
| ---------------- | ------------------------------ | -------------------------------- |
| WOWOW            | プライム、ライブ、シネマ       | プラス (12 秒の範囲で 0 件)      |
| スターチャンネル | 今回は確認できず               | BS10、BS10 プレミアム            |
| スカパー         | スカチャン 1                   | CS02/04/06 の全局、CS10 の同居局 |
| ジャパネット     | 今回のスキャンに局が無く未確認 | 未確認                           |

この結果から言えること:

- 事業者ごとに 1 局だけ見る方式は、**その 1 局が事業者共通の契約単位を
  代表している場合だけ**成り立つ。WOWOW プラスや BS10 のように、
  同じ事業者でも 0xCB を出さない局があるため、代表局方式はまだ未検証。
- すべての局で 0xCB を観測する必要はない。ただし、**契約単位ごとに
  1 局は必要**。事業者と契約単位が同じとは限らない。
- 表示するなら、事業者ごとに次の 3 つを分けるのが安全。
  - 代表局の 0xCB で期限まで確認できた
  - 復号テストで今だけ確認できた
  - 未確認 (未来の期限は分からない)
- 代表局で確認した期限を事業者全体に広げる場合は、「代表局で確認」と
  明記し、確認していない局まで「契約中」と断定しない。
- Kw の変更は契約期限とは別。EMM の受信でカードの鍵は更新できるが、
  「7 日後に契約が切れるか」を Kw から直接読むことはできない。

次の調査は、事業者ごとに「契約単位を代表する局が 0xCB を出しているか」を
1 回だけ確かめる。全局を回る必要はない。

## 6. 複数 PR の方針

レビュー負荷を下げるため、次の順で分ける。

### PR A: 状態モデルの整理と「未確認」表示

- `card_contracts.state` に `unknown` を足すか、`confirmed` フラグを追加する。
  いまの `unsubscribed` は「契約が無い」と「まだ確かめていない」を兼ねている。
- 0xCB が無く、復号も未実施の局を「未確認」と表示する。
- `source` (`eit_ca` / `decode` / `manual`) を持たせ、判定根拠を残す。
- 既存 DB の移行を含む。UI の文言も「未契約」と「未確認」を分ける。

### PR B: 7 日前通知と深夜スキャン

- `subscribed` かつ `valid_until` が 7 日以内の局を検出する。
- `contract.expiring` を追加し、Discord などへ「7 日後に期限切れ」を送る。
- `card_contracts` か別表に通知済みの期限を記録し、同じ期限で繰り返さない。
- 深夜 (例: 03:00 JST) に 1 日 1 回実行する。カードへの 0x3C は選局しないので、
  チューナーを塞がない。
- 0xCB が無い局は 7 日前通知の対象外とし、「未確認」または
  「復号テストの再確認が必要」として別に扱う。

### PR C: 契約確認方式の抽象化と拡張

- `ContractChecker` のような形で、EIT 0xCB、復号テスト、ECM 確認、
  手動設定を同じ結果にまとめる。
- EIT の 0xCB 収集範囲を広げ、局ごとに「使える方式」を記録する。
- エージェントの ECM 応答コードを API に出し、復号テストの短縮版を作る。
- 判定の優先順位を決める。例: カードの 0x3C > ECM/復号 > 手動 > 未確認。
- 7 日後を聞けない局は、この PR では「未確認」のままにする。

### PR D: 手動設定と除外

- 自動判定できない局に「契約中」「対象外」「未確認」を設定できるようにする。
- 設定した局は自動判定で上書きしない。
- 録画ルールとの関係 (契約中とみなすか) を明確にする。

### 別 PR: EMM 自動更新

- すでに feature 枝にある EMM 受信・`0x90 0x36` 更新は、契約判定とは別の PR にする。
- 上流 main には入れず、必要なら単独で提案する。

## 7. 受け入れ条件の案

- 0xCB がある局: 7 日後に切れるとき、期限切れ前に 1 回だけ通知される。
- 同じ期限で再起動・再スキャンしても二重通知しない。
- 0xCB が無い局: 「未確認」と表示され、誤って「未契約」と表示されない。
- 復号テスト成功から 31 日を過ぎた局は、契約中として自動録画しない。
- 期限切れになった局は、予約・番組表で「期限切れ」と表示される。
- 既存の契約確認、一括復号テスト、EMM が壊れない。

## 8. 決めること

1. 7 日前通知の event 名を `contract.expiring` にするか。
2. 通知を 7 日前の 1 回だけにするか、3 日前・前日にも出すか。
3. 深夜実行の時刻を固定するか、`CONTRACT_SCAN_INTERVAL` の延長で済ませるか。
4. `state` に `unknown` を足すか、`confirmed` を別に持つか。
5. 0xCB が無い局を、手動設定できるようにするか。
