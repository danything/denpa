# チューナーエージェント

**電波を掴むところ。機材に触るのはここだけです。** **なぜこの形なのか**と、
`bun` から `.NET` に落ち着くまでに測ったことを置いてあります。

| 探しもの | 見る場所 |
| --- | --- |
| 全体像 | [architecture.md](architecture.md) |
| 番組表・スキャン・持ち物 | [data.md](data.md) |
| ファイル・環境変数・画面 | [app.md](app.md) |

denpa から触れないものが3つあり、どれもチューナーを持つコンテナでしか出来ません。

- **チューナーデバイス** — `/dev/dvb/*` と `/dev/bus/usb` が見えているのはあちらだけ
- **B-CASカード** — USB のリーダーも px4d の内蔵リーダーも、あちらが直に叩きます
  ([下記](#b25-の解除もカードリーダーも自前))
- **選局そのもの** — DVB はデバイスを ioctl で直接掴みます
  ([下記](#net-で書き直すまで-経緯と実測))。PX-Q3U4 などは同梱の px4-userland、
  PX-S1UD は (カーネルが掴んでいなければ) 同梱の siano-userland に USB を叩かせます
  ([下記](#px-q3u4-などは-px4-userland-でカーネルドライバは入れてもらわない))

持っている仕事は3つ。

- **選局して TS を流す**
- **優先度つきの取り合い** (誰が何本掴んでいるか。低いものを切って高いものを通す)
- **どのチャンネルが使えるかの控え** (スキャンの結果を預かって配る。**中身は作らない**)

**TS は1バイトも解釈しません。** NIT も SDT も EIT も解かないので、
`src/lib/ts` に依存していません。総当たりのスキャンでさえ、やることは
「言われた物理チャンネルを順に開いて流す」だけです。

## なぜ denpa が全部持つのか

**局も番組表も時刻も、覚えているのは denpa だけ**です。同じものを2箇所が持つと
「あちらがまだ知らない局は、こちらからは増やせない」という縛りが必ず出ます。

持っているぶん、こちらで決められます。

- **番組表は、チューナーが空いているだけ並列に集める。** 急がせたいときに
  何かを再起動する必要が無い ([data.md](data.md#番組表の集め方))
- **録画中でもスキャンできる。** 止まるものが1つも無い
- **優先度は素直な数のまま。** 下限も、特別扱いされる値も無い ([下記](#取り合いの決まり))

## 取り合いの決まり

優先度は**大きいほうが勝ち**、下限がありません。番号は denpa が決めます
(`config.priority`)。

| | 値 | |
| --- | --- | --- |
| 録画 | 10 | 放送は二度と来ないので、ここだけは譲らせない |
| ライブ視聴 | 9 | 画面の前で人が待っている。録画にだけ譲る ([stream.md](stream.md)) |
| 番組表 (今すぐ) | 8 | 人が押して待っている番組表集め。**録画以外からは全部取り上げる** |
| チャンネルスキャン | 5 | 人が押して待っている。番組表には譲らせるが、録画中のチューナーは使わない |
| 番組表 | 3 | |
| 局ロゴ | 1 | ロゴが出なくても番組表は読めるが、逆は成り立たない |

探す順番は4段。

1. **同じチャンネルに相乗り** — 番組表・ロゴ・録画が同じ物理チャンネルなら、選局は1本で足ります
2. **畳むのを待っているだけの本** — 誰も読んでいないのに余韻 (5秒) で残っている選局。
   **1人の視聴で2本塞がないため**に、空いている本より先に使い回します
3. 空いているチューナー
4. 自分より弱い相手から取り上げる

**2段目は取引です。** 別のアダプタへ移っていた頃は直前のチャンネルへ戻るのが
4ms で済みましたが (前のアダプタが余韻の間そのまま残るため)、いまは戻りも選局し直し
(実測 802ms)。**切り替えそのものは速くも遅くもなりません** — どちらの道でも同じだけ
電波の同期を待つためです。

2段目は取りこぼすことがあります。切った直後に次を頼むと、こちらが切断に気付く前に
要求が届いて `Sinks` がまだ 0 でないためです。**そのときは3段目に落ちるだけ**なので、
映らなくなることはありません。

## 相乗りの決まり

**チューナーは数本しかありません。** 電波から読みたいもの (番組表・局ロゴ・録画・
視聴) は、どれも「その物理チャンネルを開く」ところは同じなので、**同じチャンネルなら
1本で足ります。** 乗れるものは全部乗せます。

エージェント側は1回の選局 (`Lease`) に読み手 (`Sink`) を何人でもぶら下げます。
**B25 の復号は選局につき1回**で、そこから先を人数ぶん配るだけです
(MULTI2 は TS 全部に掛かるので、読み手ごとに解くと台無しになります)。

| 誰が | 強さ | 乗り方 | 上限 |
| --- | --- | --- | --- |
| **録画** | 10 | 必ず自分で開く。**乗せる側** | 番組の終わりまで |
| **番組表** | 3 (押されている間は 8) | 開く。同じチャンネルが開いていれば只 | 1チャンネル10分 |
| **局ロゴ (PNG)** | 1 | **開いている選局にだけ**乗る (`logo.ride`) | 3分 |
| 〃 (自分から取りに行くとき) | 1 | 開く | 地上波6分 / 衛星20分 |
| **チャンネルスキャン** | 5 | 開く (総当たりなので乗れない) | 1チャンネル30秒 |

CM検出用のロゴ (`.lgd`) はチューナーを掴みません — 録れたものから覚えます
([logo.md](logo.md#cm検出用のロゴは録ったものから覚える))。

**いちばん効くのは録画です。** 録画は物理チャンネルを丸ごと開いているので、
そこに流れている EIT も只で読めます。**同じ流れから読んで5分ごとに書き出し**、
番組表集めはそのチャンネルへ**6時間行きません** (実機で、録画中の T19 と T21 は
番組表の更新が常に1分以内でした)。

**ロゴは録画の流れからは拾いません。** 衛星のカルーセルは数百KBあり、録画の
一本道に混ぜたくないためです。代わりに `tuners` の知らせを合図に**同じチャンネルを
別に開いて**乗ります。チューナーは増えず、増えるのは **TS がもう一度 HTTP を渡る**
ことだけで、足りないのはチューナーのほうなので、この取引で正しい。

**番組表は「開いているものを先に」しません。** あちらは**薄い局から先に**行く
のがもっと大事で (入れた直後は全部空)、順番の理由が2つあるとどちらも中途半端に
なります。同じチャンネルが開いていれば結局は只で乗るので、損はしていません。

## 選局は、読み手が切るまで終わらない

**向こうから終わったなら、それは失敗です。** チューナーを取り上げられた・子プロセス
(px4-ts / siano-ts) が落ちた・デバイスが黙った、のいずれかであって、「録り終えた」
ではありません。

エージェントは取り上げた相手のストリームを**接続ごと壊して**畳みます (`http.Abort()`)。
きれいに閉じると、受け取る側には正常終了として届くためです (bun 版はこれが出来ず、
取り上げられた録画が尻切れのまま「録れた」ことになっていました)。

**壊すのは、送り始めたあとだけです。** 1バイトも送らないうちに落ちたなら状態行も
まだなので、**理由を付けて 500 で返します**。どの落ち方も接続を壊していた頃は、
記録に `socket connection was closed unexpectedly` しか残らず、**電波なのか掴み損ねなのか
設定なのかが分かりませんでした**。

**それでも約束は理由ではなく「終わったという事実」に置きます。** 届く保証があるのは
*終わったこと*だけです (電源やネットワークで切れることもある)。読む側 (denpa) は
EOF も例外も録り終えたと読まず、**どちらも同じように掴み直して**終了時刻まで録り続けます
(`recorder.ts`)。この形なら、エージェントを何語で書いても成り立ちます。

### 環が溢れても畳まない

`read` が `EOVERFLOW` を返すのは「読むのが追いつかず、ドライバが捨てた」であって
終わりではなく、読み続ければ続きが来ます。これを終わりとして扱っていた頃は、番組表を
4本まとめて開いた直後に1〜2本が落ちていました。

**溢れるのは dvr の環です。** 全PIDを `DMX_OUT_TS_TAP` で流すので、中身は demux の
フィルタではなく dvr の環に積まれます。`DMX_SET_BUFFER_SIZE` を demux にだけ言っていた
頃は、実際に使われていたのはカーネルの既定 (≒1.8MB、地上波で **0.9 秒ぶん**) でした。
いまは dvr にも 8MB を言っています (3.5 秒ぶん。4本でも 32MB)。**断られても選局は
続けます** — 広げられないことは、選局を落とす理由にはなりません。

**溢れの多くは、局を変えている間に積もったぶんでした。** デバイスは選局を跨いで開き
っぱなしなので、局を変えている間は誰も読まず、読み始めた最初の1回が必ず溢れとして
返ります (実機の 24時間 249〜302 回は、ほとんどがこれ)。いまは読み始めるところで
測り直し (`DeviceStream.Begin`)、選局の前に埋まっていたぶんは数に入れず
「選局前に環が N 回溢れていました」と別に書きます。測り直した結果は **50分で1回・
空いた時間 0.0秒**でした。

溢れたときは**読み手がどれだけ空いていたか**も出します。環は 3.5 秒ぶんなので、

| 空いた時間 | 読み |
| --- | --- |
| **1秒あたりで頭打ち** | 広げたはずの溜めが効いていない (既定の 1.8MB のまま) |
| **3.5秒を超える** | 溜めではなく**読み手が止まる理由**が本題。疑わしいのは GC・CPU の取り合い。B25 の復号は読み手と別のスレッドで、間の 64MB のキューが埋まったときだけ読み手を待たせる (そのときは「キューが埋まった」と出る) |

**溢れた記録には「その間に居た読み手」を名乗らせます** (次の節の用途名)。報告は1分に
1回なので、報告した瞬間の読み手だけを見ると、**溢れた本人が抜けたあとに報告が回って
「読み手なし」になり**ます (実機の24時間で 302回のうち 128回)。

### 前の読み手が降りるまで、次の選局を始めない

デバイスはチューナー1本につき1つで、選局を跨いで開きっぱなしです。前の読み手が
まだ回っているうちに次を始めると、**同じ読み口を2本で取り合い**、前の局のパケットが
次の選局に混ざります。(復号器を選局を跨いで持ち回していた頃は、それで実機が
`double free or corruption (out)` で落ちました。いまは復号器を選局ごとに作るので、
その道は無くなっています。)

- **読み手のほうから降りる道を持たせます** (`DeviceStream.Read`)。無いと、電波が
  来ていない間 `read` は 0.2秒ごとに起きて掛け直すだけで永久に戻らず、取り上げられた
  読み手が居座ります。待つのは取り合いの錠を放してから (握ったまま待つと、その間
  どの本も開けません)
- **解けなくなった復号器は作り直します。** 途中で投げたものは中の解析が半端なまま
  なので、`reset` して使い回すと壊れたまま次の選局へ持っていきます (落ちたのは ECM の
  解析に失敗した直後でした)。デバイスは掴んだまま (掴み直すと `Device or resource busy`)
- **誰も読まなくなってから5秒は掴んだままにします。** 連続した番組を録るときに、
  閉じきっていないデバイスへ開きに行って弾かれないように
- **偽の選局 (`FAKE_TUNE`、適合テスト用) はプロセスグループごと終わらせます。**
  `sh -c` 越しに起こすので、中身が生き残って次の選局とぶつからないように

## 設定は2つのファイルに分ける

PVC に置きます (`/app-config`)。**どちらも無くて構いません** (機材は自分で見つけ、
チャンネルはスキャンするまで空)。

| ファイル | 中身 |
| --- | --- |
| `tuners.json` | 繋いである機材。**denpa の画面から書き換えます** (`PUT /denpa/tuners`) |
| `channels.json` | スキャンで見つかったチャンネルと局 (`PUT /denpa/channels`) |

**どちらも denpa が書き、どちらも JSON です。** 人が手で書く前提が消えたので、
コメントを守るためのテキスト操作や自前の YAML 読みを持つ理由が無くなりました
(丸ごと書き直せるほうが壊れにくい)。

**分けてあるのは、片方を書き換えるときにもう片方を巻き添えにしないため**です。
同居させると、スキャンのたびに機材の定義が飛ぶ危険が出ます。

## 選局コマンドは画面から渡させない

設定に持つのは**デバイスと種別と LNB** だけで、選局の仕方はエージェントが決めます。
自由な文字列を画面から受け取れるようにすると、**denpa に入れた人がチューナー側で
好きなコマンドを走らせられる**ことになります (しかもあちらは `privileged`)。
`command` の欄は外しました — `tuners.json` に残っていても読まずに捨て、次に画面から
保存すると消えます。外のコマンドを起こすのは適合テストの `FAKE_TUNE` (環境変数) だけです。

**チューナーは書かなくても動きます** (`DeviceProbe.Detect`)。定義が無ければ刺さって
いるものを自分で見つけ、地上波か衛星かまで判別します。

| 機材 | 聞き方 |
| --- | --- |
| DVB | `/dev/dvb/*` を開いて `DTV_ENUM_DELSYS` で受けられる方式を聞く (実機の PT3 で adapter0/2 が ISDB-S、adapter1/3 が ISDB-T)。sysfs にはこれを答える口が無い |
| px4-userland | `px4d --list` ([下記](#px-q3u4-などは-px4-userland-でカーネルドライバは入れてもらわない)) |
| siano-userland | `siano-ts --list` ([下記](#px-s1ud-はカーネルが掴んでいなければ-siano-userland-で)) |

書いてあればそちらが勝ちます (LNB・1本だけ止める、は人にしか決められない)。

**チューナーを開くときは用途を名乗ります** (`use`)。何も渡さないと、誰が居座って
いるのか画面から読めません。`rec 12` `logo GR/T16` `epg BS15_0` `scan T21` と短く渡し、
読める言葉に直すのはチューナー画面のほうです (番組名は DB から引き直します)。

## .NET で書き直すまで (経緯と実測)

**エージェントは .NET です** (`agent/`)。Native AOT で実行ファイル1個、依存はありません。
実機で録れて落ち着いたので bun 版は消しました。実装が2つあった頃に書いた適合テスト
(`agent/conformance.test.ts`) はそのまま残してあり、いまも本物を起こして HTTP の口に
当てています。

**`recisdb` も外しました。** 選局のたびに `recisdb` を起こすのをやめ、自分でデバイスを
掴んで解きます (`Tuning.cs` / `ChannelTable.cs` / `B25.cs`)。

**実機で1本録りました。** denpa と同じ道 (HTTP で選局して読む) で 60 秒、地上波 T27。

| 見たところ | |
| --- | --- |
| 大きさ | 139.4 MB (18.6 Mbps) |
| パケット | 741375 |
| 同期でないもの | **0** |
| 掛かったまま | **27 (0.004%)** — 最初の ECM で鍵が決まるまでの分 |
| 連続性の抜け | **2** (NULL を除く。選局した直後のもの) |
| PID | 0x0100 映像 / 0x0110 音声 / PAT 645・NIT 64・SDT 32・EIT 2792・TOT 13 |

denpa 自身の目 (`src/lib/ts`) でも、局名・リモコン番号・17 秒ぶんの番組 531 件が
ARIB の文字ごと読めています。

**カードが開けなくても選局は続きます。** カードを読めなかった試しでも
止まらずに掛かったまま録れ、チューナー画面に理由が出ました。
電波は二度と戻ってこないので、掛かったままでも録っておくほうがましです。

このとき実際の放送で1つ見つかりました。**EIT[p/f] の `running_status` が全部 0
(未定義) の局がある**ので、延長追従が効いていませんでした (偽の TS は 4 を入れて
作っていたので踏めなかった)。0 のときは**節の番号で決めます** — p/f は仕様で
section 0 が現在・section 1 が次 (`src/lib/ts/eit.ts`)。

### 掴んだままチャンネルを変える

PT3 はカーネルの `earth_pt3` が**標準の Linux DVB (v5)** として出していて
(`/dev/dvb/adapterN/{frontend0,demux0,dvr0}`)、**開いたまま `FE_SET_PROPERTY` で
選局し直せます**。1回1チャンネルの使い捨てだった `recisdb` をやめて開けっ放しにすると、

1. **掴み手が入れ替わる隙間が無くなる。** 「前のが終わってから次が開く」まで
   デバイスが宙に浮くことも、`recisdb` が読み手の居なくなったあと生き残って
   チューナーを 5 分掴んだままになる事故 (実測中にも起きた) も無くなります
2. **1回の選局を何人でも読める** ([相乗りの決まり](#相乗りの決まり))
3. プロセスの立ち上げとデバイスを開く時間が消える

**同期そのものは短くなりません。** 実測 (PT3、`denpa-agent --tune /dev/dvb/adapter0/frontend0 BS15_0,BS15_1,BS01_0,BS15_0`):

| 選局 | 同期 | 最初の1バイト | 同期バイト |
| --- | --- | --- | --- |
| BS15_0 (最初) | 229 ms | 108 ms | 100% |
| BS15_1 (**同じ周波数**) | 187 ms | 186 ms | 100% |
| BS01_0 (周波数を跨ぐ) | 198 ms | 139 ms | 100% |
| BS15_0 (戻る) | 188 ms | 104 ms | 100% |
| T27 / T21 (地上波) | 366–377 ms | 142 ms | 100% |

**「同じ中継の中なら只」は成り立ちませんでした。** `tc90522` は TSID を書き換えても
選局の手順を丸ごとやり直すので、同じ周波数でも跨いでも差がありません。

既製の常駐 (tvheadend など) に乗せる手もありますが、あちらは番組表も録画も
持っているので、**同じものを2箇所が持つ形に戻るだけ**です。欲しいのは
「開いたまま選局して、TSを配る」薄い層だけです。

#### 選局表

チャンネル名から周波数を出す表です (`ChannelTable.cs`)。**数字は `recisdb` から
取りました** — 導き直すより、実機で選局できていたものと同じ数字にするほうが大事です。

- 地上波 … `473142857 + (ch-13) × 6 MHz` **Hz で**
- BS … `1049480 + 38360 × n` **kHz で** (中継は 38.36 MHz 刻み)
- CS … `1613000 + 40000 × n` **kHz で** (40 MHz 刻み)

単位が2つあるのは DVB API の決まりです (地上波は Hz、衛星は kHz)。取り違えても
ioctl は通り、**ただ同期しない**ので気付きにくいところです。

衛星でもう1つ要るのが **TSID** です。denpa が言ってくるのは `BS15_0` のような
**相対番号**なので、ここで直します。引く先は2つ。

1. **自分の `channels.json`** — スキャン結果には TSID が入っています。**こちらが勝ちます**
2. 焼き込んだ表 — まだ1度もスキャンしていないときだけ

BS は再編があるので焼き込んだ表はいつか古くなります (実際 `recisdb` の表には、手元で
受かっている `BS13_3` `BS21_3` `BS23_3` がありません)。**スキャンした人のほうが必ず新しい**。

#### 選局は取り合いの錠の外でやる

**取り合いの錠を握ったまま選局すると、同期待ち (上限 5 秒) の間プールに触る道が全部
止まります。** 実機では、チューナーが2本あっても総当たりが1本ずつしか進まず、
スキャン中のチューナー画面 (`/denpa/tuners` も同じ錠を取る) が「空き」のまま動きません
でした。

錠の中でやるのは**本を押さえるところまで**で、選局はその外 (`TunerPool.Open`)。
押さえた印として**読み手を先に入れてから錠を放します** — 入れないまま放すと、
選局中の本が「誰も読んでいない」と見えて次の要求に持っていかれます。選局し直す間の
順番は**本ごとの錠**で守ります (別の本は待たない)。

### PX-Q3U4 などは px4-userland で。カーネルドライバは入れてもらわない

複数チューナーの PX4 系を Linux で使うには、`px4_drv` (DKMS) をホストに入れて
`/dev/px4video*` を出してもらうしかなく、「まず何かを入れてください」が要ります
(以前あった `px4_drv` の chardev 対応は、実機に当てないまま外しました)。

代わりに [px4-userland](https://github.com/Khronos31/px4-userland) を**エージェントの
イメージに同梱**します (`agent/Dockerfile`)。libusb だけで USB を叩くユーザー空間の
ドライバで、`/dev/bus/usb` が見えれば動きます。カーネルモジュールも DKMS も要りません。

| 機材 | 口 |
| --- | --- |
| PT2 / PT3 (Earthsoft) | **DVB** (mainline の `earth_pt1` / `earth_pt3`)。実機はこれ |
| PX-S1UD (ISDB-T / USB) | **DVB** (mainline の Siano `smsusb` + `smsdvb`。firmware `isdbt_rio.inp` が要る)。smsusb を blacklist してあれば **siano-userland** (同梱。`Siano.cs`。[下記](#px-s1ud-はカーネルが掴んでいなければ-siano-userland-で)) |
| PX-BCUD (ISDB-S / USB) | **DVB** (Linux 4.7 以降 mainline) |
| PX-Q3U4 / PX-W3U4 / PX-MLT 系、e-Better / Digibest 系など (USB・PCIe) | **px4-userland** (同梱。`Px4.cs`)。px4-userland が対応している機種ならそのまま使う ([一覧](https://github.com/Khronos31/px4-userland#対応機種動作環境)) |

**口は3つ。** `px4d` が筐体 (USB 機能・受信機・内蔵カードリーダー) を所有する
デーモンで、筐体1台につき1つ起こします。`px4-ts` は受信機を1本借りて選局し、
TS を標準出力に流します。`px4ctl` は状態を聞きます。

**機種のことは何も持ちません。** 刺さっている筐体と、それぞれの受信機が何を
受けられるかは `px4d --list` に聞きます (px4-userland 0.1.6 から。`Px4Userland.Enclosures`)。
Q3U4 なら8本で受信機ごとに地上波か衛星か決まっている、MLT5 系なら5本でどれも両方
受けられる — その違いは答えに入ってくるだけで、**対応機種が増えても px4-userland を
上げるだけ**で追従します。`--list` は筐体を掴まずに読むだけなので、px4d を起こす前に
顔ぶれが決まります。

- **設定の `device` は `px4:<筐体の番号>:<受信機>`。** 刺さっていれば
  `px4d --list` から組み立てるので (`Px4Userland.Detect`)、普通は書きません。
  `status=ready` 以外の筐体と `rejected` の行は、理由を記録に残して使いません
  (`open_failed` なら `/dev/bus/usb` を開く権限を疑う)。番号の桁数や受信機の上限は
  こちらでは見ず、合わなければ `px4d` / `px4-ts` が理由を付けて断ります。
  **古い `q3u4:<14桁>:<受信機>` は「知らないデバイス」として断る**ので、書いてあれば
  `px4:` に書き直してください (番号と受信機はそのまま)
- **知らない方式は飛ばして続けます。** px4-userland が新しくなって方式が増えても、
  分かる受信機は使えるように。飛ばしたことは記録に残します
- **受信機と違う方式は、px4-ts を起こす前に断ります** (`Px4Tuner.Check`)。
  受信機を聞けていなければ見ずに通し、px4-ts に任せます
- **px4-ts は1回1チャンネル。** チャンネルを変えるたびに起こし直しますが、受信機を
  持っているのは開きっぱなしの `px4d` なので、デバイスが宙に浮くことはありません。
  子の標準出力の pipe を `DeviceStream` に載せるので (`ChildTs.cs`)、読み手の振る舞いは
  DVB と同じです (電波が来なくても畳める・蹴られたら 200ms で降りる)。pipe は 8MB に
  広げます (既定の 64KB は地上波で 30ms ぶんしか無い)
- **同期の判定は「標準出力に最初の1バイトが来たか」。** px4-ts は同期するまで
  1バイトも書かない (書くのは TS だけ、診断は stderr)。先に終われば失敗で、
  理由は stderr の末尾と終了コード (4 = 受信機が使用中、5 = 同期しない、7 = USB)
- **誰も読まなくなると px4-ts は死にます。** pipe が埋まると `px4d` が
  `SLOW_CONSUMER` として切る。それは失敗ではなく受信機を離しただけで、次に同じ
  チャンネルを頼まれたら起こし直します (`ITuneDevice.Tuned` を `TunerPool` が見る。
  DVB は合ったままなので常に true)
- **15V は2段の門。** `px4d` には `--allow-lnb-power` を渡しておき、本当に頼むのは
  設定に `lnb: 15v` と書いてある本だけ (`px4-ts --lnb-voltage 15`)。`11v` は
  px4-userland に無い (0V か 15V) ので頼みません
- **内蔵カードリーダーも `px4d` が持っています。** px4d の control socket に APDU を
  投げて読みます (`Px4Card.cs`、px4-userland SPEC 6 節の portable IPC)。同梱の
  pcscd 用 IFD ハンドラは使いません — pcscd を挟んでいた頃は reader.conf を起動前に
  書き、筐体が増えるたびに pcscd を入れ直す必要がありました (#195)。いまは px4d が
  起きたあと、次にカードが要ったときに見つけます
- 起動時に顔ぶれにある筐体ぶん `px4d` を起こします (`Px4Daemon.Prepare`)。
  ファームウェアを流し込んでから ready になるので数秒かかります。起こせなくても
  他のチューナー (PT3 など) は動き、選局のときにもう一度試します

**ファームウェアは同梱しています。** IT930x は本体にファームウェアを持っておらず、
挿すたびにホストから RAM へ流し込むもので、px4-userland は受理する版を SHA-256 で
1つに固定しています。**イメージを焼くときに、PLEX 公式の Windows ドライバ
(`pxw3u4_BDA_ver1x64.zip` の `PXW3U4.sys`、著作権表示は Digital Warrior Corp.) から
切り出します** (0x287d0 から 2,169 バイト)。配布 zip・`.sys`・切り出したものの3つを
ハッシュで確かめます。**再配布の許諾は誰も持っていません**。権利者が動いていない
という事実に乗る判断で、px4-userland 本体は方針として同梱しない (SPEC 4.5) ので、
そこだけこちらが背負います。

**実機には当てていません** (手元の機材は PT3)。確かめてあるのは機材に触らない部分
(`px4d --list` / `px4ctl list` の読み方・device 文字列・px4-ts の引数・内蔵カードの IPC。
`Px4Tests.cs` / `Px4CardTests.cs`。出力の形は px4-userland の SPEC 4.6 と自身のテストの期待値に合わせてある)
と、配布物の CLI が期待どおりの引数を受けること。実機で当てるのは
`denpa-agent --tune px4:<筐体の番号>:2 T27` (`Probe.cs`)。

### PX-S1UD はカーネルが掴んでいなければ siano-userland で

PX-S1UD は mainline の `smsusb` + `smsdvb` で Linux DVB になるので、**DVB でも使えます**
(ホストに `isdbt_rio.inp` が要る)。それとは別に、
[siano-userland](https://github.com/Khronos31/siano-userland) の `siano-ts` を
**エージェントのイメージに同梱**しています (`agent/Dockerfile`)。libusb だけで USB を
叩き、ファームウェアも配布アーカイブに入っているので、ホストに何も入れずに動きます。

**カーネルが掴んでいる機材には触りません。** 作者自身が「動いている smsusb から
切り替えるのは安全と判定していない」と書いていて (unbind の境目でカーネルの異常を観測)、
DVB で動いている人の S1UD をエージェントが奪うのは論外です。siano-userland 0.1.8 からは
**siano-ts 自身が、カーネルのドライバが掴んでいるデバイスを断ります** (終了コード 4。
以前は黙って奪っていた。Khronos31/siano-userland#9)。

| 機材の様子 | 使う口 |
| --- | --- |
| smsusb が掴んでいる (`/dev/dvb` に出ている) | **DVB** (`DvbTuner`)。siano-ts は起こさない |
| どのドライバにも繋がっていない (smsusb を blacklist した・モジュールが無い) | **siano-userland** (`SianoTuner`) |

siano-userland で使うなら、ホストで `smsusb` / `smsdvb` / `smsmdtv` を blacklist して
再起動します (挿したまま unbind するのは上の理由で勧めません)。

```sh
printf 'blacklist smsusb\nblacklist smsdvb\nblacklist smsmdtv\n' | sudo tee /etc/modprobe.d/denpa-siano.conf
sudo reboot
```

- **設定の `device` は `siano:<USB のポート>`** (`siano:1-2`)。S1UD にはシリアルが
  無いので、挿したポートで見分けます。刺さっていれば組み立てるので
  (`SianoUserland.Detect`)、普通は書きません。挿すポートを変えたら組み直します
- **機材は `siano-ts --list` に聞きます** (px4d --list と同じ `key=value` の形)。
  USB ID の表は持たず、ポートと受けられる方式も siano-ts が見たものを使います。
  ポートの分からない機材 (`port=-`) と対応外の機材 (`rejected`) は、理由を記録に残して
  使いません。**自動検出では、カーネルが掴んでいる機材を sysfs (インターフェースの
  `driver`) で見て並べません** — `--list` はそこを教えてくれず、並べると同じ機材が
  DVB と siano の2本になるため
- **siano-ts には機材をポートで渡します** (`siano-ts --device 1-2.3`、0.1.8 から)。
  番号 (`--device N`) は libusb が並べた順で、カーネルが掴んでいる S1UD も入って
  ずれるので使いません。起動のあとで抜けた・挿し替えた・smsusb が掴んだ、は
  siano-ts が終了コードで答えるので (3 = 見当たらない、4 = 掴まれている、
  10 = ファームウェア)、手当てを添えて記録と選局の失敗に出します (`SianoUserland.Hint`)
- **siano-ts は起こしたまま選局し直します** (`--control`)。起こすのは最初の選局の
  ときだけで、以降は標準入力に `tune <Hz>` を1行書き、stderr の `tuned <Hz>` を待ちます
  (駄目なら `control: tune failed: …`。どちらでも siano-ts は生きたまま)。USB を
  掴み直さないので、番組表の総当たりのようにチャンネルを次々変えるときに速く、
  TS は同じ標準出力に流れ続けるので読み口も1つを使い回します (DVB と同じ)。
  選局の上限は 15 秒 (siano-ts 自身が同期を 10 秒待つ。初回はファームウェアの流し込みも入る)。
  siano-ts が死んでいたら (USB が抜けた等) 次の選局で起こし直します
- **選局し直す間は標準出力を読んで捨てます。** siano-ts は「TS を書く → 標準入力を見る」を
  1本の輪で回していて、pipe が埋まると書くところで止まり `tune` を読みに来ません。
  誰も読んでいない間 (前の読み手が降りてから次の選局まで) に pipe は埋まるので、読まずに
  頼むと進まない。読んで捨てれば前のチャンネルの残りも消えます (siano-ts は同期を待つ間
  何も書かないので、`tuned` の時点で前の TS は読み尽くしてある)。`tuned` の直後の少しは
  一緒に捨てることがありますが、録画の頭が数ミリ秒ずれるだけです
- **誰も読まなくても siano-ts は死にません。** 書くところで待つだけで、中の溜めが
  溢れたぶんは捨てます。選局は生きています (DVB の環が溢れたときと同じ)
- **地上波だけ。** 衛星を頼まれたら siano-ts を起こす前に断ります
- **実機に当てていません。** siano-userland 側で実機確認済みなのは PX-S1UD (`3275:0080`) だけで、
  `187f:0600` / `187f:0302` はあちらでも未検証です

### B25 の解除もカードリーダーも自前

**libaribb25 も pcscd も使いません。** TS から ECM を拾って MULTI2 で解くところも
(`B25.cs` / `Multi2.cs`)、B-CAS へのコマンドも (`BCas.cs`)、カードリーダーとの
やり取りも (`Ccid.cs` / `T1.cs` / `UsbFs.cs` / `Px4Card.cs`) エージェントが持ちます。

```text
Descrambler (B25.cs)   PAT → PMT → CA 記述子で ES と ECM を結び、鍵で MULTI2 を解く
   │ ECM
IKeySource             手元のカード (LocalCard → BCas) か、別の拠点 (RemoteCard)
   │ APDU
ICardLink              USB の CCID リーダーを usbfs で直に (Ccid) / px4d の内蔵リーダー (Px4Card)
```

**前は libaribb25 (`recisdb` が中で使っていたもの) を P/Invoke で呼び、カードは
pcscd 越しに読んでいました。** やめたのは、振り回されていたのがどれもそちら側だったからです。

- **スレッドセーフでない。** 1つの実体に2本の流れが入ると中が壊れ、実機で
  **プロセスごと落ちました** (`double free or corruption`)。防ぐための錠や
  「壊れた疑いがあれば作り直す」を抱えていました。いまは復号器を選局ごとに作り、
  実体どうしで共有するものがありません
- **カードに繋ぎ直さない。** pcscd を入れ直すと以降の ECM が全部失敗するので、
  入れ直すたびに復号器ごと開き直させていました。いまはリーダーが切れたら
  探し直して INT からやり直し、同じコマンドを1回だけ頼み直します (`BCas.cs`)
- **pcscd の癖。** Debian の pcscd は reader.conf を起動したときにしか読まず、
  px4-userland の内蔵リーダーを足すたびに入れ直しが要りました (#195)
- **配布物が OS と arch ごと。** mac では `DWORD` の幅の食い違いで壊れていました。
  自前なら Native AOT の1本に収まります

**挙動は前と揃えてあります。** カードに渡す ECM のバイト列 (節の頭 8 バイトと
CRC を除いた中身)、鍵の読み方、画面に出るカードの番号は、libaribb25 を答え合わせに
使って同じになることを確かめました。MULTI2 の答えと、PMT 2本・ES ごとの CA・
ECM の変化・アダプテーション・ゴミを混ぜた TS を両方に通して、カードに渡った ECM と
出てきたパケットがバイト単位で一致します (単体テストにはその答えだけを入れてある)。
拠点のあいだで鍵をやり取りする形も同じなので、前の版のエージェントとも話せます。

**解く処理は libaribb25 と同じく、流れの順に同期で鍵を貰います。** 届いた順に
PAT・PMT・ECM を読み、ECM の中身が変わったらその場でカードに聞いて、そこから後ろの
パケットをその鍵で解きます。待つあいだは次のパケットへ進まないので、鍵と流れの位置が
食い違うことがありません。貰えなかったら鍵を捨てて掛かったまま流し (古い鍵で解いて
化けたものを「解けた」として流さない)、同じ中身は 2 秒ぶん流れてから聞き直します。
録画の頭は PAT・PMT とすべての ECM の最初の答えが揃うまで (上限 8MB) 溜め、
**最初の ECM を挟んで続いている偶奇の並びだけ**を最初の鍵で解きます (libaribb25 は
溜めた頭を丸ごと解くので、その前の並びが化けていた)。

**読み手とは別のスレッドで解き、間に 64MB のキューを置きます** (`TunerPool.cs`)。
カードや配り役が固まると1回の問い合わせに何秒もかかり、読み手がそこで待つと
デバイスの溜め (3.5 秒ぶん) が溢れて録画が欠けます。欠けたものは後から解いても
戻りません。解き手が待つ長さには上限があり (CCID は 5 秒、配り役は 10 秒)、
64MB は地上波で 25 秒ぶんなので、その間を丸ごと呑めます。繋ぎ直しに失敗したら
10 秒は探し直さず、同じ理由で断ります (何本もの流れが順番にリーダーを開き直さない)。
**契約の無い局** (同じ TS に乗る有料局) は「解けなかった」に数えないので、
後からの解除がそれで失敗扱いになることはありません。

**速さ。** MULTI2 を `Vector<uint>` で並べて回し、Native AOT で1コアあたり
約 400 MB/s (Ryzen 5 5600X)。地上波1本は 2.5 MB/s 弱なので桁で余ります。

**USB のリーダーは usbfs を直に叩きます。** `/dev/bus/usb` が見えていれば動き、
**ホストや別のコンテナで pcscd が動いているとリーダーを掴めません**
(「別のプロセスがリーダーを掴んでいます」と出ます)。TPDU 単位の
リーダー (Gemalto PC Twin など) には T=1 の枠組みをこちらで組み、APDU 単位の
リーダーにはそのまま送ります。カードの無いリーダーや INT に答えないカードは飛ばし、
USB のリーダーを px4d の内蔵リーダーより先に試します (`CardLinks.cs`)。

動いているエージェントがカードと話せているかは `/denpa/card` で分かります (INT を
1回通して確かめる)。エージェントを止めた状態なら `denpa-agent --card` でも確かめられます
(リーダーを並べ、ATR とカードの番号を出す。**動いているエージェントがリーダーを
掴んでいる間は、掴めずに断られます**)。

設計として押さえておくことが2つあります。

- **解くのは選局ごとに1回** ([相乗りの決まり](#相乗りの決まり))。エージェントの中に持ちます
- **番組表とロゴには要りません。** PSI/SI (EIT・SDT・NIT・CDT・DSM-CC) は
  スクランブルされていないので、**カードが死んでいても番組表は埋まります**

#### カードは1枚でいい。**鍵を配る口を入れました**

想定しているのは「1台に4本挿す」ではなく、**拠点ごとにエージェントとチューナーが
あって、それが何箇所かある**形です。そうなるとカードは1箇所にしかありません。

そこで**カードごと持っていく代わりに、ECM を投げて鍵を貰います**
(`CardShare.cs`)。

```text
拠点B (カード無し)                     拠点A (カードあり)
  選局 → TS ─┬─ MULTI2 で解く          B-CASカード
             └─ ECM 200B ──────────→  ECM (0x34)
                鍵 16B  ←──────────
```

- **線に乗るのは鍵のやり取りだけ。** ECM は 200 バイトほど、返るのは 16 バイト
- **重いほうは動かしません。** MULTI2 は TS 全部に掛かるので各拠点の手元に残す
- **同じ ECM には同じ鍵を返します** (数秒だけ覚える)。衛星は全国で同じ電波なので、
  3拠点が同じ BS を見ていてもカードに聞くのは1回で済みます。**拠点が増えるほど効きます**

鍵の出どころは `IKeySource` の1つの口なので、手元のカード (`LocalCard`) と
別の拠点 (`RemoteCard`) を差し替えるだけで、復号の本体は何も変わりません。

実機で確かめました。**カードを持っていない側として起こしたほうが、持っている側から
鍵を貰いながら 88.2% → 0.1% まで解けます。**

```sh
denpa-agent --tune /dev/dvb/adapter1/frontend0 T27 --decode --card-url http://拠点A:25252
```

常駐させるときは環境変数 `CARD_URL` で同じことを指定します。**指定しなければ手元の
カードを読みます** (そのほうが速く、配り役が落ちても録れる)。

**配る側は denpa ではなくエージェントです。** リーダーは USB の機材で、機材に
触るのはエージェント、という境界のままにしたいのが1つ。もう1つは、denpa (bun) から
リーダーを触るには結局ネイティブの口を足すことになり、**既にカードを読めるものが
あるのに二重に持つ**ことになるからです。カードだけ挿さっていてチューナーが1本も
無いマシンでも、エージェントを1つ置けばそれが配り役になります。

なお B-CAS カードの貸与条件は受信機ごとなので、**世帯をまたいで配るのは
グレー**です。手元の拠点をまとめる範囲で使うものと考えています。

#### カードを denpa 側に持たせない理由

**「1枚のカードで何本ものチューナーを解く」は、いまも既にそうなっています。**
カードは順番に使い (`BCas` の錠)、用があるのは ECM が変わるとき (数秒に1回・
数十ms) だけなので、チューナーが4本あっても1枚で足ります。

そのうえで、解くのをエージェント側に置く理由は3つあります。

1. **カードはあちらにしかありません。** リーダーは機材のあるマシンに挿さっています。
   denpa 側に持たせるとリーダーを denpa の側へ通すことになり、拠点を分ける話が
   成り立たなくなります
2. **解くのは選局ごとに1回で足ります。** 相乗りを捌いているのはエージェントなので、
   denpa 側で解くと**送られてきた本数ぶん**解くことになり、MULTI2 が何倍にもなります
3. **denpa が中身を触らずに済みます。** 録るものをそのまま書くだけでよく、
   「解けているか」を気にするのは受け取ったあとの検査だけで済みます

### エージェントは .NET (Native AOT)

**境界のほうが言語より大事です。**

| | 誰が | 何を |
| --- | --- | --- |
| **エージェント** | 機材に触るところ | デバイスを開く・選局する・取り合いを裁く・B25 を解く → **バイト列を配る** |
| **denpa (TypeScript)** | 中身を分かるところ | PSI/SI・EIT・ロゴ・番組表・予約・録画・画面 |

ここを崩してエージェントに EIT の解析まで持たせると、どちらの言語を選んでも同じものを
2箇所に持つことになります。そのうえで、**掴んだままにするには ioctl を直に叩く必要が
ある**ので、bun では書けませんでした。

**.NET を選んだのは手が動く言語だから**です。1人で持つものなので、録画に失敗した夜中に
直せるかどうかがいちばん効きます。この用途で困らないことも確かめてあります。

- **P/Invoke で ioctl を呼べます。** `[LibraryImport]` と
  `[StructLayout(LayoutKind.Sequential)]` で `dtv_properties` も usbfs の構造体も素直に組めます
- **Native AOT で1個の実行ファイルになります。** 別PCへ置くのに「まず何かを入れて
  ください」が要らない、という条件はこれで満たせます。**AOT は必須**です
- **速さは問題になりません。** チューナー4本でも 10 MB/s 程度で、`Span<byte>` と
  `ArrayPool<byte>` で収まります。GC で気をつけるのは読み取りの一本道だけ (188バイト
  ごとに確保しない)
- **Rust と比べて安全性はほとんど変わりません。** 危ないのはどちらも同じ FFI の境目
  (ioctl の呼び出し) だけです

**書き直しにはなりませんでした。** 移したのは取り合いの決まり・チャンネルの控え・
HTTP の口だけで (スキャンは denpa へ移った)、決まりは1つも変えていません。出た違いは
2つで、**どちらも適合テストが捕まえました** — 控えの並び順 (bun 版は種別ごとに
並べ替えていた) と日本語の書き方 (`System.Text.Json` は既定で `テ` に逃がすので、
`channels.json` が読めなくなる。全角空白 U+3000 だけはどの符号化器も逃がすので
合わせていない)。ついでに、取り上げた相手に失敗を伝えられるようになりました
(Kestrel は接続を壊せる。[上記](#選局は読み手が切るまで終わらない))。

**プロセスは分けます。** ioctl は落ちるときに落ちるので、そこで画面や他の
録画まで道連れにしません (言語とは別の判断です)。

### 通信は HTTP。ローカルは Unix ドメインソケット (案。いまは TCP だけ)

**HTTP のところは入っています** (`/denpa/stream` が素のTSを chunked で流します)。
Unix ドメインソケットは**まだ入れていません** (`Program.cs` は `ListenAnyIP` だけ)。
以下は入れるときの決めごとです。

**遅延は伝送路にはありません。** 効いているのは選局の同期と、受け取った側のバッファで、
ループバックや Unix ソケットの往復は桁が3つ違います。**低遅延のためにやるべきことは
「溜めないこと」**で、どの protocol を選ぶかではありません。そのうえで、いちばん退屈な
ものを選びます。

| | 何で | 中身 |
| --- | --- | --- |
| 制御 (選局・解放・状態) | HTTP + JSON | 小さい要求と応答 |
| 知らせ (掴んだ・離した・局が入れ替わった) | SSE (`/denpa/events`) | denpa は自分の画面でもう使っている |
| **TS** | HTTP の chunked | **素のTSだけ。何も包まない** |

**ローカルは Unix ドメインソケット、別PCは TCP** にしても、denpa 側は `/denpa/stream` を
`fetch` して `response.body` を読む今の形のまま、**宛先が変わるだけ**です (bun の
`fetch(url, { unix })`、.NET 側は Kestrel が Unix ソケットと TCP を同時に listen できる)。

低遅延のために守ること:

- **溜めない。** 数パケット届いたらそのまま流します。64KB 貯めてから送ると、
  それだけで 25ms 積み上がります (1本 2.5 MB/s)
- **TCP を使うときは `TCP_NODELAY`。** 小さい書き込みが Nagle で待たされます
- **TSの上に枠を被せない。** 既に188バイトで区切られています

採らないもの:

| 案 | なぜ |
| --- | --- |
| gRPC | .NET 側は良いが bun 側が重い。**不透明なバイト列に protobuf の枠は何も足しません** |
| HTTP/2 | 流しっぱなしの1本にフロー制御の窓が増えるだけ。h1 の chunked のほうが素直 |
| 共有メモリ / リングバッファ | いちばん速いが、**ローカル専用**なので道が2本になる。10 MB/s のために背負う複雑さではない |
| 自前のバイナリ protocol | 覗けなくなるだけ |

**背圧の向きは用途で変えます。** 録画は**落としません** (詰まったら待たせる。
電波は二度と来ません)。視聴は**落として構いません** (遅れて届くコマより、
いまのコマのほうが価値がある)。同じ選局を両方が読んでいることがあるので、
**読み手ごとに決める**必要があります。

### エージェントは別イメージ・別プロセス

2つのイメージ (`denpa` と `denpa-agent`) を並べています。

- **denpa はエージェントを起こしません。** `TUNER_AGENT_URL` で繋ぐだけで、
  Helm チャートは 2 つの Deployment を一緒に立てます (`charts/denpa/templates/agent.yaml`)。
  チューナーが 1 台のマシンに挿さっているふつうの構成でも、動くものは 2 つ
  (プロセスを分ける理由は[上記](#エージェントは-net-native-aot))
- **チューナーの刺さったマシンにエージェントだけ置き、denpa は別の所で動かせます**
  (`charts/denpa-agent`)。生TSの置き場 (`denpa-recorded`) を両方に見せる必要があるのは
  [下記](#b-casカードとデスクランブル)のとおりです
- **繋げるエージェントはいまは1つだけ**です (`TUNER_AGENT_URL`)。別PCのチューナーを
  足す (複数のエージェントを1つの denpa に束ねる) のはまだ入っていません。入れるなら
  取り合いは denpa が全体を見て決め、どのエージェントの何本目かは denpa 側の帳簿になります

## Mac でチューナーを使う

**Apple Silicon の Mac なら、Linux と同じ1行で denpa ごと立ち上がってブラウザが開きます**
(入口の `install.sh` は1つで、OS を見て振り分ける)。

```sh
curl -fsSL https://raw.githubusercontent.com/danything/denpa/main/install.sh | bash
```

**エージェントは Mac の上でそのまま、denpa 本体は Docker で動かします。** Mac の Docker
(Docker Desktop / OrbStack / colima) はコンテナに USB を渡せないので、チューナーとカードに
触るエージェントだけはコンテナに入れられません。denpa のコンテナからは
`host.docker.internal` でエージェントを呼びます (`compose.mac.yml`。
compose.prod.yml から tuner-agent を外したもの)。

1. **エージェント** — 最新のリリースから取ってきて、LaunchAgent
   (`~/Library/LaunchAgents/io.github.danything.denpa-agent.plist`) に載せます。
   ログインしたら起き、落ちたら起き直し、止めるときは録画が終わるまで待ちます
   (launchd に殺されないよう、待ちの上限を 6 時間より長くしてある)
2. **denpa 本体** — エージェントと**同じ版**の compose.yml を取ってきて `docker compose up -d`。
   `http://localhost:3000` が答えたらブラウザで開きます (`--no-open` で開かない)

- **要るのは Homebrew の libusb と Docker。** libusb は px4-userland と siano-userland の Mac 版が
  繋がっているもので、Homebrew があれば `brew install libusb` まで済ませます (無ければ入れ方を
  言って止まる)。**Docker は勝手に入れません** — 無い・起きていないときはエージェントだけ入れて、
  Docker Desktop か OrbStack を入れる (起こす) ように言って終わります。入れたらもう一度流す
- 入れるのは全部ユーザーの下で、sudo は要りません

| 置き場 | 中身 |
| --- | --- |
| `~/Library/Application Support/denpa-agent/` | エージェント・px4-userland・siano-userland・設定 (`tuners.json` / `channels.json`)・`compose.yml` と `.env` |
| `~/Movies/denpa/recorded` | 生TS。**エージェントとコンテナの両方に見せる** (掛かったまま録れたものを後から解くとき、denpa は置き場からの相対パスで頼み、エージェントが直に読み書きする) |
| `~/Movies/denpa/library` | 出来上がった録画 (Finder から見える) |
| Docker のボリューム `denpa_denpa-data` | DB。SQLite の錠は Mac から見せたフォルダ越しだと当てにならないので、名前付きボリュームに |
| `~/Library/Logs/denpa-agent.log` | エージェントのログ |

- もう一度流せば上げ直し (エージェントも denpa のイメージも最新のリリースへ)。
  消すときは `… | bash -s -- --uninstall` (denpa も畳む。録画と DB は残し、消し方を言う)
- denpa 本体は別の Linux で動かし、Mac にはエージェントだけ置くなら `… | bash -s -- --no-docker`。
  denpa の `TUNER_AGENT_URL` に `http://<Mac の名前>.local:25252` を書きます
  ([別の所に置く](#エージェントは別イメージ別プロセス)のと同じ形)
- **誰を通すか** (`TRUSTED_NETWORKS`) は compose.prod.yml と同じ私設網です。Mac のブラウザから
  localhost で入ると、コンテナに見える送り元は Docker のネットワークの出口 (私設網の中) になるので、
  これで通ります

LaunchAgent に書く環境変数は、コンテナで既定にしている置き場を Mac の置き場に向け直すものだけです
(`AGENT_PORT` `TUNERS_FILE` `CHANNELS_FILE` `PX4_USERLAND_DIR` `PX4_FIRMWARE` `PX4_RUNTIME_DIR`
`SIANO_USERLAND_DIR` `SIANO_FIRMWARE` `RECORDED_DIR`)。`PX4_RUNTIME_DIR` を
`~/Library/Caches/denpa-agent` と短い所にしているのは、px4d の制御ソケットのパスが macOS では
104 バイトまでしか通らないからです。IT930x のファームウェアはコンテナと同じく PLEX のドライバから
手元で切り出します (ハッシュ3つで確かめる)。

**Linux と違うところ。**

- **チューナーは px4-userland と siano-userland の機材だけ。** macOS には DVB が無いので、
  PT2/PT3 のような PCI の機材や、カーネルのドライバで見せる道はありません
- **カードリーダー**: px4-userland の内蔵リーダーはそのまま (px4d に聞く)。USB のリーダーは、
  Linux のように usbfs を直に叩けないので、**macOS に最初から入っている PC/SC
  (PCSC.framework) 越し**に叩きます (`Pcsc.cs`)。`denpa-agent --card` はそのリーダーを並べます
- pipe を広げられない (`F_SETPIPE_SZ` が無い) ので、px4-ts / siano-ts から受ける溜めは Linux より浅い
- **Apple Silicon だけ** (Intel Mac 用の px4-userland / siano-userland が無い)。
  **Mac の実機でチューナーとカードを繋いで確かめたことはまだありません。** CI で焼いて起こし、
  エージェントの入れ方を最後まで流すところまで (`.github/workflows/test.yml` の `agent-macos`。
  Mac のランナーには Docker が無いので、compose は Linux のジョブで書き方だけ見る)

## B-CASカードとデスクランブル

スクランブルは**エージェント自身が解きます** (`B25.cs`)。カードが読めないときは
掛かったまま流し、その理由を状態に出します — 黙って素通しすると「録画は成功して
サイズもそれらしいのに中身が全部スクランブル」という分かりにくい壊れ方になるためです。
選局を畳むときに、掛かったまま流したパケットの数と理由を記録にも残します。

- **録画は止めません。** 電波は二度と戻ってこないので、スクランブルされたままでも
  録っておきます。denpa がエンコードの前に見て、掛かったままならエージェントに
  解かせます (`src/lib/server/scramble.ts` → `/denpa/decode`)
- **解くのはチューナー側のエージェントです。** カードリーダーを叩くのはあちらです
- やり取りするのは**パスだけ**です。生TSの置き場 (`denpa-recorded`) を両方のコンテナに
  見せてあるので、読むのも書くのも向こうが直接やります。数十GBを HTTP で往復させません
  (**両方の Pod が同じノードに居ることが前提**です)
- **生TSを残す設定のときは、残るのは解除済みのTSだけ**です。掛かったままのものを
  取っておいても、あとから解ける保証はありません
- 状態は**チューナー画面の「チューナーの空き」の「カードリーダー」行**に出ます
  (見えているリーダーと、実際にカードの INT が通ったか)

### 直らないとき

まず `/denpa/card` で、見えているリーダーと、カードに INT が通るかを見ます
(チューナー画面の「カードリーダー」行と同じもの)。

```sh
kubectl -n denpa exec deploy/tuner-agent -- curl -s localhost:25252/denpa/card
```

- **`readers` が空** — `/dev/bus/usb` がコンテナに見えていない
- **「別のプロセスがリーダーを掴んでいます」** — ホストで pcscd が動いている。
  止めるか、リーダーをそちらから外す。(`denpa-agent --card` を動いているエージェントの
  横で起こしたときも、エージェント自身が掴んでいるのでこう出ます)
- **応答が無い (タイムアウト)** — リーダーが固まっている。USB レベルで入れ直すと戻ります
  (`4-11` は `lsusb` と `/sys/bus/usb/devices` から引く)

```sh
echo 4-11 | sudo tee /sys/bus/usb/drivers/usb/unbind
sleep 2
echo 4-11 | sudo tee /sys/bus/usb/drivers/usb/bind
```

入れ直してもエージェントを起こし直す必要はありません。次の ECM で探し直します。

実際に解けているかは `--tune ... --decode` で見ます (解いたあとが 0% 近くなら正常)。

```sh
kubectl -n denpa exec deploy/tuner-agent -- denpa-agent --tune /dev/dvb/adapter1/frontend0 T27 --decode
```
