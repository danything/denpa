# CM とエンコード

**録ったあとの話。** 何をどう焼くか、CM をどう見つけるか、字幕をどう入れるか。
選ばなかった案と、実測して見送ったものも置いてあります。

| 探しもの | 見る場所 |
| --- | --- |
| 全体像 | [architecture.md](architecture.md) |
| 保存先とファイルの配り方 | [library.md](library.md) |
| CM検出に使うロゴ (`.lgd`) | [logo.md](logo.md) |

既定は AV1 + Opus + PGS の Matroska。同じ画質でファイルは小さくなりますが
時間がかかるので、AV1 を解けない相手 (古いテレビなど) 向けに **H.264 も選べます**
(設定画面)。音声・字幕・コンテナは変わりません。**どちらも 8bit** (下の実測)。

**両方を同時に選べます** — 1本の録画を AV1 (主) と H.264 (`… [H264].mkv`) で2本焼く。
置き方と主・従の決め方は [library.md](library.md)。CM検出も字幕の絵起こしも1回で
済ませて両方に使うので、二度手間にはなりません。

**「エンコードしない」は「どちらも選ばない」ことです。** すると生TSをそのまま
保存先へ置きます (CMのチャプターも字幕トラックも付きません。どちらもエンコードの
ときに入れているためです)。別に「エンコードする」のチェックを持っていた頃は、
外したときにコーデックの選択だけが画面に残って、どちらが効いているのか読めません
でした。**チェックが1つも入っていなければ焼かない**、が揃った形です。

## 字幕は PGS 1本だけ

ARIB字幕は libaribcaption で解いて、**放送どおりに描いた絵 (PGS) を1本だけ**入れます。

以前は文字のまま (ASS) と焼いたもの (dvdsub) も並べていましたが、どちらも
「PGS が作れなかった頃の妥協」で、見た目の違うものが「字幕」として3本並ぶだけでした。
PGS が放送どおりに出るようになった時点で残す理由が無くなっています。

> **放送に「絵」は流れてきません。** 乗っているのは文字と「どこに・どの大きさで・
> 何色で・背景の箱つきで」という指定で、絵になっているのは外字 (DRCS) だけ。
> テレビはそれを見て毎回自分で描いています。`-sub_type bitmap` はその描画を
> libaribcaption にやらせたもので、**それが「放送どおりの字幕の絵」**です。

| | 良いところ | 困るところ | いま |
| --- | --- | --- | --- |
| **PGS** | **描いたままが入る** (1枚256色 + 画素ごとの透明度)。外字もそのまま絵になる。Blu-ray と同じ形なので、読めるプレイヤーが多い (VLC もそのまま出せる) | ffmpeg に符号器が無いので denpa が書いている | **これだけ入れる** |
| ASS | Matroska が元から想定している形。文字なので軽く、検索もできる | **外字 (DRCS) が全部「〓」になる** (libaribcaption は ASS を組むとき DRCS を下駄記号に置き換える。`replace_drcs` はビットマップ専用)。背景の箱は影の色で代用、点滅は表せない。フォントは再生側任せ | やめた |
| dvdsub | 外字もそのまま絵になる。古い機器でも読める | **1枚あたり4色まで**。実測230色の字幕から、縁のなめらかさと話者ごとの色分けが落ちる | やめた |

**PGS は denpa が自分で書きます** (`src/lib/pgs.ts`)。ffmpeg で作れるビットマップ字幕は
どれも足りず、PGS だけは「読めるが作れない」ためです。

| | 表現力 | なぜそのままでは使えないか |
| --- | --- | --- |
| dvbsub | 256色 (`min_bpp` 2/4/8) | **ffmpeg が CodecPrivate を書かない** (実機: dvbsub は extradata 0 バイト、dvdsub は 136 バイト)。CodecPrivate を求める読み手はトラックごと捨てる。届いたとしても、ffmpeg が字幕ごとに必ず出す「消すための空パケット」で壊れる読み手がある |
| PGS (`S_HDMV/PGS`) | 256色 + 画素ごとの透明度 | **ffmpeg に符号器が無い** (復号のみ)。ただし `.sup` を**読む**ことはできるので、denpa が書いて `-c:s copy` で入れている |
| xsub | 4色 | Matroska の CodecID が無く、mkv には入れられない |

絵の取り出し口は ffmpeg の sub2video です。字幕をフィルタの入力にすると1枚ずつ
RGBA の映像フレームになるので、時刻は `showinfo` に喋らせ、絵はそのまま受け取ります
(`src/lib/server/subtitle.ts`)。画面まるごとの絵のうち**字幕のあるところだけ切り抜いて**
入れます (PGS は1秒あたりに送れる量が決まっているため)。

色は YCrCb の限定レンジで書きます。**読む側の戻し方に合わせるのが要点**で、
ffmpeg は「高さが 576 より大きい / 分からないときは BT.709、それ以下なら BT.601」で
戻すので、こちらもそう書き分けます。実測での往復のずれ:

| 書き方 | 最大のずれ (RGB) |
| --- | --- |
| 全レンジ (JPEG) の係数 | 30 |
| BT.601 限定レンジ | 39 |
| **高さで BT.709/BT.601 を選ぶ** | **1** |

(1440x1080 の実物の字幕1枚・1,555,200画素で、透明度の食い違いは0)

**同じ絵が続いたら、消して出し直さずに終わりだけ延ばします。** 絵は字幕が出ている
間ずっと1秒おきに流れてくるので、そのまま書くと同じ時刻に「消す」と「出す」が並び、
1枚30KBが毎秒増えます (実機の5分の番組で57枚。まとめると11枚 = 字幕の数そのもの)。

描くときは `-canvas_size` で画面の大きさを渡します。指定が無いと libaribcaption は
1440x1080 (PROFILE_A) とみなすので、1920x1080 で録れているものは字幕だけ横に伸びます。
フォントはイメージに入れてある丸ゴシック 1 本 (`captions.ts` の `SUBTITLE_FONTS`。ライブと録画で同じ) を指定します。

> **字幕トラックが1本も入らない録画があります。** 絵は描くものがあったときだけ出るので、
> 本編に字幕の無い番組では `.sup` が空になり、そのときは何も入れません
> (実機: 字幕の無いアニメで0枚)。

**「消せ」を拾うために ffmpeg に直しを当てています** ([patches/](../patches))。
放送は字幕の区切りごとに画面消去 (CS) だけの字幕文を送ってきますが、ffmpeg の
libaribcaption ラッパは**絵で受け取るときだけそれを捨てて**いました。当てる前は、
CM に入った字幕が次の字幕まで出たままになります (実機で22分35秒)。
生放送も焼き込みも同じデコーダを通るので、ここ1箇所で両方直ります。

## トラックの名前は放送のものを入れる

**音声も字幕も、番組表と同じ言い方で名前を付けます。** 付けていなかった頃は、
プレイヤーの切り替えに「Audio 1」「Audio 2」しか出ませんでした — 二カ国語や解説放送で
**どちらがどちらか分からない**のに、番組表には「主音声」「解説」と出ています。

| | 名前 | どこから |
| --- | --- | --- |
| 音声 | 「主音声 (日本語)」「解説 (日本語)」「ステレオ (日本語)」 | 番組表の `audios` (`arib.audioTitles`) |
| 音声 (デュアルモノ) | 「主音声 (日本語)」「副音声 (英語)」 | 同上。1本を左右に割るので**必ず2本** |
| 字幕 | 「字幕 (日本語)」 | ffmpeg が入口の見出しに書いた言語 (`buildPgs`) |

**番組表の行は24時間で消える**ので、音声の構成は録るときに `recordings.audios` へ
写しておきます (ジャンルと同じ扱い)。写しの無い古い録画は既定の名前
(「音声」/「主音声」「副音声」) に落ちます。

**数が食い違っても困りません。** 番組表が言っている本数と実際に入っている本数は
ずれうるのですが、ffmpeg は在りもしないトラックへの指定を黙って読み飛ばします
(実機で確認)。

**入れ物にも番組名を書きます** (mkv の title。`title.displayTitle` で `[字][デ]` の
ような装飾記号だけ落としたもの)。テレビの VLC (Android) の履歴や通知に出るのはこれ —
再生画面の見出しは URL の最後の区切りなので、そちらは再生リンクの尻に番組名を置いて
賄います ([library.md](library.md#手元のプレイヤーで観る))。字幕トラックには `language=jpn` と default の印を付け、**トラックの並びは
映像 → 音声 → 字幕**にしてあります — 字幕を先頭 (トラック0) に置いていた頃、
テレビ組み込みのデマルチプレクサで字幕を選ぶと固まる症状があり、切り分けとして直しました。

### 時刻の物差しを、焼くほうと揃える

**字幕を絵にする ffmpeg には `-copyts` を渡します。** 同じ TS を2回開くのに、
何を 0 秒とみなすかが両者で違うためです。

| | フィルタに入るもの | 0 秒とみなすもの |
| --- | --- | --- |
| 焼くほう | 映像・音声・字幕 | **入れ物の始まり** (`format.start_time`) |
| 絵にするほう | **字幕だけ** | **1本目の字幕** (数え直す基準になる映像が無いため) |

食い違うのは「録画の頭から1本目の字幕が出るまで」の長さで、これがそのまま
字幕全体の前寄りになります。実機 (火アニバル 攻殻機動隊 #05) では

```text
入れ物の始まり  6115.509   最初の字幕  6125.899   → 差 10.39 秒
```

で、出来上がりでは**CMの映像の上に本編の台詞が乗っていました**。CM を切っていない
(チャプターだけの) 回だったので、ズレていることが画面ではっきり出ます。

`-copyts` を付けると showinfo が放送の時刻をそのまま喋るので、**引く数はこちらで
決められます** — `probeVideo` の `formatStart` に、下の「捨てる長さ」を足したものを
引きます (`subtitle.rebase`)。読めなかったときは引きません
(ズレる可能性は残りますが、字幕が1本も入らないよりはましなため)。

**求めた時刻が muxer に消されないよう、`.sup` の頭には「何も無い」を1つ置きます。**
ffmpeg は入力ごとに「その入力がいつ始まるか」を引いて繋ぐので、1本目の字幕が
1秒から始まる `.sup` をそのまま渡すと字幕全体が1秒前へずれます (実機で確認)。
0秒に空の構成を置いておけば引かれる数が 0 になり、こちらで決めた時刻がそのまま入ります
(`pgs.ts` の `SupWriter`)。

### 頭の音声だけの区間は、ずらさずに捨てる

TS は**音声のほうが先に始まっている**のがふつうです。そのまま焼くと出来上がりも
音声だけの区間から始まり、**1コマ目を 0 秒として数えるプレイヤー**ではそのぶん
字幕が早く出ます。

**測るのは「実際に復号できた1コマ目」です。** `stream.start_time` は最初の
*パケット*の時刻で、そこから何コマかは参照先が録れておらず捨てられます。

```text
入れ物の始まり           6115.509
start_time (パケット)    6115.872   ← これを信じると 0.363
実際に出た1コマ目 (I)     6116.439   ← 本当は 0.930   差 0.567 = 17コマ = 半GOP
```

**ずらす (`-output_ts_offset`) のでは直りません。** Matroska は負の時刻を持てないので、
下がった音声を muxer が押し戻し、全トラックまとめて元の位置に戻ります。実測:

| | 映像 | 音声 |
| --- | --- | --- |
| ずらさない | 0.934 | 0.022 |
| `-output_ts_offset -0.363` | 0.912 | 0.000 |
| **`-ss 0.930` で捨てる** | **0.000** | **0.000** |

0.363 渡して動いたのは 0.022 だけでした。**捨てれば映像も音声も 0.000 から始まります。**
捨てるのは映像がまだ無いところなので、見えるものは減りません。

捨てる長さは `encoder.headSkip` に1箇所だけ置いています。焼くほうと `.sup` を作るほうで
食い違うと、そのぶんそのまま字幕がずれるためです。再試行のときの頭捨て
(PAT/PMT が固まる前) とは理由が別なので、両方あるときは足します。

**CMのチャプターだけは、この量を引きません** — 検出は入れ物の頭から数えていないためで、
理由は下の「チャプターを詰める量は、`-ss` と同じではない」に。

## コマ数は本編の映像から測って決める

`bwdif` の既定は `send_field` で、**1フィールドから1コマ作って 59.94p にします**。
放送は 1080i (毎秒60フィールド) なので、実写・スポーツ・報道はこれで撮られたとおりの
動きになります。ただしコマ数が倍なので、エンコードの時間もサイズもおよそ倍です。

**ffmpeg 9.0 / 9.0.1 には直しを当てています** ([patches/](../patches) の
`ffmpeg-sched-overflow.patch`)。当てないと 60コマで焼いた長尺で 20〜25 分あたりから
音声トラックが黙って終わります (2026-08-17 実機: 2時間の映画で AV1 版 23:28・H.264 版
22:07。エラーは 1 行も出ない。30分番組は本編 24 分前後で境界の手前なので気付けなかった)。

実測 (地上波1分、AV1):

| | 所要 | サイズ | コマ数 |
| --- | --- | --- | --- |
| `send_field` (60コマ/秒) | 31.8秒 | 26 MB | 3598 |
| `send_frame` (30コマ/秒) | **16.9秒** | **15 MB** | 1799 |
| H.264 medium (60コマ/秒) | 29.2秒 | 34 MB | 3598 |
| AV1 `-preset 8` (60コマ/秒) | 59.5秒 | 27 MB | 3598 |

アニメは元が毎秒24コマ前後で描かれていて、それをプルダウンして60フィールドに
乗せているだけなので、フィールドごとにコマを起こしても同じ絵が並ぶだけで、
滑らかさは1つも増えません。そこで**同じ絵が並ぶ素材か
どうかを、焼く前に本編から実測します** (`encoder.measureSmoothMotion`)。

**放送のTSに「本当のコマ数」は入っていません** (本番で実測):

- EIT の component_descriptor は中身が何でも `1080i` (アニメも映画も同じ)
- `avg_frame_rate` は常に 30000/1001、`field_order` は常に `tt`
- MPEG-2 の per-frame フラグ (interlaced_frame) もほぼ全部立つ。
  テレシネの印 (repeat_pict) も付いていない
- 縞の検出 (idet) も使えない — アニメ本編ですらプログレッシブ 0〜2% と出る
  (パン・合成・ノイズで縞が出るため)

唯一の見分け方が**「60コマに起こして、同じ絵が続く割合を数える」**でした。
本編から30秒の窓を5つ取り、`bwdif=send_field` → `mpdecimate` の生存率の中央値で
決めます (閾値は `FPS_SURVIVE`、既定 50%)。
窓は 3 → 5 に増やしました (2026-08)。本番の録画を 30秒刻みで全部測って採り方を
比べると、5窓の中央値はアニメが 24〜31% → 17〜28% と閾値から遠のき、実写 (CM の窓を
代わりに) は 60〜79% で変わりません。**下位や最小を採るのは駄目**で、実写でも静止した
窓は 42% まで落ちるため、動きのある素材を 30コマに落とす側の誤判定が出ます。
窓を増やしても中央値が 45〜50% に留まる作品 (毎秒 30 枚が違う絵のアニメ、実測 48%) が
あり、45% だった閾値ではこれが 60コマに倒れていました。閾値は **50%** に上げてあります
(2026-08) — 実測の並びは 30コマのアニメ 17〜28% / このアニメ 48% / 実写 60〜79% (下位 1/4
でも 53% 以上) で、50% はその間。実写側の余裕は 3〜10 ポイントしか無いので、これ以上は
上げないでください。
測るのは `-map 0:v:0` で主映像に固定します — 地上波の TS にはワンセグ
(320x180 の H.264) も残っていて、任せるとフィルタがそちらに当たることが
ありました (実測で判明)。
CM は実写の 60i なので、CM検出があれば**一番長い本編区間**の中で測ります。
最初の区間で測っていた頃は、アニメのアバン+OPに窓が乗り、OPの激しい動きが
生存率 57〜74% になって 30コマの本編 (実測 20〜32%) を 60コマと誤判定して
いました (本番の実測)。一番長い区間は本編そのものなので、OP帯を自然に避けられます。
迷ったら 60コマに倒します — 本物の 60i を 30 に落とすと動きが崩れますが、
逆は無駄が出るだけです。

以前は番組のジャンル (国内アニメだけ30コマ) で決めていました。設定の
「コマ数を映像から決める」を外すと実測せず、**全部 60コマ**で焼きます。
ライブ視聴は映像が来る前に決めないといけないので、常に 60コマです。

どちらに転んだかは `recordings.fps` に書き、**番組詳細に「30コマ/秒」「60コマ/秒」の札**で
出します (ログにしか出ていなかった)。未エンコードの録画と、記録を始める前に
焼いたものには付きません。

## H.264 は crf 24 (AV1 と同じ画質の段)

**画質の段は AV1 の既定に揃えます** — 同じ番組をどちらで焼いても見た目が
変わらないように。

実写100秒 (grain の多い映画・59.94p。H.264 には厳しい素材) で測りました:

| | SSIM | 大きさ | AV1比 |
| --- | --- | --- | --- |
| AV1 crf35 (既定) | 0.9719 | 22.1 MB | 1.0x |
| h264 crf22 (前の既定) | 0.9760 | 77.9 MB | 3.5x |
| h264 crf23 | 0.9745 | 63.3 MB | 2.9x |
| **h264 crf24** | **0.9729** | **51.4 MB** | 2.3x |
| h264 crf25 | 0.9715 | 41.9 MB | 1.9x |

- **crf24 が AV1 とちょうど同じ画質** (0.9729 ≥ 0.9719) で最小。crf25 まで
  下げると AV1 を下回る。**AV1 と揃える下限が 24**
- 前の crf22 は AV1 より一段上の画質を **3.5倍の容量**で焼いていた。crf24 に
  下げると画質は AV1 基準を保ったまま**容量が3割減る** (78→51MB)
- H.264 はどのみち AV1 の 2〜3倍。これは高 fps・grain の多い素材での上限で、
  国内アニメのような素材だと差はもっと小さい
- **preset は medium。** slow にしても同じ画質で時間だけ 25% 増える
  (crf22 で slow 0.9757/76MB ↔ medium 0.9760/78MB)

## preset は 9・crf 35 (値は書いておく)

**書かずに既定へ任せません。** SVT-AV1 の既定は版で変わります — preset は
2.3.0 が 10、4.2.0 が 8。黙って入れ替わると焼く速さも大きさも変わってしまい、
焼く速さと大きさは denpa が決めることで、上流の都合で変わっていいものでは
ありません。**crf 35 のほうは 2.3.0 でも 4.2.0 でも既定のまま**で、今の指定と
一致しています (ffmpeg の `-crf` は既定 0 と出ますが、あれは「未指定」の番兵で、
渡さなければ SVT-AV1 内部の 35 が使われます)。

### 10 は使ってはいけない値でした

長らく `-preset 10` で、2.3.0 の既定をそのまま書き写したものでした。
**4.x ではこれが「人が見る絵のための段」から外れています。**

    Svt[warn]: Non-RTC M10+ are meant for automation tooling usage.
               Visual artifacts may occur otherwise.

上流が既定を 10 から 8 に下げたのはこのためで、こちらは**時間と大きさの話だと
思って 10 に留まっていました**。実際に出ていたのは画質の話です。

症状は**シーンの変わり目のブロックノイズ**。カットの直後の数コマだけが大きく
崩れ、すぐ戻るので「たまに一瞬汚い」という見え方になります。

実測は実素材 (地上波アニメ 90 秒、1440x1080 を denpa と同じ道で 1920x1080 へ、
カット 22 箇所)。「カット直後」はカットのコマから 4 コマの PSNR です。

| preset | カット直後 最低 | カット直後 平均 | 全体 | 所要 | 大きさ |
| --- | --- | --- | --- | --- | --- |
| 10 | **29.74 dB** | 42.15 dB | 46.27 dB | 17秒 | 8.5 MB |
| **9** | **37.77 dB** | 43.89 dB | 46.70 dB | 20秒 | **8.1 MB** |
| 8 | 37.69 dB | 44.64 dB | 47.50 dB | 25秒 | 10.0 MB |

**9 は 10 の上位互換です** — 崩れが 8dB 戻り、全体の画質も上がり、しかも
**小さくなります**。増えるのは時間だけで 18%。

**8 までは落としません。** カットの崩れは 9 でもう戻っており (差 0.08dB)、
8 が勝つのは全体の平均だけで、その代わり **+18% 大きく +47% 遅い**。
速い側へ振ると絵が壊れ、**遅い側へ振っても時間が増えるだけ**です
(H.264 medium と比べても、AV1 のほうが同じ速さで小さくなります)。

### 他のオプションは触りません

**`scd=1` (シーン変わり目でキーフレーム) は効きません。** 4.2.0 は指定すると
こう返して無視します — 「SVT-AV1 has an integrated mode decision mechanism to
handle scene changes and will not insert a key frame at scene changes」。
実際、付けても付けなくてもキーフレームの位置は 0 と 161 のままでした。

`tune` (0/2)・`enable-variance-boost`・`qp-scale-compress-strength`・`sharpness`
も同じ素材で測りましたが、**大きさを揃えると差は 0.05dB 以内**で、変える価値が
ありませんでした。固定 crf のままだと variance-boost がよく見えますが、
**5割ビットを積んでいるだけ**です。**効くのは preset だけ**でした。

## 10bit では出しません (実測して 8bit へ)

AV1 は 10bit で出していました。**説明のどこにも根拠が書いてありませんでした**ので、
測りました。素材は実機の録画から100秒 (地上波の実写)、denpa と同じ手・
SVT-AV1 2.3.0 `-preset 10 -crf 35`。画質は同じフィルタを通した元との SSIM です。

| | 所要 | 大きさ | SSIM | PSNR |
| --- | --- | --- | --- | --- |
| 10bit | 39秒 | **21.71 MB** | **0.97582** | **44.65 dB** |
| 8bit | **34秒** | 22.09 MB | 0.97472 | 44.47 dB |

**差はあります。1.7% 小さく、SSIM +0.0011 (PSNR +0.18dB)。** 8bit の素材を 10bit で
焼くと丸め誤差が溜まりにくいという、教科書どおりの結果です。

**元の放送が 8bit なのだから、8bit で出します。** AV1 10bit をハードウェアで解ける
Android 機はまだ少なく、実機 (Android TV のプレイヤー) で `1080p59.94` の AV1 10bit が
まともに再生できませんでした。2% は、観られなくなる代償に見合いません。

**既にある 10bit のファイルはそのままです。** 焼き直しはしません
(元の生TSを消してあるものは焼き直せませんし、残っているものも焼き直す理由が
「2% の差を捨てるため」では釣り合いません)。

## GPU で焼く (Intel QSV / VA-API)

**GPU が見えれば、起動時に自分で見つけて使います。** イメージには Intel の GPU 向けの
ものが入っていて (ffmpeg に libvpl と VA-API、実行イメージに `intel-media-va-driver` /
`libmfx-gen`)、コンテナに `/dev/dri` を渡してあれば `src/lib/server/hwenc.ts` が
起動のたびに **`HW_DEVICES` (既定 `/dev/dri/renderD*`) に当たる口を全部拾い、口ごとに
道 (QSV / VA-API) × コーデック (H.264 / AV1) の4通りを実際に1コマ焼いて**確かめます。
`ffmpeg -encoders` に載っているかでは分かりません — あれは「組み込んであるか」で
「動くか」ではないので。世代でも違います (Arc より前は AV1 のエンコードが無い)。

結果は設定画面の「GPU」カードに口ごとに出て、**使えるものには自動で印が付き
ます**。外したいものだけ外してください。**グラボが2枚あれば口ごとに割り振れます**
(こちらは AV1、あちらは H.264、のように)。同じコーデックを焼ける口が複数あれば
ジョブごとに先頭を入れ替えて、2本並べて焼くとき片方に寄らないようにします。
使えないものの印は触れないので、あとで GPU を挿し替えればそのまま効きます。
挿し直した・権限を直したときは「確かめ直す」で、再起動せずに見直せます。

**試す順は (口ごとに) QSV → VA-API、最後にソフトウェア**で、落ちたら次で焼き直します
(どの道でも、素のまま → 頭を少し捨てて の2回試してから次へ)。起動時の試し焼きは通っても素材しだいで
落ちることはありうるので、GPU が駄目なだけで録画が失敗になることはありません。
Linux では QSV の下に必ず VA-API が居る (libvpl → libmfx-gen → libva →
`/dev/dri`) ので同じ GPU なら速さは変わりませんが、QSV のほうがレート制御が
豊富で Intel が手入れしているので先に使い、QSV が初期化できない世代 (libmfx-gen
の対応外) の逃げ道として VA-API を残しています。

**画質は ICQ (`-global_quality 24`) で、QSV も VA-API も、H.264 も AV1 も同じ
値です。** ICQ はビットレートを決めずに「この画質」を頼む、x264 の crf に相当する
もの。1〜51 の同じ物差しなので、コーデックが違っても同じ値で同じ見た目になり、
AV1 はそのぶん小さくなります — ソフトウェアで H.264 crf 24 と AV1 crf 35 を
「同じ画質の段」に揃えたのと同じ考えです。**手元に GPU が無いので実測はまだ**で、
ソフトウェアで焼いたものと大きさが違って見えたら `hwenc.hwArgs` の値を動かして
ください。インタレ解除と引き伸ばしは CPU のフィルタで済ませ、焼くところだけ
GPU に渡します。

渡し方は、Helm なら既定で `/dev/dri` を hostPath で渡してあります (`denpa.gpu.hostPath`。
そのぶん Pod は privileged。デバイスプラグインを使うなら false にして `resources.limits`
で)。Compose は `devices: - /dev/dri:/dev/dri` (compose.prod.yml のコメント。ホストに
無いと起動できないので既定では書いていません)。

## SVT-AV1 は上流をソースから組みます

**上流の 4.2.0 をソースから組んでイメージに入れています** (Debian trixie のパッケージは
2.3.0 で止まっていて、3 系以降は速度も画質も別物のため。`Dockerfile` の
`SVT_AV1_VERSION`。静的に繋ぐので実行イメージに共有ライブラリは増えない)。
上げるかどうかは一度実測しました。**素材は実機の録画から100秒**(地上波の国内アニメ、
denpa と同じフィルタ。当時はまだ 10bit)。画質は同じフィルタを通した元との SSIM です。

| SVT-AV1 | preset | crf | 所要 | 大きさ | SSIM |
| --- | --- | --- | --- | --- | --- |
| 2.3.0 | 10 (2.3.0 の既定) | 35 | 28秒 | 5.25 MB | 0.98900 |
| **4.2.0** | 10 | 35 | **26秒** | 5.65 MB | 0.98821 |
| 4.2.0 | 10 | 36 | — | 5.27 MB | 0.98770 |
| 2.3.0 | 8 | 35 | 45秒 | 5.87 MB | 0.99133 |
| 4.2.0 | 8 (4.2.0 の既定) | 35 | 37秒 | 6.69 MB | 0.99090 |
| 4.2.0 | 8 | 37 | — | 5.77 MB | 0.99034 |

読み取れることは2つです。

- **同じ preset なら速くなります** (preset 10 で 7%、preset 8 で 18%)
- **大きさあたりの画質は変わりません。** 大きさを揃えて比べると
  (5.25 MB どうし・5.8 MB どうし)、SSIM は 2.3.0 のほうがわずかに上

差は小さいので、**preset と crf はこちらで書いておく** (上の「preset は 9・crf 35
(値は書いておく)」) ことで、版を上げても焼き上がりが黙って変わらないようにしています。
上げた理由は速さと、上流の直しに乗り続けるため (パッケージの 2 系は更新が来ない)。

## CM はチャプターが既定、切るなら TS の段階で

CM は既定で**チャプターを打つだけ**です。実カットは誤検出すると本編が消えるので明示的に
選びます。

### チャプターを詰める量は、`-ss` と同じではない

チャプターの時刻は焼き込む前に前へ詰めますが (`cm.shiftRanges`)、**引く量は字幕とは違います。**

**CM 検出は絵を頭から数えています。** logoframe / chapter_exe は TS の映像を
1コマ目から数え、その番号を `番号 ÷ fps` で秒に直します (`cm-jls.ts`)。
音声だけの区間は見ていません。一方 ffmpeg は**最初の I フレームまでのコマを捨てます** —
先頭の GOP には参照先の無い先行 B が並んでいて復号できないためで、
焼いたものの 0 秒はその I フレームになります。実機 (ブチ切れ令嬢 / 2026-08-18):

```text
入れ物の頭       72575.147
いちばん早い絵   72575.563   ← 検出の 0 コマ目 (先行 B)
復号できた1コマ  72575.730   ← 焼いたものの 0 秒 (I)。ここまでの5コマが捨てられる
```

つまり引くのは**捨てられる5コマぶん (0.167秒)** だけです (`cm.droppedHead`)。
字幕と同じ量 (`-ss` = 0.583秒) を引いていた頃は **0.416 秒 = 12.5 コマ引きすぎ**ていて、
**跳んだ先が CM の途中に着地し、本編が始まるまでの CM が見えて**いました。
実測した8つのチャプターすべてで、実際のカットがチャプターの 0.415〜0.416 秒あとに
ありました。再試行で足した頭捨て (`encodeRetrySeek`) はそのぶん本当に頭が減るので、
こちらは足します。

### 切るときは TS の段階で

切るときは**エンコードの前にTSの段階で切ります**。残す区間を `-c copy` で
切り出して concat デマクサで繋ぎ、そのTSを普通にエンコードします。

エンコードのフィルタ (`select`) で切っていた頃は ARIB字幕のタイミングを追従させられず
`-sn` で落とすしかありませんでした。先にTSを切ってしまえば**字幕もそのまま残ります**
(焼き込みではないので再生中に消せます)。再エンコードを挟まないぶん速くもなります。
`-c copy` はキーフレーム単位ですが、地上波の MPEG-2 は GOP が 0.5 秒程度なので
CM検出の許容誤差に収まります。元のTSは残るので失敗しても戻せます。

## 進み具合は入力の読み位置から出す

画面に出すエンコードの進み具合は、**ffmpeg が入力TSをどこまで読んだか**
(`/proc/<pid>/fdinfo` の読み位置 ÷ ファイルの大きさ) だけから出します
(`encoder.ts` の `inputProgress`)。

以前は ffmpeg の `-progress` が言う時刻 (`out_time_us`) を使っていましたが、
これは「出力の mux が最後に書いたパケットの時刻」でしかなく、3通りの外し方をします —
AV1 (libsvtav1) の先読み中はずっと `N/A` (30分番組の最初の数分がまるごと)、壊れた
副音声が混ざるとそこで止まったまま (TOKYO MX の録画で `Packet corrupt (stream = 3)` の
あと 8.576 秒のまま 0%)、疎な字幕 (.sup の copy) が先に mux されると**先に飛んで
「99% あと1秒」のまま数分止まる** (入力を 65% しか読んでいないのに 99.1%)。
どれも実機で起きました。コマ数 (`frame=`) のほうも分母 (尺×出力fps) が見積もりで、
単独では信じられません。

読み位置はコーデックにもストリーム構成にも依りません。放送TSはビットレートが
ほぼ一定なので、読んだ割合が時間で見た割合ともよく一致します。残り時間も同じ
出どころ (直近30秒の読み速度) から出します — 出どころを混ぜると、止まった時刻を
動いている速度で割って「残り20時間」のような値が出ます。

## 検出方法は2つ (設定画面の「CMの探し方」)

**`silence`** — 無音とシーンの尺だけで判断。追加の依存が無くどこでも動きます。
CM が15秒の倍数で並ぶ性質で絞り込みますが、本編中の「間(ま)」を拾うことがあり、
Amatsukaze ほどの精度は出ません。

**`jls`** — Amatsukaze と同じ考え方。無音・シーンチェンジ (`chapter_exe`) に加えて
**局ロゴが出ているか** (`logoframe`) を見て `join_logo_scp` が判定します。CM 中はロゴが
消えるので無音だけより格段に確かです。**これが既定です** — 検出できなければ
無音検出に落ちるので、これで録れなくなることはありません。引き換えに録画1本あたり
数分かかります (初めて見る局は、ロゴを覚えるぶんさらに)。時間のほうが惜しければ
設定画面で「無音だけ」に戻せます。

**一式はイメージに入っています** (`/opt/jls`)。

かつてこの移植は AviSynth+ と L-SMASH Works と Node の上に載っていて、丸ごと
抱えるのは重すぎました。いまの [tobitti0 版](https://github.com/tobitti0/logoframe)は
**dtvindex (FFmpeg) で TS を直接読める**ので、そのどれも要りません
(`WITH_AVISYNTH=no` で組んで30秒ほど)。実行役の Node アプリがやっているのも
3つのコマンドを順に呼ぶだけなので、denpa から直接起動しています。

```text
logoframe      局ロゴが出ているコマを拾う
chapter_exe    無音とシーンチェンジを拾う
join_logo_scp  その2つを突き合わせて本編とCMに分ける → Trim() の並んだ avs
```

**`join_logo_scp` だけ出どころが違います。** `logoframe` と `chapter_exe` は
tobitti0 の Linux 移植ですが、`join_logo_scp` は本家筋の
[yobibi 版](https://github.com/yobibi/join_logo_scp) (ver5.1.1) を使います。
移植版は ver4.0 (2021年) で止まっている一方、**ver5.1 で Linux が本流に入った**ので
移植を使う理由がありません。効くのは 5.1.1 の「15秒単位からの差認識が正常に
できていなかった所を修正」で、ここは CM判定の芯です。

**実行ファイルと判定規則 (`JL/`) は必ず対で採ります。** 文字コードが違い
(4.0 は Shift-JIS、5.x は BOM付きUTF-8)、取り違えると `error: wrong command in` で
**何も切らない**結果になります (実際に組んで確かめました)。

**ロゴを先に回します。** 逆にしていた頃は、`chapter_exe` が落ちた録画ではロゴを
当てられたかどうかが分からないまま無音検出に落ちていました (実機で2本。テレ東と NHK は
`chapter_exe` が音声で落ちます: `FFmpeg audio packet submission failed`)。無音検出に
落ちたときは、落ちた理由を検出の覚え書き (`recordings.cm_note`) に残します。

**`join_logo_scp` が区切れなかったときは、ロゴの在り処だけで分け直します。**
あちらが黙っても、`logoframe` は「どのコマにロゴが出ているか」を別に出しています
(`-oa`)。日本の地上波・BSは**CMの間だけロゴを消す**ので、その在り処を裏返せば
それだけでCMになります。番組の構成 (提供・予告・エンドカード) までは読めないぶん
`join_logo_scp` ほど細かくはありませんが、**無音検出に落ちるよりは確か**です。
実機の TOKYO MX がこれでした — `logoframe` は 79.74% の合致率で5区間を正しく
出していたのに `join_logo_scp` が何も返さず、無音検出に落ちて本編を60秒ぶん
取り違えていました。ロゴだけで分け直すと 20% がCMという妥当な答えになります。
ここでも多すぎれば捨てる (`tooMuchCm`) ので、ロゴがロゴでなかったときは
これまでどおり無音検出へ落ちます。

**「ロゴの位置を教える口を出すか」はその覚え書きから決めます** (`format.logoUnusable`)。
印を別の列で持っていた頃は、**後から条件を広げても既に録ってある分に効きませんでした** —
「結果の100%がCM判定だったので捨てた」ときも教えられるようにしたのに、実機の2本は
印が 0 のままで画面に出ないままでした。状態は事実から決まるほうに寄せます。

denpa はその avs を読んで秒の区間に直すだけで、エンコードは ffmpeg のままです
(`src/lib/server/cm-jls.ts`)。

**起動は ffmpeg と同じく引数の配列で渡します。** 以前はシェルスクリプトに逃がして
`sh -c` で呼んでいましたが、番組名にも局名にも空白と引用符が入るので、コマンド文字列を
組み立てる限りどこかで引数が割れます。どの段階で落ちたのかも、混ざった標準エラーから
読み取るしかありませんでした。

### ロゴの覚え方

**ロゴデータ (`.lgd`) は logoframe が自分で作ります。** 局名を渡すと、初めて見る局なら
その場でロゴを覚え、2本目からは使い回し、合致率が落ちたら作り直します。置き場は
放送波から拾った PNG の隣 (`data/logos/jls/<局ID>`)。

**覚えるのは CM検出のときです。** 録れたものをそのまま材料にします。

**チューナーを掴んで覚えに行くのはやめました。** 以前は30分ごとに見回り、
まだ覚えていない局を1局ずつ5分掴んで覚えていました (`logo-learn.ts`)。相乗りが
効けば只とはいえ、**割に合いません** —

- **材料が悪い。** 覚えるために掴めるのは5分ぶんで、しかも同じ場面が続きます。
  ロゴの在り処は**中身が変わるほど**はっきりするので (「ロゴの在り処はこちらで
  割り出す」)、30分の録画のほうが桁違いに良い材料です
- **只とは限らない。** 誰も開いていない局は空きチューナーを数分潰します。
  局の数だけこれが要ります
- **要る局しか要らない。** 覚えて意味があるのは録る局だけで、見回りは
  録らない局まで平等に掴みに行っていました

いまは**録ってエンコードするときに、その録画から覚えます**。録る局は必ず通るので
取りこぼしません。かつて「1本目が自分自身から覚えたロゴで自分自身を判定していた」
のを嫌って先回りさせたのですが、**弱かったのは順番ではなく在り処の推定**でした。
そちらを直した (`-logo-area` を渡す) ので、先回りする理由が無くなりました。

**同じ絵を映している局は1つにまとめます** (`logo-data.stations`)。放送局はサブチャンネルの枠を
常時流していて、マルチ編成をしていない間は本チャンネルと同じ絵が出ています。SDT の
局名も同じで、実機では TOKYO MX1 が 23608/23609、フジテレビが 1056/1057/1058 と
並んでいました。束ねずに回していた頃は、**画面に「TOKYO MX1」が2つ並び**、掴むほうも
同じ局を3回ぶん5分ずつ塞いでいました。覚えたら**同じ絵の局へ写します** (`share`) —
束ねて1局ぶんしか掴まないので、写さないとサブチャンネルの枠で録れた番組が
「ロゴを覚えていない」ことになります。束ねる鍵に**ネットワークも入れます**
(局名だけだと、たまたま同名の別系列を1つにしてしまいます)。

**覚え方の閾値は既定のままにしてあります。** 一度は締めましたが、実機で測って戻しました。

| 渡すもの | 既定 | denpa | 実測 |
| --- | --- | --- | --- |
| `-logo-edge-threshold` | 40 | **40** | 60 にすると TOKYO MX が覚えられない |
| `-logo-match` | 10 | **10** | 上げる根拠が無かった |
| `-logo-samples` | 600 | 600 | 覚えるのに見るコマ数 |

60 に上げると、探し当てる場所はむしろ正確になります (`1244,62,136,44` = ロゴのある所)
が、そこから作る推定が「有効な画素が少なすぎる」と弾かれます。MX のロゴは**半透明の
細い白文字**なので、強い縁を要求すると画素が残りません。`-logo-match` を上げたのは
「雑音を覚えたまま作り直されない」のを避けるためでしたが、**その雑音というのが
こちらの読み間違い**でした (`.lgd` の幅と高さを逆に読んでいて、絵が転置されていた)。

**一度覚えたものは、薄くても十分よく当たります。** 実機の MX1 の `.lgd` は
158×48・いちばん濃いところ 252/1000・枠の中でロゴの画素は 12% しかありませんが、
28分の録画で合致 93.28%、別の録画でも 79.74% です。**濃さは当たり外れの目安に
なりません** (NHKEテレ1東京は 512/1000・22%)。

外れるのは「覚えたてのロゴで判定した回」で、そこは `tooMuchCm` が捨てます。
**閾値を振っても覚えられない局はあります** — 空から覚え直す実測では、
`-logo-edge-threshold 20`・`-logo-samples 3000`・`-logo-bg-threshold 30` の
どれでも `no persistent edge` でした。**効くのは閾値ではなく在り処を渡すこと**で、
それは自分で割り出します (下の「ロゴの在り処はこちらで割り出す」)。
それでも当たらなければ、画面から手で囲ってもらいます。

### ロゴをどれだけ当てにするか

**ロゴをどれだけ当てにするかは設定画面から変えられます** (`logo_level`、既定 6)。
`join_logo_scp` は無音・シーンチェンジとロゴを突き合わせて番組の構成を推測しますが、
その推測でロゴをどれだけ優先するかがこれです。ロゴが正しいのに区切れないなら上げ、
覚え違えているようなら下げ、1 でロゴを使わなくなります。

渡し方は `-set logo_level N` です。規則ファイルの中は `Default logo_level 6` で、
**`Default` は未定義のときだけ効く**ので、先に決めたほうが勝ちます。書き換えた写しを
渡していた頃は、規則が `JL/` の外へ出て隣のファイルを見失っていました
(`warning: not found setup-file`)。**規則は置いたまま、変えたい1つだけを外から渡します。**

判定規則そのものも見ました。`JL_標準`・`JL_MBS`・`JL_構成30分単位` は同じ答えを
出しますが、**`JL_ATX` は `Trim(0,50310)` = 何も切らない**という答えになります。
既定の `JL_標準` のままにしておきます。

### ロゴの在り処はこちらで割り出す

**logoframe の自動検出は画面全体を見ます。** 半透明の細いロゴだと、本物より強い縁が
画面のどこかに必ずあるので、そちらを掴んで降ります。テレ東の実素材では
**家具の縁 (`1004,216`)** を「恒常的な縁」として選び、
`The initial logo estimate contains too few active pixels` で失敗していました。
テレ東で `no persistent edge` / `too few active pixels` が続いていたのはこれです。

**透かしは隅にしか出ません。** 画面全体を探す必要が無いので、**位置だけこちらで
出して `-logo-area` で渡します** (`src/lib/ts/logo-area.ts`)。判定そのものは
logoframe のままです — 位置さえ渡せば合致 99.9% が出るので、置き換える理由がない。

探し方は**コマをまたいだ画素ごとの中央値**です。番組のあちこちからコマを集めて
中央値を取ると、中身は場面ごとに変わるので滲んで消え、**毎コマ同じ所に重なって
いるロゴだけが輪郭を保ちます**。その中央値画像に Sobel をかけ、いちばん強い
縁 1% のかたまりを取ると、それがロゴです。

**「動かなさ」では駄目でした。** 半透明の重ねは `画素 = (1-α)×中身 + α×ロゴ色` で
振れ幅が縮む、という筋で MAD を測りましたが、実素材ではロゴの所が `46.4`・
隅全体の中央値が `60.5` で**差が小さすぎ**ました (テレ東は α が小さい)。
中央値に残る輪郭のほうが、薄いロゴでもはっきり出ます。

実測 (テレ東・30分から 83 コマ、1440x1080):

| 渡した枠 | logoframe の結果 |
| --- | --- |
| 自動 (今まで) | **失敗** (`1004,216` を掴む) |
| **内製が出した `1296,35,124,58`** | **合致 99.93%** |
| 手で当てた `1290,20,140,80` | 合致 99.96% |

**コマは散らして渡します。** 90秒ぶんだけ渡した試作では中身が滲みきらず、
その場面の輪郭をロゴとして拾って外しました。

**枠が空のときだけ書きます** (`services.logo_area`)。画面から手で教わったものが
あればそちらが勝つので、合っていなければ囲い直せます。

#### 外したら、無かったことにする

**この割り出しは外すことがあります。** 実機の TOKYO MX1 で外しました — 半透明の
細い「TOKYO MX1」の文字ではなく、背景の**窓枠の縁**を掴んで `1059,39,129,144`
と書き、その枠を渡された logoframe は `too few active pixels` で降りました。
ロゴは実際には `x≈1240〜1380, y≈75〜100` にあり、**枠はロゴにまったく重なって
いません**。

まずいのは、**その局は枠を渡す前まで自動検出で当たっていた**ことです
(MX1 の録画は 4本続けて `join_logo_scp` で成功していた)。こちらの当てずっぽうが、
当たっていたものを壊していました。

そこで**枠を渡して転んだら、渡さずにもう一度**回します。それで通れば、割り出した
枠は捨てて `logo_area_auto = 2` (割り出したが外れた) を立てます。以降その局では
**二度と割り出しません** — 捨てるだけにすると、次のエンコードでまた同じ絵から
同じ枠を出して同じところで転ぶためです。

**捨てるときに誰が入れた枠かは問いません。** 枠を渡すと転び、渡さないと通るので
あれば、その枠は誰が入れたものでも間違っているためです。人が教えたものだった
ときは画面が「自動」に戻るので囲い直せます (捨てたことはログにも出します)。

### 位置を教える

**局ごとの入れ物に分けてあります。** 位置を教え直したときに丸ごと捨てるためです。
`-logo-area` が効くのは**ロゴを覚えるときだけ**で、既に覚えているものがあれば合致率が
落ちるまで作り直しません。捨てられないと、位置を教えても覚えているほうが使われ続けます。
logoframe は局名をファイル名に埋めますが、多バイト文字を `_E7_B7_8F` のように潰した
名前なので、こちらから組み立て直しても当たる保証がありません。

**囲ってもらう枠は広めに。** 実機の TOKYO MX で試すと、文字ぴったりの `146×24` では
「有効な画素が少なすぎる」と弾かれ、まわりを空けた `200×70` で初めて覚えられました
(`uniform=98 logo=77 active=786`)。まわりの背景も見て判断しているようです。

自動で位置を見つけられない局もあります (薄いロゴ、動くロゴ)。そのときは
**録画一覧に「ロゴでのCM判定に失敗」と出し、無音検出に落として録り続けます**。

**教える口はチューナー画面です。** ロゴは録画ごとではなく**局ごと**の話で、
一度教えれば以降の全部に効きます。録画の詳細に置いていた頃は、同じ局の録画が
並ぶたびに同じことを何度も聞かれているように見えました。その局で録れているものから
1コマ出すので、**ロゴを四角で囲って**もらいます。コマは**放送どおりの縦横比**で出し、
囲ってもらった座標は記録されているコマの大きさ (地上波のHDなら 1440×1080) へ
戻して渡します。logoframe が見るのはそちらで、表示用に縮めた座標のままでは合いません。
囲った範囲は局ごとに覚えて (`services.logo_area`)、次に覚えるときに
`-logo-area` として渡します。

### 半分以上がCMなら捨てる

**番組の半分以上がCM判定になった結果は捨てます。** ロゴを覚えたての回など、
`join_logo_scp` が「頭の2秒だけ本編」のような結果を返すことがあり、実機では30分アニメ
2本が丸ごとCM扱いになっていました (`Trim(0,59)` の1つだけ = CM 2秒〜1802秒)。
無音検出と同じ判断で、本編を削るよりCMが残るほうが被害が小さいためです。

**ffprobe の出力は鍵で読みます。位置では読みません。** `join_logo_scp` が返す `Trim`
はコマ番号なので、秒に直すのにフレームレートが要ります。ここで実機で2回踏みました。
どちらも「**1本のTSに局が何本も乗っている**」ことが効きます (TOKYO MX は MX1 と MX2 が
同じTSにいます)。

1. **同じ行が番組の数だけ並ぶ。** `-select_streams v:0` を付けても、ffprobe は番組ごとに
   v:0 を1つずつ出します。丸ごと `split('/')` していた頃は分母が `1001\n30000` になって
   `NaN` に落ち、分子の **30000** を採っていました (本編4万2千コマ → 1.4秒 →「100%がCM」)。
2. **`-show_entries` に書いた順では返らない。** `avg_frame_rate,width,height` と頼んでも
   `1440,1080,30000/1001` (幅,高さ,fps) の順で来ます。位置で受けていた頃は **1440** を
   採っていました (→ 29秒 →「98%がCM」)。ついでに高さが `30000/1001` になっていて、
   字幕を焼くときの画面の大きさも壊れていました。

どちらも上の「半分以上はCM」に引っかかって無音検出へ落ちます。`logoframe` は合致率79%で
ロゴを正しく当てており、`Trim` も3ブロックのまともな結果だったので、画面からは
**ロゴが悪いようにしか見えませんでした** (実機の録画34・35・38)。

いまは `-of default=nw=1` で `key=value` として受け、`fields()` で鍵から引きます
(同じ鍵が並んだら最初のものを採る)。尺と一緒に1回で測って (`probeVideo`)、
`detectWithJls` へ渡します。

**捨てたときも位置を教える口を出します。** ロゴを見つけられなかったときしか出して
いなかった頃は、この状態が一番直しようがありませんでした: `logoframe` は「合致した」と
言っているので何も出ず、毎回100%がCM判定で捨てられて無音検出に落ち続けます。
自動探索が拾えるのは**画面の右上にずっと同じ縁があること**だけなので、ロゴではない縁
(常時出ている枠や字幕の下地) を覚えるとこうなります。同じ理由で「`Trim` が1つも
入っていなかった」ときも出します。

**うまくいった回はCM欄ごと出しません。** 覚え書きに `join_logo_scp` とだけ書いてあっても
読む人には何の情報にもならず、切れ目はチャプターを見れば分かります
(`format.cmNoteWorthShowing`)。**そこに何か書いてあること自体が「いつもの精度は出て
いない」の合図**になります。

### 覚えたロゴを画面で確かめる

**覚えているロゴはチューナー画面から見られます。** `.lgd` の中身を白黒の絵にして
出します (`/api/services/<id>/logo-data`)。濃さ (0〜1000) を明るさにしたもので、
いちばん濃いところが白になるように伸ばしてあります — 満点を白にしていると、薄いものが
真っ黒になって「薄い」ことしか分かりません。色は使いません (実機の `.lgd` は cb/cr が
全画素 0 でした)。

**出すのは絵と「いつ覚えたか」だけです。** 枠の座標も濃さも数字で並べていましたが、
どちらも判断の材料になりませんでした。座標は絵と枠を見れば分かりますし、濃さは
上のとおり当たり外れの目安になりません。答えは結局その隣の絵にしかありませんでした。

**違う絵を覚えていたら捨てられます** (「この絵は違う」)。`.lgd` を消すだけで、
あとは定期の見回りが覚え直します。位置を教えるのと違って**何も決めなくていい**のが
効きます — 絵が壊れていることは見れば分かりますが、正しい枠を引けるとは限りません。

**`.lgd` は高さが先に入っています** (`x, y, 高さ, 幅`)。`-logo-area` に渡した値と
突き合わせて確かめました。逆に読んでいた頃は、画面に出る枠も絵も転置されていて、
ちゃんと写っているロゴを「雑音」と読み違えていました。
