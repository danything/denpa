# CM とエンコード

**録ったあとの話。** 何をどう焼くか、CM をどう見つけるか、字幕をどう入れるか。
選ばなかった案と、実測して見送ったものも置いてあります。

| 探しもの | 見る場所 |
| --- | --- |
| 全体像 | [architecture.md](architecture.md) |
| 保存先とファイルの配り方 | [library.md](library.md) |
| CM検出に使うロゴ (`.lgd`) | [logo.md](logo.md) |

既定は AV1 + Opus + PGS の Matroska。同じ画質でファイルは小さくなりますが
時間がかかるので、AV1 を解けない相手 (古いテレビなど) 向けに **H.264 も選べます**
(設定画面)。音声・字幕・コンテナは変わりません。**どちらも 8bit** (下の実測)。

**両方を同時に選べます。** 1本の録画を AV1 (主) と H.264 (`… [H264].mkv`) で2本焼きます。
置き方と主・従の決め方は [library.md](library.md)。CM検出も字幕の絵起こしも1回で
済ませて両方に使うので、二度手間にはなりません。

**「エンコードしない」は「どちらも選ばない」ことです。** すると生TSをそのまま
保存先へ置きます (CMのチャプターも字幕トラックも付きません。どちらもエンコードの
ときに入れているためです)。別に「エンコードする」のチェックを持っていた頃は、
外したときにコーデックの選択だけが画面に残って、どちらが効いているのか読めません
でした。いまは「チェックが1つも入っていなければ焼かない」の1つに揃えています。

## 字幕は PGS 1本だけ

ARIB字幕は libaribcaption で解いて、**放送どおりに描いた絵 (PGS) を1本だけ**入れます。
以前は文字 (ASS) と4色の絵 (dvdsub) も並べていましたが、これは「PGS が作れなかった頃の
妥協」で、見た目の違う「字幕」が3本並ぶだけでした。PGS が放送どおりに出るようになった
時点で外しました (理由は下の表)。

> **放送に「絵」は流れてきません。** 乗っているのは文字と「どこに・どの大きさで・
> 何色で・背景の箱つきで」という指定で、絵になっているのは外字 (DRCS) だけ。
> テレビはそれを見て毎回自分で描いています。`-sub_type bitmap` はその描画を
> libaribcaption にやらせたもので、**それが「放送どおりの字幕の絵」**です。

| | 良いところ | 困るところ | いま |
| --- | --- | --- | --- |
| **PGS** | **描いたままが入る** (1枚256色 + 画素ごとの透明度)。外字もそのまま絵になる。Blu-ray と同じ形なので、読めるプレイヤーが多い (VLC もそのまま出せる) | ffmpeg に符号器が無いので denpa が書いている | **これだけ入れる** |
| ASS | Matroska が元から想定している形。文字なので軽く、検索もできる | **外字 (DRCS) が全部「〓」になる** (libaribcaption は ASS を組むとき DRCS を下駄記号に置き換える。`replace_drcs` はビットマップ専用)。背景の箱は影の色で代用、点滅は表せない。フォントは再生側任せ | やめた |
| dvdsub | 外字もそのまま絵になる。古い機器でも読める | **1枚あたり4色まで**。実測230色の字幕から、縁のなめらかさと話者ごとの色分けが落ちる | やめた |

**PGS は denpa が自分で書きます** (`src/lib/pgs.ts`)。ffmpeg で作れるビットマップ字幕は
どれも足りず、PGS だけは「読めるが作れない」ためです。

| | 表現力 | なぜそのままでは使えないか |
| --- | --- | --- |
| dvbsub | 256色 (`min_bpp` 2/4/8) | **ffmpeg が CodecPrivate を書かない** (実機: dvbsub は extradata 0 バイト、dvdsub は 136 バイト)。CodecPrivate を求める読み手はトラックごと捨てる。届いたとしても、ffmpeg が字幕ごとに必ず出す「消すための空パケット」で壊れる読み手がある |
| PGS (`S_HDMV/PGS`) | 256色 + 画素ごとの透明度 | **ffmpeg に符号器が無い** (復号のみ)。ただし `.sup` を**読む**ことはできるので、denpa が書いて `-c:s copy` で入れている |
| xsub | 4色 | Matroska の CodecID が無く、mkv には入れられない |

絵の取り出し口は ffmpeg の sub2video です。字幕をフィルタの入力にすると1枚ずつ
RGBA の映像フレームになるので、時刻は `showinfo` に喋らせ、絵はそのまま受け取ります
(`src/lib/server/subtitle.ts`)。画面まるごとの絵のうち**字幕のあるところだけ切り抜いて**
入れます (PGS は1秒あたりに送れる量が決まっているため)。

色は YCrCb の限定レンジで書きます。**読む側の戻し方に合わせるのが要点**で、
ffmpeg は「高さが 576 より大きい / 分からないときは BT.709、それ以下なら BT.601」で
戻すので、こちらもそう書き分けます。実測での往復のずれ:

| 書き方 | 最大のずれ (RGB) |
| --- | --- |
| 全レンジ (JPEG) の係数 | 30 |
| BT.601 限定レンジ | 39 |
| **高さで BT.709/BT.601 を選ぶ** | **1** |

(1440x1080 の実物の字幕1枚・1,555,200画素で、透明度の食い違いは0)

**同じ絵が続いたら、消して出し直さずに終わりだけ延ばします。** 絵は字幕が出ている
間ずっと1秒おきに流れてくるので、そのまま書くと同じ時刻に「消す」と「出す」が並び、
1枚30KBが毎秒増えます (実機の5分の番組で57枚。まとめると11枚 = 字幕の数そのもの)。

描くときは `-canvas_size` で画面の大きさを渡します。指定が無いと libaribcaption は
1440x1080 (PROFILE_A) とみなすので、1920x1080 で録れているものは字幕だけ横に伸びます。
フォントはイメージに入れてある丸ゴシック 1 本 (`captions.ts` の `SUBTITLE_FONTS`。ライブと録画で同じ) を指定します。

> **字幕トラックが1本も入らない録画があります。** 絵は描くものがあったときだけ出るので、
> 本編に字幕の無い番組では `.sup` が空になり、そのときは何も入れません
> (実機: 字幕の無いアニメで0枚)。

**「消せ」を拾うために ffmpeg に直しを当てています** ([patches/README.md](../patches/README.md))。
ffmpeg の libaribcaption ラッパは、字幕を**絵で受け取るときだけ**画面消去 (CS) を捨てていて、
CM に入った字幕が次の字幕まで出たままになっていました (実機で22分35秒)。
生放送も焼き込みも同じデコーダなので、ここ1箇所で両方直ります。

## トラックの名前は放送のものを入れる

**音声も字幕も、番組表と同じ言い方で名前を付けます。** 付けていなかった頃は、
プレイヤーの切り替えに「Audio 1」「Audio 2」しか出ませんでした。二カ国語や解説放送では
**どちらがどちらか分からない**のに、番組表には「主音声」「解説」と出ています。

| | 名前 | どこから |
| --- | --- | --- |
| 音声 | 「主音声 (日本語)」「解説 (日本語)」「ステレオ (日本語)」 | 番組表の `audios` (`arib.audioTitles`) |
| 音声 (デュアルモノ) | 「主音声 (日本語)」「副音声 (英語)」 | 同上。1本を左右に割るので**必ず2本** |
| 字幕 | 「字幕 (日本語)」 | ffmpeg が入口の見出しに書いた言語 (`buildPgs`) |

**番組表の行は24時間で消える**ので、音声の構成は録るときに `recordings.audios` へ
写しておきます (ジャンルと同じ扱い)。写しの無い古い録画は既定の名前
(「音声」/「主音声」「副音声」) に落ちます。

**数が食い違っても困りません。** 番組表が言っている本数と実際に入っている本数は
ずれうるのですが、ffmpeg は在りもしないトラックへの指定を黙って読み飛ばします
(実機で確認)。

**入れ物にも番組名を書きます** (mkv の title。`title.displayTitle` で `[字][デ]` などの
装飾記号を落としたもの)。テレビの VLC (Android) の履歴や通知に出るのはこれです
(再生画面の見出しは再生リンクの尻の番組名。[library.md](library.md#手元のプレイヤーで観る))。
字幕トラックには `language=jpn` と default の印を付け、**並びは映像 → 音声 → 字幕**にしてあります。
字幕がトラック0だった頃、テレビ組み込みのデマルチプレクサで字幕を選ぶと固まる症状があったためです。

### 時刻の物差しを、焼くほうと揃える

**字幕を絵にする ffmpeg には `-copyts` を渡します。** 同じ TS を2回開くのに、
何を 0 秒とみなすかが両者で違うためです。

| | フィルタに入るもの | 0 秒とみなすもの |
| --- | --- | --- |
| 焼くほう | 映像・音声・字幕 | **入れ物の始まり** (`format.start_time`) |
| 絵にするほう | **字幕だけ** | **1本目の字幕** (数え直す基準になる映像が無いため) |

食い違うのは「録画の頭から1本目の字幕が出るまで」の長さで、これがそのまま
字幕全体の前寄りになります。実機 (火アニバル 攻殻機動隊 #05) では

```text
入れ物の始まり  6115.509   最初の字幕  6125.899   → 差 10.39 秒
```

で、出来上がりでは**CMの映像の上に本編の台詞が乗っていました**。CM を切っていない
(チャプターだけの) 回だったので、ズレていることが画面ではっきり出ます。

`-copyts` を付けると showinfo が放送の時刻をそのまま喋るので、**引く数はこちらで
決められます**。`probeVideo` の `formatStart` に、下の「捨てる長さ」を足したものを
引きます (`subtitle.rebase`)。読めなかったときは引きません
(ズレる可能性は残りますが、字幕が1本も入らないよりはましなため)。

**求めた時刻が muxer に消されないよう、`.sup` の頭には「何も無い」を1つ置きます。**
ffmpeg は入力ごとに「その入力がいつ始まるか」を引いて繋ぐので、1本目の字幕が
1秒から始まる `.sup` をそのまま渡すと字幕全体が1秒前へずれます (実機で確認)。
0秒に空の構成を置いておけば引かれる数が 0 になり、こちらで決めた時刻がそのまま入ります
(`pgs.ts` の `SupWriter`)。

### 頭の音声だけの区間は、ずらさずに捨てる

TS は**音声のほうが先に始まっている**のがふつうです。そのまま焼くと出来上がりも
音声だけの区間から始まり、**1コマ目を 0 秒として数えるプレイヤー**ではそのぶん
字幕が早く出ます。

**測るのは「実際に復号できた1コマ目」です。** `stream.start_time` は最初の
*パケット*の時刻で、そこから何コマかは参照先が録れておらず捨てられます。

```text
入れ物の始まり           6115.509
start_time (パケット)    6115.872   ← これを信じると 0.363
実際に出た1コマ目 (I)     6116.439   ← 本当は 0.930   差 0.567 = 17コマ = 半GOP
```

**ずらす (`-output_ts_offset`) のでは直りません。** Matroska は負の時刻を持てないので、
下がった音声を muxer が押し戻し、全トラックまとめて元の位置に戻ります。実測:

| | 映像 | 音声 |
| --- | --- | --- |
| ずらさない | 0.934 | 0.022 |
| `-output_ts_offset -0.363` | 0.912 | 0.000 |
| **`-ss 0.930` で捨てる** | **0.000** | **0.000** |

0.363 渡して動いたのは 0.022 だけでした。**捨てれば映像も音声も 0.000 から始まります。**
捨てるのは映像がまだ無いところなので、見えるものは減りません。

捨てる長さは `encoder.headSkip` に1箇所だけ置いています。焼くほうと `.sup` を作るほうで
食い違うと、そのぶんそのまま字幕がずれるためです。再試行のときの頭捨て
(PAT/PMT が固まる前) とは理由が別なので、両方あるときは足します。

**CMのチャプターだけは、この量を引きません。** 検出は入れ物の頭から数えていないためです
(下の「チャプターを詰める量は、`-ss` と同じではない」)。

## コマ数は本編の映像から測って決める

`bwdif` の既定は `send_field` で、**1フィールドから1コマ作って 59.94p にします**。
放送は 1080i (毎秒60フィールド) なので、実写・スポーツ・報道はこれで撮られたとおりの
動きになります。ただしコマ数が倍なので、エンコードの時間もサイズもおよそ倍です。

**ffmpeg 9.0 / 9.0.1 では、60コマで焼いた長尺の音声が 20〜25 分あたりで黙って終わっていました**
(CLI の溢れ FIFO の上限。9.0.2 で FIFO ごと無くなったので直しは取り下げ。経緯と数字は
[patches/README.md](../patches/README.md))。9.0.2 で1時間超を通しで焼いた実測はまだ無いので、
次に焼いたら音声が最後まであるかを見ること。

実測 (地上波1分、AV1):

| | 所要 | サイズ | コマ数 |
| --- | --- | --- | --- |
| `send_field` (60コマ/秒) | 31.8秒 | 26 MB | 3598 |
| `send_frame` (30コマ/秒) | **16.9秒** | **15 MB** | 1799 |
| H.264 medium (60コマ/秒) | 29.2秒 | 34 MB | 3598 |
| AV1 `-preset 8` (60コマ/秒) | 59.5秒 | 27 MB | 3598 |

アニメは毎秒24コマ前後の絵をプルダウンして60フィールドに乗せているだけなので、フィールドごとに
コマを起こしても同じ絵が並ぶだけで、滑らかさは増えません。そこで**同じ絵が並ぶ素材かどうかを、
焼く前に本編から実測します** (`encoder.measureSmoothMotion`)。

**放送のTSに「本当のコマ数」は入っていません** (本番で実測):

- EIT の component_descriptor は中身が何でも `1080i` (アニメも映画も同じ)
- `avg_frame_rate` は常に 30000/1001、`field_order` は常に `tt`
- MPEG-2 の interlaced_frame もほぼ全部立ち、テレシネの印 (repeat_pict) も無い
- 縞の検出 (idet) も使えない。アニメ本編ですらプログレッシブ 0〜2% (パン・合成・ノイズで縞が出る)

唯一の見分け方が**「60コマに起こして、同じ絵が続く割合を数える」**でした。本編から30秒の窓を5つ取り、
`bwdif=send_field` → `mpdecimate` の生存率の**中央値**が閾値 (`FPS_SURVIVE`、既定 50%) 以下なら 30コマ。
本番の録画を30秒刻みで全部測った並びは、30コマのアニメ 17〜28% / 毎秒30枚が違う絵のアニメ 48% /
実写 60〜79% (下位 1/4 でも 53% 以上) です。

- **5窓の中央値。** 3窓よりアニメが閾値から遠のく (24〜31% → 17〜28%)。**下位や最小を採るのは駄目** —
  実写でも静止した窓は 42% まで落ち、動く素材を 30コマに落とす
- **閾値は 50%** (45% では 48% のアニメが 60コマに倒れていた)。実写側の余裕は 3〜10 ポイントしか
  無いので、これ以上は上げないこと
- **`-map 0:v:0` で主映像に固定。** 地上波の TS にはワンセグ (320x180 の H.264) も残っていて、
  任せるとフィルタがそちらに当たることがあった
- **CM検出があれば一番長い本編区間の中で測る。** CM は実写の 60i。最初の区間で測っていた頃は
  アバン+OP の激しい動き (57〜74%) に窓が乗り、30コマの本編 (20〜32%) を 60コマと誤判定していた
- **迷ったら 60コマ。** 本物の 60i を 30 に落とすと動きが崩れるが、逆は無駄が出るだけ

設定の「コマ数を映像から決める」を外すと実測せず**全部 60コマ**で焼きます (以前はジャンルで決めていた)。
ライブは映像が来る前に決めないといけないので、常に 60コマです。

どちらに転んだかは `recordings.fps` に書き、**番組詳細に「30コマ/秒」「60コマ/秒」の札**で
出します (ログにしか出ていなかった)。未エンコードの録画と、記録を始める前に
焼いたものには付きません。

## H.264 は crf 23 (AV1 と同じ画質)

**画質は AV1 の既定に揃えます。** 同じ番組をどちらで焼いても見た目が
変わらないようにするためで、大きさは揃えません。

**揃え方を一度間違えました** (以前の crf 24 は実写100秒1本の SSIM だけで決めた値)。
本番の録画4か所を可逆で切り出し、同じコマを両方で焼いて XPSNR で測り直したもの:

| 素材 | AV1 crf35 | h264 crf24 | h264 **crf23** | h264 crf22 |
| --- | --- | --- | --- | --- |
| 実写60コマ・忙しい所 | 35.28 dB | 34.34 (**−0.94**) | 34.93 (−0.35) | 35.53 (+0.25) |
| 実写60コマ・静かな所 | 35.36 dB | 35.23 (−0.14) | 35.64 (+0.28) | 36.05 (+0.69) |
| アニメ30コマ | 34.86 dB | 35.10 (+0.24) | 35.52 (+0.66) | 35.97 (+1.11) |
| アニメ30コマ その2 | 38.52 dB | 37.80 (−0.72) | 38.16 (−0.36) | 38.50 (−0.02) |
| | | **平均 −0.39** | **平均 +0.06** | 平均 +0.51 |

**crf 23 が AV1 の真上に乗ります** (平均 +0.06dB、いちばん外して −0.36dB)。
crf 24 は平均で 0.4dB 低く、**実写の忙しいところでは 0.94dB 低い**。
crf 22 まで上げると今度は AV1 を追い越します (平均 +0.51dB)。

> **「60コマだと H.264 のほうが小さい」の正体はこれでした。** 60コマ判定 ≒ 実写の忙しい絵で、
> そこがちょうど crf24 のいちばん外していたところでした。小さいのではなく、一段低い画質で焼いていただけです。

**SSIM で当てると 22 寄り、XPSNR で当てると 23 寄り**です (一致点は SSIM で 21.3〜23.7、XPSNR で
21.9〜24.6)。**23 は両者の間で、かつ AV1 を下回りにくいほう**。物差し1本・素材1本で決めないのが教訓です。

大きさは crf24 のときより **2割ほど増えます** (実写の忙しい所で 14.4→17.1MB、
アニメで 5.2→6.2MB)。画質を揃えたうえで比べると、AV1 との差はこうなります:

| 素材 | AV1 crf35 | h264 crf23 | H.264 は |
| --- | --- | --- | --- |
| 実写60コマ・忙しい所 | 20.7 MB | 17.1 MB | **0.8倍** (ここだけ H.264 が小さい) |
| 実写60コマ・静かな所 | 1.6 MB | 3.9 MB | 2.4倍 |
| アニメ30コマ | 2.6 MB | 6.1 MB | 2.4倍 |
| アニメ30コマ その2 | 0.8 MB | 2.1 MB | 2.7倍 |

**忙しい実写では2つの効率はほぼ互角**で、AV1 の強みは簡単な絵で出ます (そこで AV1 を crf38 に落とすと
18.7MB / 34.34dB となり、h264 crf24 とぴったり重なる)。

- **preset は medium。** slow にしても同じ画質で時間だけ 25% 増える
  (crf22 で slow 0.9757/76MB ↔ medium 0.9760/78MB)

## preset は 9・crf 35 (値は書いておく)

**書かずに既定へ任せません。** SVT-AV1 の既定は版で変わり (preset は 2.3.0 が 10、4.2.0 が 8)、
黙って入れ替わると焼く速さも大きさも変わるためです。**crf 35 は両方の版で既定のまま**です
(ffmpeg の `-crf` が既定 0 と出るのは「未指定」の番兵で、渡さなければ SVT-AV1 内部の 35 が使われる)。

### 10 は使ってはいけない値でした

長らく `-preset 10` (2.3.0 の既定の書き写し) でしたが、**4.x ではこれが「人が見る絵のための段」から
外れています** (`Svt[warn]: Non-RTC M10+ are meant for automation tooling usage. Visual artifacts may occur otherwise.`)。
上流が既定を 8 に下げたのはこのためで、こちらは時間と大きさの話だと思って留まっていました。
症状は**シーンの変わり目のブロックノイズ**。カット直後の数コマだけ大きく崩れてすぐ戻る、「たまに一瞬汚い」見え方です。

実測は実素材 (地上波アニメ 90 秒、1440x1080 を denpa と同じ道で 1920x1080 へ、
カット 22 箇所)。「カット直後」はカットのコマから 4 コマの PSNR です。

| preset | カット直後 最低 | カット直後 平均 | 全体 | 所要 | 大きさ |
| --- | --- | --- | --- | --- | --- |
| 10 | **29.74 dB** | 42.15 dB | 46.27 dB | 17秒 | 8.5 MB |
| **9** | **37.77 dB** | 43.89 dB | 46.70 dB | 20秒 | **8.1 MB** |
| 8 | 37.69 dB | 44.64 dB | 47.50 dB | 25秒 | 10.0 MB |

**9 は 10 の上位互換です。** 崩れが 8dB 戻り、全体の画質も上がり、しかも
小さくなります。増えるのは時間だけで 18%。

**8 までは落としません。** カットの崩れは 9 で戻っており (差 0.08dB)、8 が勝つのは全体の平均だけで、
その代わり **+18% 大きく +47% 遅い**。

### 他のオプションは触りません

**`scd=1` (シーン変わり目でキーフレーム) は効きません。** 4.2.0 は指定すると
こう返して無視します。「SVT-AV1 has an integrated mode decision mechanism to
handle scene changes and will not insert a key frame at scene changes」。
実際、付けても付けなくてもキーフレームの位置は 0 と 161 のままでした。

`tune` (0/2)・`enable-variance-boost`・`qp-scale-compress-strength`・`sharpness`
も同じ素材で測りましたが、**大きさを揃えると差は 0.05dB 以内**で、変える価値が
ありませんでした。固定 crf のままだと variance-boost がよく見えますが、
5割ビットを積んでいるだけです。**効くのは preset だけ**でした。

## 10bit では出しません (実測して 8bit へ)

AV1 は 10bit で出していました。**根拠がどこにも書いていなかった**ので、
測りました。素材は実機の録画から100秒 (地上波の実写)、denpa と同じ手・
SVT-AV1 2.3.0 `-preset 10 -crf 35`。画質は同じフィルタを通した元との SSIM です。

| | 所要 | 大きさ | SSIM | PSNR |
| --- | --- | --- | --- | --- |
| 10bit | 39秒 | **21.71 MB** | **0.97582** | **44.65 dB** |
| 8bit | **34秒** | 22.09 MB | 0.97472 | 44.47 dB |

**差はあります。1.7% 小さく、SSIM +0.0011 (PSNR +0.18dB)。** 8bit の素材を 10bit で
焼くと丸め誤差が溜まりにくいという、教科書どおりの結果です。

**元の放送が 8bit なのだから、8bit で出します。** AV1 10bit をハードウェアで解ける
Android 機はまだ少なく、実機 (Android TV のプレイヤー) で `1080p59.94` の AV1 10bit が
まともに再生できませんでした。2% は、観られなくなる代償に見合いません。

**既にある 10bit のファイルは焼き直しません** (生TSが無いものは焼き直せず、あるものも 2% のためでは釣り合わない)。

## GPU で焼く (Intel QSV / VA-API)

**GPU が見えれば、起動時に自分で見つけて使います。** コンテナに `/dev/dri` を渡してあれば、
`src/lib/server/hwenc.ts` が起動のたびに **`HW_DEVICES` (既定 `/dev/dri/renderD*`) に当たる口を全部拾い、
口ごとに道 (QSV / VA-API) × コーデック (H.264 / AV1) の4通りを実際に1コマ焼いて**確かめます。
`ffmpeg -encoders` で分かるのは「組み込んであるか」までで「動くか」は分からず、動くかは世代でも違う
(Arc より前は AV1 のエンコードが無い) ためです。イメージに何を入れてあるかは `Dockerfile` の ffmpeg 段の説明にあります。

結果は設定画面の「GPU」カードに口ごとに出て、**使えるものには自動で印が付きます** (外したいものだけ外す)。
グラボが2枚あれば口ごとに割り振れ、同じコーデックを焼ける口が複数あればジョブごとに先頭を入れ替えます。
使えないものの印は触れないので、GPU を挿し替えればそのまま効きます。挿し直した・権限を直したときは
「確かめ直す」で、再起動せずに見直せます。

**試す順は (口ごとに) QSV → VA-API、最後にソフトウェア**で、どの道でも「素のまま → 頭を少し捨てて」の
2回が落ちたら次へ移ります。試し焼きが通っても素材しだいで落ちることはあるので、GPU が駄目なだけで
録画が失敗にはなりません。Linux では QSV の下に必ず VA-API が居るので、速さは同じです。QSV のほうが
レート制御が豊富で Intel が手入れしているので先に使い、VA-API は QSV が初期化できない世代の逃げ道にしています。

**画質は ICQ (`-global_quality 24`) で、QSV も VA-API も、H.264 も AV1 も同じ値です。** ICQ は x264 の crf に
当たる「この画質で」の頼み方で、1〜51 の同じ物差しなので、コーデックが違っても同じ見た目になり AV1 はそのぶん
小さくなります。**手元に GPU が無いので実測はまだ**で、ソフトウェアで焼いたものと大きさが違って見えたら
`hwenc.hwArgs` の値を動かしてください (ソフトウェアの 23 を写さないのは、測らずに写すと当てずっぽうが二重になるため)。
インタレ解除と引き伸ばしは CPU のフィルタで済ませ、焼くところだけ GPU に渡します。

**QSV は amd64 のイメージだけです** (Debian の QSV まわりが amd64 にしか無い)。arm64 は VA-API だけで、
試し焼きで QSV が落ちるだけなので denpa は arch を見ていません。arm64 向けの VA-API ドライバはいま入れていない
ので、実際にはソフトウェアで焼きます (実機では未確認)。

渡し方は、Helm なら既定で `/dev/dri` を hostPath で渡してあります (`denpa.gpu.hostPath`。
そのぶん Pod は privileged。デバイスプラグインを使うなら false にして `resources.limits`
で)。Compose は `devices: - /dev/dri:/dev/dri` (compose.prod.yml のコメント。ホストに
無いと起動できないので既定では書いていません)。

## SVT-AV1 は上流をソースから組みます

**上流の 4.2.0 をソースから組んでイメージに入れています** (`Dockerfile` の `SVT_AV1_VERSION`。Debian trixie の
パッケージは 2.3.0 で止まっていて更新が来ない。静的に繋ぐので実行イメージは増えない)。上げるときに実測したもの
(実機の録画から100秒、地上波の国内アニメ、denpa と同じフィルタ、当時は 10bit。画質は元との SSIM):

| SVT-AV1 | preset | crf | 所要 | 大きさ | SSIM |
| --- | --- | --- | --- | --- | --- |
| 2.3.0 | 10 (2.3.0 の既定) | 35 | 28秒 | 5.25 MB | 0.98900 |
| **4.2.0** | 10 | 35 | **26秒** | 5.65 MB | 0.98821 |
| 4.2.0 | 10 | 36 | — | 5.27 MB | 0.98770 |
| 2.3.0 | 8 | 35 | 45秒 | 5.87 MB | 0.99133 |
| 4.2.0 | 8 (4.2.0 の既定) | 35 | 37秒 | 6.69 MB | 0.99090 |
| 4.2.0 | 8 | 37 | — | 5.77 MB | 0.99034 |

**同じ preset なら速くなり** (preset 10 で 7%、8 で 18%)、**大きさあたりの画質は変わりません** (5.25 MB どうし・
5.8 MB どうしで比べると、SSIM は 2.3.0 がわずかに上)。上げた理由は速さと上流の直しに乗り続けるためで、
焼き上がりが黙って変わらないよう、preset と crf は書いてあります (上の「preset は 9・crf 35」)。

## CM はチャプターが既定、切るなら TS の段階で

CM は既定で**チャプターを打つだけ**です。実カットは誤検出すると本編が消えるので明示的に
選びます。

### チャプターを詰める量は、`-ss` と同じではない

チャプターの時刻は焼き込む前に前へ詰めますが (`cm.shiftRanges`)、**引く量は字幕とは違います。**

**CM 検出は絵を頭から数えています。** logoframe / chapter_exe は dtvindex の索引で
TS の**映像パケットを全部**表示の順 (PTS) に並べて0から番号を振り、その番号を
`番号 ÷ fps` で秒に直します (`cm-jls.ts`)。音声だけの区間は見ていません。
一方 ffmpeg は**最初に復号できるコマより前を捨てます**。録画は GOP の途中から始まり、
頭のコマは参照先が録れていないためで、焼いたものの 0 秒はその1コマになります。
引くのは**その手前にあるコマの数 ÷ fps** です (`cm.droppedHead`)。

**時刻の差では引けません。** 録画が B から始まると、その B のあとに出るはずの P は
復号の順で前にあって録れておらず、**表示の時刻に1コマぶん穴が空きます**。索引は
穴を詰めて数えるので、時刻の差で引くと1コマ引きすぎます。実機 (令和のダラさん / 2026-09-24):

```text
入れ物の頭       69116.802
いちばん早い絵   69117.098   ← 検出の 0 コマ目
(穴)             69117.165   ← 録れていない P。索引に無い
復号できた1コマ  69117.465   ← 焼いたものの 0 秒 (I)。時刻の差は 11 コマ、手前にあるのは 10 コマ
```

**2026-09-26 に実機の9本 (TOKYO MX1 3本・BS11 3本・日テレ1 2本・TBS1 1本) で突き合わせました。** 索引 (`.dtvi`)
を作り、join_logo_scp が返した境目 70箇所で、TS のシーンチェンジ (scdet) がどのコマにあるかを見ました。

- **検出の番号は索引の番号そのもの。** カットのはっきりした 65箇所のうち 55箇所で境目 = カットのコマ、10箇所は
  1コマ前 (join_logo_scp の置き方。穴の無い録画でも出る)。残る5箇所はフェードでカットが無い
- **穴は9本中8本にあり、どれも頭の1つだけ** (尻にも1つ空くが、最後のコマのあとなので効かない)。受信の欠けで途中がずれる録画は無かった
- **時刻の差で引いていた頃は、65箇所中48箇所でチャプターが1コマ (33ms) 早かった。** コマの数で引くと、65箇所すべてで境目のコマちょうどに入る
- **焼いたものの 0 秒が B になる録画もある** (閉じた GOP で I の前の B から出る)。数えるのは「最初に復号できたコマ」より前なので、これもそのまま合う

字幕と同じ量 (`-ss` = 0.583秒) を引いていた頃は **0.416 秒 = 12.5 コマ引きすぎ**ていて、**跳んだ先が CM の途中に
着地**していました (ブチ切れ令嬢 / 2026-08-18。測った8箇所すべてで、実際のカットがチャプターの 0.415〜0.416 秒あと)。
再試行で足した頭捨て (`encodeRetrySeek`) はそのぶん本当に頭が減るので、こちらは足します。

### 切るときは TS の段階で

切るときは**エンコードの前にTSの段階で**、残す区間を `-c copy` で切り出して concat デマクサで繋ぎ、そのTSを普通に焼きます。
エンコードのフィルタ (`select`) で切っていた頃は ARIB字幕の時刻を追従させられず `-sn` で落とすしかありませんでしたが、
先に切れば**字幕もそのまま残り**、再エンコードを挟まないぶん速くもなります。`-c copy` はキーフレーム単位ですが、地上波の
MPEG-2 は GOP が 0.5 秒程度なので CM検出の許容誤差に収まります。元のTSは残るので、失敗しても戻せます。

## 中止は畳み終わってから返す

「エンコード中止」は、**ffmpeg が死んで後始末が終わるのを待ってから**返します (`encoder.cancel`)。押した人の画面は
その返事で読み直すので、待たずに返すと**押した直後は必ず何も変わらず** (まだ ffmpeg が生きていて、同じ「エンコード中
60.9%」が出る。実機、2026-09-10)、SSE の繋ぎが切れている端末では**リロードするまで永久に変わりません**でした。

**上限は5秒** (ffmpeg は SIGTERM から1秒ほどで終わる。実測 923ms / 1078ms)。間に合わなければ返して、知らせ (SSE) に任せます。
待つ前に段階の名前を「中止しています」に書き換え (CM検出のように数分かかる段階で効く)、**頼まれた後は書き換えません**。
畳むまでに通る段階が上書きして、押したのに「CMを探しています」に戻って見えていました。

**ボタンは畳み終わるまで回したままにします。** 上限で切り上げた返事で戻すと「回るのが止まったのにまだエンコード中」に
なるので、行に `isCanceling` (DB には無く、動いている間だけ) を添え、立っている間は押せない回ったボタンを出します。

**押された後の合図は聞き耳に届きません。** `AbortSignal` の `abort` は押された*瞬間*にしか鳴らないので、あとから
起こした道具は最後まで走り切っていました。中止を押したあとに無音検出 (`detectSilences`) へ落ち、字幕まで絵にして
(`buildPgs`) から畳んでいたのはこれで、**焼く前の段階で押すと何分も止まらない**原因でした。道具を起こす口
(`stream.run`・`detectSilences`・`buildPgs`) は起こす前に `signal.aborted` を見て降ります (`stream.run` は殺された
ときと同じ 143 を返す)。合図を受け取らない下調べ (ffprobe) の前にも、押されていたら降りる判定があります。

**行を先に `canceled` にする道は採っていません。** 速く見えますが、**まだ ffmpeg が元のTSを読んでいる間に削除の口が
開きます** (動いている間に出すのは中止だけ、が画面側の決まり)。

> **試験で1度騙されました。** 偽 ffmpeg は止められると即死するので、直っていなくても通っていました。
> 止められてから抜けるまでの間を本物に似せて (`trap 'sleep 2'`) はじめて、直す前の形で落ちます。

## 進み具合は焼けたコマ数から出す

画面に出す進み具合は、**ffmpeg が何コマ焼いたか** (`-progress` の `frame=` ÷ 焼くコマ数) から出します
(`encoder.encodeProgress`)。残り時間も同じ出どころ (直近30秒で何コマ焼けたか) です。出どころを混ぜると、
止まった数を動いている速度で割って「残り20時間」のような値が出ます。

焼くコマ数は**焼く前に測った入力**から出します (`expectedFrames` = 尺 × 入力の毎秒コマ数 × 60コマなら 2)。
インタレ解除は入力1コマからコマを作るので、入力が 29.97 (1080i) でも 59.94 (720p の局) でも同じ式で当たります。
CM を切るなら、切ったあとのTSを測ります。本番の録画を最後まで焼いて突き合わせたもの:

| 素材 | 見込み | 実測 | |
| --- | --- | --- | --- |
| 闇芝居 十七期 (5分26秒) | 19553 コマ | 19498 コマ | 99.7% |
| さよならララ (30分25秒) | 109412 コマ | 109374 コマ | 99.96% |

**見込みのほうが少しだけ多い**ので、バーは 99.7% あたりで頭打ちになります (終わるまで 99% で止めるので見えない)。
逆向きに外すと、終わる前に 100% と出て止まって見えます。

**要点はエンコーダの居場所を直に数えること**で、以前の2つはどちらも別のものを見ていました
(2026-09、BS-TBS の映画を libx264 で 240秒焼いた時点で、3つを同時に測ったもの):

| 物差し | 実際には何か | 言っている位置 |
| --- | --- | --- |
| **`frame=9576`** (毎秒 39.89 コマ) | エンコーダの居場所 | **2分40秒ぶん** (正しい。240秒 × 39.89) |
| `out_time_us` | mux が最後に書いたパケットの時刻。疎な字幕 (.sup の copy) が先に mux されると先に飛び、壊れた副音声が混ざるとそこで止まる (`Packet corrupt` のあと 0% のまま) | 13分10秒ぶん (`speed=3.29x` もこれ由来) |
| 入力TSの読み位置 (`/proc/<pid>/fdinfo`) | デマクサの居場所。7.4GB の映画では焼き上がり半分で読み切り、**99% に貼り付いた** | 12分30秒ぶん (RSS 1.07GB) |

**読み位置は控えとして残してあります** (`encodeProgress` の第2引数)。尺が測れなかったとき (映像の無い録画、
ffprobe が使えない環境) はこちらで出します。ログには両方を並べて書くので、**詰まったときに「デマクサだけ先に
走っているのか、本当に遅いのか」が分かります**。

## 検出方法は2つ (設定画面の「CMの探し方」)

**`silence`** — 無音とシーンの尺だけで判断。追加の依存が無くどこでも動きます。
CM が15秒の倍数で並ぶ性質で絞り込みますが、本編中の「間(ま)」を拾うことがあり、
Amatsukaze ほどの精度は出ません。

**`jls`** — Amatsukaze と同じ考え方。無音・シーンチェンジ (`chapter_exe`) に加えて
**局ロゴが出ているか** (`logoframe`) を見て `join_logo_scp` が判定します。CM 中はロゴが
消えるので無音だけより格段に確かです。これが既定です。検出できなければ
無音検出に落ちるので、これで録れなくなることはありません。引き換えに録画1本あたり
数分かかります (初めて見る局は、ロゴを覚えるぶんさらに)。時間のほうが惜しければ
設定画面で「無音だけ」に戻せます。

**一式はイメージに入っています** (`/opt/jls`)。

かつてこの移植は AviSynth+ と L-SMASH Works と Node の上に載っていて、丸ごと
抱えるのは重すぎました。いまの [tobitti0 版](https://github.com/tobitti0/logoframe)は
**dtvindex (FFmpeg) で TS を直接読める**ので、そのどれも要りません
(`WITH_AVISYNTH=no` で組んで30秒ほど)。実行役の Node アプリがやっているのも
3つのコマンドを順に呼ぶだけなので、denpa から直接起動しています。

```text
logoframe      局ロゴが出ているコマを拾う
chapter_exe    無音とシーンチェンジを拾う
join_logo_scp  その2つを突き合わせて本編とCMに分ける → Trim() の並んだ avs
```

**`join_logo_scp` だけ出どころが違います。** `logoframe` と `chapter_exe` は
tobitti0 の Linux 移植ですが、`join_logo_scp` は本家筋の
[yobibi 版](https://github.com/yobibi/join_logo_scp) (ver5.1.1) を使います。
移植版は ver4.0 (2021年) で止まっている一方、**ver5.1 で Linux が本流に入った**ので
移植を使う理由がありません。効くのは 5.1.1 の「15秒単位からの差認識が正常に
できていなかった所を修正」で、ここは CM判定の芯です。

**実行ファイルと判定規則 (`JL/`) は必ず対で採ります。** 文字コードが違い
(4.0 は Shift-JIS、5.x は BOM付きUTF-8)、取り違えると `error: wrong command in` で
**何も切らない**結果になります (実際に組んで確かめました)。

**ロゴを先に回します。** 逆にしていた頃は、`chapter_exe` が落ちた録画ではロゴを
当てられたかどうかが分からないまま無音検出に落ちていました (実機で2本。テレ東と NHK は
`chapter_exe` が音声で落ちます: `FFmpeg audio packet submission failed`)。無音検出に
落ちたときは、落ちた理由を検出の覚え書き (`recordings.cm_note`) に残します。

**`join_logo_scp` が区切れなかったときは、ロゴの在り処だけで分け直します。** `logoframe` は「どのコマにロゴが
出ているか」を別に出していて (`-oa`)、日本の地上波・BSはCMの間だけロゴを消すので、裏返せばそれだけでCMになります。
番組の構成 (提供・予告) までは読めませんが、**無音検出に落ちるよりは確か**です。実機の TOKYO MX では `logoframe` が
合致率 79.74% で5区間を正しく出していたのに `join_logo_scp` が何も返さず、無音検出で本編を60秒取り違えていました
(ロゴだけなら 20% がCMという妥当な答え)。多すぎれば捨てる (`tooMuchCm`) ので、ロゴがロゴでなかったときは無音検出へ落ちます。

**「ロゴの位置を教える口を出すか」はその覚え書きから決めます** (`format.logoUnusable`)。別の列に印を持っていた頃は、
後から条件を広げても、既に録ってある分には効きませんでした。

denpa はその avs を読んで秒の区間に直すだけで、エンコードは ffmpeg のままです (`src/lib/server/cm-jls.ts`)。
**起動は引数の配列で渡します。** `sh -c` にコマンド文字列を組んでいた頃は、番組名や局名の空白・引用符で引数が割れ、
どの段階で落ちたかも混ざった標準エラーからしか読めませんでした。

### ロゴの覚え方

**ロゴデータ (`.lgd`) は logoframe が自分で作ります。** 局名を渡すと、初めて見る局なら
その場でロゴを覚え、2本目からは使い回し、合致率が落ちたら作り直します。置き場は
放送波から拾った PNG の隣 (`data/logos/jls/<局ID>`)。

**覚えるのは CM検出のときで、録れたものをそのまま材料にします。** 以前はチューナーを30分ごとに見回り、まだ覚えて
いない局を1局ずつ5分掴んで覚えていましたが、やめました。5分の同じ場面より**30分の録画のほうが桁違いに良い材料**で
(ロゴの在り処は中身が変わるほどはっきりする)、誰も開いていない局では空きチューナーを塞ぎ、録らない局まで掴みに
行っていたためです。録る局は必ずエンコードを通るので取りこぼしません。先回りさせていたのは「1本目が自分から覚えた
ロゴで自分を判定する」のを嫌ったからですが、**弱かったのは順番ではなく在り処の推定**で、そちらを直した
(`-logo-area` を渡す) ので理由が無くなりました。

**同じ絵を映している局は1つにまとめます** (`logo-data.stations`)。放送局はサブチャンネルの枠を
常時流していて、マルチ編成をしていない間は本チャンネルと同じ絵・同じ SDT の局名が出ています
(実機では TOKYO MX1 が 23608/23609、フジテレビが 1056/1057/1058)。束ねずに並べていた頃は、
チューナー画面に「TOKYO MX1」が2つ並んでいました。覚えたら**同じ絵の局へ写します** (`share`)。
写さないと、サブチャンネルの枠で録れた番組がまた1から覚え直します。位置を教えるのも
覚えたロゴを捨てるのも、束ねた局まとめてです。束ねる鍵には**ネットワークも入れます**
(局名だけだと、たまたま同名の別系列を1つにしてしまいます)。

**覚え方の閾値は既定のままにしてあります。** 一度は締めましたが、実機で測って戻しました。

| 渡すもの | 既定 | denpa | 実測 |
| --- | --- | --- | --- |
| `-logo-edge-threshold` | 40 | **40** | 60 にすると TOKYO MX が覚えられない |
| `-logo-match` | 10 | **10** | 上げる根拠が無かった |
| `-logo-samples` | 600 | 600 | 覚えるのに見るコマ数 |

60 に上げると探し当てる場所はむしろ正確 (`1244,62,136,44`) ですが、そこから作る推定が「有効な画素が少なすぎる」と
弾かれます (MX のロゴは**半透明の細い白文字**)。`-logo-match` を上げたのは「雑音を覚えたまま作り直されない」のを
避けるためでしたが、**その雑音はこちらの読み間違い**でした (`.lgd` の幅と高さを逆に読んでいた。下の「覚えたロゴを画面で確かめる」)。

**一度覚えたものは、薄くても十分よく当たります。** 実機の MX1 の `.lgd` は 158×48・いちばん濃いところ 252/1000・
枠の中のロゴの画素 12% ですが、28分の録画で合致 93.28%、別の録画でも 79.74%。**濃さは当たり外れの目安に
なりません** (NHKEテレ1東京は 512/1000・22%)。

外れるのは「覚えたてのロゴで判定した回」で、そこは `tooMuchCm` が捨てます。
**閾値を振っても覚えられない局はあります。** 空から覚え直す実測では、
`-logo-edge-threshold 20`・`-logo-samples 3000`・`-logo-bg-threshold 30` の
どれでも `no persistent edge` でした。**効くのは閾値ではなく在り処を渡すこと**で、
それは自分で割り出します (下の「ロゴの在り処はこちらで割り出す」)。
それでも当たらなければ、画面から手で囲ってもらいます。

### ロゴをどれだけ当てにするか

**ロゴをどれだけ当てにするかは設定画面から変えられます** (`logo_level`、既定 6)。
`join_logo_scp` は無音・シーンチェンジとロゴを突き合わせて番組の構成を推測しますが、
その推測でロゴをどれだけ優先するかがこれです。ロゴが正しいのに区切れないなら上げ、
覚え違えているようなら下げ、1 でロゴを使わなくなります。

渡し方は `-set logo_level N` です。規則ファイルの中は `Default logo_level 6` で、
**`Default` は未定義のときだけ効く**ので、先に決めたほうが勝ちます。書き換えた写しを
渡していた頃は、規則が `JL/` の外へ出て隣のファイルを見失っていました
(`warning: not found setup-file`)。**規則は置いたまま、変えたい1つだけを外から渡します。**

判定規則そのものも見ました。`JL_標準`・`JL_MBS`・`JL_構成30分単位` は同じ答えを
出しますが、**`JL_ATX` は `Trim(0,50310)` = 何も切らない**という答えになります。
既定の `JL_標準` のままにしておきます。

### ロゴの在り処はこちらで割り出す

**logoframe の自動検出は画面全体を見ます。** 半透明の細いロゴだと、本物より強い縁が
画面のどこかに必ずあるので、そちらを掴んで降ります。テレ東の実素材では
**家具の縁 (`1004,216`)** を「恒常的な縁」として選び、
`The initial logo estimate contains too few active pixels` で失敗していました。
テレ東で `no persistent edge` / `too few active pixels` が続いていたのはこれです。

**透かしは隅にしか出ません。** 画面全体を探す必要が無いので、**位置だけこちらで
出して `-logo-area` で渡します** (`src/lib/ts/logo-area.ts`)。判定そのものは
logoframe のままです。位置さえ渡せば合致 99.9% が出るので、置き換える理由がありません。

探し方は**コマをまたいだ画素ごとの中央値**です。番組のあちこちからコマを集めて
中央値を取ると、中身は場面ごとに変わるので滲んで消え、**毎コマ同じ所に重なって
いるロゴだけが輪郭を保ちます**。その中央値画像に Sobel をかけ、いちばん強い
縁 1% のかたまりを取ると、それがロゴです。

**「動かなさ」では駄目でした。** 半透明の重ねは `画素 = (1-α)×中身 + α×ロゴ色` で
振れ幅が縮む、という筋で MAD を測りましたが、実素材ではロゴの所が `46.4`・
隅全体の中央値が `60.5` で**差が小さすぎ**ました (テレ東は α が小さい)。
中央値に残る輪郭のほうが、薄いロゴでもはっきり出ます。

実測 (テレ東・30分から 83 コマ、1440x1080):

| 渡した枠 | logoframe の結果 |
| --- | --- |
| 自動 (今まで) | **失敗** (`1004,216` を掴む) |
| **内製が出した `1296,35,124,58`** | **合致 99.93%** |
| 手で当てた `1290,20,140,80` | 合致 99.96% |

**コマは散らして渡します。** 90秒ぶんだけ渡した試作では中身が滲みきらず、
その場面の輪郭をロゴとして拾って外しました。

**枠が空のときだけ書きます** (`services.logo_area`)。画面から手で教わったものが
あればそちらが勝つので、合っていなければ囲い直せます。

#### 外したら、無かったことにする

**この割り出しは外すことがあります。** 実機の TOKYO MX1 では、半透明の細い「TOKYO MX1」の文字
(`x≈1240〜1380, y≈75〜100`) ではなく背景の**窓枠の縁**を掴んで `1059,39,129,144` と書き、logoframe は
`too few active pixels` で降りました。**その局は枠を渡す前まで自動検出で当たっていた** (4本続けて成功) ので、
当たっていたものを壊したことになります。

そこで**枠を渡して転んだら、渡さずにもう一度**回します。それで通れば枠を捨てて `logo_area_auto = 2` (割り出したが
外れた) を立て、以降その局では**二度と割り出しません** (捨てるだけだと、次のエンコードで同じ絵から同じ枠を出して転ぶ)。
**誰が入れた枠かは問いません。** 渡すと転び、渡さないと通るなら、その枠は間違っているためです。人が教えたものだったときは
画面が「自動」に戻るので囲い直せます (ログにも出す)。

#### 言い切れないときは、出さない

**外すのは、ロゴと張り合う「動かない縁」が同じ隅にあるときです。** 窓枠 (MX1)、
番組が出し続けるテロップ、動かないセット。どれも中央値にロゴと並んで残ります。
そうなると**いちばん大きいかたまりが強い縁を独り占めしません**。当たるときは
ロゴが上位 1% の縁のほぼ全部を持っていきます。

そこで、選んだかたまりが上位 1% の縁の**半分に届かなければ、その隅は飛ばします**
(`EDGE_SHARE`)。どの隅も駄目なら `null` で、logoframe の自動検出に任せます。
枠は空のままなので、**次の録画でまた割り出します**。

実測 (実機の録画 4局9本。散らした 60 コマの組を1本あたり8通り、続いたコマ 40 枚
= 番組の 1/3 の窓を5つ。当たり外れは `.lgd` の枠 = 目視でロゴと確かめたもの の
中心が入るかどうか):

| 局 (本数) | 本番と同じ散らし方 | 取り分 (当たり) | 取り分 (外れ) |
| --- | --- | --- | --- |
| BS11 (3) | 当たり 2本 / `null` 1本 | 0.35〜0.99 | — |
| TBS1 (1) | 当たり | 0.84〜1.00 | 0.21 (窓1つ) |
| TOKYO MX1 (3) | 当たり 3本 | 0.23〜1.00 | 0.11〜0.36 |
| 日テレ1 (2) | 当たり 1本 / **外れ 1本** | 0.46〜0.95 | 0.12〜0.46 |

全部で 108 回、当たり 89・外れ 19。**外れは全部 0.46 以下**で、当たりの多くは
0.6 以上でした。0.5 で切ると外れ 19 → 1、当たり 89 → 78 (残り 11 は `null`)。
本番と同じ散らし方の 72 回に限ると、外れ 10 → **0**、当たり 56 → 49 です。

| 外し方 | 何が起きていたか |
| --- | --- |
| 日テレ1 (アニメ) | ロゴ「日テレ / NIPPON TV」の下の中身と繋がって縦が上限を超え、右上を飛ばして**左上のがらくた**を掴んだ (取り分 0.22) |
| 日テレ1 (55分の番組) | 映画の宣伝テロップが半分以上のコマに出ていて、ロゴより大きなかたまりになった (0.35) |
| TOKYO MX1 (アニメ) | ロゴの輪郭が薄く、背景の滲み残りと取り合った。同じ録画の散らし方違いで 当たり/外れ が入れ替わる (0.11〜0.38) |

**比 (`EDGE_RATIO`) では分けられませんでした** (ロゴの無い隅でも上位 1% は中央値の 4〜6 倍出る)。**2番目のかたまりとの比**
(MX1 の当たりで 0.88 まで上がる) も、**前半と後半で枠が揃うか** (揃ったまま外れる) も、外れを分けませんでした。

**まだ外すもの:**

- **ロゴより強く大きい動かない縁**は、取り分でも止まりません。MX1 の末尾 1/3 だけを見た窓で1回、エンディングの著作権表記を
  掴みました (録画全体に散らす本番の取り方では出ていない)。ここは「外したら捨てる」作り頼みです。MX1 で窓枠を掴んだ録画
  そのものは残っておらず、その回の取り分は測れていません
- **黒帯のある映画** (BS11) は帯の縁がロゴと繋がって横が上限を超え、`null` になる (外れもしないが、当たりもしない)
- 確かめたのは右上に出す4局で、**テレ東の録画は手元に無く**、閾値を決めた局で取り分がいくつかは見ていない (枠は既に入っているので、いまは効かない)

### 位置を教える

**局ごとの入れ物に分けてあります** (`logo-data.logoRepo`)。`-logo-area` が効くのは**ロゴを覚えるときだけ**で、
既に覚えたものがあれば合致率が落ちるまで作り直さないので、位置を教え直したら丸ごと捨てる必要があるためです
(logoframe は局名を `_E7_B7_8F` のように潰してファイル名に埋めるので、こちらから名前を組み立てても当たる保証がない)。

**囲ってもらう枠は広めに。** 実機の TOKYO MX で、文字ぴったりの `146×24` は「有効な画素が少なすぎる」と弾かれ、
まわりを空けた `200×70` で初めて覚えられました (`uniform=98 logo=77 active=786`。まわりの背景も見ているらしい)。

自動で位置を見つけられない局 (薄いロゴ、動くロゴ) は、**録画一覧に「ロゴでのCM判定に失敗」と出し、無音検出に落として録り続けます**。

**教える口はチューナー画面です。** ロゴは録画ごとではなく局ごとの話なので (録画の詳細に置いていた頃は、同じ局の録画が
並ぶたびに同じことを聞かれているように見えた)。その局の録画から1コマを**放送どおりの縦横比**で出して**ロゴを四角で囲って**
もらい、座標は記録されているコマの大きさ (地上波のHDなら 1440×1080) へ戻して `services.logo_area` に覚え、次に覚えるときに
`-logo-area` として渡します。

### 半分以上がCMなら捨てる

**番組の半分以上がCM判定になった結果は捨てます。** ロゴを覚えたての回など、
`join_logo_scp` が「頭の2秒だけ本編」のような結果を返すことがあり、実機では30分アニメ
2本が丸ごとCM扱いになっていました (`Trim(0,59)` の1つだけ = CM 2秒〜1802秒)。
無音検出と同じ判断で、本編を削るよりCMが残るほうが被害が小さいためです。

**ffprobe の出力は鍵で読みます** (`cm.fields`。`-of default=nw=1` の `key=value` を引き、同じ鍵は最初のもの)。`Trim` はコマ番号なので
秒に直すのに fps が要りますが、**1本のTSに局が何本も乗っている** (TOKYO MX は MX1 と MX2) と `-select_streams v:0` でも番組ごとに
同じ行が並び、`-show_entries` の順でも返りません。位置で受けていた頃は分子の 30000 や幅の 1440 を fps と採り、「100%がCM」で
無音検出へ落ちていました (実機の録画34・35・38。ロゴは正しく当たっていたので、画面からは**ロゴが悪いようにしか見えなかった**)。
尺と一緒に1回で測って (`probeVideo`)、`detectWithJls` へ渡します。

**捨てたときも位置を教える口を出します。** logoframe は「合致した」と言っているのに毎回100%が
CM判定で捨てられる状態は、ロゴを見つけられなかったときしか口を出していなかった頃、一番直しようが
ありませんでした。logoframe が覚えるのは「ずっと同じ所にある縁」なので、ロゴではない縁
(常時出ている枠や字幕の下地) を覚えるとこうなります。「`Trim` が1つも入っていなかった」ときも同じです。

**うまくいった回はCM欄ごと出しません。** 覚え書きに `join_logo_scp` とだけ書いてあっても
読む人には何の情報にもならず、切れ目はチャプターを見れば分かります
(`format.cmNoteWorthShowing`)。**そこに何か書いてあること自体が「いつもの精度は出て
いない」の合図**になります。

### 覚えたロゴを画面で確かめる

**覚えているロゴはチューナー画面から見られます。** `.lgd` の中身を白黒の絵にして
出します (`/api/services/<id>/logo-data`)。濃さ (0〜1000) を明るさにしたもので、
いちばん濃いところが白になるように伸ばしてあります。満点を白にしていると、薄いものが
真っ黒になって「薄い」ことしか分かりません。色は使いません (実機の `.lgd` は cb/cr が
全画素 0 でした)。

**出すのは絵と「いつ覚えたか」だけです** (座標は絵と枠を見れば分かり、濃さは当たり外れの目安にならない)。
**違う絵を覚えていたら捨てられます** (「この絵は違う」)。`.lgd` を消し (同じ絵の局に写したぶんも)、その局の次の録画を焼くときに
覚え直します。位置を教えるのと違って**何も決めなくていい**のが効きます。絵が壊れていることは見れば分かっても、正しい枠を引けるとは限りません。

**`.lgd` は高さが先に入っています** (`x, y, 高さ, 幅`)。`-logo-area` に渡した値と
突き合わせて確かめました。逆に読んでいた頃は、画面に出る枠も絵も転置されていて、
写っているロゴを「雑音」と読み違えていました。
