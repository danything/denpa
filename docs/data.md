# どこに何を持つか

エージェントと denpa は同じものを二重に知りうる。どちらが持つかを決めておかないと、
画面と実際が食い違ったときにどちらが正しいか分からなくなる。

**分け方は1つだけ。「機材の今」はエージェントに都度聞き、
「電波から読んだもの」と「後から要るもの」は denpa が自分のDBに持つ。**

**エージェントは中身を読まない** (NIT も SDT も EIT も解かない。[agent.md](agent.md))。
読むのは全部こちら側で、足場は `src/lib/ts/` にある。

## エージェントに都度聞くもの

denpa は写さない。聞けなければ、その部分だけ出さない。

| もの | 口 | 使うところ |
| --- | --- | --- |
| チューナーの空きと、いま誰が掴んでいるか | `/denpa/tuners` | 予約の衝突解決、チューナー画面 |
| 選局できるチャンネル (スキャンの結果) | `/denpa/channels` | 局の取り込み、番組表集め、チューナー画面 |
| スキャンの結果を預ける | `PUT /denpa/channels` | チャンネルスキャン |
| 繋いである機材を書き換える | `PUT /denpa/tuners` | チューナー画面 |
| 放送そのもの | `/denpa/stream?type=…&channel=…` | 録画、番組表集め、ロゴ収集 |
| カードリーダーの状態 | `/denpa/card` | チューナー画面 |

**写さない理由は、写した瞬間に嘘になるから。** チューナーの空きは秒で変わるし、
チャンネル定義は「いま何を選局できるか」そのものなので、denpa 側の写しを見せると、
スキャン直後なのに古い顔ぶれが出る。

**掴み方は1つしかない。** 物理チャンネルを丸ごと開くだけで、「サービス単位」
「番組単位」のような開き方は無い。局を選り分けるのは denpa
(`ts/service-filter.ts`)、番組の切れ目を見るのも denpa (`ts/eit.ts`)。

## denpa が持つもの

`DENPA_DB` の SQLite。ロゴだけは PNG のままファイル (`data/logos/`)。

| もの | どこから | なぜ持つか |
| --- | --- | --- |
| 局 (`services`) | エージェントの `/denpa/channels` (元は SDT) | 局が消えても、その局の録画は残る。**行は消さず、直近の取り込みで見かけなかったものは画面に出さない** (`CURRENT_SERVICES`) |
| 番組表 (`programs`) | **放送波の EIT を denpa が自分で読む** | 下記 |
| 局ロゴ | **放送波の CDT / データカルーセルを denpa が自分で読む** | 下記 |
| 予約・録画・ルール・設定 | denpa 自身 | エージェントは何も知らない |

局の内部ID (`services.id`) は `networkId * 100000 + serviceId`。番組のIDも同じで、
`局の内部ID * 100000 + event_id`。**この作り方は変えられない。** 録画も予約も
これを参照しているので、変えると過去の録画が辿れなくなる。

### 番組表を写している理由

電波に出ているのは「いま流れている番組表」だけで、放送が終われば消える。
denpa が要るのはそこではない。

- **予約は番組表より長生きする。** 録画が終わったあとも「何を録ったのか」は残る
- **録画に付ける名前と概要は、録ったときの値で固定したい。** 番組表は放送直前まで
  書き換わるので、後から引き直すと別の名前になることがある
- **ルールの判定と衝突解決は SQL でやる。** 数千件の番組に対して JOIN と索引で
  一気に当てる
- **チューナーが塞がっていても画面は出る。** 番組表と予約一覧は読めるべきもの

### 番組表の集め方

**番組表を持っているのが denpa なので、集め方もこちらで決められる。**

| | |
| --- | --- |
| 並列 | チューナーが**空いているだけ**並べる |
| 周期 | 30分ごとに「集め直すべき局」を選び直す |
| 順番 | **番組表が薄い局から** |
| 打ち切り | **EIT 自身が「どこまであるか」を言っている**ので、揃った時点で離す |
| 録画中 | 同じチャンネルなら**相乗り** (チューナーは増えない) |

集め終わりの判定は `ts/eit.ts` の `ScheduleProgress`。EIT のセクションは8本ずつの
セグメントに分かれていて、`segment_last_section_number` が「このセグメントで
実際に使っている最後の番号」を言う。**使っていない番号は永久に来ない**ので、
そこまで揃えばそのセグメントは終わり。これを見ずに「0〜last_section_number が
全部」で待つと、いつまでも終わらない。

同じことが `table_id` にもある。1つの `table_id` が受け持つのは4日ぶんで、
基本は `0x50` から、詳細は `0x58` から始まる。8日ぶんの放送なら実際に流れてくるのは
`0x50` `0x51` と `0x58` `0x59` だけで、**`0x52`〜`0x57` は永久に来ない**。
`0x50` から `last_table_id` まで全部を待っていた頃は、詳細を積んでいる局が一度も
「揃った」にならなかった。

**版 (`version_number`) も `table_id` ごとに別々**に振られる。局に1つだけ持っていた
頃は、基本と詳細を行き来するたびに数えたものを全部捨てていた。

**もう過ぎた時間帯のセグメントは流れてこない。** セグメントは 0:00 から3時間ずつの枠で、
`table_id` と節番号から枠の時刻が決まる (`0x50` が当日 0:00 から4日ぶん=32枠、`0x51` がその次)。
「空でも先頭の1本は来る」として待つと必ず取り残される。実機では14チャンネルが全部上限の
600秒を使い切り、欠けはどの局も 0:00 から今までの枠で、時計が進むと1つ増えた (電波の欠けでは
起きない形)。過ぎた枠の番組は、まだ未来だった数日前に取り込んである。

「見えていない先頭は飛ばす」という時計を使わない直し方は**採らない**。カルーセルの途中から
拾うと、まだ来ていないだけの先頭まで飛ばして `0x51` を揃ったことにし、4〜7日先が丸ごと落ちる。

**「揃った」で閉じるのは denpa だけ** (よそは時間で打ち切る。Mirakurun も版は `version[table_id]`)。
だから判定が間違っていると、開きっぱなしのうえ先の日ほど題名が埋まらない (実機の TBS1 は
3〜5日後が 0) 形で黙って取りこぼす。

| いつ | 何を |
| --- | --- |
| 起動直後に1回 | 番組表を集める。薄い局から行くので、数分で画面に出る |
| 30分ごと (`EPG_COLLECT_INTERVAL`) | 集め直すべき局を選び直す |
| 1分ごと (`CHANNEL_SYNC_INTERVAL`) | **局だけ**を取り直す (スキャンの結果はここで届く) |
| **録画している間ずっと** | そのチャンネルの EIT は只で読める。5分ごとに書き出す |
| 誰かがチューナーを開いたら | その選局に**相乗り**して局ロゴを拾う。ロゴが**無い/1週間より古い/(地上波で) 小さい版しか無い**局だけが対象 |
| 録画を焼くとき | CM検出用のロゴ (`.lgd`) をその録画から覚える。**チューナーは掴まない** ([logo.md](logo.md#cm検出用のロゴは録ったものから覚える)) |
| スキャンが終わったら | 局を取り込み直して、番組表を集め直す |
| 「番組表をいますぐ集める」を押したら | **全チャンネルを、録画とライブ以外からは取り上げる強さで** (下記) |

「集め直すべき局」は、**番組表が3日先まで埋まっていない** (`EPG_MIN_COVERAGE`) か
**6時間行っていない** (`EPG_CHANNEL_INTERVAL`) もの。前者は再起動しても分かるので、
Pod が入れ替わっても全チャンネルを回し直さない。

**ただし行った直後は行き直さない** (`EPG_CHANNEL_RETRY`、既定2時間)。実機の CS には開いても
EIT が1件も来ないチャンネルが4つ (22局) あり、「薄いから行く」だけでは30分ごとに選ばれて
毎回上限 (`EPG_CHANNEL_TIMEOUT`) まで開きっぱなしだった。掴めなかった回は数えない。
録画に譲っただけの局まで休ませると番組表が古くなる。

**番組表に出てこない局 (データ放送・ワンセグ) は「薄い」と数えない。** 数えていた頃は、ほぼ全局が
これを積んでいる地上波が丸ごと毎周回の対象になっていた。

**同じ TS を指す枠は1回だけ開き、「最後に集めた時刻」は局から引く** (下記「相対番号の穴」)。

**開くのはチューナー1本につき1人**で、種別をまたいで1つの列を引く。種別ごとに本数ぶん並べて
いた頃は、BS と CS を同時に集めると衛星の2本を二重に数え、溢れたぶんが 409 で落ちていた。

### 衛星の番組表 — 1中継でも取れるが、**TS ごとに開きます**

**BS はどの中継にも他の中継ぶんの番組表 (他TS: `0x4F` / `0x60-0x6F`) が流れています。**
denpa は自TS ぶん (`0x4E` / `0x50-0x5F`) だけ読み、他TS ぶんは捨てています (`ts/eit.ts`)。
捨てているものを数えました。

#### 実測 (実機 / BS03_0 と BS05_1 に相乗り / 2分 / 372 MB)

| 何 | セクション | 番組 | TSID | 局 | いちばん先 |
| --- | --- | --- | --- | --- | --- |
| `0x4E` いま/次 (自TS) | 199 | 199 | 2 | 4 | 1 日先 |
| `0x4F` いま/次 (他TS) | 1089 | 1041 | **26** | **48** | 1 日先 |
| `0x50-57` 番組表 基本 (自TS) | 230 | 711 | 2 | 3 | 7 日先 |
| `0x58-5F` 番組表 詳細 (自TS) | 70 | 170 | 2 | 2 | 7 日先 |
| `0x60-67` 番組表 基本 (他TS) | 5427 | **18311** | **26** | **43** | **7 日先** |
| `0x68-6F` 番組表 詳細 (他TS) | 111 | 200 | 3 | 3 | 7 日先 |

**2分で 26 TS・43 局ぶんの番組表が7日先まで来ます** (いま denpa は、写しの枠を落とした 26 TS を
1つずつ選局し直して集めています。下記)。ただし詳細 (`0x68-6F`) はほとんど来ません
(5427 対 111)。他TS ぶんに付くのは番組名と概要までで、`extended_event_descriptor` (出演者など) は
自分の TS ぶんしか流れていない、と読むのが妥当です。CS は別ネットワークなので別に測る必要があります
(上の TSID はすべて BS)。

**やらない。詳細を全局ぶん取るほうを選びました。** 1中継で済ませると、自動予約ルールの
「詳細説明まで広げる」が BS で当たらなくなります。基本だけ先に入れる手も、あとで詳細に
上書きされるまで詳細の無い番組が出る (番組名が同じなので直ったことにも気付けない) ので採りません。
空くチューナーより番組表の中身を取り、代わりに同じ TS を二度開かないようにしました。

#### 相対番号の穴 — 同じ TS を指す枠が9つあった

衛星は `BS01_0` のような**相対番号**で選びますが、何本乗っているかは中継ごとに違い、
**無い番号を指すと復調器は先頭の TS を返します** (断らない)。実機のスキャン結果 35 枠のうち
9 枠が既知の TS の写しでした。

| 枠 | 実体 |
| --- | --- |
| `BS01_3` | `BS01_0` (16400) |
| `BS03_3` | `BS03_0` (16432) |
| `BS05_2` `BS05_3` | `BS05_0` (17488) |
| `BS09_2` `BS09_3` | `BS09_0` (16528) |
| `BS13_3` | `BS13_0` (16592) |
| `BS21_3` | `BS21_0` (18256) |
| `BS23_3` | `BS23_0` (18288) |

**取りこぼしではありません。** 残った 26 TS は、上の他TS 調査で放送自身が名乗った 26 TS と
完全に一致します。

**スキャンで落とし (`twinOf`)、開く側でも落とします (`withoutTwins`)。** 衛星の1周が
35 → 26 回になります。開く側でも要るのは、控えを書いたのが古いスキャンだと写しが残るため
です (実機の `channels.json` がそうでした)。しかも `services.channel` には最後に取り込んだ枠の
名前が1つしか入らないので、残った9枠は永久に「一度も集めていない」ことになり、周回の
たびに開かれていました。だから「最後に集めた時刻」は枠ではなく局から引きます。

### 入れたばかりのとき — 「番組表をいますぐ集める」

普段の番組表集めは弱い部類 (`EPG` = 3) で開き、録画・ライブ・スキャンに譲る。それで正しいが、
**入れた直後は番組表が空**で、そこでスキャンが動いているといつまでも画面に何も出ない
(ロゴ (1) には普段から勝つ)。

チューナー画面のこのボタンを押している間だけ **優先度 8** で掴む。録画 (10) とライブ (9) からは
取り上げないが、スキャン (5) からは取り上げる。選り好みもせず、上の2条件を無視して全チャンネルを
薄いほうから回る (集め終えた直後に押して1本も回らないのでは押した意味が無い)。
走っている周回があれば、その回を強くする。開くのは1チャンネルずつなので次に開くところから
効き、仕切り直すより早い。

### 録画中の番組表はただで手に入る

録画は物理チャンネルを丸ごと開いているので、その EIT も一緒に流れてくる。**読んで捨てる理由が
無い**ので5分ごとに書き出し、番組表集めがそこへ行く手間を省く。延長への追従も同じ流れから来る
([下記](#放送の延長に追従する))。

### 消えた局の持ち物は片付ける

取り込みで見かけなかった局は、**番組表を消し、まだ始めていない予約を取り消す** (一覧から戻せる)。
置いたままにしていた頃は、もう選局できない局の番組が数万件残って検索に引っかかり続け、予約は
始まるのを待って失敗していた。局の行そのものは残す。消すとその局の録画や過去の予約が
辿れなくなる (画面から外すのは `CURRENT_SERVICES`)。映像の無い局 (データ放送・ワンセグ) だけは、
何も紐付いていないので行ごと消す。

- **1回見かけなかっただけでは片付けない** (`SERVICE_FORGET_AFTER`、既定30分)。1回で決めていた
  頃は、エージェントから欠けた一覧が返った拍子に現役の局の予約が44件まとめて取り消された
- **1局も取れなかった回では何もしない。** 起動直後や不調で空が返ることはあり、「全部消えた」と
  読むと番組表が丸ごと消える

### チャンネルスキャン

**画面の「チューナー」から実行します。** 走査は Mirakurun に合わせてあります。

- 地上波 13〜62ch を総当たり、BS は 01〜23 の各4スロット、CS は 02〜24ch
- 1チャンネル最大30秒。**NIT と SDT が両方揃って**受信できたとみなします (SDT だけでは
  どのネットワークのものか分からず、設定に書けない)。局名も SDT から `ts/aribtext.ts` で読みます
- 録るに値するサービス種別だけ残します
- **回すのは denpa です。** 1チャンネルずつエージェントに選局を頼み、流れてきた TS を読みます。
  エージェントに読ませると、ARIB の文字符号から局の選り分けまで2箇所に持つことになります
- チューナーの台数ぶん並べます。**録画中でも実行できます。** 選局は取り合いに乗るので、
  録画中のチューナーが使われないだけです (空きが無ければ待つ。飛ばすとそのチャンネルが設定から消える)
- **途中で中断できます** (十数分かかる)。中断したときは設定を書き換えません。途中までの結果で
  上書きすると、まだ回っていない局の定義が消えます

失敗の理由は「何も来なかった」(配線・デバイス指定を疑う) と「電波は来たが NIT/SDT が揃わなかった」
(受信環境を疑う) に分け、エージェントが返した選局の失敗理由も1行添えます。**揃わなかった
チャンネルだけもう一度回します。** NIT は10秒に1回しか来ないので、選局が落ち着くのが遅れると
1回も入らないことがあります。

1チャンネル読み終えたら**接続ごと切ります**。エージェントはそれを合図に選局を畳みます
([agent.md](agent.md#選局は読み手が切るまで終わらない))。畳みそこねると、以降が全部
「受信できませんでした」になります。

**探した種別だけを差し替えます** (地上波だけのスキャンで全部を置き換えて BS と CS が消え、
BS の予約が録れなくなったことがある)。**1件も見つからなければ失敗**として、今までの局を消しません。

見つけた顔ぶれは `PUT /denpa/channels` でエージェントに預けます。読んだのは denpa ですが、
控え (`channels.json`) はエージェントが持ちます。アンテナに何が映るかは機材ごとの話で、
エージェントを増やせば顔ぶれも変わるからです。**局を増やすのはスキャンだけ**で、番組表を何回
集め直しても増えません。預かったエージェントは何も再起動せず、`channels` を知らせるだけです
(掴んでいる録画も切れない)。取り込み直して番組表を集め直すのは denpa です。

### 時刻合わせ (TDT / TOT) は持たない

放送波には時刻 (TDT / TOT) が流れていて、それと自分の時計を突き合わせる作りの
ものもある。denpa は**やらない**。録画の開始と終了は壁の時計で決めていて、
放送波の時刻を基準にしているところが無い (使うのはライブの「放送から N秒」の
表示だけ。[stream.md](stream.md#遅延は2つある))。ホストの時刻が合っている
ことのほうが大事で、そちらは NTP の仕事。

### 知らせはエージェントから来る

エージェントは起きたことを **`GET /denpa/events`** (SSE) で流している。

| イベント | denpa の使い道 |
| --- | --- |
| `tuners` | チューナー画面を更新する。開いた選局に**相乗り**してロゴを拾う |
| `channels` | 局が入れ替わった。取り込み直して番組表も集め直す |

スキャンの進み具合はここに乗らない (**回しているのは denpa 自身**なので、自分の画面へ直接流す)。
途切れたら繋ぎ直すが、黙って止まる可能性までは消せないので、**定期実行は保険として残してある**。

**黙っている間もエージェントは 30 秒ごとにコメント行 (`: keep-alive`) を流し、繋いだ時点で
ヘッダも送る。** これが無かった頃は最初の知らせまで 1 バイトも来ず、Bun の `fetch` が黙った接続を
5 分で切るので、深夜に選局が 5 分止まると「チューナーに繋がりません」→「繋がりました」が
1 時間おきに鳴っていた。

### 自動予約は「番組表に当て直す」

ルールから予約を作るところは、**足すだけでなく外れたものを消します。** 番組表を取り込み直す
たびに当て直します (足すだけだった頃は、条件から外れた予約を消す手立てが「取り消し」しか
ありませんでした)。

**消すのであって「取り消し」にはしません。** 取り消しは*人が押したこと*の記録で、ルールはそれを
二度と作り直しません。番組表が動いただけのものを取り消しにすると、条件に戻っても永久に立たなく
なります。

**取り消しは放送単位で効きます** (物理チャンネル・題名・開始時刻 ±10 分。`rules.ts` の
`canceledBroadcasts`)。番組 id だけで当てていた頃は、枝番違い (23608 / 23609) や別の event_id で
載り直した回が立ち直って録れていました。ルールを消すと取り消しの記録も消します (残していた頃は
「ルール: (削除済み)」が実機で149件並びました)。

**手違いで消すほうが、余分に録るより高くつきます。** 引っ込めないものは次のとおりです。

- **手動の予約と、録り始めたもの**
- **番組表からその番組ごと消えているとき**と**題名が空の番組**。「条件から外れた」のか
  「まだ読めていない」のか区別が付きません (題名が空は実機で 23,000 件中 11,000 件)
- **もうすぐ始まるもの** (`RULE_RETRACT_GRACE`、既定1時間)。番組表は直前まで書き換わる
  ([新] が付く、サブタイトルが入る、誤字が直る) ので、その拍子に外れても録っておきます。
  ただし**ルールごと消された/止められたぶんは直前でも引っ込めます** (人が押した結果なので)

**ルールを足したときは、そのルールしか見ません。** 新しいルールは他の予約を外せないので、
全ルール × 全番組 (実機で 318 × 25,608) を回し直す理由がありません。

#### 同じ放送は1本だけ — 枝番の局に気をつける

局は分割放送のために枝番を持ちます (TOKYO MX なら 23608 / 23609。SDT の名前はどちらも
「TOKYO MX1」)。分割していない間は同じ回が両方に載り、実機ではルールが両方に当たって2本録れ、
**2つのエンコードが同じ名前のファイルへ同時に書いて中身が壊れました** (片方は `ENOENT`、残ったほうは
復号で145行のエラー。焼き直すと0行)。

そこで同じ物理チャンネル・同じ時刻・同じ題名なら同じ放送とみなし、**枝番の小さいほう**だけを
予約します (中身が違えば題名が違うので両方残る)。番組表が空の枝番を隠す `airing` では足りません。
あちらは番組が1つも無い局を落とすだけで、中身の入った写しは隠せません。

### 放送の延長に追従する

番組表の時刻は予定でしかなく、野球が延びれば後ろもずれる。追従の元は録画中の TS に流れている
**EIT[p/f]** (いまと次の番組) で、EIT[schedule] と違って実際の放送に合わせて書き換わる。
問い合わせる相手が要らないので、同時録画の本数にも響かない。

1. 録画は物理チャンネルを丸ごと開き、`ServiceFilter` でその局だけを書き出す
2. 同じ TS の EIT[p/f] で、「放送中」の番組が録画中のもの (event_id 一致) なら終了時刻を見る
3. 後ろへ動いていたら予約と録画の終了時刻も動かす (動かさないとスケジューラが元の時刻で止める)。
   **前へ動いても縮めない。** まだ流れているのに切ると取り返しがつかない

EIT[p/f] を流さない局でも、番組表の時刻どおりには録れる。

**残っている穴**: 延長で後ろの予約と重なっても、録画中のものは競合計算の対象外なので調停されない。
同じ物理チャンネルなら相乗りで実害は無いが、別チャンネルでチューナーが埋まっていると後続が録れない。

## 消えないものは置かない

DBに残り続けるものには必ず期限を切る。1台のサーバで何年も動かすものなので、
放っておくと一覧が伸びるだけで探すのが遅くなる。

| もの | いつ消えるか |
| --- | --- |
| 番組表 (`programs`) | 終わってから1日 |
| 終わった予約 | 2週間 (取り消し・録り逃しか、もう録り始めたもの) |
| 削除済みの録画の行 | 同上 |
| エンコードの記録 | 同上。ただし**録画ごとに最新の1件は残す** (一覧の状態表示がそれを見ている) |
| 局 (`services`) | 消さない。代わりに画面から外す (上記)。映像の無い局 (データ放送・ワンセグ) だけは、何も紐付いていないので行ごと消す |
| ルール・設定・局ロゴ | 消さない (ユーザーが入れたもの) |

## この分け方で困るところ

- **チャンネルの顔ぶれだけは両方が知っている。** denpa の `services` (前回の取り込み
  時点) とエージェントの `channels` (いまのスキャン結果) で、スキャン直後は食い違う。
  これは隠さずチューナー画面に**両方並べて**出している。食い違い自体が
  「スキャンしたのに、まだ取り込んでいない」という情報になる
- **番組表を持っているので、集め直すまでは古い番組が残る。** 終わった番組は
  `pruneOldPrograms` が消すので、放っておいても数日で揃う
