# ライブの経緯

[stream.md](stream.md) の仕組みを入れた順序と、採用しなかったもの・やめた作り・決めたときの測定・残っているリスクの記録です。

## 実装の順序

**映像音声 (`ffmpeg → fMP4 → WebSocket → MSE`) → 字幕 (同じ ffmpeg の 2 つ目の出口から
サイドチャネルへ) → データ放送 (1 局に絞った TS を自前の `BmlDecoder` でデコードする。[データ放送の統合](stream.md#データ放送の統合))
の順に入れ、どれも入っています。** 低遅延は WebRTC / WHEP にせず ([不採用の理由](#webrtc--whep-による低遅延化))、MoQ にもせず ([不採用の理由](#media-over-quic-moq))、エンコードしない放送のままの経路で縮めました ([stream.md](stream.md#放送そのままmpeg-2を送る))。

## 採用しなかったもの

### `tsreadex` は挟まない

一度は入れかけたが、**挟む理由はどれも ffmpeg 単体で足りた**。

| 欲しかったもの                     | 結論                                                                                                                 |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| デュアルモノ分離                   | ffmpeg で足りる。選ばれた側を両耳へ配る ([多重音声はサーバで 1 本に決める](stream.md#多重音声はサーバで1本に決める)) |
| 局の選び分け                       | ffmpeg で足りる。`-map 0:p:<局>:v:0`                                                                                 |
| 音声・字幕が消えたときに無音を挿す | tsreadex にしかできない。ただし**実害を確認していない**                                                              |
| `aac: Input buffer exhausted`      | 直らない。壊れた AAC フレームの修復は tsreadex の仕事ではない                                                        |

3 行目の実害を踏んだら入れる。

### ブラウザ側での字幕デコード（aribb24.js）

B24 をそのままブラウザへ送り、クライアントでデコードして描く構成。**デコード方法が受け側ごとに別実装になり
(ブラウザとテレビのアプリで 2 つ)、置き場所や外字の置き換えが揃わない。** デコードするのはサーバ (libaribcaption を
写したもの) に寄せ、受け側は描くだけにした ([下の比較](#字幕を画像で配っていた頃))。

### H.264 + MPEG-TS + mpegts.js で先に全機能を通す

前例が豊富 (KonomiTV / web-bml と同一構成) で、段階を踏む案として有力だった。
**字幕の経路が録画側で先に完成した**ので、あとで捨てるコードを書く理由が無くなった。
H.264 は段階ではなく、流すコーデックの 1 つとして残した (メニューには並べず、AV1 を再生できない端末に自動で流す)。

### GStreamer

「tsdemux の private pad で B24 を映像と同一クロック上で取れる」ことを理由に有力視したが、字幕は ffmpeg の
2 つ目の出口で同じ時計に乗り、データ放送は denpa の中で自前でデコードするので、**この論拠は無くなった**。
周辺 (tsreadex / psisiarc / KonomiTV) も CLI パイプラインの構成で、GStreamer には ARIB/ISDB の知識も前例も無い。

### WebRTC / WHEP による低遅延化

**縮むのは待っている間だけで、開いてから映像が出るまではむしろ伸びる。** WHEP で消せるのは受け側の貯め
(`ts/pacing.ts`。宅内で 0.2〜0.9 秒) だけで、エンコードするのに掛かるぶんは運び方では消えない。
代わりに開くたびに ICE と DTLS の往復が増え、「押してから映るまで」が遅くなる。

|                                  | いま (WebSocket + MSE)                                                         | WHEP にすると                                       |
| -------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------- |
| 積むもの                         | Bun.serve の WebSocket 1 本                                                    | MediaMTX がもう 1 プロセス (+ SFU の設定・鍵・NAT)  |
| 字幕・データ放送                 | 同じ 1 本で一緒に送る ([WebSocket プロトコル](stream.md#websocket-プロトコル)) | 別建て (DataChannel を自分で組む)                   |
| 止めて見る・追っかけ・5 分戻れる | MSE の `buffered` がそのまま                                                   | 全部書き直し (バッファが無いので追い越されて終わる) |
| 音声・エンコード方式の選び直し   | 再エンコードして繋ぎ直すだけ                                                   | 交渉からやり直し                                    |

「止めた所から見られる」「戻れる」は貯めているから成り立ち、低遅延はその貯めを削ることなので、両者は同じものの
両端にある。実測では 0.2 秒では止まり続け、落ち着いたのは 0.6 秒だった
([一瞬止まって遅延が増えていく](stream.md#一瞬止まって遅延が増えていく))。1 秒足らずのためにその 2 つを捨てるのは割に合わない。
**本当に縮めたいなら、エンコードするのをやめるほうが桁違いに効く** ([放送そのまま (MPEG-2) を送る](stream.md#放送そのままmpeg-2を送る))。
ffmpeg の WHIP muxer も H.264/Opus 固定の experimental で AV1 が使えない。

### Media over QUIC (MoQ)

**縮まないのは WHEP と同じで、MoQ が効くのはパケットがよく欠ける回線だけ。家の外から見る経路の多くでは WebSocket か TCP に落ちて、今と変わらない。**
MoQ は運び方を変えるだけで、エンコードするのに掛かるぶんは残る。受け側の受信バッファも消えない。どれだけ貯めるかは受け側が決める。
効くのは、パケットが落ちたときに後ろが全部待たないことだ。MoQ はグループごとに別の QUIC ストリームで送り、古いグループは捨てられる。ただし
それは QUIC (UDP) で繋がったときだけで、Cloudflare Tunnel 越し・UDP を塞ぐ回線・tailscale の DERP では TCP に戻る。

|                                                             | いま (WebSocket + MSE)                                                                                      | MoQ にすると                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 積むもの                                                    | Bun.serve の WebSocket 1 本                                                                                 | リレー (moq-relay など) がもう 1 プロセス + UDP の 443 番 + 証明書。Bun の HTTP/3 は試験段階で、WebTransport は別の計画 ([Bun v1.3.14](https://bun.com/blog/bun-v1.3.14)、2026-05-13)                                                                                        |
| 字幕・データ放送                                            | 同じ 1 本で一緒に送る ([WebSocket プロトコル](stream.md#websocket-プロトコル))                              | トラックを分けて載せられる。選局などの双方向の指示 (`0x40`) は購読の仕組みに合わないので、別に組む                                                                                                                                                                           |
| 止めて見る・追っかけ・5 分戻れる                            | MSE の `buffered` がそのまま                                                                                | 受け側を WebCodecs で書くなら全部作り直し。MSE に流し込めば残るが、その受信バッファのぶん遅延も戻る。過去のグループを取る FETCH はリレーが持っているぶんだけ                                                                                                                 |
| 音声・エンコード方式の選び直し                              | 再エンコードして繋ぎ直すだけ                                                                                | 別のトラックを購読し直す (今と同じくらい)                                                                                                                                                                                                                                    |
| 細い回線での振る舞い                                        | TCP 1 本なので、1 つ落ちると再送まで後ろが全部待つ。詰まった客には映像を捨てる (`ws.ts` の `BACKLOG_LIMIT`) | 古いグループを捨てて新しいものを先に送れる。差が出るのはここだけ                                                                                                                                                                                                             |
| 通る経路 (Cloudflare Tunnel・tailscale・UDP が塞がれる回線) | どれも通る                                                                                                  | Cloudflare は配信元へ HTTP/3 で繋がない ([HTTP/3 の説明](https://developers.cloudflare.com/speed/optimization/protocol/http3/)、2026-08-14 更新) ので、Tunnel 越しは WebSocket に落ちる。tailscale は直結なら通り、DERP では TCP になる。UDP を塞ぐ回線も WebSocket に落ちる |
| ブラウザ・端末の対応                                        | 全部                                                                                                        | Safari / iOS は 26.4 (2026-03) から。https でしか使えない。denpa-tv の Media3 に MoQ は無い                                                                                                                                                                                  |

**仕様がまだ毎月のように変わる。** moq-transport は 2026-11-02 の draft-23 で、2026 年だけで 8 回 (draft-16〜23) 出ている
([履歴](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/history/))。draft-23 でも FETCH_OK が REQUEST_OK になり、FORWARD が意味を逆にして PAUSED になるなど、
前のバージョンと繋がらない変更が入っている。IESG へ出す予定は 2026-12 ([moq WG](https://datatracker.ietf.org/wg/moq/about/))。
映像の載せ方 (MSF・CMSF は 2026-06 の 01、LOC は 2026-11 の 05) はもっと手前で、moq.dev の moq-lite / hang は個人のドラフト (2026-09-24) のまま
([WG のドキュメント](https://datatracker.ietf.org/wg/moq/documents/))。Cloudflare のリレーもベータで、対応は draft-14 / 16 ([Cloudflare MoQ](https://developers.cloudflare.com/moq/)、2026-07-31 更新)。

**WebSocket に戻る経路のほうが、外から見る経路の多くを占める。** moq.dev のクライアントも WebTransport と `wss://` を同時に試して先に繋がったほうを使い、
WebSocket では TCP の詰まりを避けられないと書いている ([WebSocket](https://doc.moq.dev/concept/layer/web-socket)、2026-11-04 に確認)。Safari は 26.4 で入ったが、
長い接続が止まる WebKit の不具合があるとして WebSocket に留めている (同じページ)。iPhone はどのブラウザも中身が WebKit なのでこちらになる。
UDP をまるごと塞ぐ回線は 3〜5% ([RFC 9308](https://www.rfc-editor.org/rfc/rfc9308.html)。2016 年の測定) で、携帯の回線と会社の網に分けた新しい数は見つからなかった。
tailscale の DERP は TCP で、直結できないときは QUIC も TCP の中を通る。結局 WebSocket の経路を残すことになり、運び方が 2 通りに増えるだけになる。

**効きそうなのは、外の細い回線で画質を段階で落とすとき。** 解像度を 720p・540p・360p のように測った帯域で切り替えるには
(いまは画面が段を決めてリクエストし直す形で入っている。[stream.md](stream.md#回線に合わせて画質を下げる))、
解像度ごとにトラックを分けて受け側が選び直す形がよく合う (個人のドラフト [draft-ugur-moq-fast-switching](https://datatracker.ietf.org/doc/draft-ugur-moq-fast-switching/) など)。
ただ今の WebSocket でも、サーバがキーフレームで切り替え、詰まった客には映像を捨てられる。MoQ でしか作れないものではない。
放送のままの TS を載せるドラフトもある ([draft-lcurley-moq-mpegts](https://datatracker.ietf.org/doc/draft-lcurley-moq-mpegts/)・[draft-gregoire-moq-msfts](https://datatracker.ietf.org/doc/draft-gregoire-moq-msfts/))
が、放送のままは家の中から開いたときの経路で、家の中なら欠けはほぼ無い。

リレーで大勢へ配れるのも、セルフホストでは要らない。同じ局を何人で見ても ffmpeg は 1 つで、配る先は数人しかいない。
ffmpeg の MoQ の muxer は 2026-05-28 に出た PR ([#23263](https://mail-archive.com/ffmpeg-devel@ffmpeg.org/msg189252.html)) で、libmoq に頼り、H.264 と AAC の fMP4 だけ。
AV1 は載らず、取り込まれたかは確かめていない。

次の 3 つが揃ったら見直す。

- moq-transport が RFC になり、互換の無い変更が止まる
- Bun が WebTransport を受けられるようになるか、Cloudflare Tunnel が WebTransport を配信元まで通す (今は HTTP/3 で配信元に繋がない)
- 画質を段階で落とす仕組みを入れたあとも、外の細い回線で WebSocket が詰まって途切れることが実測で残る

Cloudflare Tunnel が WebTransport を通さないことは、配信元へ HTTP/3 で繋がないことからの推定で、確かめていない。
テスラの車載ブラウザの Chromium のバージョンと WebTransport の有無、Safari の `serverCertificateHashes` (自己署名の証明書で LAN から繋ぐ方法) の対応も確かめていない。

### mpeg2toh264 で H.264 に書き換える

[otya128/mpeg2toh264](https://github.com/otya128/mpeg2toh264) (2026-09-19 のコミット `7b008c6` で試した) は、MPEG-2 を画素まで戻さずに
H.264 へ書き換える変換です。量子化した係数・マクロブロックの種類・動きベクトル・参照の関係をそのまま使い、H.264 (High プロファイル・CAVLC) の
ビットストリームに組み直す。動き補償も逆 DCT も (ほぼ) しない。ネイティブ (Rust) と WASM があり、TS を読んで fMP4 (AAC はそのまま) を書く。

考えた理由は 2 つ:

- **サーバで使えば**、エンコードするよりずっと軽く H.264 を出せる (ライブの CPU 350〜470% が減る)
- **ブラウザで使えば**、放送のまま送ったものを MSE の H.264 (GPU でデコード) で見られ、WASM の MPEG-2 のデコードと WebGL で描くのを置き換えられるかもしれない

**どちらにも使わない。サーバでは出てくるもののビットレートが元の TS の 2 倍以上になり、ブラウザでは変換だけで今のデコードより重い。**

ffmpeg で作った 20 秒の 1080i の MPEG-2 TS 3 本 (testsrc2 の 1440x1080i・mandelbrot の 1920x1080i・雑音を足した 1920x1080i。17.7〜18.7Mbit/s) で、
ライブと同じ設定の x264 (`ultrafast`・`bwdif`) と比べた:

|                                         | mpeg2toh264                                                               | x264 (ライブと同じ設定) |
| --------------------------------------- | ------------------------------------------------------------------------- | ----------------------- |
| サーバの CPU (映像 1 秒あたりの CPU 秒) | **0.21〜0.30**                                                            | 0.98〜1.25              |
| ビットレート                            | 36〜45 Mbit/s (**元の TS の 2.0〜2.4 倍**)                                | 27〜67 Mbit/s           |
| 輝度の PSNR (3 本)                      | 47.8 / 36.6 / 44.5 dB                                                     | 46.6 / 37.1 / 40.5 dB   |
| 最初の断片が出るまで                    | 1.1〜1.3 秒                                                               | 0.8 秒                  |
| ブラウザで変換だけ (WASM、コマ/秒)      | 135 / 97 / 93 (同じ回に測った denpa の WASM のデコードは 410 / 255 / 235) | —                       |

途中で大きさ・プログレッシブとインタレ・PMT が変わっても通った。**弱いのはパケットの欠け**で、0.5% 落とすと 600 コマのうち 44 コマしか出ず
(ffmpeg は 597 コマ)、3% では何も出ない。`-r 1` では 0.03% の欠けで「GOP sample count」と言って止まった。インタレの H.264 は、Windows と
macOS の Chrome で GPU のデコードからソフトウェアに落ちることがある (mpeg2toh264 の README)。

実機 ([stream.md の実機](stream.md#どこに時間が掛かっているか)と同じ PC・Edge) でも確かめた:

| 同じ合成の 1080i を `<video>` で再生          | GPU のビデオデコードのエンジン  | Edge 全体の CPU       |
| --------------------------------------------- | ------------------------------- | --------------------- |
| mpeg2toh264 で変換した H.264 (インタレのまま) | **0% (ソフトウェアでデコード)** | 1 コアの約 15% 増える |
| x264 でインタレ解除した 60p の H.264          | 約 25% (GPU でデコード)         | ほぼ増えない          |

WASM の中の速さ (同じ Edge・worker 1 本) は、今の denpa のデコードが 365 / 214 コマ/秒 (1440x1080i / 1920x1080i)、mpeg2toh264 の変換だけが
125 / 85 コマ/秒で、ここでも変換だけで 2.5〜2.9 倍重い。

- **サーバ:** CPU は x264 の 1/4 だが、出てくるもののビットレートは元の TS より高い。エンコードする経路の役目は回線に合わせてビットレートを下げることなので、その役に立たない。
  軽さだけが欲しいなら放送のまま送るほうが帯域も少なく軽い。欠けにも弱く、電波の悪い局では映像ごと止まる
- **ブラウザ:** 変換だけで、今の WASM の MPEG-2 のデコード (デコードを全部やっても) より 2.5〜3 倍重い。H.264 のデコードを GPU に任せても、
  変換の段だけで負けている見込みが高い。逆転するのは、今の経路の描画 (WebGL・インタレ解除) がデコードの 2 倍以上重い場合だけで、
  描画の重さは GPU の無いコンテナ (SwiftShader) と机の上の PC でしか測れておらず、PC では重くなかった ([どこに時間が掛かっているか](stream.md#どこに時間が掛かっているか))。
  **Windows のブラウザはインタレの H.264 を GPU でデコードしない** (上の実機の表) ので、書き換えた H.264 はそこでもソフトウェアでデコードすることになる
- **活きる余地があるのは、** インタレの H.264 を GPU でデコードできて CPU が非力な端末 (Android・ChromeOS・Safari の VideoToolbox) だけ。
  非力な実機ではまだ測れていない

**JS で軽い変換を書き直しても、これより速くはならない。** 変換の大半は、MPEG-2 の可変長符号を全部読んで係数に戻すところ (エントロピーデコード) と、
H.264 の CAVLC に書き直すところで、画素に戻さない変換でもここは省けない。今のデコードとの差は画素に戻す手間 (逆 DCT・動き補償) だけで、
mpeg2toh264 はそのぶんを省いてもビットの読み書きのほうが重かった。ビット単位の処理は JS より WASM のほうが速いので、JS に移せば遅くなるだけ。

見直すのは、欠けたところを補う処理 (エラーコンシールメント) が良くなったとき。

## やめた作り

### 字幕を画像で配っていた頃

以前は描画も libaribcaption にやらせ、画像 (PNG) を配っていた。描く側だけを受け側に移した (#586) ときの比較:

|                              | 画像を配る (前)         | 文字の配置を配る (いま)                | ブラウザで B24 をデコードする (aribb24.js) |
| ---------------------------- | ----------------------- | -------------------------------------- | ------------------------------------------ |
| 置き場所・色・外字の置き換え | libaribcaption          | **libaribcaption と同じ計算** (写した) | 実装依存                                   |
| 全画面での字                 | 1920x1080 の画像の拡大  | **画面の画素で描く**                   | 画面の画素で描く                           |
| 帯域                         | 1 枚 20〜50KB の PNG    | 1 枚 数百バイト〜1KB                   | 数百バイト                                 |
| サーバ負荷                   | 字幕を描いて PNG に組む | 写してデコードするだけ                 | なし                                       |
| 持つコード                   | 出口だけ                | デコードする側 (表は手で持つ) と描く側 | 字幕ライブラリ 1 つ                        |

同じ録画の 103 秒をライブと同じエンコード方式で通すと、CPU は 152 秒 → 101 秒 (1 本あたり 0.5 コア軽い)、字幕に配る量は
1.08 MB → 14.3 KB になった (sub2video が映像のコマごとに 1920x1080 の画像を起こして PNG に組んでいたぶん)。
作り物の字幕と実機の録画 30 枚を同じ丸ゴシックで描いて画像と画素単位で比べると、墨の外枠は全部 ±1 画素、色の差は平均 1〜3/255 だった。
外字を丸める処理は画像の頃はパッチで当てていた (#554) が、描く側を移したときに落ちていたのを `packages/arib/src/drcs-smooth.ts` へ移した。

以前は字幕のために映像を作らない ffmpeg をもう 1 本、チューナーの共有をもう 1 つリクエストして当てていた。地上波 2 台のうち 1 台を番組表集めが
使っていると断られていた (`[captions] GR:T15: チューナーに空きがありません`)。

### 字幕の時刻を測って合わせようとした頃

どれも別々の ffmpeg の出口どうしを突き合わせて測っていた:

| 使った基準                                             | 実測のずれ                                                             |
| ------------------------------------------------------ | ---------------------------------------------------------------------- |
| mp4 の 0 (＝エンコードされた 1 コマ目のつもり)         | **2.4 秒**。マルチプレクサが 0 に合わせるのは probe の間に溜まった音声 |
| エンコードしているフレームの時刻 (映像側の `showinfo`) | **5 秒**。フィルタはエンコーダより先を走る                             |
| 字幕側の `showinfo` が言う放送時刻                     | **1 秒ほど遅れる**。行とフレームの数が合わず、組がずれる               |

「待たせる量を渡す」に替えても 3 回外した。別々に起こした ffmpeg はキーフレームが 0〜0.5 秒ずれるので、測れないものを測っていた。
**直したのは測り方ではなく作り**で、1 本の ffmpeg に両方を書き出させた ([1 本にしたのは、時刻を揃えるため](stream.md#1本にしたのは時刻を揃えるため))。
`-copyts` は効かないうえ、実機で `Assertion next_dts <= 0x7fffffff failed at libavformat/movenc.c` で映像ごと落ちた (放送時刻は 32bit に収まらない)。

「放送から N 秒」を TDT と組にしていた頃は、局ごとの固定のずれ (11 局で -0.72〜+0.90 秒) がそのまま出て、T26 と T15 で「放送から」が 1.3 秒違って見えていた。

### 選局の待ちで試したこと

- **PSI を先に流す手は外した。** 前に開いたときの PAT/PMT を先に流し、選局待ちに ffmpeg の入口の仕事を重ねる手で、単体では効いた
  (888ms → 707ms)。実機では、電波より先に入口を読み終えた ffmpeg が `-map 0:p:<局>:v:0` を解決できずに終了した
  (`Failed to set value '0:p:24632:v:0' for option 'map'`。測ったときは選局済みだったので見えなかった)
- `dvb_override_tune_delay` を 1ms にすると、DVB core が同期の途中で周波数を振り直して 451ms に悪化した。あの値は「打ち切るまでの猶予」で、
  ロックの検出間隔ではない (検出はこちらが 10ms 間隔で直に読んでいる)
- インタレ解除・音声・塊の細かさを外してもエンコーダの遅れは縮まなかった
- **ffmpeg の立ち上がりを 530ms と見ていたのは `-fflags nobuffer` を付けていた頃。** 入口の解析の間に読んだ I フレームを捨てて
  次の GOP を待っていた。外して 40〜270ms になった (`server/live.ts` の `encodeArgs`「入口の解析で読んだぶんを捨てさせない」)

### 一瞬止まって遅延が増えていったときの測定

エージェントのリングバッファ (6 分視聴 + 番組表 3 本で溢れ 0 回)・送り出し (H.264 25 分で 0.5 秒以上の間 0 回)・流量
(`-maxrate 8M` で削っても 8 分に 10 回) と順に外して、残ったのがちょうど 60 秒ごとという周期だった。

|                                 | 途切れ                            | バッファ 中央    | バッファ 最大 |
| ------------------------------- | --------------------------------- | ---------------- | ------------- |
| 直す前                          | 8 分に 10 回                      | 1.4 秒           | 3.2 秒        |
| 下限を覚える                    | 8 分に 5 回                       | 0.7 秒           | 3.2 秒        |
| 下限を下げ直すまでを 2 分→10 分 | 10 分に 3 回 (最後の 6 分は 0 回) | 0.9 秒           | 1.1 秒        |
| `-maxrate` を外す               | **10 分に 1 回**                  | **0.6 秒で平ら** | **0.7 秒**    |

### MPEG-2 の音を AudioDecoder でデコードしていた頃

WebCodecs の AudioDecoder は安全な繋ぎ (https か localhost) でしか出てこないので http の LAN では使えず、iPhone の Safari には
iOS 26 まで無かった。iOS 27 の Safari では出てくるのに ADTS のまま渡すと失敗した (1 枚目の映像のあと「音声を再生できませんでした」)。
ブラウザごとの癖を追うより、映像と同じ FFmpeg (WASM) でデコードすることにした (AudioDecoder と切り替えない)。

### web-bml を使っていた頃

2026-10 までは描く側を otya128/web-bml から借りていた。web-bml をサイドカーとして起動して iframe で抱えると、web-bml は自前の ffmpeg で
HLS を作って自分の `<video>` に映すので**映像を出すプレイヤーが 2 つ**になる。そこで描画側 (`BMLBrowser`) だけを npm から引いていたが、
映像の入れ物を BML の Shadow DOM の中へ移す・`onclick` を本物の属性のまま DOM に入れる・ES の処理系ごと 700KB ある、といった癖への
手当てが重なったので、自前のエンジン (`src/lib/bml/`) に置き換えた。

デコードする側 (web-bml の `server/decode_ts.ts`) も一度は借りたが、denpa が通るのは 3 割 (DSM-CC と PMT の記述子) で、そのために
`@chinachu/aribts` (2.3MB) を抱えるより書き直した。自前の `BmlDecoder` は借りていた `decodeTS` と、揃うモジュール・ファイル数・
バイト数・種別まで一致することを確かめてある。古い端末に残る `denpa_bml_denpa_nvram_…` (web-bml の頃の NVRAM) は読まない。

## WASM のデコーダの組み方を決めたときの測定

[デコーダ](stream.md#デコーダ) の組み方を決めたときの表。測り方は [どこに時間が掛かっているか](stream.md#どこに時間が掛かっているか) と同じで、
組み方だけを変えて、デコードだけの速さを比べた (コマ/秒、6 回の中央値)。

採った組み方 (Dockerfile の `mpeg2wasm` 段) は `-O3 -msimd128 -flto`・`--disable-asm` (手書きのアセンブリは使わない)・`--disable-pthreads` で、
組むのは mpeg2video・aac・opus のデコーダと mpegvideo の parser だけ。FFmpeg 9.0.2 が持つ WASM の SIMD (`--enable-simd128`) は HEVC のぶんだけで
MPEG-2 には無く、効くのはコンパイラが自動でベクトルにするぶんだけ。

| 組み方                         | 1440x1080i | 1920x1080i | 雑音の 1920x1080i | 大きさ (brotli) |
| ------------------------------ | ---------- | ---------- | ----------------- | --------------- |
| `-O3 -msimd128`                | 370        | 211        | 209               | 1,063KB (356KB) |
| `-O3` (SIMD 無し)              | 355        | 216        | 201               | 995KB (341KB)   |
| `-O2 -msimd128`                | 344        | 216        | 191               | 1,060KB (357KB) |
| `-O3 -msimd128 -flto` (採った) | 376        | 228        | 215               | 1,090KB (354KB) |
| スライスのスレッド 2 本        | 552        | 387        | 364               | 1,113KB (364KB) |
| スライスのスレッド 4 本        | 895        | 602        | 603               | 1,113KB (364KB) |
| フレームのスレッド 2 本・4 本  | 変わらない | 変わらない | 変わらない        | 1,113KB (364KB) |

- **SIMD と `-O2` / `-O3` の差は揺れの中** (SIMD は −2〜+4%)。MPEG-2 の重いところ (可変長符号を読む・整数の逆 DCT) は、コンパイラが自動でベクトルにしにくい
- LTO (`-flto`) は +2〜8%。brotli ではかえって 2KB 縮む
- **はっきり効くのはスライスのスレッドだけ**で、2 本で 1.5〜1.8 倍、4 本で 2.4〜2.9 倍。CPU の合計はほとんど増えない (+2〜12%)。1 コマを何本かで分けて早く終えるだけ。
  放送の MPEG-2 は横 1 列ごとにスライスが切ってあるので分けやすい。見送った理由は [スライスのスレッドを見送った理由](stream.md#スライスのスレッドを見送った理由)
- フレームのスレッドは効かない。FFmpeg の mpeg2video はスライスのスレッドしか持っていない
